## 任务定义

你的任务是根据全部输入中可识别的用户需求语义与数据库模式相关证据，构造一个**面向问题表达的概念查询结构（Conceptual Query Plan）**。

这里的概念查询结构不是要求生成一条可直接执行的数据库 SQL，或是完整的数据库 schema 结构。
它是一条作为中间语义表示的**概念 SQL / SQL-like 查询伪代码**，用于表达：

* 用户真正想分析的语义对象与分析主轴；
* 构建整个问题的分析语义对象序列与子问题依赖关系；
* 哪些中间语义结果需要被显式保留，以清楚表达问题的求解过程；
* 后续语义步骤如何依赖前序步骤逐步形成；
* 数据库模式相关证据如何用于将需求语义对齐到可能的实现结构。

本任务的目的是将用户问题组织为**符合用户表述口径的概念查询结构（conceptual SQL）**，并通过 SQL 清晰表示问题求解过程中的对象、连接、属性、条件与中间结果。

注意：本阶段的输出首先是**问题表达层 / 推理表达层**，不是最终的 ER 检索规格。  
本阶段不负责收敛出最小基础实体-关系-连接模型；该工作由后续解析阶段完成。

---

## 核心原则：并非所有语义成分都应成为 CTE

问题中的对象、字段、条件、连接依据、分组聚合要求等，都属于需要识别的语义成分；
但**并非所有语义成分都应被显式组织为概念 SQL 中的命名查询单元**。

只有在当前问题中满足以下条件的语义成分，才值得被显式命名为查询单元（CTE）：

1. 具有相对独立且稳定的语义边界，能够单独说明“它是什么”；
2. 能够单独定义粒度与成员范围，能够说明“一行代表什么”；
3. 在当前问题的求解过程中，值得作为阶段性语义结果被后续步骤继续引用；
4. 在当前问题中需要被显式保留，而不只是一次性临时桥接、局部匹配或实现支撑步骤。

其中需要特别注意：

* 用户需求中被直接表达、且对问题成立有直接作用的对象间连接，不应因为其属于连接就自动退化为局部 `JOIN ... ON ...` 条件；
* 但并非所有连接都必须拆成独立 CTE；只有当该连接在问题表达过程中形成值得单独保留和继续引用的中间语义结果时，才应显式组织为查询单元；
* 命名查询单元优先服务于**清楚表达查询计划**，而不是提前完成最终基础实体/关系/连接模型的收敛；
* 对于数据实现提示中的空间映射、编码映射、桥接路径、键关联路径等实现相关内容，不单独组织为概念层查询单元，而应隐藏在相应查询单元内部作为实现支撑表达；
* 即使输入中显式提供了某个需求语义单元对应的数据库实现线索，这些实现对象也仍仅属于该语义单元在 CTE 内部的实现支撑来源，不得因此上升为新的概念层查询单元。

其余语义成分应作为：

* 查询单元的属性；
* 属性上的常值约束；
* 查询单元之间的局部连接条件或属性匹配条件；
* 实现支撑路径；
* 分组、聚合、排序等分析操作

附着在相关查询单元上，或在主要 Query 表达，而不应自动成为独立 CTE。

## 2.2 值得单独命名的查询语义单元

**值得单独命名的查询语义单元**，指的是在当前问题中具有相对独立且稳定的语义边界、能够单独定义粒度与成员范围，并且值得作为整体被后续查询步骤继续引用的查询语义对象。

只有这类语义单元才应被显式组织为概念 SQL 中的 CTE。

需要注意：

* 对象语义单元、关系类型语义单元，以及在当前问题中需要被独立保留的连接语义单元，都可能成为命名查询单元；
* 连接语义单元是否需要显式组织，不以前置地区分其属于“稳定关系类型”还是“属性匹配”为条件；只要该连接在问题表达中需要被独立保留，就可以先被视为查询单元候选；
* 数据库实现提示中的实现相关来源：表、列、值等，需要作为需求语义的实现，被包含在相关语义单元的 CTE 内，不得独立建模或影响命名查询单元 CTE。

下列内容默认**不应**单独命名为 CTE，除非它们在当前问题中确实形成独立查询步骤或独立中间结果：

* 单纯的属性常值约束；
* 单纯的时间范围、类别范围、状态范围；
* 单纯的一次性跨单元属性匹配或时间对齐；
* 单纯的空间映射、编码映射、键关联、桥接路径；
* 只为一次局部连接服务的临时中间结果；
* 仅作为实现支撑而存在的局部步骤。

## 2.3 查询语义单元

在本任务中，只有被判定为值得单独命名的语义单元，才进一步组织为以下几类命名查询单元与来源对象。

### 1. 起始查询单元（Starting Query Unit）

起始查询单元是指：**在当前概念查询计划中，不依赖此前已命名 CTE、可直接由来源对象建立的起始查询单元**。

它通常具有以下特点：

* 具有相对稳定的语义边界；
* 可以单独定义粒度与成员范围；
* 可以直接从来源对象建立；
* 作为查询计划中的起始阶段性语义结果存在。

注意：

* 起始查询单元是一种**查询计划中的位置角色**，不是最终 ER 检索模型中“基础实体/关系/连接”的正式分类；
* 某个在最终 ER 看来可能属于基础语义的对象，在本阶段如果是通过前序 CTE 才形成的，仍可作为后续查询单元出现；
* 第一阶段不对“最终基础单元”作正式判定。

### 2. 后续查询单元（Subsequent Query Unit）

后续查询单元是指：**由已有查询单元经由筛选、组合、角色化、匹配、对齐、聚合、重命名、粒度变化或其它语义变换后形成的后续查询单元**。

后续查询单元的作用是：

* 组织概念查询结构中的阶段性查询结果；
* 表达某种阶段性必要的中间语义结构；
* 承载连接语义、角色信息、跨对象属性对应、条件约束、上下文补充或分析中间结果；
* 为最终主查询提供可复用的中间查询输入。

注意：

* 这里的“后续”只表示其在**当前查询计划中的依赖位置**；
* 它不是最终 ER 提取阶段中“派生实体 / 派生关系 / 派生连接”的正式结论；
* 单纯的一次性桥接、局部匹配结果或局部实现路径，通常不应单独命名为后续查询单元。

### 3. 实现支撑来源（Implementation Support Source）

实现支撑来源是由数据库模式相关证据引入、用于支撑需求语义落地的实现来源或实现背景。

它们通常来自：

* schema / table / column 提示；
* 主键、外键、桥接表、映射表；
* 时间列、空间列、编码列；
* 其它能够揭示实现承载位置、连接路径或属性来源的数据库线索。

实现支撑来源的作用是：

* 为概念查询结构提供可能的实现落点；
* 支撑对用户需求语义的规范化重写；
* 提供属性来源、连接依据或路径展开的实现背景。

实现支撑的定义规则：
实现支撑需要用后缀明确分类：
根据问题语义推知该来源对象必然存在，但是来源对象的数据实现未明确在提示中给出，此时必须使用 `*_source`。
只有当输入中明确提供了某来源对象的具体数据库模式相关证据（如具体 schema、table、column 或其它可直接指向实现对象的线索）时，才可使用 `*_impl`。

注意：

* 实现支撑来源默认不直接成为命名查询单元；
* 它们通常作为 `FROM` / `JOIN` 中引用的来源对象出现；
* 若当前问题需要引用某类来源对象，但输入未提供其明确的数据库模式相关证据，必须使用 `*_source` 作为抽象来源占位；不得假设存在实现，并写为`*_impl`。只有输入存在明确的数据库模式相关证据，才能使用 `*_impl` 后缀；
* `*_impl` 与 `*_source` 都不是独立 CTE 类型。


### 4. 关系类型 / 连接查询单元建模

对于关系类型/连接一类的语义要素，可以将其显式组织为关系型或连接型查询单元，其首要职责是表达参与对象之间的关系类型定义或属性连接约束；不得默认写成“表达连接完成后形成的复合实体类型结果”。

这类查询单元应优先回答：

* 连接的是哪些对象；
* 各对象在连接中的参与角色是什么；
* 连接基于哪些属性、条件或约束成立；
* 连接本身是否承载局部约束或连接属性；
* 一行代表一个什么关系类型实例或连接约束实例。

若后续确有需要构造复合实体类型结果，也应建立在已显式保留的关系类型/连接查询单元之上，而不应直接用复合实体类型结果替代本应保留的连接语义表达。

注意：在本阶段中，是否把某条关系/连接显式写成独立 CTE，首先取决于它是否有助于清楚表达查询计划；其是否最终需要下沉为基础实体之间的基础 relation / connection，由后续解析阶段统一判断。

## 2.4 连接语义的说明

在概念查询结构中，对于**已被判定为需要显式保留的连接语义单元**，可进一步说明其内部连接性质。

连接语义通常可表现为以下几种倾向：

### 1. 关系类型性连接（Relation-like）

指该连接更接近一个需要被独立保留的关系类型语义，通常具有以下特征之一：

* 参与对象结构明确；
* 存在稳定的参与角色；
* 连接自身可能承载属性或局部约束；
* 去掉具体实现路径后，该连接仍然是当前问题中的重要语义结构。

### 2. 属性匹配性连接（Connection-like）

指该连接主要用于在对象之间完成属性附着、上下文补充或分析所需的对齐，通常具有以下特征之一：

* 主要作用是补充上下文或附着属性；
* 更依赖时间对齐、类别对齐、同值匹配、条件匹配等方式；
* 连接本身通常不作为独立关系类型对象保留。

### 3. 实现支撑路径（Implementation Support Path）

指该连接在落地时所依赖的实现路径、桥接路径或局部实现依据，例如：

* 键关联；
* 桥接表路径；
* 空间映射；
* 编码映射；
* 其它实现层的连接步骤。

需要注意：

* 实现支撑路径不是概念层连接语义单元的同级替代类型；
* 它通常作为连接语义单元内部的实现支撑而存在；
* 不应直接上升为概念层对象。

注意：上述 `relation-like` / `connection-like` / `implementation-support` 更偏向**概念查询计划中的表达辅助标签**，用于帮助后续解析，不等同于最终 ER 收敛阶段的正式分类结论。

## 2.5 用户需求到概念查询结构的映射规则

用户需求中与问题成立直接相关的对象、字段、实例值、条件、连接依据和分析要求，应尽量在概念查询结构中得到对应表达。

它们可以分别落实为：

* 查询单元的属性；
* 属性上的常值约束；
* 查询单元之间的连接语义；
* 查询单元之间的局部属性匹配和约束条件；
* 计算、分组、聚合、排序等分析操作；
* 最终分析单元的输出要求。

映射时应遵守以下原则：

* 用户提及的对象概念，优先映射为查询单元候选；
* 用户提及的字段，优先映射为相关查询单元的属性；
* 用户提及的实例值、时间值、类别值、范围值，优先映射为相关属性上的常值约束或范围约束；
* 用户需求中被直接表达、且对问题成立有直接作用的对象间连接，应优先映射为连接语义单元候选，而不默认退化为局部 `JOIN` 条件；
* 该连接最终是否组织为独立 CTE，取决于它是否在当前问题中形成值得独立保留并被后续继续引用的查询语义单元；
* 与该连接落地相关的空间映射、编码映射、桥接路径、键关联路径等实现内容，不单独映射为概念层查询单元，而应尽量附着在相应查询单元内部表达；
* 不要求所有需求片段都被对象化或单独组织为查询单元；只有当某一语义成分形成独立查询语义时，才考虑将其提升为命名查询单元。

## 2.6 概念 SQL 的结构说明

概念查询结构应采用**概念 SQL**的方式组织。这里的概念 SQL 不是可执行 SQL，而是用接近 SQL 的形式表达：

* 问题求解过程中的起始查询步骤；
* 后续语义步骤如何依赖前序查询结果逐步形成；
* 当存在数据库模式相关证据时，这些查询单元如何引用实现来源；
* 查询单元之间的连接、约束与依赖如何组织。

### 1. 两类命名对象

概念 SQL 中需要区分两类命名对象：

* **CTE**：概念查询结构中的命名查询单元，用于承载问题求解过程中的阶段性结果；
* **来源对象**：CTE 内部 `FROM` / `JOIN` 所引用的对象，用于表示概念来源或实现来源。

### 2. CTE 的命名规则

CTE 命名应优先表达**语义对象本身**，而不是在名称中编码其“基础 / 派生 / 起始 / 后续”的阶段位置。

推荐命名方式：

* 直接使用语义名称：`trip`、`weather_record`、`trip_weather_alignment`
* 或在必要时保留类型后缀：
  * `*_ent`：表示查询单元主要表达实体类型语义；
  * `*_rel`：表示查询单元主要表达关系类型语义；
  * `*_conn`：表示查询单元主要表达基于属性匹配的连接语义。

注意：

* 查询计划中的“起始步骤 / 后续步骤”应由 SQL 依赖关系、CTE 顺序以及必要注释表达，而不是由名称硬编码；
* `*_ent / *_rel / *_conn` 是可选的类型提示。

### 3. 来源对象的命名规则

当概念 SQL 需要引用数据库模式相关证据中的实现来源时：

* 若输入提供了明确的数据库模式相关证据，可使用 `*_impl` 后缀；
* 若当前问题需要引用某类来源对象，但输入未提供其明确实现证据，可使用 `*_source` 作为抽象来源占位。

注意：

* `*_impl` 与 `*_source` 都不是独立 CTE 类型；
* 它们仅是 CTE 内部引用的来源对象命名后缀。

### 4. 连接语义的表达方式

在概念 SQL 中，查询单元之间的连接通过 `JOIN ... ON ...` 表达，在必要时通过简洁注释标明该连接单元更偏向何种连接性质。

当某条连接或条件的内部性质对后续解析十分关键时，可使用如下简洁注释辅助表达：

* `-- relation-like: ...`
* `-- connection-like: ...`
* `-- implementation-support: ...`
* `-- Global Condition: ...`
* `-- Local Condition: ...`

这些注释仅用于帮助表达该连接或条件在当前查询计划中的语义角色，便于后续解析阶段判断其是否应进入基础模型。

注释是可选的，但当连接语义、条件作用域或中间步骤性质容易混淆时，建议显式标明。

### 5. 使用原则

构造概念 SQL 时，应遵守以下规则：

* 并非所有识别出的语义成分都必须写成 CTE；只有值得单独命名的查询语义单元才应显式组织为 CTE；
* 单纯的属性约束、一次性跨单元属性匹配、实现桥接路径和临时中间结果，原则上不单独组织为 CTE；
* 不依赖此前已命名 CTE、可直接从来源对象建立的起始步骤，应通过 CTE 顺序和依赖结构自然体现；
* 依赖前序查询单元形成、且值得作为整体被后续继续引用的中间查询语义，应显式写成后续 CTE；
* 后续 CTE 可以依赖前序任意 CTE，但不得形成循环依赖；
* 连接语义是否单独写成 CTE，不取决于它是不是连接，而取决于它在当前问题中是否形成独立查询步骤；若未形成独立步骤，可仅在相关查询单元之间以显式连接结构表达；
* 参考数据、映射数据、编码数据、空间归属数据等实现相关来源，默认不直接写成概念层 CTE；它们所支撑的对象或连接语义若需要保留，应在相关 CTE 内表达；
* 只有在存在数据库模式相关证据时，才在 CTE 内部引用 `*_impl` 来源对象；若无明确实现证据但概念上需要引用来源，可使用 `*_source`；
* 最终主查询应保持用户问题的语义口径，不得退化为物理实现结构的直接转写；

# 分析步骤

在生成 JSON 形式的概念 SQL 之前，必须先基于以下步骤完成分析。**禁止直接生成 Json**；

## Step 0. 区分用户需求与实现提示

重述问题，区分用户需求的描述与实现提示字段，明确数据实现提示的存在性与具体内容；


## Step 1. 构造 Logical Query Plan

先暂时撇开具体数据库表、列、join key 与物理实现细节，围绕用户问题本身，构造一份 **Logical Query Plan**。

这里的 Logical Query Plan 不不得给出任何实体/关系/属性的假设，仅仅用自然语言进行推理。
它是一组按依赖顺序展开的**命名子问题**，用于表达：

* 最终结果是什么；
* 为了得到该结果，必须先求出哪些阶段性结果；
* 每一步的主要计算动作是什么；
* 每一步依赖哪些前提；
* 哪些隐含约束必须在该步被显式考虑。

### Step 1.1 明确最终结果口径

先从最终结果出发，说明：

* 用户最终想得到什么结果；
* 最终结果中一行代表什么；
* 用户明确要求输出哪些内容；
* 结果围绕什么分析主轴展开；
* 是否存在明确的分组、排序、比较、聚合、时间或角色口径。

本步骤只负责明确**结果定义**，不要在这里提前把基础概念对象完整摊开。

### Step 1.2 将问题拆解为命名子问题

围绕最终结果的形成过程，将问题拆解为若干按依赖顺序展开的**命名子问题**。
每个子问题都应回答：

> 为了得到最终结果，必须先求出的哪一个阶段性结果？

不要按“对象清单”拆解，而要按“阶段性结果”拆解。
每个子问题都应是一个可以说明“这一步在求什么”的求解节点。

### Step 1.3 为每个子问题补充关键说明

对每个命名子问题，至少说明以下内容：

1. **子问题名称**：用简洁自然的短语命名该步骤；
2. **子问题目标**：该步骤在整体求解中解决什么问题；
3. **阶段性结果**：这一步产出的结果是什么；


### Step 1.4 标明每个子问题的主要操作类型

对每个子问题，判断其主要操作类型。使用自然语言描述，不要求固定枚举，但至少应明确它更接近下列哪类操作：

* 选择对象，根据条件筛选子集；
* 建立连接、匹配或对齐；
* 角色化拆分；
* 时间顺序或窗口限制；
* 分组聚合；
* 比较、排序或 Top-k；
* 派生计算；
* 最终结果整合。

若某一步同时包含多种操作，应指出主操作与次操作，不要只做笼统描述。

### Step 1.5 显式检查隐含约束

对每个子问题，检查是否存在以下隐含约束；若存在，必须明确写出其作用：

* 角色约束；
* 方向约束；
* 时间先后约束；
* 局部子集范围；
* 比较基准；
* 参考对象；
* 分子 / 分母口径；
* 去重口径；
* 聚合前提；
* 局部分析范围。

所有问题中提及的约束都需要纳入考虑，不得默认省略这些条件。

### Step 1 输出要求

本步骤应输出一份**按依赖顺序组织的 Logical Query Plan**，形式为自然语言编号步骤。

## Step 2. 判断哪些语义成分应被显式组织为命名查询单元

对于 Step 1 中的子问题，判断哪些成分在当前问题中应被显式组织为命名查询单元。

迭代所有子问题，必须进行如下分析：

(1) 问题相关内容列举：完整列举问题中提及该成分的内容部分，作为该查询单元表达的基准来源；

(2) 是否构建为命名查询单元及其在查询计划中的角色：判断该成分是：

* 适合作为可直接从来源对象建立的起始查询单元；
* 适合作为依赖已有查询单元形成的后续查询单元；
* 还是不应该独立作为查询单元，而是作为其它单元的属性 / 角色 / 条件 / 局部连接表达；

(3) 查询单元类型：该查询单元主要表达的是实体类型语义、关系类型语义，还是连接语义；若是关系 / 连接，需要说明参与对象及其角色；必要时可标注其更偏 `relation-like` 或 `connection-like`；

(4) 用户需求的属性字段化：将用户需求中提及的语义信息准确、全面地落实为查询单元中需要显式保留的概念属性；优先保留用户显式提及、或对后续连接 / 角色 / 条件表达必需的稳定属性；

(5) 禁止将数据实现 / 数据源建模为查询单元：在给出数据库实现提示时，若数据库实现中的要素在用户需求中未显式提及，则将其视为实现支撑，不应被显式组织为命名查询单元，也不得以任何形式影响查询单元的命名；实现细节需要被包裹在单元 CTE 内部。

判断时遵守以下原则：

* 能单独定义“这一步在求什么”，且能单独说明“一行代表什么”的，可作为命名查询单元候选；
* 若某语义单元需要建立在已有查询单元之上，通过组合、角色化、属性匹配、上下文附着、条件组合或其它语义变换后才成立，则更适合作为后续查询单元候选；
* 若某语义单元表达的是实体类型之间的关系类型定义，或多个对象之间基于属性成立的连接约束，并且该语义在当前查询计划中需要被后续继续引用，则可以显式组织为关系型或连接型查询单元；
* 不得用“带连接上下文的实体类型”“聚合前宽表”“附着多个外部属性后的复合实体类型单元”替代本应独立保留的关系类型 / 连接查询表达；
* 保持角色区分：对于同类对象在一个连接中的不同角色，必须在查询单元中显式区分，不得忽略角色概念；
* 单纯的属性约束、一次性局部匹配、实现桥接路径、一次性临时中间结果，默认不单独命名为查询单元；
* 查询单元定义严格按照用户需求描述口径，实施细节必须包裹在查询单元内部，不得影响单元本身的概念定义；。


## Step 3. 命名查询单元的属性字段化

（2）反推逻辑表属性规格：重述 Step 1里针对每个步骤的语义表达属性、数据操作与隐含约束；分析该语义表达、操作/约束的对逻辑表提出的属性字段要求；每个步骤的中间表示和最终查询的所有属性皆派生于起始查询单元；起始查询单元作为源头，必须有最够的规格支持所有派生属性和约束条件。

（3）定义起始查询单元属性集： 对每个起始查询单元，基于满足完整性、语义准确性与最小化原则，进行必要的逻辑属性集的设计；对于可能有多种表示的属性，需要明确其多义性，并在conceptual SQL中标明alternative：

* 完整性：支持所有后续步骤与表示的属性派生计算需求；满足所有语义表示，连接，条件约束的字段需求。
* 最小化：当某个属性可以通过与其他属性的连接、计算得到时，不应直接在逻辑表中定义为独立属性。
* 语义准确性：明确语义的合理归属对象；
* 多义性分析：如果某种逻辑属性定义存在多种表示可能性，必须明确说明其它的属性表示可能性，在sql实现选择以最符合标准数据库设计与业务常识的形式表示；

## Step 4. 组织概念查询计划并检查表达完整性

基于上述子问题、命名查询单元、连接说明与条件作用域，组织整条概念查询计划。

（1）按子问题依赖顺序排列 CTE：前序 CTE 应为后续 CTE 提供清晰输入；后续 CTE 应明确说明自己依赖哪些前序结果。

（2）检查每个 CTE 的表达是否清晰：

* 一行代表什么；
* 当前 CTE 解决哪个子问题；
* 依赖哪些前序 CTE 或来源对象；
* 保留了哪些关键属性、角色、连接或条件。

（3）检查关键语义是否显式：

* 关键对象是否已被表达；
* 关键连接是否已被表达；
* 关键角色是否已被区分；
* 关键条件是否已被显式写入；
* 中间结果是否足以支撑后续步骤继续引用。

（4）检查结构是否便于解析：

* CTE 依赖关系应清晰、无环；
* 关键连接条件尽量显式；
* 避免将多个不相关的语义变换揉入同一个 CTE；
* 尽量保证每个 CTE 具有单一、稳定的阶段性语义边界。

（5）注意：

* 本步骤不要求补齐最终最小基础实体 / 关系 / 连接集合；
* 若某条连接在当前查询计划中仅作为一次性局部依赖，并已在相关 CTE 中被清晰表达，可以暂不独立组织为单独 CTE；
* 是否需要把某条派生层暴露出的连接进一步回落为基础 relation / connection，由后续解析阶段统一判断。

## Step 5. 构造概念 SQL 并输出

完成上述全部分析步骤 Step 1 - Step 4，基于已识别的语义成分、命名查询单元以及连接说明，构造概念 SQL。  
概念 SQL 的首要目标是**正确表达问题求解过程中的语义结构**，而不是完全符合具体数据库结构的可执行 SQL。

```json
{
  "conceptual_sql": "..."
}
```

conceptual_sql 要求：

* 注意：目标不是生成可执行业务 SQL，但是必须生成“语法完整、结构稳定、便于 AST 解析和表列提取”的概念 SQL；表、列、函数、常量可以占位表示，但必须语法合法；
* CTE 名称优先表达语义对象本身；是否是起始步骤或后续步骤，应由 SQL 依赖关系和必要注释体现，而不是由名称后缀编码；
* 可选使用 `*_ent / *_rel / *_conn` 作为类型提示，但不使用 `*_base / *_derived` 或其它表示阶段位置的后缀；
* `*_impl` / `*_source` 的后缀命名必须严格基于数据来源来定义：当语义上明确数据源的存在性，但是实现上的数据没有名曲给出时，必须用 `*_source`后缀，不得以任何形式假设物理数据的存在；仅当输入中明确的物理数据实现存在时才能用`*_impl`.

约束如下：

1. 可以使用伪代码函数进行占位，但必须保持 SQL 语法完整。
2. 不允许出现 `...`、`WHERE ...`、`ON ...`、不完整函数参数、不完整表达式。
3. 每个 CTE 都必须写成完整的 `name AS (SELECT ... FROM ...)` 结构。
4. 所有引用项尽量显式起别名。
5. 默认按 Snowflake 风格书写。
6. 最终主查询应保持用户问题的语义口径，不得退化为物理实现结构的直接转写。
