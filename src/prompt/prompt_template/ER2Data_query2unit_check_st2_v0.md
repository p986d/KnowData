# 用户需求语义单元与数据库实现落地校验任务

你的任务是判断一个语义单元对应的 SQL，是否真的把该语义单元在数据库中的实现找准、找全。

你会收到以下输入：

1. 当前语义单元的自然语言查询语句；
3. 外部知识；
4. schema linking 命中的候选表列；
5. SQL 执行结果证据：
   只包含结果列名、前 5 行结果样本、空值/零值列提示；
6. 最终被分析的 SQL。

其中：

- SQL 执行结果证据是强证据，可用于判断输出结果到底在表达什么；
- SQL 本身是最终实现依据，可用于判断这些结果是否真的是由正确的表、列、连接、过滤、映射、聚合和转换得到的；
- schema linking 只是辅助线索，不能因为命中了某个表列，就默认 SQL 已经真正落实了对应语义。

请按以下顺序进行内部分析：


# 步骤1：先看执行结果证据，归纳结果语义

优先结合“SQL 执行结果证据”分析这条 SQL 实际产出的数据像什么：

- 样本行中的每一列分别在表达什么；
- 这些行整体上更像哪类实体、关系、事件、映射或聚合结果；
- 样本结果是否明显偏题、过宽、过窄、为空、全零、全空，或只返回了表面同名字段。

如果执行结果证据缺失、不完整或不足以判断，要明确说明不确定性，然后再更多依赖 SQL 本身。

# 步骤2：再看 SQL 本身，规范化 SQL 实际语义

结合“语义单元实现 SQL”，参考“schema linking 命中的候选表列”和“SQL 执行结果证据”，
用一段简洁的话概括这条 SQL 实际做了什么：

- 真正使用了哪些表/列；
- 做了哪些过滤、连接、映射、转换、聚合、去重或范围限定；
- SQL 的输出字段最终代表什么语义；
- 结果样本中的语义，是否真的能由 SQL 的实现逻辑支撑。

注意：

- 以 SQL 本身为准；
- 不要把别名、列名相似、linking 命中，当成真实实现；
- 如果结果看起来合理，但 SQL 缺关键连接、关键过滤或关键映射，仍然不能判为完全正确；
- 如果 SQL 语义和样本结果相互矛盾，要优先指出矛盾，并降低判定。


# 步骤3：规范化目标语义

结合“当前语义单元的自然语言查询语句”“外部知识”，
用一段简洁的话概括这个语义单元真正要表达的内容：

- 核心实体或关系是什么；有哪些属性需要显式返回；
- 输出结果应该代表什么。

不要扩展到其他语义单元。

# 步骤4：做“找准 / 找全”判断

一、判断“找准”

“找准”是指：SQL 实际表达的核心语义，是否就是目标语义单元本身，
而不是相近但不同的对象、关系、条件、粒度或实现方式。

以下情况通常不能算找准：

- 语义漂移；
- 用了相邻但错误的实体/关系；
- 缺少关键连接导致伪命中；
- 结果样本看似接近，但本质对象或字段语义不对；
- schema linking 提到了相关表列，但 SQL 并未真正使用。

二、判断“找全”

“找全”是指：目标语义单元所必需的数据库实现成分，是否都已经在 SQL 中被真正落实。

重点检查是否缺少：

- 关键表列；
- 关键过滤条件；
- 关键连接/映射；
- 关键转换；
- 关键范围约束；
- 关键输出字段或输出粒度。

只有“真正落实在 SQL 中”才算覆盖，不能按名字相近或 linking 命中来算。

# 步骤5：输出

先逐步分析，再在最后输出 JSON。
不要直接跳过分析过程。

判定规则：

- exact_match：找准 = true，找全 = true，且结果样本与 SQL 语义、目标语义三者一致；
- partial_match：找准 = true，但找全 = false；
- mismatch：找准 = false，或者结果样本/SQL 明显不支持目标语义。

{{unit_nl_query}}

# External Knowledge

{{external_knowledge}}

# 可能相关的表列数据

{{schema_linking_json}}
