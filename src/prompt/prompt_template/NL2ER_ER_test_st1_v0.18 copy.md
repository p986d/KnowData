# 任务定义

根据全部输入中可识别的用户需求语义与数据库模式相关证据，构造一个支持该问题查询的**基础逻辑实体-关系草图**。

本阶段的目标不是直接生成最终查询。
本阶段只负责：

* 将问题分解为语义单元与查询子问题；
* 根据查询子问题，识别支撑该问题成立所必需的**基础逻辑实体**、**基础逻辑关系**与**逻辑属性**；
* 将聚合、排序、Top-k、窗口、派生计算、局部子集等**派生语义节点**排除在基础建模之外；
* 输出一份便于后续阶段继续收敛的轻量对象草图。


---

# 基本原则

## 1. 先组织问题求解结构，再考虑逻辑查询的语义需求

首先对问题抽取语义单元，并根据查询计算的逻辑顺序构建一系列有顺序的查询子问题。
对每个查询子问题，依次判断其它的输入是哪些实体-关系的概念；这些实体-关系可能是整个问题查询所需要的基础逻辑实体-关系，也可能是之前的子问题输出的中间表示阶段性语义结果。阶段性结果只用于理解求解过程，不默认进入基础 ER 草图。只有支撑这些阶段性结果成立的基础对象、基础联系、基础属性与必要约束，才允许进入最终建模。
数据库模式相关证据只作为实现支撑背景，用于帮助这些步骤落地到可能的数据来源；它可以影响某一步如何表达，但不得主导问题本身的求解结构，也不得替代用户问题的语义拆解。

## 2. 根据顺序子问题，明确查询逻辑，推理子问题需要的逻辑输入

顺序分析每个子问题，解析其查询逻辑与语义依赖，定义其需要的输入：哪些实体-关系和相关属性，与其输出：哪些实体-关系和相关属性。
每个子问题的输入可以是基础的逻辑实体-关系，或之前子问题输出的派生中间表示实体-关系；每个子问题的输出是派生中间表示实体-关系；

---

## 3. 基础逻辑实体的定义

基础逻辑实体是问题中具有稳定语义身份、明确基础粒度、可独立指称的对象类/对象集合。实体作为类，可以包含多个实例。问题中的实体可能以一个类，一个类的子集或单独的实例等形式给出。


**实体的语义来源**：
它不仅包括问题直接查询、筛选或统计的核心对象，也包括那些虽然在表面上常表现为筛选条件、分类口径、参照范围或分析限定，但在当前问题中实际上具有独立语义地位的对象。

判断一个语义是否应建模为基础逻辑实体，它是否在问题中引入了一个可被单独识别的对象身份、独立的语义范围，而不在于它在表述上是否像“条件”或“属性”。

需要特别避免一种过度简化的倾向：将问题中的非核心语义一律下沉为属性。
这样做虽然在形式上可行，但会导致独立对象被抹平、关系结构被压缩、子集与全集混淆，也会削弱后续连接、分组、聚合和范围限定的语义完整性。

只有当某一语义仅仅作为其它实体的单纯内在性质存在，脱离该实体则不能独自成立时，才应将其建模为属性。

否则，应优先考虑将其提升为基础逻辑实体，而不是默认落为属性。

**实体定义应严格遵循问题的概念表达口径层级，不得任意泛化或细化**:

所定义的基础逻辑实体，必须与题面实际指称的对象范围、语义边界和分析粒度保持一致。不得为了形式整齐、复用方便或迎合实现结构，将题面中明确指向的对象上推为更抽象的父类、上位类或更宽泛的集合；也不得将题面中的一个完整对象无依据地下拆为更细粒度的多个子实体。

当问题指向的是某一特定对象类、特定子集、特定角色对象或特定范围对象时，应严格按该概念描述口径建模，而不是泛化或细化为其它概念。
判断标准不是“能否勉强归入某个更一般或更细的概念”，而是“该定义是否准确保留了题面所给对象的独立身份、边界范围和后续分析口径”。凡是会改变问题原始对象边界、混淆分析对象范围、替换题面语义焦点的泛化或细化，都应避免。

**实体定义避免使用泛化父类**：

当题面中明确出现多个语义不同、粒度不同、在问题中承担不同作用或角色的对象类时，应优先分别建模为独立的基础逻辑实体，不得仅因为它们共享某个更抽象的上位概念、层级结构或类别体系，就将其合并为一个统一的父类实体，再依赖“类型”“层级”“类别”等属性进行区分。父类化会把题面中原本独立的对象身份压缩为同一实体的不同取值形式，导致对象边界、关系角色或结果口径被抹平，则应避免这种建模。只有当题面本身就是以该统一父类为分析对象，且后续语义不再区分这些子类的独立身份与作用时，才允许采用统一父类实体的抽象方式。

## 4. 基础逻辑关系的定义

基础逻辑关系是**两个或多个基础实体的角色**之间具有明确独立语义的关联、交互或事件。

## 基础逻辑关系的定义

基础逻辑关系是问题中两个或多个基础实体角色之间发生、成立或被描述的原子语义事实。它用于表达实体之间的关联关系或共同参与的事件，而不是为了查询实现临时建立的连接动作。

**关系的语义来源**：

基础逻辑关系不仅包括题面中直接出现的动词性、事件性或关联性表达，也包括那些表面上表现为条件、限定、统计口径或分析背景，但实际表达了多个实体之间基础联系的语义。

判断一个语义是否应建模为基础逻辑关系，不在于它表面上是否写成“关系词”或“连接词”，而在于它是否引入了多个实体角色之间不可压缩的基础事实。

如果某一语义必须依赖两个或多个实体角色才能完整表达，例如一个实体与另一个实体的语义关联或者多个实体共同构成一个事件、行为、记录或关联事实，则应优先考虑建模为基础关系，而不是简单压缩为某个实体的属性、外键、标签或取值。

如果某一语义只描述单个实体自身的性质、状态、类别、标签或取值，脱离该实体后不能独立成立，则应建模为属性或约束，而不是关系。

**基础关系与派生关系的区分**：

基础逻辑关系必须是支撑问题成立的原始承载关系，而不是在其它基础事实之上经过派生计算之后得到的结果关系。

如果某个候选关系只有在完成某种计算、比较或选择之后才成立，则它不是基础关系。此时应继续向下追溯：

该派生关系依赖哪些基础实体；
这些实体之间原本存在什么基础联系；
派生判断依赖哪个基础属性；该属性应挂载在哪个更基础的关系上。

**关系定义不得任意泛化或细化**

基础关系的定义必须与题面实际表达的实体间联系、语义边界、角色结构和关系粒度保持一致。

不得为了形式整齐、复用方便或迎合实现结构，将题面中明确表达的具体关系上推为更抽象的泛化关系；也不得无依据地把一个完整关系事实拆成多个更细粒度关系。

当题面中出现多个语义不同、粒度不同、角色结构不同或业务含义不同的关系时，应优先分别建模为独立的基础关系，不得仅因为它们都能归入某个抽象关系类型，就合并为一个统一关系，再依赖“关系类型”“关系类别”等属性区分。

一个基础关系必须同时满足以下条件：

1. 参与者条件：
   - 关系至少包含两个参与者；
   - 每个参与者都必须是已定义的基础实体；
   - 参与者在关系中必须具有明确角色；
   - 同一实体类型可以在同一关系中以不同角色出现，但不得因此重复定义实体。

2. 事实性条件：
   - 关系必须表达一个可以独立陈述的语义关联或事实；
   - 该事实不能只解释为某个单一实体的属性、状态、类别、标签或取值；
   - 若去掉该关系，实体之间的核心语义联系会丢失。

3. 原子性条件：
   - 关系应表示一个基础层面的关联事实；
   - 如果某个联系可以由其它更基础的关系链、聚合、排序、窗口、比较或派生计算得到，则它不是基础关系；
   - 如果某个联系只是某个中间分析结果、局部子集或统计口径的产物，也不是基础关系。

4. 实例粒度条件：
   - 每个关系都必须能说明一个关系实例代表什么；
   - 关系粒度应描述“一条关系事实”的单位，而不是描述查询结果、聚合分组或实现记录。


注意：

* 单个实体的属性限定 / 标签限定 / 状态限定，默认优先落到属性或约束，不得轻易升级为关系；
* 关系的参与者应为实体，在关系中承担角色；不能以关系作为参与者。
* 关系可以有多个参与者，至少需要有两个参与者。

## 5. 逻辑属性的定义


基础实体和关系的属性必须是能够支持问题查询的**原子逻辑抽象属性集**；
不得包含任何**派生元素**：例如查询计算的中间表示；
不得包含任何**冗余表示**：对相同语义。

实体和关系都可以有属性：实体属性是对单个实体类型的性质描述和定义的变量域;关系属性是多个实体之间的关联或事件的性质描述和定义的变量域。

> **属性应遵循原子非派生定义原则**：对于任一相关属性，若其语义可以由其它更基础的属性通过计算、判断或映射得到，则不应在逻辑表中再将其定义为独立属性。逻辑表应优先保留支撑问题语义所必需的基础属性，而避免引入冗余的派生属性。
>
> **属性应优先定义为抽象的性质槽位**：属性建模的目标，是表达实体需要具备哪些性质表达能力，而不是在语义尚不充分时，过早将其固化为某一种具体字段形式。对于尚未明确的属性，不应强行具体化为某个特定属性名称或表示方式。
>
> **同一性质可能存在多种属性表达形式**：问题中提到的某一性质，未必天然对应唯一的属性实现。例如“老人”这一概念，既可能通过“年龄”属性及其取值范围表达，也可能通过“年龄段”或“是否老人”这类分类属性表达。对此，应优先保留符合问题定义、能够支撑该性质判断的最基础、最通用的抽象属性槽位，而不应过早将其固定为某一种派生表达形式。

> **属性应该确定正确的挂载位置**：注意区分属性的正确挂载位置是实体还是关系；判断属性在语义上描述的是“对象自身”还是“对象之间的关联事实”；
* 属性挂在实体上：当它描述的是某个实体实例本身，脱离当前关系语境也成立。
* 属性挂在关系上：当它描述的是实体之间这次关联/参与/交互本身，离开这段关系就说不清楚；
脱离关系语境后，不能独立成立的属性就是关系属性；


---

## 6. 实现证据只作支撑，不主导建模

数据库模式相关证据、表名、列名、外部知识只能作为落地支撑。

它们可以帮助你：

* 判断对象与属性是否可能存在；
* 确认某些对象的实现证据是否明确。

它们不得：

* 替代用户问题本身的语义依赖；
* 主导基础对象的定义；
* 把实现字段直接当成基础逻辑对象名；
* 把某个实现表直接等同于最终基础实体或基础关系。

# 分析步骤

在输出最终 JSON 之前，必须按如下步骤，完成整个分析流程。
**禁止跳过分析**直接生成最终对象草图。

---


## Step 0. 校准问题语义边界

先从用户问题本身出发，确定本次建模允许使用的语义范围。

需要明确：

1. 问题所属专业领域；
2. 题面明确给出的语义内容，并按原问题口径解释；
3. 题面中存在边界不确定或多种理解方式、但与问题求解有关的语义；
4. 数据库模式提示或外部知识中与问题相关的部分，以及与问题无关、不得纳入建模的部分；
5. 用户问题使用的语言，后续所有名称与说明必须与该语言一致。

要求：

* 只分析问题语义，不提前假设实体、关系、属性或字段；
* 未在题面或问题相关提示中**明确出现**的限定、状态、时间窗口、有效性、类型、归属方式、范围限制等，不得主动补充；没提到的都是问题不需要考虑的语义内容，不是不确定或需要确定的语义内容。
* 数据库实现提示只作为辅助证据，不得替代用户问题本身的语义边界。

---

## Step 1. 问题分解与子问题组织

本步骤的目标是：按照问题本身的自然求解逻辑，将原问题拆解为一组相互关联的子问题，并用自然语言说明各子问题在整体求解中的作用。

本步骤**不得**提前定义实体、关系、属性、连接，也不得提前写成任何数据库实现形式。
本步骤只允许使用自然语言描述问题如何被逐步求解，不得将语义提前固化为后续建模结构。

### 1. 提取问题中的关键语义内容

首先，通读问题，识别其中涉及的关键语义内容，包括但不限于：

* 问题关注的对象或对象范围；
* 对象之间可能存在的联系、交互、从属、参与或对齐关系；
* 对对象或联系施加的条件、限制、范围、角色、时间、方向、比较基准等约束；
* 为形成最终答案所需要的聚合、比较、排序、Top-k、窗口、比例、差值、派生指标等计算要求。

这些内容仅作为问题理解与求解拆解的依据，不等于后续的实体、关系或属性定义。

要求如下：

* 尽量使用原问题中的术语与表达；
* 必须对齐问题本身的语义边界；
* 对未确定语义，仅保留其抽象语义作用，不提前决定其承载形式；
* 不得因为某一语义后续可能需要被单独检索，就在本步骤中先行将其认定为实体、关系或属性。

### 2. 分析语义多义性

对于问题中存在多义表示、抽象性或多种合理理解方式的语义，需要说明其可能的语义解释，并选择一种**最自然、最符合常见数据库模式设计**的理解方式作为本步骤的分析基础。
**语义严格遵守语义边界**：语义不确定性应与Step 0 问题语义边界的结论对齐，不考虑任何**未提及即不考虑**的内容，不考虑已声明的与问题不相关的内容。
表示为字典形式：对每个问题的特定文本段给出多义性分析。

处理原则如下：

* 若某一语义表现为对象性内容，但其具体边界未定，仅保留其对象性，不提前落为逻辑实体；
* 若某一语义表现为关联性内容，但其具体承载方式未定，仅保留其关联性，不提前落为逻辑关系或连接；
* 若某一语义表现为条件约束，仅保留其约束作用，不提前落为逻辑属性或字段条件；
* 若某一语义表现为分析或计算要求，仅保留其分析目标，不提前写成具体计算表达式。

### 3. 按自然求解逻辑设计子问题序列

基于问题的自然分析逻辑，将原问题拆解为若干独立的子问题。

**严格遵守语义边界**：子问题定义应与Step 0 问题语义边界的结论对齐，不考虑已声明的与问题不相关的内容。

子问题拆分应遵循以下原则：

* 一个子问题应对应一个相对清晰、可说明、对后续求解有支撑作用的语义任务；
* 子问题可以围绕对象范围的确定、对象之间联系的识别、约束的施加、分析口径的形成、聚合比较排序的执行、以及结果整合等自然步骤来组织；
* 多个语义内容若共同服务于同一个求解目标，可以在同一个子问题中统一处理；
* 只有当某个语义内容在求解过程中需要被单独建立、单独保留或被后续重复依赖时，才适合形成独立子问题。

子问题描述：对每个子问题，使用自然语言描述其在整体求解中的语义作用，并说明其的语义操作与语义约束条件。

语义操作：说明该子问题需要完成什么语义任务，例如：

* 确定对象或对象子集；
* 确定对象之间的联系、参与或匹配；
* 建立必要的上下文附着、空间/时间/编码对齐；
* 对既有对象或联系施加范围限制；
* 在对象或联系基础上进行聚合、比较、排序、Top-k、派生计算；
* 形成后续步骤所依赖的阶段性结果。

约束语义：说明该子问题受到哪些限制，例如：

* 角色限制；
* 时间或顺序限制；
* 方向限制；
* 局部范围或子集范围；
* 参考对象或比较基准；
* 分子 / 分母口径；
* 去重口径；
* 聚合前提；
* 局部分析范围。


候选基础语义收集：同时对子问题，收集其中涉及的对象性内容与关联性内容，形成候选基础语义集合。

收集范围包括：

* 直接作为查询对象出现的内容；
* 出现在约束语义中的对象性内容；
* 出现在比较、参考、对照语义中的对象性内容；
* 出现在分组、聚合、比例、排序、Top-k、窗口等计算支撑语义中的对象性内容与关联性内容；
* 为某一分析口径成立所必须存在的基础对象与基础联系。

不包括：
* 已在 Step 0 问题语义边界中声明与问题不相关的内容。

这里需要注意：

本步骤关注的不是“哪些内容最终要展示在结果里”，而是“哪些基础对象与基础联系是问题成立所必需的”。


要求如下：
* 子问题定义必须与Step 0 问题语义边界的结论对齐，禁止考虑任何已声明的与问题不相关的内容。
* 只描述“需要什么语义作用”和“受到什么语义限制”；
* 不得提前写成实体、关系、属性、字段、连接方式、join key 或计算表达式；
* 不得把数据库实现支撑细节误写成问题本身的求解步骤；
* 不得遗漏问题中关键但隐含的限制条件。

---

## Step 2. 从子问题中识别基础逻辑实体与基础逻辑关系

本步骤的目标是：基于 Step 1 得到的子问题序列，识别出支撑该问题成立所需的基础逻辑实体与基础逻辑关系。


### 2.1 判断候选语义是否应作为实体或关系语义单元

对于每个子问题的候选语义单元，需要判断其是否应作为独立的实体或关系语义单元进入后续建模。

本步骤的核心不是直接给出实体或关系分类，而是先判断该候选语义是否具有独立语义单元资格：

* 如果该语义能够独立承载问题中的对象语义或关联语义，则应作为实体或关系候选单元保留；
* 如果该语义不能独立承载对象或关联结构，而只是描述、限定、修饰或计算某个实体/关系，则不应作为实体/关系，而应作为该实体/关系的附属属性、条件、角色或计算约束处理。

#### 应作为实体/关系语义单元的情况

候选语义满足以下情况之一时，应作为实体/关系候选单元保留：

* 表示一个具有稳定语义身份、可独立指称的对象类型或对象集合；
* 表示两个或多个对象之间的基础联系、参与、归属、引用、交互、匹配或对齐；
* 在问题中被单独引用、区分、比较、约束或反复依赖；
* 具有明确的基础粒度，且该粒度是后续筛选、关联、聚合、比较或分析成立的前提；
* 如果不作为实体/关系单元保留，会导致对象语义被压缩为属性，或关联语义被压缩为字段条件，从而造成语义结构不清；
* 如果不作为实体/关系单元保留，会导致问题中的角色、方向、范围、参照对象或对象间约束无法清楚表达。

#### 不应作为实体/关系语义单元的情况

候选语义满足以下情况时，通常不作为实体/关系单元，而应作为其它语义单元的附属内容处理：

* 仅表示某个实体或关系的属性、状态、类型、标签、数值或时间；
* 仅表示某个实体参与关系时的角色，应作为关系参与者的 role 表达；
* 仅表示对实体或关系的筛选条件、范围限制、有效性限制或局部分析口径；
* 仅表示聚合结果、排序结果、Top-k 结果、比例、差值、窗口统计等派生分析语义；
* 仅表示数据库实现中的字段、外键、编码、映射或连接路径，而不是问题本身的对象或关联语义。

需要注意：不作为实体/关系语义单元，并不表示该语义被丢弃。它仍然需要在后续步骤中根据语义归属，挂载到相应的实体或关系上，作为属性、条件、角色、约束或计算说明保留。


## 2.2 判断需要建模语义单元的语义承载基础性

在确定完需要独立建模的候选语义之后，可能为基础实体或关系，也可能为中间表示的派生实体或关系。
在语义建模判断时，需要注意保持实体与关系的如下性质，识别可能的派生实体或关系并定位基础实体或关系，以保证构建的是原子、基础的实体和关系：

基础实体定义需要满足的约束：
- 实体必须被建模为类型概念，不得将特定实例直接建模为实体。
- 基础实体的**原子性**：实体语义需要保持原子性，如果一个实体的语义能够由更基础的实体派生得出，则该实体是派生的，不应构建为基础实体。
- 实体定义的**语义对齐性**： 尽量使用原问题的专有名词和描述，尽量不自行构建；对齐 Step 0 中定义的问题的语义边界，包括确定语义和未确定语义的抽象描述定义。 
- 保持实体类型的**语义单一性**：不得把不同实体类型父类化，也不得把同一实体类型的不同角色实体化。
    - 若题面中出现的是多个具有不同语义的实体类型，即使它们在概念上可以被归入某个更抽象的共同父类，也不得在本阶段将其合并为一个父类实体；应优先按题面语义分别建模为独立实体。
    - 但是如果差异仅来自同一实体类型在关系中的不同角色，则应复用同一实体类型，并在关系参与者中用 role 表达差异。
- 保持实体描述的**独立性**：实体的定义、粒度和属性集不涉及任何其它的实体和关系。不能把其它实体或关系作为外键属性/引用属性定义在实体里。

基础关系定义需要满足的约束：
- 关系必须有**两个或多个基础实体的角色**作为参与者；
- 关系的**原子性**：基础关系应表达实体角色之间的原始关联事实，而不是由其它基础关系、关系属性或分析计算派生出关系，如果一个关系的语义能够由更加基础的关系派生得出，则该关系是派生的，不应构建为基础关系。
- 关系定义的**语义对齐性**： 尽量使用原问题的专有名词和描述，尽量不自行构建；对齐 Step 0 中定义的问题的语义边界，包括确定语义和未确定语义的抽象描述定义。 
- 保持关系描述的**独立性**：关系的命名、描述粒度不涉及除了其参与实体以外的任何其它的实体和关系。
  关系必须显示定义，不能压缩为实体间的引用属性。关系应保证实体之间的连通性。当题面明确表达实体之间的联系时，必须用关系表达；不得用某个实体上的引用属性、外键属性替代该关系。



## Step 3. 确定基础逻辑实体类型

明确基础逻辑实体的定义。
实体是问题中具有稳定语义身份、明确基础粒度、可通过属性明确标识和重复引用的对象类。

本步骤定义基础逻辑实体与逻辑关系，与相应属性。

实体定义需要遵照如下的规则：

禁止将条件约束、实例值或子类型直接并入实体定义：条件约束、筛选值、统计口径和子类型不得直接写入实体名，也不得借此把实体定义成带条件的集合；这类语义由属性的条件约束或关系语义表示，而不是体现在实体定义中；这样的定义会语义重复。

禁止将关系中的角色独立为实体定义：一个关系中，同一个实体类型可能多次出现，在关系中承载不同的角色。角色本身依赖于关系的语义，角色语义必须在关系中表达，不得将角色直接作为脱离关系的独立实体定义。

禁止父类合并：若题面中出现多个语义不同的实体类型，即使它们概念上可归入同一更抽象的父类，也不得在本阶段合并为一个父类实体后再用“类型”“类别”“层级”等属性区分；应优先按题面语义分别建模为独立实体。

禁止重复定义实体：对同一语义对象，不得同时定义“基础实体”与“带约束条件的实体”或“其子类型实体”形成重复建模；关系中若不同参与角色指向的是同一实体类型，应复用同一个实体定义，在关系中通过 角色 role 区分其语义位置，不得因角色不同而重复定义实体，除非题面明确要求将其建模为两个语义不同的实体类型，例如不同的角色有不同的约束条件和属性定义。

对每个基础实体，都要明确：

* `name` 必须符合问题的表达口径和上述定义规则，不将条件约束、实例值与角色作为实体定义的语义部分，按照问题定义口径，不随意泛化或细化定义。
* `desc` 必须保持实体语义的独立性，进行语义的简短说明，禁止提及其它实体和关系。
* `grain`准确描述一个实例代表什么；

---

## Step 4. 确定基础逻辑关系

明确基础逻辑关系的定义。
关系是**两个或多个实体类型**之间具有明确独立语义的关联、交互或事件，用于表达实体之间实际存在的联系。参与关系的实体具有角色：一个基础实体可以以不同角色在关系中出现多次。

* 基础逻辑关系类型：明确该关系类型的详细语义，每个关系实例指代什么，是否可标识。参与该关系的必须为两个以上的角色化逻辑实体类型，在问题中的作用；
通过关系定义表达确定语义：关系不仅是实体间的连接，也是实体间关联的语义承载；关系定义必须保有明确的与问题口径对应的明确语义；

对每个基础关系，都要明确：

* `name`
* `desc`
* `grain`
* `participants`

其中：

* `participants` 中每个参与者必须包含：
  * `entity`
  * `role`

要求：

* `participants` 中引用的实体必须来自 `entities`；
* 每个关系至少包含两个参与者；

本阶段不定义详细的属性语义。


## Step 5.确定实体与关系的基础属性：

基础逻辑属性的定义：

1. 首先列举所有需要由逻辑属性表达的语义内容及语义约束，先不指派具体的实体和关系挂载；

2. 其次，对每个内容与约束单元必须显式分析定义其语义：
* 挂载对象与类型：该字段是单纯依赖单个实体实例的作为实体属性；脱离关系语境后，不能独立成立的属性就是关系属性；
* 非派生：当某个属性可以通过与其他属性的连接、计算得到时，不应直接在逻辑表中定义为独立属性。
* 语义表示准确性：同一性质存在多种可能的属性表达形式时，应优先选择最基础、最不预设实现方式的表达；
* 多义性分析：如果某种逻辑属性定义存在多种表示可能性，必须明确说明其它的属性表示可能性，在逻辑建模中选择最符最基础、最少预设实现方式的属性表达；
* 逻辑属性的定义必须完全来源于问题：每个属性必须用于表示语义，支持计算或条件约束，禁止基于常识：“从常识上来看”，或为“可读性”，“定义完整性”擅自添加任何额外属性。

3. 最后，检查所有实体与关系的属性分配：

标识符属性key_attributes：若用户没有直接给出天然标识属性或可作为标识符属性的自然键，则允许构建补充标识符；补充标识符必须带上 `_surrogate_id` 作为后缀，以明确这是为了定义的可行性构建的标识符槽位。

对每个实体，明确属性集与标识符属性集：
* `key_attributes`
* `attributes`

* `key_attributes` 必须是标识该实体的基础属性；
* `attributes` 只能保留基础属性；
* 若某属性只是计算中间值，不得写入。

对每个关系，明确关系自身的属性集：
* `attributes`
* `attributes` 只能保留该关系本身的基础属性；不得将关系参与者的属性作为关系的属性。
* 不得把单个实体上的状态/标签/类别限定错误建模为关系。

---

**推理步骤约束**： 你必须顺序完成上述Step 1 - 4 所有推理任务，禁止跳过步骤直接生成Step 5

# Step 6. 输出

完成上述所有分析步骤后，才能输出最终的基础逻辑实体-关系草图，注意所有实体、关系、属性的名称与说明必须与用户输入语言一致。格式如下：

```json
{
  "entities": [
    {
      "name": "",
      "desc": "",
      "grain": "",
      "key_attributes": [
        {
          "name":"",
          "semantics":""
        }
      ],
      "attributes":[
        {
          "name":"",
          "semantics":""
        }
      ]
    }
  ],
  "relations": [
    {
      "name": "",
      "desc": "",
      "grain": "",
      "participants": [
        {
          "entity": "",
          "role": ""
        }
      ],
      "attributes": {}
    }
  ]
}
```

# 输出要求

* 输出必须是单个合法 JSON 对象；
* 不得输出 conceptual SQL；
* 不得输出 CTE；
* 不得输出执行步骤；
* `entities` 与 `relations` 只保留基础层对象；
* 所有说明使用与用户输入一致的语言；
* 字段值必须具体、清晰，不得使用 `...`、`same as above`、`TBD` 等占位表达。
