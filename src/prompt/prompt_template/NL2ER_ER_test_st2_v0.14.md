# 任务定义

基于用户问题、数据库模式相关证据、外部知识，以及 **已产出的基础逻辑实体-关系草图（Object Sketch）**，完成一轮 **ER 复核 + 逻辑查询草图构建 + 约束补全**。

本阶段的目标：

* 复核基础实体、基础关系和稳定基础属性是否足以准确表达问题；
* 在必要时对 Stage1 的对象草图做最小必要修正；
* 补充 Stage1 中尚未建模的约束条件；
* 用 **逻辑查询草图（Logical Query Sketch）** 复查当前 ER 建模是否足以支撑问题语义；
* 显式指出哪些问题语义已经被当前 ER 与约束支撑，哪些仍然没有被准确承载。

这里的“逻辑查询草图”不是 SQL，也不是 CTE 序列，更不是物理执行计划。
它是一个面向语义验证的轻量查询表达，用于说明：

* 最终答案的粒度是什么；
* 查询从哪些基础实体/关系出发；
* 需要哪些连接语义；
* 需要施加哪些过滤与存在性条件；
* 需要构造哪些派生指标；
* 需要哪些分组、排序、Top-k 或最终投影；
* 这些步骤是否都能被当前的基础 ER 与约束支撑。

本阶段的核心作用，是把 Stage1 的“基础对象层”与问题中的“查询语义层”对齐，并借此复查建模表达是否准确。

---

# 基本原则

## 1. 先复核基础 ER，再补查询语义，不直接写 SQL

本阶段允许使用查询逻辑来验证建模，但禁止直接退化为 conceptual SQL 或 SQL-like 伪代码生成。

你要复核的是：

* Stage1 的实体是否真的是基础对象；
* Stage1 的关系是否真的是稳定关系；
* Stage1 的属性是否真的是稳定基础属性；
* 问题中的约束、过滤、存在性条件、时间/空间限定是否被遗漏；
* 当前 ER 是否足以支撑最终问题所需的聚合、排序、Top-k、比例、窗口或统计结果。

你不要输出：

* conceptual SQL；
* CTE；
* SELECT / FROM / JOIN / WHERE / GROUP BY / ORDER BY 等 SQL 片段；
* 物理表、列、join key 的显式执行过程；
* 任意可执行语句。

---

## 2. Stage1 Object Sketch 不是最终真相，但默认优先保留

Stage1 输出提供了一个基础对象草图，但它可能存在以下问题：

* 漏掉必要基础实体；
* 漏掉必要基础关系；
* 把本应是约束的内容漏掉；
* 基础属性的内容建模得不够准确；
* 缺失用于表达语义和约束条件的属性；
* 多写了基于常识推断的，但对问题不必要/冗余的属性。
* 关系粒度、命名、角色定义不够清晰；
* 用过于抽象或过于实现化的对象名表达基础对象。


本阶段必须优先做 **最小必要修正**：

* 若 Stage1 已经正确表达了基础对象，应尽量保留；
* 在问题语义无法被当前草图支撑时，才允许新增、删除、重命名或重分类；
* 对明显冗余或基于常识推理、与问题无关的属性，可优化删去；
* 不得为了让逻辑查询草图“更顺手”而随意重写 Stage1；
* 每个修正必须能归入以下类型之一：命名/粒度修正；删除冗余；补充缺失的稳定承载属性；补充缺失的基础对象（实体或关系）；
* 若某个修改仅仅是为了让逻辑查询草图更完整、更容易书写，或为了把未定语义具体化，则不得修改 refined_object_sketch。

## 2.1 允许问题语义表示与补充约束支撑属性，但禁止基于常识和完整性擅自添加属性

在 refined_object_sketch 中，允许补充问题显式语义、约束语义所必需的最小稳定属性，但不允许为了让逻辑实体-关系更像真实 schema、逻辑查询草图更完整、或更容易书写而补充属性。
若某个语义根据用户题面可以判断为“题面显式给出但形式未定”，Stage2 只能补充抽象承载，不得将其具体化为某一种阈值、规则、关系路径、分析口径、实体拆分或实现字段。

## 2.2 所有实体必须有可用标识属性，关系参与者必须可锚定

在 Stage2 的最终 refined_object_sketch 与输出 JSON 中，所有实体都必须具有至少一个可用的标识属性，并以非空 `primary_key` 表示。

* 若用户题面或 Stage1 已给出可稳定标识该实体的自然属性，应优先保留并作为 `primary_key`；
* 若题面未显式给出自然标识属性，但实体在逻辑层面需要被唯一引用、连接、去重、计数或作为关系参与者，则允许定义一个代理标识属性，用 `_surrogate_id` 作为后缀，表示标识属性槽位；如果输入基础逻辑实体-关系草图存在已定义的 `key_attributes`，包括自然键或代理键，本步骤不得修改或补充代理标识属性。

* 任何参与 `relations.participants` 的实体，其 `anchor_attribute` 必须是非空的，并且必须落到该实体自身的 `primary_key` 或等价稳定标识属性上；不得输出无法锚定的关系参与者。

---

## 3. 约束、筛选与操作语义必须先经过逻辑查询草图定位，再决定是否进入 conditions

本阶段要显式识别问题中的约束、筛选、存在性与操作语义，但它们并不都进入 `conditions`。

在后续分析中，必须先构造逻辑查询草图，明确每个候选语义在查询链条中的作用位置、传播范围和依赖关系；再将这些候选语义分为三类：

* `global_condition`：直接作用于基础实体、基础关系或其稳定属性上，用于定义该对象在**当前问题中的整体有效全集**的条件。这里的“全局”是相对于当前问题而言，而不是相对于整个领域、整个数据库或未来其它问题而言。若最终答案的整个计算过程都只在满足该条件的实体或关系集合上展开，且问题中没有再单独使用该对象在该条件之外的更大集合或平行集合，则该条件默认判为 `global_condition`。只有这类内容才允许进入 `conditions`。
* `query_level_predicate`：只用于定义某个局部步骤、中间集合、候选集、存在性判断、分子/分母分支或局部筛选条件。只有当问题中同时需要该对象的更大集合与其受限子集，或该条件仅服务于某个局部分支而不定义整个问题中的对象有效全集时，才应判为 `query_level_predicate`。这类内容只允许出现在逻辑查询草图中，不得回流为基础对象，也不得进入 `conditions`。
* `operation_semantics`：只表达计数、聚合、分组、排序、Top-k、比例、去重口径、distinct counting 口径等查询操作，不定义对象成员资格，不定义对象有效全集。这类内容只允许出现在逻辑查询草图中，不得进入 `conditions`。

常见候选语义包括：

* 属性取值过滤；
* 时间范围限定；
* 空间范围限定；
* 状态限定；
* 类型限定；
* 角色方向限定；
* 存在 / 不存在某类关联；
* 至少一个 / 恰好一个 / exactly one 等局部筛选；
* 去重口径；
* distinct counting 口径；
* Top-k、排序、比较与比例等操作语义。

只有被判定为 `global_condition` 的内容，才输出为 `conditions`；其余内容只能保留在逻辑查询草图中，禁止重新建模为实体或关系。

---

## 4. 逻辑查询草图用于验证，而不是替代基础 ER

逻辑查询草图的作用，是检查：

* 答案能否从当前基础对象推导出来；
* 推导链条是否闭合；
* 聚合与排序依赖的对象是否齐全；
* 缺失的其实是基础对象，还是仅仅是约束条件；
* 当前实体、关系、属性是否足够；
* 当前实体、关系、属性是否冗余；

逻辑查询草图可以用sql形式给出，其中的数据源全部为逻辑实体/关系和相关属性。

---

## 5. 派生内容不得回流成基础属性或基础对象

问题里很多内容是派生的，不属于基础 ER。

不得把以下内容重新写回基础实体、基础关系或稳定基础属性：

* count / sum / avg / ratio / percentage / rank / score；
* lag / lead / rolling / window 结果；
* top-k 结果集；
* grouped summary；
* “最高/最低/前 N / 后 N”结果；
* 由多个基础属性计算出的中间指标；
* 仅在当前问题分析中出现的临时集合。

这些内容只能放在 `logical_query_sketch.derived_metrics`、`ranking`、`final_projection` 等派生层中。

---

## 6. 实现证据只作支撑，不主导建模

数据库模式、表名、列名、外部知识只能作为支撑证据。
它们可以帮助你：

* 识别对象是否可落地；
* 判断某个属性是否合理；
* 判断某个关系是否确有实现支撑；
* 判断某个约束是否可能是时间、空间或存在性条件。

但它们不得：

* 直接替代用户问题的语义；
* 主导基础 ER 的抽象定义；
* 把物理字段名直接当作基础对象名；
* 把实现过程直接变成逻辑查询草图。

# 分析步骤

在输出最终 JSON 之前，必须按如下步骤，完成整个分析流程。
**禁止跳过分析**直接生成任何内容。

---



## Step 0. 校准问题语义边界，并设置输出语言

先基于**用户题面**与 **Stage1 object sketch**，重新完成一轮**语义边界校准与冲突检查**。


本步骤识别明确下列信息信息：
0. **识别问题的专业领域**：判断查询问题的专业领域。
1. **题面已明确给出的语义**：分析问题，明确语义确定的对象、范围、分类、统计目标、结果要求与约束条件；这些内容可直接作为后续分析依据；综合考虑问题上下文进行分析定义。
  **明确确定语义**：对于明确出现的专业名词和术语，给出符合专业领域和问题上下文的合理定义。
  定义应符合题面的概念口径，禁止额外泛化或细化；只允许按照题面解释，禁止任何隐含猜测。所有隐含和假设都属于表达形式未定的内容。


2. **完全排除题面未给出的内容**：对于其它常见数据分析场景、业务习惯或实现经验才会出现的内容，例如范围、统计口径等。
  任何题面并未**直接提及**的内容，则不得假设其存在，不得认为它是表达形式未定的语义，不得进行隐含假设，不得在后续步骤中作为任务独立语义单元、基础对象、约束条件或分析口径继续展开。

3. **题面显式给出，但其承载形式、判定形式或表达形式未定的内容**：若 Stage1 object sketch 已以抽象方式承载，应继续保持抽象；若 Stage1 尚未显式承载，也只能在后续步骤中补充抽象承载，不得在 Stage2 中直接具体化为阈值、规则、关系路径、实体拆分、分析口径或实现字段。

4. **对未定语义的统一抽象描述定义**：对于此类不确定内容，定义符合用户问题表述口径的、最直接的抽象化描述，以统一后续分析。其规则如下：
  未定的对象语义：不确定语义涉及对象的情况，优先按独立的抽象对象定义；对于聚合总数一类的描述，视为对象型，按被聚合的对象定义；
  未定的描述语义：不确定语义描述的对象确定，只是具体的描述形式不确定的，采用最简单的形式定义抽象描述字段：布尔变量或多分类变量，最简化表示语义功能，不设计任何未定的表示。
  若 Stage1 object sketch已完成抽象描述定义，后续分析和逻辑建模统一按照该描述进行，不允许重新设计或扩展实现。


5. **题面是否给出数据库模式或语义的实现提示**:数据库实现提示用于补充说明问题的实现提示，其本身不直接作为基础实体和关系看待；

外部知识、常识和实现提示在本步骤中只可用于帮助判断语义类别与术语边界，不得扩展用户问题本身，不得替用户补充定义，不得把未明确语义解释成某个具体版本。
后续所有步骤只能继承本步骤中“题面已明确给出”或“词语层面可稳定理解”的部分；凡被标记为“未定”的语义，后续必须继续保持抽象，不得提前落为具体实体、关系、属性、条件或计算规则。

6. 明确用户输入问题所使用的语言；后续所有实体、关系、属性与说明必须与用户语言一致。

## Step 1. 复核 Stage1 基础对象草图

逐项检查 Stage1 的：

* `entities`
* `relations`
* `attributes`

**ER复核** 尽量使用原问题的专有名词和描述，尽量不自行构建；
**ER复核**必须对齐 Step 0 中定义的问题的语义边界，包括确定语义和未确定语义的抽象描述定义。必须服从抽象描述定义，不得重新设计。
**ER复核**不得从数据实现中提取任何实现作为逻辑实体或关系。

对实体和关系检查：
* 实体/关系命名：命名是否完全贴合其粒度与语义，与原问题的描述对比是否存在歧义或范围的偏差；
* 这些实体是否都是真正的基础实体；
* 这些关系是否都是真正的基础关系；
* 是否存在粒度不对、命名不准、语义过泛或过窄的情况；
* 是否缺少为支撑问题所必需的基础对象；
* 对于关系，额外检查实体节点之间是否连通，是否存在孤立的实体节点；



对属性检查：
* 首先检查完整性：考虑所有基础属性和可派生属性后，是否还存在遗漏问题中显式表达的语义；
* 其次检查非派生性：禁止任何派生属性表示为基础属性：对于可以基于现有基础属性派生计算得到的属性，一律不得建模，一律不得作为新属性补充；
* 再检查最小必要性：禁止构建问题没有明确要求或冗余的属性：属性语义不得重复、冗余和互斥：不得出现任何冗余的属性；不得出现任何问题没有明确要求，只是基于隐含假设和猜测构造的属性。
* 是否把本应是约束的语义遗漏了；约束缺少相应的作用属性；
* 每个实体是否都有可用的标识属性与非空 `primary_key`；若无自然键但后续需要连接、引用、去重或计数，必须补充代理标识属性，允许使用 `_surrogate_id` 后缀；
* 每个关系参与者是否都能用非空 `anchor_attribute` 锚定到对应实体的 `primary_key` 或等价稳定标识属性；

本步骤的结果不是立即生成最终输出，而是形成一个 **refined_object_sketch**：

* 保留正确的内容；
* 最小必要修正错误内容；
* 仅在问题语义无法被当前草图支撑时，才补充新的基础实体或基础关系。
* 若根据用户题面可判断某类语义属于“题面显式给出但形式未定”，且 Stage1 已以抽象方式承载，Stage2 不得将其进一步具体化为阈值、规则、关系路径、分析口径、实体拆分或实现字段。
* 若某个实体缺少可用标识属性，而后续逻辑查询草图或关系锚定需要该实体被唯一引用，则必须补充最小标识属性；若题面未显式给出自然键，允许构造带 `_surrogate_id` 后缀的代理标识属性。

---

## Step 2. 先构造逻辑查询草图

基于 `refined_object_sketch` 与用户题面，先构造一份逻辑查询草图 conceptual SQL，用于表达：

* 最终答案粒度是什么；
* 查询从哪些基础对象出发；
* 需要哪些连接语义；
* 需要施加哪些过滤与候选集限定；
* 需要构造哪些派生指标；
* 需要哪些分组；
* 需要哪些排序或 Top-k；
* 最终返回哪些结果；
* 哪些条件在整个查询链条中持续定义问题整体的有效全集；
* 哪些条件只出现在局部步骤、中间集合、候选集、分子/分母分支或存在性判断中；
* 哪些内容只是聚合、分组、排序、Top-k、比例、去重等操作语义。

Conceptual_Sql 的数据对象是逻辑性的，基于逻辑实体关系和逻辑属性，但是其语法结构需要满足**语法完整、结构稳定、便于后续解析**；

Conceptual SQL需要基于确定的语义构建查询，不得引入其它额外的隐含假设和猜测；不得直接使用数据实现中的表列；

Conceptual SQL 是验证产物，不是对基础ER的重构；它仅用来检测 refined_object_sketch 对语义表示和查询计算的完整性支持。逻辑查询草图只能使用 refined_object_sketch 中已有的实体、关系、稳定属性；

---

## Step 3. 从逻辑查询草图回溯候选语义，并反查建模是否足够和多余

构造完逻辑查询草图后，反向检查：

1. 完整性覆盖
* 逻辑查询草图中的基础对象是否足够覆盖查询需求；
* 每个约束是否都能落到明确的逻辑属性；
* 每个派生指标是否都能回溯到基础实体、基础关系、稳定基础属性和约束；
* 是否仍有问题语义无法被当前模型支撑；
* 如果不能支撑，原因是：
  * Stage1 漏了基础对象；
  * Stage1 命名/粒度有误；
  * 仅仅缺少约束，还是缺少约束可作用的属性；
  * 问题本身语义存在歧义；

2. 多余性检查
* 是否存在没有用上的多余实体、关系与属性；查询里用不上的语义单元必须直接删除，不得造成建模冗余。
* 对于没有直接参与查询的冗余属性/对象，必须删除；

3. 约束条件检测
* 对逻辑查询草图中的每个候选条件，必须按以下顺序判断其作用域：
  * 该条件直接作用于哪个基础实体、基础关系或稳定属性；
  * 该条件是在定义整个问题所讨论的对象集合，还是只在某个局部步骤中定义一个中间子集；
  * 在该条件出现之后，后续所有涉及该对象的计算，是否都建立在满足该条件的集合之上；
  * 问题中是否还单独使用了该对象在该条件之外的更大集合，或与之平行的其它子集；
  * 若后续所有使用都建立在该条件限定后的集合之上，且不存在对更大集合或平行集合的并行使用，则默认判为 `global_condition`；
  * 只有当该条件仅服务于某个中间步骤、候选集、局部分支、存在性判断、分子/分母一侧，或问题中同时使用了更大集合与其子集时，才判为 `query_level_predicate`；
  * 若某个语义只是在说明如何计数、分组、排序、限制结果数量或计算比例，则判为 `operation_semantics`；
* 是否把本应停留在 `query_level_predicate` 或 `operation_semantics` 的内容错误回流为了基础对象、基础属性或全局 `conditions`；
* 不得因为 `query_level_predicate` 或 `operation_semantics` 的书写便利而重构基础 ER。


在每个阶段发现的问题，允许对`refined_object_sketch`进行修改、新增和删除；
若某个关系参与者缺少可用锚点，必须优先检查并补足其对应实体的标识属性与 `anchor_attribute`，而不是输出未闭合的关系结构。

## Step 4. 补充约束条件

基于 Step 3 中已完成的候选语义分类，只从被判定为 `global_condition` 的内容中抽取 `conditions`。任何被归类为 `query_level_predicate` 或 `operation_semantics` 的内容，此处不得转入 `conditions`。

判断某个条件是否进入 `conditions` 时，必须以“它是否定义了当前问题中的对象整体有效全集”为标准，而不得以“它是否只是一次查询过滤”或“它是否不是领域中的永久约束”为标准。某个条件即使只在当前问题中成立，只要整个问题的计算都建立在该条件限定后的对象集合之上，且问题中没有再使用该对象在此条件之外的更大集合或平行集合，它仍然应作为 `global_condition` 进入 `conditions`。

只有那些明确只服务于局部步骤、中间集合、候选集、存在性判断、分子/分母分支或局部筛选的条件，才不得进入 `conditions`。

根据条件涉及的实体/关系在**整个问题**中的出现情况，明确其作用域：若某个实体/关系与其被特定条件约束的子集在整个问题中同时出现，则这些额外条件通常只用于定义该子集的成员范围，属于局部属性条件，不得直接建模为该基础实体/关系的全局属性约束。
只有当某个条件作用于该实体/关系在整个问题中的全部出现，并且问题中不存在与之并列出现的更大范围全集时，才应将其视为全局性条件。

对每个作用在基础实体/关系上的条件，根据conceptual SQL的计算逻辑，判断：

(1) **该条件是否在建立关系本身**  
   关系的连接条件不得进入 `conditions`。

(2) **条件全局性判断**  
   若条件约束了当前实体 / 关系类型在整个问题中出现的所有可能元素集合；整个问题不会以任何形式用到这个集合以外的其它元素，则该条件约束定义了一个问题中出现的整体全集。
   若当前对象 / 关系在整个问题中还存在更大范围的全集，而该条件只作用于其中一个子集，用于数据分析、计算、条件筛选；同时问题中会涉及到其它不属于该集合的元素，则该条件属于局部条件，不得进入 `conditions`。
   局部性条件处理：不可用局部性条件来限定基础实体/关系，这会导致检索范围过小的错误，必须明确说明**这是局部条件，不参与建模，不在后续步骤以任何形式出现**，不添加至`conditions`。这些局部条件语义禁止在后续步骤中以任何形式来体现补充；错误添加会导致检索范围偏差。

(3) 抽取作用域为问题整体的条件：`conditions`仅允许建模**全局性的基础实体/关系上的属性约束条件**以表示对实体/关系/连接本身的属性限定；这些属性限定直接作用于检索，表示为基础的`entity`/`relationship`上的属性条件约束。明确作用对象与属性，不要将关系的约束错误表达在实体上，或者将实体约束错误表达在关系上。任何作用域为局部的条件不得被认为是全局性的，不得参与建模，避免污染检索。

(4) 条件可以定义在实体、关系和角色上；问题可能对某个关系的参与角色定义条件约束，而不是对该实体本身进行约束，注意区分对实体本身的限定条件与对实体在某个关系中的角色的限定条件，特别是当某个实体以多个角色参与关系时。如果同一个实体以不同角色参与一个关系（在关系种多次出现），条件必须优先考虑角色，而不是该实体整体。

* 条件约束必须用自然语言简单描述，禁止使用conceptual SQL的具体实现；

抽取进入 `conditions` 的条件时：

* 若是单个稳定属性的取值限制，建模为 `single_attribute`；
* 若是多个稳定属性之间的全局对应 / 比较，建模为 `inter_attribute`；
* 涉及两个实体以上的复杂约束条件（例如两个实体+关系），由查询逻辑表示，不在此处建模。

注意：

* 不得把局部子集定义条件误写成基础实体 / 关系的全局约束；

* 所有进入 `conditions` 的约束都必须用自然语言简洁描述，不得引用 conceptual SQL 的具体实现写法；
* 进入 `conditions.based_on` 的属性必须是稳定属性；不得把仅用于定义局部中间子集的临时列、派生列或实现绑定字段写入 `based_on`。

## Step 5. 输出

完成上述所有分析步骤后，才能输出最终的修订好的逻辑实体-关系，注意所有实体、关系、属性、约束与说明必须与用户输入语言一致。格式如下：


```json
{
  "entities": [
    {
      "entity_name": "",
      "desc": "",
      "grain": "",
      "attributes":[
        {
          "name":"",
          "semantics":""
        }
      ],
      "primary_key": [
        "attr_name_1",
        "attr_name_2"
      ]
    }
  ],
  "relations": [
    {
      "relation_name": "",
      "desc": "",
      "grain": "",
      "participants": [
        {
          "role": "",
          "entity": "",
          "anchor_attribute": ["attr_name_1"]
        }
      ],
      "link_condition": "",
      "attributes": [
        {
          "name":"",
          "semantics":""
        }
      ]
    }
  ],
  "conditions": [
    {
      "condition_name": "",
      "condition_type": "single_attribute | inter_attribute ",
      "targets": [
        "entity_name.attr",
        "relation_name.attr",
        "role.attr",
        "connection_name.attr"
      ],
      "description": ""
    }
  ]
}

```

# 输出要求

* 输出必须是单个合法 JSON 对象；
* 不得输出 conceptual SQL；
* 不得输出 CTE；
* 不得输出 SQL 语法片段；
* `refined_object_sketch` 只保留基础层对象；
* `conditions` 只保留稳定语义约束；
* `logical_query_sketch` 只表达逻辑查询语义，不表达执行代码；
* 每个 `entity` 都必须有非空 `primary_key`；若题面未显式给出自然键，允许使用带 `_surrogate_id` 后缀的代理标识属性；
* 每个 `relations.participants[].anchor_attribute` 都必须是非空数组，并落到对应实体的 `primary_key` 或等价稳定标识属性上；
* 所有说明使用与用户输入一致的语言；
* 字段值必须具体、清晰，不得使用 `...`、`same as above`、`TBD` 等占位表达；
* 若某项为空，也必须返回空数组，而不是省略字段。
