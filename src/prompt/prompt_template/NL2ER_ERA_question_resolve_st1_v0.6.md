# 任务定义

根据全部输入中可识别的用户需求语义与数据库模式相关证据，完成该问题的**语义边界校准**与**查询子查询序列设计**。

本阶段的目标不是直接生成对问题的最终查询，也不是抽取实体、关系和属性。

本阶段只负责：

* 将问题分解为语义单元与查询子查询；
* 明确每个子查询在整体求解中的作用、语义操作、语义限定与多义性；
* 为后续从子查询中抽取基础逻辑实体、基础逻辑关系与逻辑属性提供稳定输入。

本阶段不得：

* 正式定义实体、关系和属性；
* 输出字段、连接方式、join key 或 SQL 计算表达式；
* 将数据库模式实现直接转化为逻辑模型。

---

# 基本原则

## 1. 先组织问题求解结构

首先提取问题中的语义单元，并根据查询计算的逻辑顺序构建一系列查询子查询。

数据库模式相关证据作为实现支撑，用于将语义内容落地到可能的数据来源；它可以作为问题的补充说明，但不得主导问题本身的求解结构，也不得替代用户问题的语义分解。

---

## 2. 实现证据只作支撑，不主导语义拆解

数据库模式相关证据、表名、列名、外部知识只能作为落地支撑。

它们可以帮助你：

* 判断对象与属性是否可能存在；
* 确认某些对象的实现证据是否明确；
* 补充题面未明说但由输入提示直接给出的查询语义。

它们不得：

* 替代用户问题本身的语义依赖；
* 主导子查询定义；
* 把实现字段直接当成子查询对象；
* 把某个实现表直接等同于逻辑对象。

# 分析步骤

**Think step by step**: 完成 Step 0 和 Step 1 的所有分析步骤，才能得到详实准确的子查询序列。**禁止跳过分析**直接生成 Json 输出。

---

## Step 0. 问题背景与输出语言设置

判断查询问题的专业领域，并明确用户输入问题所使用的语言。后续所有子查询、约束与说明必须与用户语言一致。

---

## Step 1. 校准问题语义边界，分解问题

本步骤的目标是：按照问题本身的自然求解逻辑，将原问题拆解为一组用自然语言定义的子查询。

### 1.0 分析相关外部知识

对给出的输入：外部知识，分析理解其中与问题相关的语义内容。
判断给出的外部知识是否指出了某种查询计算的逻辑，或实体-关系属性建模的提示。

### 1.1 先从题面和相关外部知识分析语义

只看输入：用户原始输入问题和输入：外部知识，明确问题的查询逻辑，并用自然语言描述。

此处需要理清问题的求解逻辑，但不是确定实体-关系和属性。从题面分析和相关外部知识分析语义时，先不考虑任何数据实现的内容。

明确语义：对于问题中的关键语义内容，给出符合题面上下文与相关外部知识的语义解释。关键语义内容的定义必须使用题面原文和外部知识的口径，不得额外泛化、细化或补充题面未声明的限制。

未提及即无关：需要明确所有未提及的对象都是与问题不相关的语义内容：如果题面没有明确给出某类限定语义或分析语义，这些就不是未确定的内容，而是不需要确定这些内容，后续步骤的任何分析与建模均不以任何形式考虑它们。

### 1.2 理解问题相关的数据提示，补充语义

如果输入中包含数据库模式实现说明或外部知识提示，这些内容可能与问题相关，也可能无关。
需要找出与理解问题的相关数据实现与提示，以此补充解释问题题面没有明确的逻辑语义。

#### 1.2.1 分析提示中的物理模式表列

如果输入没有给出相关物理数据库模式和实现支持，则不需要进行分析。

分析物理表列的语义：
首先列举出问题的实现支持提及的所有物理表和列，分析它们作为数据本身的语义；数据语义是指在数据库中该模式信息的语义，而不是在这个具体问题下的语义。

注意，物理数据的实体-关系语义建模与逻辑模型不一定一致；后续阶段建模需要以题面的逻辑模型与语义要求为主，物理数据的实体-关系语义仅提供语义解释和实现支持。

语义解释：说明问题中需要哪些逻辑语义，或某些语义通过什么问题口径得出；该语义在题面中未表达，通过数据提示可以发现。对于语义解释的物理数据，需要将其重抽象为问题的逻辑定义补充，并将其整合到问题整体的查询逻辑中。

#### 1.2.2 对题面语义的补充解释

识别与题面语义相关的提示，补充解释题面的语义：

与问题的逻辑语义相关的提示可能以两种形式存在：实现支持或补充语义解释。

实现支持：实现提示中的对象、字段和连接路径，只说明问题中逻辑对象或逻辑联系的可存在性，不补充语义内容的，不需要纳入后续分析过程。对于实现支持的物理数据，**不需要以任何形式出现在逻辑模型中**。

语义解释：如果实现提示直接补充了当前问题求解的语义逻辑，则可以将其抽象为问题相关的补充语义单元。该语义单元必须视为对题面语义的补充、说明和解释，重新命名和定义，将补充的逻辑语义单元整合到问题整体的查询逻辑中，而不是保留物理数据中的物理表、字段、函数或连接路径命名。

对数据提示判断相关、无关性：只有直接为题面补充说明逻辑语义的提示才是问题相关的提示。

对于已经确认相关的提示，后续子查询分解必须继承其对题面语义的解释，但不是把数据的实现表、实现字段、连接路径、函数调用、编码转换或中间实现步骤直接作为子查询内容。

无关提示不得影响后续分析：如果某个数据实现提示不能用于直接说明和解释题面明确语义信息，则将其视为无关信息，不得带入后续分析。

### 1.3 按自然求解逻辑设计子查询序列

基于问题的自然分析逻辑，将原问题拆解为若干独立的子查询。

**严格遵守语义边界**：子查询定义应与问题语义边界的结论对齐，不考虑已声明的与问题不相关的内容。

子查询设计应遵循以下原则：

* 子查询是一个逻辑查询任务：必须明确查询的对象、查询计算和返回结果。
* 子查询对齐问题语义表示与题面语义解释，必须用逻辑形式和语义操作的口径表述。禁止直接使用数据提示和操作步骤作为子查询内容。
* 子查询序列必须逻辑清晰，明确覆盖问题所有语义要素，包括操作和约束条件。

对每个子查询，明确如下内容，并将实现提示对问题的解释与补充整合进子查询中：

1. 在问题整体求解中的作用；
2. 语义操作；
3. 语义限定；
4. 查询表示的多义性。

语义操作：说明该子查询需要完成什么语义任务，需要哪些语义支持。例如：

* 确定对象或对象子集；
* 确定对象之间的联系、参与或匹配；
* 对既有对象或联系施加条件约束；
* 在对象或联系基础上进行聚合、比较、排序、Top-k、派生计算；
* 形成后续步骤所依赖的阶段性结果。

语义限定：说明该子查询中的对象、联系和计算具体受到哪些语义约束；需要全面表述问题语义包含的约束，不得遗漏。

语义约束可以包括：角色限制、时间限制、方向限制、局部范围、参考对象、比较基准、分子/分母口径、去重口径、聚合前提和局部分析范围等。

查询表示的模糊性判断：主要指如下两个方面：
1) 查询本身的计算逻辑: 查询所使用的的实体、关系及属性这些计算对象是明确的，但是计算方法可能有多种；
2) 查询面向的数据对象：查询所使用的的实体、关系和属性本身定义不明确，有多种可能的计算对象选择方法；

#### `question` 与 `ambiguity` 的分工：

`question` 字段不是把题面短语机械改写为具体实现步骤，而是描述该子查询在整体求解中的**抽象语义任务定义**。它必须用一个能够覆盖局部口径差异的抽象语义单元来表达求解逻辑，例如“确定符合独居老人语义的人群”“计算每个居委的人口总数”“确定目标范围内的常住人口集合”。

局部语义口径歧义应被包含在 `question` 的抽象语义中：`question` 保持抽象，不预先落定具体口径；`ambiguity` 只补充说明该抽象语义单元下可能存在的候选业务口径。不得因为存在局部口径歧义，就把 `question` 改写成某一种具体口径或拆成多个实现步骤。

`ambiguity` 不用于记录数据实现选择、名称匹配方式、字段/表/连接路径、编码枚举、空间匹配方式、物理层级展开方式、SQL 截断细节等实现不确定性。只有当不同解释会改变查询逻辑路径、答案口径，或是问题中某个局部语义概念的业务判断口径时，才可写入 `ambiguity`。

判断标准：

* 如果差异只是“同一抽象语义单元如何由数据承载或匹配”，不写入 `ambiguity`；
* 如果差异只是局部业务定义，例如“老人”的年龄阈值、“独居”的判断口径、“人口总数”的去重口径，则 `question` 使用覆盖性抽象概念，`ambiguity` 记录候选口径；
* 如果差异会改变整体求解路径，例如统计居住人口还是户籍人口、引用方向不同、分子分母定义不同，则写为查询逻辑歧义；
* 不得引入题面未要求、数据提示未直接补充的外部假设作为歧义。

子查询要求如下：

* 不得提前写成实体、关系、属性、字段、连接方式、join key 或计算表达式；
* 不得遗漏问题中关键但隐含的约束和限制条件。

在完成上述分析后输出查询逻辑子问题序列；
ambiguity仅允许列举查询语义逻辑的模糊性；不得列举任何具体数据实现相关的内容；若查询逻辑唯一确定则不需要填写。

```json
{
  "language": "",
  "resolve_process": [
    {
      "id": "SQ1",

      "ambiguity": []
    }
  ]
}
```
