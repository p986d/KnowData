# 任务定义

根据全部输入中可识别的用户需求语义与数据库模式相关证据，以及一个基础逻辑实体-关系草图，校对实体-关系的定义，判断是否符合已定义规则，并补充定义属性与约束条件。

本阶段的目标：

* 复核基础实体、基础关系的定义是否准确。
* 基于基础实体-关系，构建逻辑查询草图；
* 补充定义实体与关系的属性与约束条件；

这里的“逻辑查询草图”不是可执行SQL或查询计划。
它是一个面向语义验证的轻量查询表达，用于说明查询的语义操作与计算逻辑。

# 分析步骤

## Step 0. 问题背景与输出语言设置

判断查询问题的专业领域，并明确用户输入问题所使用的语言。后续所有实体、关系、属性与说明必须与用户语言一致。

## Step 1.  校准问题语义边界，分解问题

本步骤的目标是：按照问题本身的自然求解逻辑，将原问题拆解为一组用自然语言定义的子查询。
**不得预先假设概念建模形式**：本步骤只关注语义，不得将语义提前固化为逻辑间模结构。**不得**定义实体、关系、属性等概念建模的形式，也不得提前写成任何数据库实现形式。

### 1.1  分析题面确定语义

通读问题，识别其中涉及的关键语义内容，包括但不限于：

* 问题提及的对象概念；
* 对象概念之间可能存在的关联；
* 查询和计算所用的相关字段；
* 查询和计算逻辑。

明确语义：对于问题中的关键语义内容，给出符合专业领域和题面上下文的语义解释。关键语义内容的定义必须使用题面原文文本的口径，不得额外泛化、细化或补充题面未声明的限制。

如果题面没有明确给出某类限定语义或分析语义，例如筛选条件、统计口径、状态、类型、时间窗口、有效性、归属方式或范围限制，则禁止考虑这些未声明的限制或分析。

未提及即无关：需要明确所有未提及的对象都是与问题不相关的语义内容：不是未确定的内容，而是不需要确定这些内容，后续步骤的任何分析与建模均不以任何形式考虑它们。

### 1.2 理解问题相关的数据提示与外部知识

如果输入中包含数据库模式、实现说明或外部知识提示，这些内容可能与问题相关，也可能无关。
需要理解问题的相关提示，并明确哪些提示与问题相关且补充解释了问题的逻辑语义。

### 1.2.1 物理表列与计算逻辑语义理解：

分析数据实现提示:

1. 列举提示中的物理表列与计算逻辑，分析表列语义与计算逻辑语义；
  
  首先综合分析所有的物理表列与计算逻辑，理解相关物理模式的语义。 提示可能直接说明某个题面语义单元如何在数据中表示，也可能需要从模式信息，例如表、列、值、函数说明和数据采样中推断其落地方式，需要综合理解分析提示。
  对数据提示判断相关、无关性：只有直接为题面补充说明逻辑语义的提示才是问题相关的提示。

2. 识别与题面语义相关的提示，分析哪些提示为题面补充了哪些逻辑语义。

  注意，不得将“数据库中存在某张表、某个字段、某条连接路径或某个函数调用”直接等同于“问题建模中需要存在对应的概念实体、关系或属性”。实现提示中的对象、字段和连接路径，只有在能够直接解释题面中明确语义内容的识别、映射、归属、对齐、约束或计算方式时，才可作为语义补充依据。
  如果实现提示直接补充了当前问题求解的语义逻辑，则可以将其抽象为问题相关的补充语义单元。该语义单元必须按照题面语义重新命名和定义，将补充的逻辑语义单元整合到问题整体的查询逻辑中，而不是保留物理数据中的物理表、字段、函数或连接路径命名，不得机械得将物理模式直接转化为逻辑实体或关系。

3. 无关提示不得影响后续分析
  如果某个数据实现提示不能用于直接说明和解释题面明确语义信息，则将其视为无关信息，不得带入后续分析和建模。
  实现层面的存储结构、字段来源、函数调用、编码转换和中间连接步骤，只有在被重新抽象为题面语义的补充口径后，才可以影响后续建模。

### 1.2.2 题面语义解释：

给出题面解释：说明相关数据为题面补充解释了哪些逻辑语义，而不是说明数据实现具体是如何支持题面落地。
相关数据提示应作为题面语义的补充说明进行重新抽象，而不是保留具体表名、字段名或实现路径结构。实现提示可以解释和补充题面语义，但不得改变题面语义本身的对象、关系、属性、条件和分析口径边界。

* 后续使用：

对于已经确认相关的提示，后续子查询分解和语义建模必须继承其对题面语义的解释和限定；但不得把实现表、实现字段、连接路径、函数调用、编码转换或中间实现步骤直接作为基础 ER 单元。后续建模应基于提示对问题语义的补充解释进行抽象，形成面向问题语义的逻辑实体、关系和属性，而不是基于数据库实现结构逐表、逐字段、逐连接地生成概念模型。



### 1.3 语义多义性

对于问题中存在多义表示、抽象性或多种合理理解方式的语义，需要说明其可能的语义解释，并优先选择一种**最符合问题上下文**的理解方式作为本步骤的分析基础。

如果问题对该语义没有任何其它可以支持判断的有效上下文，则选择一种最自然、符合常规数据库查询理解习惯的方式。

本步骤只分析问题自然语言表达中的语义不确定性，不提前判断这些语义最终应被建模为实体、关系、属性或约束。实体、关系和属性的结构化定义应在后续基于 query plan 的语义单元抽取阶段完成。

**语义严格遵守语义边界**：语义不确定性应与题面确定语义与问题相关提示对齐，不考虑任何**未提及即不考虑**的内容，不考虑已声明的与问题不相关的内容。

语义多义性从两个角度分析：

1. **语义表达的多义性**

   语义表达的多义性指：问题中的对象描述、关联描述和条件描述本身可能存在多种合理理解。

   重点分析：
   - 该表达可能指向哪些不同的语义对象、语义范围或语义口径；
   - 该表达的边界、粒度或适用范围是否清楚；

   若存在多种解释，需要说明不同解释之间的差异，并选择最符合问题上下文的一种作为当前分析基础。若缺少上下文，则采用最自然、最符合常规查询理解习惯的解释，但不得补充题面未给出的具体业务规则、判断标准或实现细节。

2. **计算逻辑的多义性**

   计算逻辑的多义性指：问题中的查询计算口径可能存在多种合理解释。


   若存在多种计算口径，需要说明不同口径会如何影响问题结果，并优先选择最符合问题表达和常规查询习惯的一种。若缺少足够上下文，则采用最自然、最符合常规查询理解习惯的解释，但不得补充题面未给出的具体业务规则、判断标准或计算逻辑。

## Step 2. 复核与修订基础逻辑实体-关系

### 基础逻辑实体的定义

基础逻辑实体是问题中具有确定语义身份、明确基础粒度、可独立指称的对象类。实体应理解为类型概念，是一个包含多个实例的集合。

实体应当建模在查询中需要作为独立的单个对象的语义数据源，实体建模需要满足以下条件：
   * 非派生：可由其它基础实体、关系、条件或计算得到的语义，不作为基础实体。
   * 建模口径对齐问题表述：实体定义尽可能使用题面已有概念表述；
   * 不得定义泛化实体：对于问题中具有独立语义身份、独立筛选范围或独立分析作用的实体，必须分别建模为独立实体。**禁止将多个问题中明确区分的实体合并为泛化实体，再通过分类属性加以区分**。
   * 关系语义不得影响实体：实体本身不带关系语义，同一实体类型在关系中的多个不同角色的语义仅在关系中表达。
   * 实体定义不表示条件约束：条件约束不得直接写入实体定义，这类语义由属性条件约束或关系语义表示。

### 基础逻辑关系的定义

基础逻辑关系是**两个或多个基础实体的角色**之间具有明确独立语义的关联。它用于表达实体之间的关联关系。

   * 多参与者：每个关系表示**多个参与者实体**之间的关联语义，参与者必须是基于已确定的实体类型的角色，不得为定义关系编造子问题中没有明确提及的语义内容；属性到实体或关系的归属不得用关系表达。
   * 非派生：可由其它基础关系的语义组合、或需要计算推导得到的关系，不作为基础关系；
   * 不得定义泛化角色：对于每个关系，需要明确其所有参与角色。若同一实体类型在关系中多次出现，承担多个不同角色，或不同实体在关系中的参与含义不同，应分别定义独立角色；
     不得将这些角色合并为泛化角色，也不得用泛化的父类指代多个具体参与角色。
  
  对每个关系，定义其参与者，参与者的角色，语义和粒度。关系必须保持非派生，建模口径对齐问题表述，不得泛化表达关系与角色，同一实体在关系中多次出现时必须明确定义不同角色，不涉及关系参与者以外的其它实体。


注意：语义单元建模不得重复：语义要素的实体-关系建模不得重复，一个语义要素只能建模为单个实体、关系或属性，不得用多个建模单元重复表达同一个语义要素。

如果基础逻辑实体-关系不满足上述定义，则进行适当的修订和改正。

## Step 3. 构造逻辑查询草图

基于已确定的实体关系与确定的问题语义边界，构造一份逻辑查询草图 conceptual SQL，用于表达：

* 最终查询和计算的逻辑；
* 产出的中间结果步骤；
* 如何引用基础实体-关系，需要哪些属性；
* 如何明确表达问题提到的所有约束语义；

Conceptual_Sql 的数据对象是逻辑性的，基于逻辑实体关系和逻辑属性，但是其语法结构需要满足**语法完整、结构稳定、便于后续解析**；

Conceptual SQL需要基于确定的语义构建查询，不得引入其它额外的隐含假设和猜测；不得直接使用数据实现中的表列；

Conceptual SQL 的逻辑需要明确语义操作和约束语义。

语义操作：说明该子查询需要完成什么语义任务，例如：

* 确定对象或对象子集；
* 确定对象之间的联系、参与或匹配；
* 建立必要的上下文附着、空间/时间/编码对齐；
* 对既有对象或联系施加范围限制；
* 在对象或联系基础上进行聚合、比较、排序、Top-k、派生计算；
* 形成后续步骤所依赖的阶段性结果。

约束语义：说明该子查询受到哪些限制，例如：

* 角色限制；
* 时间或顺序限制；
* 方向限制；
* 局部范围或子集范围；
* 参考对象或比较基准；
* 分子 / 分母口径；
* 去重口径；
* 聚合前提；
* 局部分析范围。



## Step 4. 定义逻辑属性

基础实体和关系的属性必须是能够支持问题查询的**原子逻辑抽象属性集**；

实体和关系都可以拥有属性：

- 实体属性描述单个实体实例自身的稳定性质；
- 关系属性描述多个实体之间的关联性质。

**完整的语义表达**：
**原子非派生**：如果某一属性可以由更基础的属性通过计算、判断、聚合或映射得到，则不应作为独立基础属性。查询计算结果视为派生，不作为基础属性。
**非冗余**：对于同一语义要素，不应同时保留多个等价或可相互推导的属性表达。
**逻辑抽象**：属性可以保持为抽象性质槽位，在语义内容不充分时，不必过早固定为具体数据库字段；但必须能明确支撑问题中的计算。
**属性挂载位置**：判断属性在语义上描述的是“对象自身”还是“对象之间的关联”；若属性描述对象自身，挂载到实体；若属性描述实体之间的关联本身，挂载到关系。脱离关系语境后，不能独立成立的属性就是关系属性；

## 2.1 所有实体必须有可用标识属性，关系参与者必须可锚定

所有实体都必须具有标识属性或属性集，并以非空 `primary_key` 表示。
标识属性可以为一个或多个属性。
标识属性可以为技术键或自然键：

* 若用户题面明确实体的标识符属性，将其直接作为 `primary_key`；
* 若题面未显式给出合适的自然标识属性，但实体在逻辑层面需要被唯一引用、连接、去重、计数或作为关系参与者，则允许定义一个代理标识属性，以 `_surrogate_id` 作为后缀，表示标识属性槽位。
关系本身不需要标识属性，关系的参与者必须有标识属性。




## Step 5. 定义约束条件

对逻辑查询草图中条件约束进行分类，提取直接作用于基础实体-关系的约束条件。

* `global_condition`：直接作用于基础实体、基础关系或其稳定属性上，用于定义该对象在**当前问题中的整体有效全集**的条件。这里的“全局”是相对于当前问题而言，而不是相对于整个领域、整个数据库或未来其它问题而言。若最终答案的整个计算过程都只在满足该条件的实体或关系集合上展开，且问题中没有再单独使用该对象在该条件之外的更大集合或平行集合，则该条件默认判为 `global_condition`。只有这类内容才允许进入 `conditions`。
* `query_level_predicate`：只用于定义某个局部步骤、中间集合、候选集、存在性判断、分子/分母分支或局部筛选条件。只有当问题中同时需要该对象的更大集合与其受限子集，或该条件仅服务于某个局部分支而不定义整个问题中的对象有效全集时，才应判为 `query_level_predicate`。这类内容只允许出现在逻辑查询草图中，不得回流为基础对象，也不得进入 `conditions`。
* `operation_semantics`：只表达计数、聚合、分组、排序、Top-k、比例、去重口径、distinct counting 口径等查询操作，不定义对象成员资格，不定义对象有效全集。这类内容只允许出现在逻辑查询草图中，不得进入 `conditions`。


判断某个条件是否进入 `conditions` 时，必须以“它是否定义了当前问题中的对象整体有效全集”为标准，而不得以“它是否只是一次查询过滤”或“它是否不是领域中的永久约束”为标准。某个条件即使只在当前问题中成立，只要整个问题的计算都建立在该条件限定后的对象集合之上，且问题中没有再使用该对象在此条件之外的更大集合或平行集合，它仍然应作为 `global_condition` 进入 `conditions`。

根据条件涉及的实体/关系在**整个问题**中的出现情况，明确其作用域：若某个实体/关系与其被特定条件约束的子集在整个问题中同时出现，则这些额外条件通常只用于定义该子集的成员范围，属于局部属性条件，不得直接建模为该基础实体/关系的全局属性约束。
只有当某个条件作用于该实体/关系在整个问题中的全部出现，并且问题中不存在与之并列出现的更大范围全集时，才应将其视为全局性条件。

对每个作用在基础实体/关系上的条件，根据conceptual SQL的计算逻辑，判断：

(1) **该条件是否在建立关系本身**  
   关系的连接条件不得进入 `conditions`。

(2) **条件全局性判断**  
   若条件约束了当前实体 / 关系类型在整个问题中出现的所有可能元素集合；整个问题不会以任何形式用到这个集合以外的其它元素，则该条件约束定义了一个问题中出现的整体全集。
   若当前对象 / 关系在整个问题中还存在更大范围的全集，而该条件只作用于其中一个子集，用于数据分析、计算、条件筛选；同时问题中会涉及到其它不属于该集合的元素，则该条件属于局部条件，不得进入 `conditions`。
   局部性条件处理：不可用局部性条件来限定基础实体/关系，这会导致检索范围过小的错误，必须明确说明**这是局部条件，不参与建模，不在后续步骤以任何形式出现**，不添加至`conditions`。这些局部条件语义禁止在后续步骤中以任何形式来体现补充；错误添加会导致检索范围偏差。

(3) 抽取作用域为问题整体的条件：`conditions`仅允许建模**全局性的基础实体/关系上的属性约束条件**以表示对实体/关系/连接本身的属性限定；这些属性限定直接作用于检索，表示为基础的`entity`/`relationship`上的属性条件约束。明确作用对象与属性，不要将关系的约束错误表达在实体上，或者将实体约束错误表达在关系上。任何作用域为局部的条件不得被认为是全局性的，不得参与建模，避免污染检索。

(4) 条件可以定义在实体、关系和角色上；问题可能对某个关系的参与角色定义条件约束，而不是对该实体本身进行约束，注意区分对实体本身的限定条件与对实体在某个关系中的角色的限定条件，特别是当某个实体以多个角色参与关系时。如果同一个实体以不同角色参与一个关系（在关系种多次出现），条件必须优先考虑角色，而不是该实体整体。

* 条件约束必须用自然语言简单描述，禁止使用conceptual SQL的具体实现；

抽取进入 `conditions` 的条件时：

* 若是单个稳定属性的取值限制，建模为 `single_attribute`；
* 若是多个稳定属性之间的全局对应 / 比较，建模为 `inter_attribute`；
* 涉及两个实体以上的复杂约束条件（例如两个实体+关系），由查询逻辑表示，不在此处建模。

注意：

* 不得把局部子集定义条件误写成基础实体 / 关系的全局约束；

* 所有进入 `conditions` 的约束都必须用自然语言简洁描述，不得引用 conceptual SQL 的具体实现写法；
* 进入 `conditions.based_on` 的属性必须是稳定属性；不得把仅用于定义局部中间子集的临时列、派生列或实现绑定字段写入 `based_on`。

---

## Step 6. 输出中间表示

问题里很多内容是派生的，不属于基础 ER。

不得把以下内容重新写回基础实体、基础关系或稳定基础属性，但是需要作为查询过程的中间表示数据说明：

* count / sum / avg / ratio / percentage / rank / score；
* lag / lead / rolling / window 结果；
* top-k 结果集；
* grouped summary；
* “最高/最低/前 N / 后 N”结果；
* 由多个基础属性计算出的中间指标；
* 仅在当前问题分析中出现的临时集合。

将逻辑查询中具有阶段性、代表性作用的语义内容作为中间表示输出。
