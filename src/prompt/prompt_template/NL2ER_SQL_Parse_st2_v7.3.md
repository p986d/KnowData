# 一：任务定义

你的任务是：根据用户输入的问题、相关数据库实现提示，以及一条 SQL 形式的概念查询方案 **conceptual SQL**，提取并优化一份面向数据检索的结构化规格。

这份规格不是最终 SQL，也不是数据库物理实现方案，而是一份 **ER Retrieval Spec**，用于显式定义：

* 需要检索的基础实体；
* 需要检索的基础关系；
* 在不存在更合适基础关系时、为完成基础层语义连通而保留的基础连接；
* 基础实体 / 关系的稳定属性；
* 作用于基础实体 / 关系 / 连接的全局性约束条件。

---

# 二：核心思路

本任务不再把 conceptual SQL 中的 CTE 当作基础实体 / 关系 / 连接的直接定义入口，而采用如下流程：

1. 解析 conceptual SQL 中出现的基础逻辑表来源 `*_ent_source` / `*_ent_impl` / `*_rel_source` / `*_rel_impl`，建立基础实体 / 基础关系初稿；
2. 再将 SQL 的以CTE作为阶段性结果的查询推理过程对齐到问题的相应·子问题，检查其语义表达是否完整；
3. 检查每个子问题所需的对象、属性、角色、约束是否都已被基础实体、基础关系的属性集充分支撑；注意问题中的约束条件必须有明确的属性对应，不能隐含表示。
4. 将缺失或不准确之处反馈到基础实体 / 关系及其属性定义中，进行补充、修正与优化；
5. 仅在两个已建模基础实体之间不存在更合适的基础关系，且某个派生步骤暴露了可回落到基础层的确定性对齐 / 补充语义时，才补建基础连接；
6. 最后统一收敛全局条件，输出优化后的 `entities / relations / connections / conditions`。

注意：

* conceptual SQL 中的每个 CTE 可能表达某个命名子问题、某个阶段性结果，或某种局部分析组织方式；
* CTE 的名称、顺序、是否显式独立命名，都只是语义线索，不直接决定最终 ER 分类；
* 基础实体 / 基础关系的主识别来源，不再是 CTE，而是 conceptual SQL 中出现的基础逻辑表来源；
* 中间步骤默认不直接进入最终 ER Retrieval Spec，除非它暴露出基础层必需但尚未显式建模的实体 / 关系 / 连接。

---

## 2.1 基础语义单元

本任务中的基础语义单元，包括：

* 基础实体 `entity`
* 基础关系 `relation`
* 基础连接 `connection`

其中：

### （1）基础实体

表示在问题中应被保留为独立检索起点的原生对象。
基础实体应满足：

* 能单独说明“它是什么”；
* 能单独定义粒度与成员范围；
* 其属性和标识在问题语义中稳定成立；
* 不是仅服务于某一步分析的中间复合结果。

### （2）基础关系

表示对象之间具有明确、稳定、可独立保留的语义联系。
基础关系应满足：

* 去掉具体实现路径后，该联系仍然成立；
* 联系本身具有明确语义，而不仅仅是属性匹配；
* 参与对象与参与角色清晰；
* 必要时可承载关系本身的非标识性属性。

### （3）基础连接

表示两个基础实体之间为了完成属性匹配、时间 / 空间 / 类别 / 标识对齐、上下文补充而需要保留的基础层连通语义。
基础连接不是基础逻辑表来源，不应反向作为基础实体 / 基础关系的定义入口。
仅当两个基础实体之间不存在更合适的基础关系，且某个派生步骤暴露了一个可稳定回落到基础层的确定性连接语义时，才应建模为 `connection`。

---

## 2.2 基础逻辑表来源

本任务中，conceptual SQL 里的下列对象应被优先解析为基础语义单元来源：

* `*_ent_source`
* `*_ent_impl`
* `*_rel_source`
* `*_rel_impl`

它们的作用是：作为某个基础实体或基础关系的**逻辑来源槽位**。

解析原则如下：

* `*_ent_source` / `*_ent_impl` 只用于建立基础实体候选；
* `*_rel_source` / `*_rel_impl` 只用于建立基础关系候选；
* 输出时不得保留 `_source / _impl` 作为最终概念对象名；
* 最终实体名 / 关系名应回到其概念语义本身，而不是沿用逻辑表来源名；
* `*_impl` 只有在输入中存在明确数据库实现证据时才可视为有效来源；
* 若无明确实现证据，则只能使用 `*_source` 作为抽象来源承载。

注意：

* `*_source / *_impl` 是基础实体 / 基础关系的来源承载，不是独立命名子问题；
* 它们本身不应被当作新的 CTE 类型或中间步骤类型；
* 不得将中间结果、局部桥接、映射路径、临时匹配、局部子集或仅为某一步服务的实现动作伪装成 `*_source / *_impl`。

---

## 2.3 中间语义单元

conceptual SQL 中还可能包含大量中间语义单元，它们常由如下操作形成：

* 局部筛选；
* 局部组合；
* 角色化；
* 匹配 / 对齐；
* 聚合；
* 排序；
* Top-K；
* 窗口计算；
* 重命名；
* 粒度变化；
* 最终结果整合。

这些中间语义单元默认**不直接进入**最终 ER Retrieval Spec。
它们的作用主要是：

* 作为问题求解结构中的阶段性结果；
* 暴露基础实体 / 基础关系对属性与约束的支撑需求；
* 暴露某些此前未显式建模、但基础层必须保留的连接语义；
* 检查 conceptual SQL 是否完整表达了用户问题语义。

---

## 2.4 实现来源与概念对象的边界

本任务允许先解析 `*_source / *_impl` 作为基础实体 / 基础关系的逻辑来源，但必须严格区分：

* **逻辑来源槽位**；
* **最终概念对象名**；
* **实现字段 / 实现绑定路径**。

因此：

* 不得把实现表名、桥接表名、空间表名、映射表名原样当作最终概念实体 / 关系名称；
* 不得因为某个 `*_impl` 出现，就把其所有实现字段自动提升为概念层属性；
* 不得把仅用于实现绑定、局部桥接或下推剪枝的实现条件，误写为概念层全局条件。

# 四：提取内容

提取结果包括四部分：

* `entities`
* `relations`
* `connections`
* `conditions`

---

## 4.1 实体 `entity`

实体表示问题中应被保留为独立检索起点的基础对象。
对于每个实体，应提取：

* `entity_name`
* `grain`
* `attributes`
* `primary_key`

---

## 4.2 关系 `relation`

关系表示对象之间具有明确、稳定、可独立保留的语义联系。
对于每个关系，应提取：

* `relation_name`
* `grain`
* `participants`
* `link_condition`
* `attributes`

其中：

* `participants` 用于定义参与实体及其角色；
* `participants.anchor_attribute` 用于列出参与实体上用于建立该关系的稳定锚点属性；
* `link_condition` 用自然语言描述关系成立的方式；
* `attributes` 仅用于承载关系本身的非标识性语义属性。

---

## 4.3 连接 `connection`

连接表示两个已建模基础实体之间，为完成属性匹配、时间 / 空间 / 类别 / 标识对齐、上下文附着而需要保留的基础层连接语义。
连接不表示独立业务关联，不应与 `relation` 混淆。

对于每个连接，应提取：

* `connection_name`
* `grain`
* `participants`
* `link_condition`

其中：

* `participants` 用于定义参与实体及其角色；
* `participants.anchor_attribute` 用于列出参与实体上用于建立该连接的稳定锚点属性；
* `link_condition` 用自然语言描述对齐 / 匹配 / 补充的方式。

注意：

* `connection` 只能存在于两个基础实体之间；
* `connection` 仅在不存在更合适的基础关系时才补建；
* 不得把 relation 的成立条件误降级为 connection；
* 不得把实现桥接路径本身误写成 connection。

---

## 4.4 条件 `conditions`

`conditions` 用于记录**作用于基础实体 / 关系 / 连接本身**的全局性约束条件，但不重复记录 relation / connection 的锚点属性匹配与 `link_condition`。

`conditions` 包括：

* `single_attribute`
* `inter_attribute`
* `link_quantified`

其中：

### （1）`single_attribute`

作用于单个稳定属性的全局取值约束。

### （2）`inter_attribute`

作用于多个稳定属性之间的全局对应 / 比较 / 依赖约束。

### （3）`link_quantified`

沿已建模 relation / connection 路径，对相关对象集合施加存在 / 不存在 / 全部满足 / 至少一个满足等资格限制的全局约束。

每个条件需包含：

* `condition_name`
* `condition_type`
* `targets`
* `description`

注意：

* relation / connection 成立所依赖的锚点匹配，不得进入 `conditions`；
* 仅用于定义局部子集的条件，不得进入 `conditions`；
* 仅用于实现绑定、桥接路径、局部下推或执行剪枝的条件，不得进入 `conditions`；
* `targets` 中只能出现稳定属性，不得放入临时列、聚合列、局部派生列或纯实现绑定字段。

---

# 五：提取规则

## 5.1 基础实体 / 基础关系的主识别入口

基础实体 / 基础关系的主识别入口是 conceptual SQL 中出现的基础逻辑表来源：

* `*_ent_source`
* `*_ent_impl`
* `*_rel_source`
* `*_rel_impl`

提取时应遵守：

1. 先解析这些逻辑来源各自承载的基础语义单元；
2. 一个逻辑来源只能承载一个基础实体或一个基础关系；
3. 逻辑来源名称只用于识别来源，不直接作为最终对象名称输出；
4. 最终对象名称必须回到用户问题语义与 conceptual SQL 中的概念表达；
5. 若某基础对象语义上必须保留，但没有被写成显式逻辑来源，允许在后续步骤中补建；
6. `*_impl` 只有在明确实现证据存在时才可被采纳为有效来源。

---

## 5.2 对实体的提取

当某对象满足以下条件时，应提取为 `entities` 中的实体类型：

* 能单独说明“它是什么”；
* 能单独定义粒度与成员范围；
* 是问题中应保留的原生对象，而不是局部分析结果；
* 其属性和标识在问题语义中稳定成立；
* 它能够作为 conceptual SQL 各步骤反复引用的基础语义承载。

实体提取时应优先依据：

* `*_ent_source` / `*_ent_impl`；
* 问题中稳定出现、但尚未显式写成逻辑来源的原生对象；
* 派生步骤中暴露出的、语义上必须补建的基础对象。

不得因为某个 CTE 单独投影了一组字段，就直接将其认定为新的基础实体。

---

## 5.3 对关系的提取

当对象间联系满足以下条件时，应提取为 `relations` 中的关系类型：

* 该联系本身具有明确、稳定的语义；
* 去掉具体实现路径后，该联系仍然成立；
* 联系中存在明确参与对象与参与角色；
* 联系本身可能承载非标识性语义属性；
* 该联系不是单纯的属性匹配、时间对齐、空间映射或上下文补充。

关系提取时应优先依据：

* `*_rel_source` / `*_rel_impl`；
* 问题中明确表达的原生关系语义；
* 派生步骤中暴露出的、应回落为基础关系的稳定联系。

不得把若干基础实体经局部步骤组合出来的宽表结果直接当作新的关系。

---

## 5.4 对连接的提取

只有在以下条件同时满足时，才允许提取为 `connections` 中的连接类型：

1. 两端都是已建模的基础实体；
2. 两者之间当前不存在更合适的基础关系；
3. 连接语义本质是属性匹配、时间 / 空间 / 类别 / 标识对齐或上下文补充；
4. 该连接可由基础实体的稳定属性与确定性变换回落表达；
5. 该连接不是分析性选择结果，不依赖聚合、排序、Top-K、窗口、最近一次 / 最大值 / 最小值等选择过程。

因此：

* 基础连接不是通过 `*_source / *_impl` 直接识别出来的；
* connection 是在基础实体 / 基础关系已初步建立之后，由对子问题与派生步骤的检查中补建的；
* 不得把纯实现桥接路径、映射路径或局部匹配动作本身直接写成 connection。

---

## 5.5 中间步骤的处理原则

conceptual SQL 中的中间步骤默认不直接新增新的基础实体 / 关系 / 连接。
对于每个中间步骤，应重点判断：

* 它依赖哪些基础实体 / 基础关系；
* 它只是做局部筛选、聚合、排序、Top-K、窗口、组合或结果整合；
* 它是否暴露了某个此前未显式建模、但在基础层必须保留的实体 / 关系 / 连接；
* 它是否只是带上下文的复合结果，而不是新的基础对象。

处理原则如下：

* 若某中间步骤仅表达分析性组织，则原则上不转写为新的实体 / 关系 / 连接；
* 若某中间步骤只是已有基础对象的局部子集或局部结果，不得额外构建新的基础对象；
* 若某中间步骤暴露了原本漏掉的基础对象或基础联系，则应补建到基础模型；
* 若某中间步骤提及未独立存在、但问题语义上必须保留的对象，则这些对象必须被补建到 `entities` 或 `relations` 中。

---

## 5.6 属性提取与优化规则

属性提取不是直接抄 conceptual SQL 中所有投影列，而应围绕基础实体 / 基础关系的稳定语义进行收敛。
属性应优先包括以下两类：

1. **核心语义属性**：用户明确提及、直接参与问题表达的属性；
2. **支撑属性**：虽不一定是最终输出字段，但对对象识别、关系建立、连接建立、角色区分、全局约束表达确有必要的稳定属性。

属性定义时必须检查：

### （1）正确性

属性必须贴合用户问题的表述口径，不得臆造未被语义支持的属性。

### （2）必要性

属性只在其对当前问题的对象定义、关系 / 连接表达或全局约束有直接作用时才保留。

### （3）原子性

每个属性只表达一个稳定单一语义，条件、角色、派生结果或复合含义不得直接固化为属性。

### （4）来源层级

不得将仅存在于 `*_impl / *_source` 内部、且未上升为概念层稳定属性需求的实现字段，直接提升为实体 / 关系属性。

---

### 实体标识性属性定义

实体的主键 / 识别属性，优先使用用户在问题中**直接提及**、且能稳定唯一标识该实体的属性或属性组。
若用户未直接提及可作为标识符的属性，则不得因为实现层常见有主键或某列看起来像 id，就直接将其固化为确定概念属性名。

当为保证建模完整性需要补充识别属性，而该识别属性不是用户显式提出的属性时，必须统一命名为带 `"_surrogate_id"` 后缀的属性，例如：

* `customer_surrogate_id`
* `patent_surrogate_id`

只要不是用户显式提出的标识性属性，都必须使用 `"_surrogate_id"` 后缀。

---

### 关系属性定义

关系的标识由：

* `participants`
* `participants.anchor_attribute`
* `link_condition`

共同定义。
`relations.attributes` 只用于承载关系本身的非标识性语义属性，例如：

* 关系发生时间；
* 关系状态；
* 关系数量；
* 关系金额；
* 关系类型中的附加描述属性。

不得将参与实体的锚点属性、外键式连接字段、仅用于建立关系成立的字段，重复写入 `relations.attributes`。

---

### 连接属性定义

`connection` 一般不额外定义普通属性。
其核心表达位于：

* `participants`
* `participants.anchor_attribute`
* `link_condition`

只有当问题语义中确有必要保留某个连接自身的稳定附加描述时，才可谨慎扩展；默认不添加。

---

## 5.7 条件抽取与优化规则

约束条件是对基础实体 / 关系 / 连接的**问题级检索范围**所施加的语义约束。
并非 conceptual SQL 中出现的所有过滤条件都属于 `conditions`。

注意：

* 凡是带限定条件的对象范围，本质上都可以视为某个基础实体集合 / 关系集合的子集；
* 判断某条件是否进入 `conditions`，关键不在于它是不是“子集条件”，而在于它定义的是**问题级基础分析对象集**，还是仅服务于求解过程的**过程级局部子集**。

其中：

### （1）问题级基础分析对象集

问题级基础分析对象集，是指在当前问题中真正需要被检索、统计、比较、排序、输出或作为最终分析范围保留的基础对象集合。

若某条件虽然写在上游 CTE 中，但最终参与定义了问题真正要分析的基础对象范围，则该条件应视为全局条件候选。

### （2）过程级局部子集

过程级局部子集，是指在 conceptual SQL 的求解过程中，为了完成连接、量化、排除、比较、聚合、排序、Top-K、窗口、分子 / 分母定义等步骤而临时构造的对象子集。

若某条件只服务于这类过程性中间子集，而不直接定义问题整体真正要分析的基础对象范围，则该条件属于局部条件，不得进入 `conditions`。

对任一条件，必须按以下顺序判断：

### （3）它是否用于建立 relation / connection 本身

若是，则应写入 `participants.anchor_attribute` 或 `link_condition`，不得进入 `conditions`。

### （4）它是否只作用于过程级局部子集

若是，则属于局部条件，不得进入 `conditions`。

### （5）它是否最终限定了问题级基础分析对象集

只有当某条件最终限定了当前问题真正要分析的基础对象范围，而不是仅服务于某个中间过程时，才可进入 `conditions`。

进入 `conditions` 时：

* 单个稳定属性取值限制，建模为 `single_attribute`；
* 多个稳定属性之间的对应 / 比较 / 依赖，建模为 `inter_attribute`；
* 沿 relation / connection 路径施加存在 / 不存在 / 全部满足 / 至少一个满足等资格限制，建模为 `link_quantified`。


---
## 5.8 全局 / 局部条件的判断规则

判断全局 / 局部条件时，必须基于**整个问题语义**与**整个 conceptual SQL 结构**，而不是单看某个 CTE 的局部写法。

### （1）先判断条件在限定什么对象范围

先明确该条件是在：

* 定义问题整体真正要分析的基础对象范围；
* 还是只在构造某个中间使用的局部子集、局部分支或局部分析口径。

只有前者才可能进入 `conditions`。

### （2）再判断该条件定义的是问题级基础分析对象集，还是过程级局部子集

若某条件定义出来的对象范围，是问题中真正要检索、统计、比较、输出或保留的基础对象集合，则它属于全局条件。

若某条件定义出来的对象范围，只是为后续连接、量化、排除、比较、聚合、排序、Top-K、窗口、分子 / 分母等步骤服务的中间子集，则它属于局部条件。

### （3）CTE 与 Local Condition 只提供结构提示，不直接决定作用域

* 写在上游 CTE 中的条件，不必然是局部条件；
* 写在中间 CTE 中的条件，也可能最终参与定义问题整体真正要分析的对象范围；
* 标注为 `Local Condition` 的条件，只能视为局部性的强提示，而不是最终结论；
* 必须结合整个问题语义与最终基础分析对象集，判断该条件是否应在 `conditions` 或 `link_quantified` 中体现。

### （4）禁止误判

* 不得把仅服务于过程级局部子集的条件误写成全局条件；
* 不得把最终定义问题级基础分析对象范围的条件，仅因其出现在局部 CTE 中就误判为局部条件；
* 不得把 relation / connection 的成立条件重复写入 `conditions`；
* 不得把实现下推条件误写成原始条件；
* 不得把本质属于 `link_quantified` 的量化约束拆散写成多个普通条件。

---

## 5.9 ER 建模完整性与原子性

提取结果必须同时满足：

### 完整性

* 整个基础模型中的实体应通过关系 / 连接保持连通；
* 若某个子问题语义上要求两个基础对象连通，而当前基础模型中缺失该联系，则必须补建合适的 relation 或 connection；
* 若关系 / 连接提及的参与实体尚未被建模，则这些实体必须补建。

### 原子性

* 不得把带上下文的实体、聚合前宽表、附着多个外部属性后的复合结果误建模为新的基础实体；
* 若参与实体之间已经存在更合适的稳定基础关系，则不得额外补建同义 connection；
* 若某 connection 只是已有 relation 或 connection 的结果性重复表达，则不得再作为新连接建模。

---

## 5.10 禁止事项

你必须遵守以下限制：

* 不得将 `*_source / *_impl` 的名字原样作为最终实体 / 关系名输出；
* 不得把实现表、映射表、桥接表、空间表直接改写为概念层对象名；
* 不得把中间步骤默认理解为新的复合宽表实体；
* 不得为了让结果更像可执行 SQL 而发明输入中未明确给出的物理字段名；
* 不得将仅存在于 `*_impl / *_source` 内部的实现字段，直接提升为实体 / 关系属性或 `conditions.targets`；
* 不得将 `SUM`、`COUNT`、`AVG`、`ORDER BY`、`LIMIT`、Top-K、窗口排序条件等分析性内容纳入 `conditions`；
* 不得把应作为 relation 的稳定业务联系误降级为 connection；
* 不得把纯实现桥接路径、映射路径或局部匹配步骤直接写成基础 connection。

---

# 六：分析步骤

在生成 JSON 形式的 ER Retrieval Spec 之前，必须先完成以下分析。
**禁止跳过分析直接生成 JSON。**

---

## Step 0. 区分用户需求、基础来源与实现提示

先整体理解输入，并区分：

* 哪些内容属于用户真正的分析需求；
* 哪些内容属于 conceptual SQL 中的问题求解结构；
* 哪些内容属于基础逻辑表来源；
* 哪些内容属于实现提示、桥接路径或局部实现动作。

要求：

* 明确输入中是否存在有效的 `*_ent_source / *_ent_impl / *_rel_source / *_rel_impl`；
* 明确哪些 `*_impl` 具有明确实现证据；
* 明确哪些内容虽然出现在 SQL 中，但只属于实现支撑，不应直接进入 ER 模型。

---

## Step 1. 基础逻辑来源解析：建立 base entities / base relations 初稿

优先遍历 conceptual SQL 中出现的基础逻辑表来源，建立基础实体 / 基础关系初稿。

### Step 1.1 识别基础逻辑来源

识别并列出：

* `*_ent_source`
* `*_ent_impl`
* `*_rel_source`
* `*_rel_impl`

对每个来源，判断：

* 它对应的基础语义单元是什么；
* 它应被解析为基础实体还是基础关系；
* 它是否拥有足够的实现证据支撑使用 `*_impl`；
* 它是否被错误地写成了中间结果、局部桥接或局部子集。

### Step 1.2 建立基础实体 / 基础关系候选

实体/关系的定义：

实体（Entity）：实体是问题中具有稳定语义身份、明确基础粒度、可独立指称和重复引用的对象；实体属性应描述该对象自身稳定拥有的信息。分组、统计、聚合或作为对象集合统称而出现的内容，不得直接建模为实体；这类表达默认视为分析口径、聚合结果或对象集合。当某个分组本身在问题语义中也是明确存在、具有标识性区分性属性的对象，才可建模为实体。

关系（Relation）：关系是两个或多个实体之间具有明确独立语义的关联、交互或事件，用于表达实体之间实际存在的联系。仅表示两个实体间基于属性对齐的连接，不建模为关系。仅用于分组、统计、筛选、排序或结果组织的分析操作，不得建模为关系。

对每个有效来源：

* 将 `*_ent_*` 解析为一个基础实体候选；
* 将 `*_rel_*` 解析为一个基础关系候选；
* 去掉 `_source / _impl` 后缀，回到概念语义名称；
* 给出该候选的初步粒度与语义说明。


### Step 1.3 初步检查缺失对象

检查用户问题中是否存在语义上必须保留、但未被显式写成基础逻辑来源的基础对象。
若存在，允许先作为“待补建基础对象”记录，后续在对子问题的检查中确认是否正式加入。

本步骤结束时，应得到：

* 基础实体初稿；
* 基础关系初稿；
* 待补建基础对象候选；
* 明确排除的伪来源对象。

---

## Step 2. 问题分解与子问题对齐

基于 conceptual SQL 的整体结构，将当前问题拆解为多个相互依赖的命名子问题。对子问题集，判断按当前conceptual SQL的查询分解是否完全覆盖了所有语义：包括覆盖问题提及的所有对象和所有限定条件。

要求：

* 将Conceptual SQL的CTE与最终查询表示为自然语言的子问题；
* 从原问题的自然语言出发，检查是否自然语言问题里的**每一个字段**都在子问题集里有表示出来；尤其注意检查限定条件字段，每一个字段都应该落实到属性上，不能假设隐含。
* 根据问题里来源陈述，判断子问题里是否完全包含了问题里所提到的主体与所有限定条件，没有遗漏。
* 若一个节点同时服务多个子问题，应说明其复用作用；
* 若某个子问题没有被任何 SQL 节点清楚表达，必须指出该语义缺口。

注意：

* 这一步的重点不是给节点做最终分类，而是建立“子问题—SQL 节点—基础对象与属性集”的对应关系；
* 必须明确检查所有限定性条件是否落实到子问题内部。

---

## Step 3. 逐节点语义覆盖检查

在完成子问题对齐后，再遍历 conceptual SQL 中的每个 CTE 与 Final SQL，检查它是否完整表达了对应子问题语义。

对于每个节点，必须按顺序分析：

### Step 3.1 判断节点性质

判断该节点更偏向于：

* 基础来源消费节点；
* 局部筛选节点；
* 局部匹配 / 对齐节点；
* 局部聚合 / 排序 / Top-K / 窗口节点；
* 阶段性结果整合节点；
* 暴露缺失基础对象的节点；
* 暴露缺失基础连接语义的节点。

### Step 3.2 检查对象覆盖

检查该节点所需的基础实体 / 基础关系是否已在 Step 1 初稿中存在：

* 若已存在，说明它依赖了哪些基础对象；
* 若缺失，则判断是否需要补建新的基础实体或基础关系；
* 不得因节点中出现中间结果而直接新增复合实体。

### Step 3.3 检查属性覆盖

检查该节点的语义表达对基础实体 / 基础关系提出了哪些属性需求，包括：

* 语义表示属性；
* 角色区分属性；
* 关系 / 连接锚点属性；
* 全局条件支撑属性；
* 局部子问题表达所需但仍应回落到基础层的稳定属性。

判断这些属性：

* 是否已在当前基础对象上被合理定义；
* 是否存在属性归属错误；
* 是否把实现字段误写成概念属性；
* 是否把派生分析结果误写成基础属性。

### Step 3.4 检查约束覆盖

检查该节点中是否显式表达了其子问题所需的关键约束：

* 角色约束；
* 方向约束；
* 时间先后约束；
* 局部子集范围；
* 比较基准；
* 参考对象；
* 去重口径；
* 分子 / 分母口径；
* 局部分析范围。

若约束缺失或表达模糊，必须指出这些约束应反馈到：

* 关系参与角色；
* `anchor_attribute`；
* `link_condition`；
* 基础属性定义；
* 或最终 `conditions`。

### Step 3.5 判断是否暴露连接语义

若该节点表面上连接的是中间结果，必须判断其底层是否暴露了两个基础实体之间应保留的连接语义。

只有当：

* 该语义可回落到两个已建模基础实体；
* 两者之间不存在更合适的稳定基础关系；
* 连接成立不依赖聚合、排序、Top-K、窗口等分析性选择；
* 连接可由稳定属性与确定性变换表达；

才允许将其记为待补建 `connection`。

---

## Step 4. 回写优化基础实体 / 基础关系 / 基础连接

基于 Step 3 的覆盖检查结果，对 Step 1 的基础对象初稿进行回写优化。

### Step 4.1 补全与优化基础实体

对每个基础实体，先检查是否存在定义缺失，再对已有定义进行修正与优化：

* 若某个子问题语义上需要该实体，但当前尚未显式建模，则必须补建该基础实体；
* 检查实体边界是否准确；
* 检查粒度是否清楚；
* 检查是否混入了角色化语义或中间结果语义；
* 检查是否缺少支撑后续子问题表达所需的必要稳定属性，若缺失则补全；
* 检查是否错误包含了实现字段、局部中间字段或分析结果字段，若有则删除或降级处理；
* 检查 `primary_key` 是否符合用户语义与标识性规则，必要时补充或修正。

### Step 4.2 补全与优化基础关系

对每个基础关系，先检查是否存在定义缺失，再对已有定义进行修正与优化：

* 若某个子问题语义上已经明确依赖某个基础关系，但当前尚未显式建模，则必须补建该基础关系；
* 检查关系语义是否独立稳定；
* 检查参与实体是否齐全，若缺失则补全相关实体或参与项；
* 检查参与角色是否准确；
* 检查 `anchor_attribute` 是否来自参与实体的稳定属性，若缺失或归属错误则补全或修正；
* 检查 `link_condition` 是否准确表达关系成立方式，若表达不足则补充或重写；
* 检查 `relations.attributes` 是否只保留关系自身的非标识性属性，若缺失必要属性则补充，若混入连接锚点字段或参与实体属性则删除或调整。


### Step 4.3 补全优化基础连接

仅当某个连接候选满足前述 connection 建模条件时，且连接的实体间不存在关系时，才允许正式补建到 `connections` 中。不得将connection与关系表示的连接语义重复。

补建时必须明确：

* 两端实体；
* 两端角色；
* 两端锚点属性；
* `link_condition`；
* 为什么它不能更合理地建模为基础关系；
* 为什么它不是纯实现桥接路径。

---

## Step 5. 条件约束定义

将整个问题视为全局，CTE 单元只是一种局部组织形式。判断某个条件是否属于全局条件时，必须基于它对**问题整体真正要分析的基础对象范围**所起的作用，而不是仅依据它写在哪个 CTE 中。

凡是带限定条件的对象范围，本质上都可以视为某个基础实体 / 关系集合的子集。真正需要区分的，不是“它是不是子集”，而是：

* 它定义的是问题级基础分析对象集；
* 还是仅服务于求解过程的过程级局部子集。

对每个条件，按以下顺序判断：

(0) **先回看最终检索对象是谁**  
先明确最终查询真正要检索、统计、比较或输出的是哪个基础实体 / 关系 / 连接的对象集合。若某条件虽然写在上游 CTE 中，但它在语义上参与定义了该最终对象集合的成员资格，则不得仅因其出现在局部 CTE 中而将其判为局部条件。

(1) **该条件是否在建立 `relation` / `connection` 本身**  
若是，则应写入 `participants.anchor_attribute` 或 `link_condition`，不得进入 `conditions`。

(2) **该条件是否只是在定义过程级局部子集**  
若某条件只服务于中间集合、比较集合、排除集合、分子 / 分母口径，或仅服务于后续聚合、排序、Top-K、窗口、量化判断等过程性步骤，而不直接定义问题整体真正要分析的基础对象范围，则该条件属于局部条件，不得进入 `conditions`。

局部性条件处理：对于任何派生语义单元，作用域为 CTE 局部的条件及在 CTE 中标注为 **Local Condition** 的，均应优先视为局部性的强提示，而不是最终结论。必须继续检查该条件是否在后续步骤中实际定义了最终结果集或最终检索对象的成员范围：

* 若该条件仅服务于中间构造、局部筛选或过程性分析，则这是局部条件，不参与建模，不添加至 `conditions`；
* 若该条件虽然写在局部 CTE 中，但最终决定了问题要检索、统计、比较或输出的基础对象范围，则不得仅依据其局部写法将其排除，仍应在 `conditions` 或相应的 `link_quantified` 中体现。

(3) **抽取作用域为问题整体的条件**  
`conditions` 仅允许建模最终作用于问题级基础分析对象集的条件，以表示对实体 / 关系 / 连接本身检索范围的限定。明确作用对象与属性，不要将关系的约束错误表达在实体上，或者将实体约束错误表达在关系上。任何仅作用于过程级局部子集的条件不得参与建模，避免污染检索。

* 条件约束必须用自然语言简单描述，禁止使用conceptual SQL的具体实现；


抽取进入 `conditions` 的条件时：

* 若是单个稳定属性的取值限制，且该限制最终作用于问题级基础分析对象集，建模为 `single_attribute`；
* 若是多个稳定属性之间的全局对应 / 比较，且该对应 / 比较最终作用于问题级基础分析对象集，建模为 `inter_attribute`；
* 若是沿已建模的 `relation` / `connection` 路径，对相关对象集合施加存在 / 不存在 / 全部满足 / 至少一个满足等资格限制，且该资格限制最终定义了问题整体的检索范围，必须整体建模为 `link_quantified`。


注意：

注意：

* 不得把仅服务于过程级局部子集定义的条件误写成基础实体 / 关系的全局约束；
* 不得把最终定义问题级基础分析对象范围的条件，仅因其先写在局部 CTE 中就排除出 `conditions`；
* 不得把 `relation` / `connection` 的成立条件重复转写进 `conditions`；
* 不得把一个本质上属于 `link_quantified` 的量化约束拆散写成一个内层普通属性条件，再加一个外层跨对象条件；
* 所有进入 `conditions` 的约束都必须用自然语言简洁描述，不得引用 conceptual SQL 的具体实现写法；
* 进入 `conditions.targets` 的属性必须是稳定属性；不得把仅用于中间构造的临时列、派生列或实现绑定字段写入 `targets`。


---

## Step 6. 单元查询问题构建

基于已构建的实体/关系单元模型，将原问题按**每个实体和关系**拆解为一组单元问题"unit_queries" ：
每个单元查询的"unit_name"即为其对应的实体和关系；
一个"nl_query"是针对单个实体或关系语义单元定义的一个自然语言查询，目的是用自然语言描述将单个实体/关系作为对象的检索。
将每个实体/关系分别作为检索对象，说明需要查询的实体/关系及其语义，以及所有需要的属性和语义；同时，如果某个实体/关系的属性具有单个属性(single attribute)的全局约束条件，以约束单个实体/关系参与检索时的范围，将该约束条件也整合进问题中；其它约束条件不参与建模。
语言要求：nl_query与用户原始输入的问题需要是相同的语言；用户输入是中文，nl_query是中文；用户输入是英文，nl_query是英文；

问题的参考模板：每个问题必须包含一个明确的实体/关系概念定义，该实体/关系的所有属性（包括实体的主键属性，关系的参与者锚点属性），以及单独作用于该实体的属性约束；
属性命名：对于`_surrogate_id`的代理标识符，需要用宽泛的属性定义`自然键或技术键`,而不是具体的标识符名；所有属性给出语义定义即可，不得也不需要明确其为主键/标识符属性/锚点属性。


* 注意unit query与子问题的区别：unit query 的目的是明确完成问题所需要的所有基础单元的查询集；子问题是居于这些基础单元逐步构建最终查询的查询序列；

# 八：输出要求

* 输出结果必须是最终收敛后的基础 ER Retrieval Spec，而不是分析过程摘要；
* 输出的ER Retrieval Spec实体、关系、属性定义必须是英文；涉及具体条件的取值，允许使用中文；
* 不得输出 `*_source / *_impl` 作为最终实体 / 关系名称；
* 不得将中间步骤直接写入 `entities / relations / connections`；
* 不得将局部条件、实现桥接条件、下推条件写入 `conditions`；
* `relations.attributes` 只保留关系自身的非标识性属性；
* `connections` 只能存在于两个已建模基础实体之间；
* `conditions.targets` 只能引用稳定属性；
* 若某属性或条件定义存在多种合理可能性，应选择最符合用户问题语义、且最有利于后续基础检索的表达方式；
* 在保证完整性的前提下，结果应尽量最小化，避免冗余建模。
