

# ER语义单元到自然语言问题构造任务

给定一个概念层 ER 模型中的**单个**实体、关系或连接语义单元，以及该单元相关的属性与条件约束，请将其改写为一条**独立的自然语言检索问题**，用于后续的数据查询。

输入的目标语义单元是以下三类中的一种：

1. **实体概念**：实体名称、语义描述、粒度、标识属性与属性集；
2. **关系概念**：关系名称、语义描述、参与实体及其标识属性、关系属性，以及可能相关的条件；

此外，输入中还可能提供与该语义单元直接相关的 `conditions`。

---

## 任务目标

本任务输入中已经给定了一个明确的目标语义单元。

你的任务是：

* 理解当前目标语义单元的定义；
* 识别该单元中必须覆盖的实体 / 关系 / 连接语义、属性与条件；
* 将其改写为一条**仅围绕该单元本身**的自然语言检索问题。

输出的问题必须能够独立表达当前语义单元的检索需求，而不能夹带其它未给定的语义单元、整题目标或分析任务。

---

## 核心原则

### 0. 输入只包含当前目标语义单元及其补充信息

本任务的主语义依据仅包括：

* `target_unit_type`
* `target_unit`
* `conditions`

* 可选的 `db_hint`
* 可选的 `external_knowledge`

不得自行补入其它实体、关系、连接、分析目标或任务上下文。

### 1. 任务针对单个语义单元：实体、关系或连接

输入只包含一个目标语义单元：一个实体、一个关系；关系附带其参与实体集合。

输出的问题只能围绕给定单元展开，不得扩展任何其他内容，不得自行定义未提供的其它实体类型、关系类型、属性或分析目标。

### 2. 输出必须是“检索型问题”，而不是“判断型问题”

输出的问题应当用于请求“找出什么”，而不是判断“是否成立”。

因此：

* 优先使用“找出哪些……”“给出……”“返回……”“对于……找出……”这类检索型表达；
* 不要生成 yes/no 判断句；
* 不要使用“是否”“是不是”“能否判断”“是否存在”等表述，除非目标语义单元本身明确是一个布尔判断语义。

### 3. 问题必须覆盖当前单元中明确定义的核心属性

若目标是 `entity`，问题中必须体现：

* 该实体的标识符属性集；
* 该实体的其它明确定义的属性集。

若目标是 `relationship`，问题中必须体现：

* 所有参与该关系的实体标识符属性集；
* 关系本身明确定义的属性集。


### 4. 条件只在与当前单元直接相关时融入问题

若输入中提供的 `conditions` 与当前语义单元直接相关，应将其自然融入问题表达，例如：

* 时间范围；
* 来源限定；
* 属性取值限定；
* 上下文限定；
* 对某一参与实体的筛选范围。

条件应优先写成实体 / 关系 / 连接限定或属性限定，例如：

* “对于状态为 active 的 customer”
* “与下单日期位于 2023 年 6 月的 order”
* “在仅考虑评分大于 4 的 review 的情况下”

不要把条件机械罗列在句尾，也不要把条件改写成新的判断子句。

若某个条件与当前目标单元没有直接约束关系，则不得纳入问题。

### 5. 标识属性的作用是“识别实例”，不要误写成“相同值描述”

`identifier_attrs` 的作用是说明如何识别一个实体实例或关系参与者实例。

因此：

* 应优先表述为“给出用于识别实例的……”
* 或“由……标识的……实例”

不要改写成：

* “……均相同的对象”
* “……一致的记录”

因为这类表述会把“标识属性”误写成“重复值条件”，改变原语义。

### 6. 问题应保持单元边界清晰

输出的问题必须只覆盖当前语义单元，不得：

* 扩展到整题级统计；
* 引入聚合指标；
* 引入排序、比较、排名；
* 引入未给出的其它语义单元；
* 引入完整分析任务背景；
* 因为实现提示或外部知识而额外补充新的检索目标。

### 7. 允许利用实现提示或外部知识优化表达，但不得改变单元边界

若输入中提供 `db_hint` 或 `external_knowledge`，可用于：

* 帮助理解当前单元的语义；
* 帮助更准确表达属性、参与者或条件；
* 帮助生成更合理的概念检索 SQL 草稿。

但不得因此：

* 增加未定义的实体 / 关系 / 连接；
* 引入新的分析背景；
* 扩展当前单元的查询边界。

### 8. 输出应以当前语义单元的自然语义为主，不得退化为表列名堆砌

自然语言问题应使用实体、关系、连接及其属性语义来表达，不得直接把数据库表名、列名机械拼接成问题。

只有在“数据实现说明”中，才允许列出与当前单元直接相关的模式 / 表 / 列名称；该说明是补充信息，不得替代自然语言问题主体。

---

## 输入字段

### 输入：目标语义单元类型

`target_unit_type`

取值为：

* `entity`
* `relationship`


### 输入：目标语义单元定义

`target_unit`

当 `target_unit_type = entity` 时，输入包含：

* `name`
* `desc`（可选）
* `grain`
* `identifier_attrs`
* `attrs`

当 `target_unit_type = relationship` 时，输入包含：

* `name`
* `desc`（可选）
* `grain`
* `participants`
* `attrs`
* `link_condition`（可选）

补充说明：

* `identifier_attrs` 是字符串列表。
* `attrs` 是属性对象列表；每一项至少包含 `name`，可选包含 `semantics`。
* 当前 NL2ER stage2 原始输入在进入本阶段前，`attributes` 允许为以下任一形式，系统会先将其归一化为上述 `attrs`：

  * `["attr_a", "attr_b"]`
  * `[{"name": "attr_a", "semantics": "..."}, {"name": "attr_b", "semantics": "..."}]`
  * `{"attr_a": "...", "attr_b": "..."}`

### 输入：相关条件

`conditions`

这是与当前语义单元可能相关的条件集合，仅当该条件明显作为当前实体、关系、连接的实例约束或属性取值约束时，才融入问题。

### 输入：数据库实现提示（可选）

`db_hint`

若提供，则表示与当前语义单元直接相关的数据库模式、表、列等实现线索。

### 输入：外部知识（可选）

`external_knowledge`

若提供，则表示帮助理解当前语义单元语义的补充知识。

## 问题构造规则

### A. 当目标是 `entity`

问题中通常应包含：

1. 该实体的语义定义；
2. 该实体的粒度定义；
3. 该实体的标识符属性；
4. 该实体的关键属性；
5. 与该实体直接相关的条件，应优先定义为属性限定。

参考模板：

找出实体[实体定义]，并给出它的相关属性：[identifier_attrs] [attrs]，[可选条件]

属性说明：

* 若 `attrs` 为空，则只保留实体对象与标识属性，不要强行补充其它属性。

代理标识符说明：

* 如果一个标识符属性名称带有 `_surrogate_id` 后缀，说明该标识符属性是占位标识符，仅代表一个标识符概念，而不是一个具体属性定义；
* 针对这种情况，问题化时应表述为“该实体的主键”，而不是具体的属性名。

---

### B. 当目标是 `relationship`

问题中通常应包含：

1. 哪些实体参与了该关系；
2. 每个参与实体的标识符属性；
3. 该关系的语义；
4. 该关系的粒度定义；
5. 关系属性（若有）；
6. 与该关系直接相关的条件（若有）。

参考模板：

找出实体[实体A]、实体[实体B]、实体[实体C]之间的[关系定义]，并给出用于识别各参与实体实例的相关属性，以及该关系的相关属性：[participants identifier_attrs] [relationship attrs]，[可选条件]

---

## 条件合并规则

若条件作用于某个实体 / 关系 / 连接，应优先写成该对象的限定语或相关属性的限定值，例如：

* “属于西部区域的 store”
* “下单日期位于 2023 年 6 月的 order”
* “顾客为活跃用户的 purchase”

若条件作用于整体上下文，可写成：

* “在仅考虑……的情况下”
* “在……范围内”

但前提仍然是：该条件必须与当前目标单元直接相关。

## 输出要求

在生成 JSON 形式的查询问题之前，必须先基于以下步骤完成分析。**禁止直接生成 JSON**。

### Step 0. 重述当前目标语义单元,判定输出自然语言问题的语言类型

判断当前目标是 `entity`、`relationship` 还是 `connection`，并概括其核心语义。
确定输入的实体-关系模型定义的语言：是中文还是英文；输出的自然语言问题必须是相同语言。

### Step 1. 提取当前目标语义单元中必须覆盖的核心信息

若是 `entity`，至少覆盖：

* 实体对象；
* 实例标识方式；
* 关键属性；
* 相关条件。

若是 `relationship`，至少覆盖：

* 关系参与实体；
* 参与者标识；
* 关系语义；
* 关系属性（若有）；
* 相关条件。

同时判断给定 `conditions` 中哪些应当纳入当前单元，哪些不应纳入。

### Step 2. 对齐到当前单元定义与可选实现提示，同时保持独立性

将查询语义严格限定在当前目标单元内部：

* 仅允许依据 `target_unit` 的定义补足当前单元的表达；
* 若提供了 `db_hint` 或 `external_knowledge`，仅可用于帮助理解和表达当前单元；
* 不得提及其它实体 / 关系 / 连接；
* 不得引入整题背景、聚合任务、排序任务或分析目标。

若提供了与当前单元直接相关的数据库实现提示，可在后续问题中作为“数据实现说明”补充列出相关模式 / 表 / 列名称；但不得让表列名替代自然语言语义表达。

### Step 3. 为当前单元构造概念检索 SQL 草稿

为当前目标语义单元设计一个**仅服务于该单元**的概念检索 SQL 草稿，用来帮助组织自然语言问题。

要求：

* SQL 草稿只包含当前单元明确定义的实体 / 关系 / 连接、属性与必要条件；
* 不得为了补全查询而引入未给定的其它语义单元；
* 允许自行设计概念 schema / table 名称；
* 该 SQL 是中间语义表达，不是最终答案。

### Step 4. 构造最终的自然语言问题并自检

以输入实体-关系模型定义的相同语言类型,将 Step 3 中的概念检索逻辑映射为表达通顺的自然语言问题。

要求：

* 问题必须以实体、关系、连接及属性语义来表达，而不是 SQL 表列名；
* 若需要补充数据实现说明，只能作为附加说明放在句末，不得喧宾夺主；
* 对于 `_surrogate_id` 的代理标识符，直接表述为“该实体的主键”，而不是具体标识符名；
* 问题应自然、完整、边界清晰，不重复说明，不提及无关信息。

参考模板：

* 实体类型：找出实体[实体定义]，并给出它的相关[属性]，[可选条件] [可选数据实现说明]
* 关系类型：找出实体[实体A]、实体[实体B]、实体[实体C]之间的[关系定义]，并给出相关[属性]，[可选条件] [可选数据实现说明]
* 连接类型：找出实体[实体A]、实体[实体B]之间的[连接定义]，并给出用于识别这些实体实例的相关[属性]，[可选条件] [可选数据实现说明]

对自然语言问题进行检查：

1. 是否只覆盖当前语义单元；
2. 是否是检索型问题而不是判断型问题；
3. 是否覆盖了该单元的核心语义；
4. 是否只纳入了与当前单元直接相关的条件；
5. 是否没有扩展到其它单元或整题任务；
6. 是否自然、完整、边界清晰。

---

## 输出格式

经过上述分析步骤之后，将构造并自检完毕的自然语言问题作为 JSON 返回；不允许直接返回 JSON 文件。

输出语言限定：输出问题语义必须与输入的实体-关系模型定义的语言一致。

输出格式：

```json
{
  "target_unit_name": "...",
  "query_concept_sql": "...",
  "question": "..."
}
```
