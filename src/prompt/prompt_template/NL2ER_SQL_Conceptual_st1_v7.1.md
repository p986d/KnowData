
## 任务定义
根据全部输入中可识别的用户需求语义与数据库模式相关证据，构造一个**面向问题表达的概念查询结构（Conceptual Query Plan）**。

这里的概念查询结构不是要求生成一条可直接执行的数据库 SQL，也不是要求还原完整数据库 schema。
它是一条作为中间语义表示的 **conceptual SQL / SQL-like 查询伪代码**，用于表达：

* 用户真正想分析的对象、关系、连接与分析目标；
* 问题可以如何被拆解为若干相互依赖的子问题；
* 哪些中间结果需要被显式保留，以支撑后续步骤；
* 数据库模式相关证据如何作为实现支撑，帮助需求语义对齐到可能的数据来源。

本阶段输出的是**问题表达层 / 推理表达层**的概念查询结构，重点是把问题如何成立、如何逐步求解表达清楚。
本阶段**不是**最终的 ER 检索规格构建阶段，也不要求在这里收敛出最小基础实体-关系-连接模型。

---

## 基本原则

### 1. 先表达问题，再考虑实现

概念查询结构首先服务于**表达用户问题的求解过程**，而不是直接转写物理实现。
数据库模式相关证据只作为实现支撑背景，不得主导问题的语义拆解。

### 2. 并非所有语义成分都要成为 CTE

问题中的对象、条件、连接依据、分组聚合、排序等都需要识别；
但只有当某个子问题或中间结果**值得被后续继续引用**时，才需要显式组织为 CTE。

下列内容通常**不必单独写成 CTE**，除非它们在当前问题中确实形成独立中间结果：

* 单纯的属性约束；
* 单纯的一次性局部匹配；
* 单纯的时间对齐、同值匹配、键关联；
* 单纯的桥接路径、映射路径、空间映射路径；
* 只为一次局部连接服务的临时步骤；
* 仅作为实现支撑存在的局部来源。

这些内容可以直接写在相关 CTE 或主查询中。

### 3. CTE 只用来承载必要的子问题

CTE 的作用是表达**问题求解过程中值得保留的阶段性结果**。
你不需要提前把每个 CTE 严格归类为“基础 / 派生 / 起始 / 后续”；只需要确保：

* 该 CTE 对应一个相对清晰的子问题；
* 一行代表什么是可说明的；
* 它确实为后续步骤提供了可复用输入。

### 4. 数据源表的 `_source` / `_impl` 规则

当 conceptual SQL 需要引用来源对象时，必须遵守以下规则：

* 若输入中**明确提供了**某来源对象的数据库模式相关证据，例如具体 schema、table、column 或其它可直接指向实现对象的线索，才可使用 `*_impl`；
* 若问题语义上明确需要某类来源对象，但输入中**没有明确提供**其实现证据，则必须使用 `*_source` 作为抽象来源占位；
* 不得在没有明确实现证据时，擅自假设物理表存在并写成 `*_impl`。

注意：

* `*_impl` 与 `*_source` 都只是 CTE 内部引用的来源对象命名方式；
* 它们不是独立 CTE 类型；
* 实现来源默认不直接上升为新的概念查询单元，除非用户问题本身就在分析该来源对象。

# 分析步骤

在输出最终 JSON 之前，必须先完成以下分析。
**禁止跳过分析直接生成 conceptual SQL。**

## Step 0. 区分用户需求与实现提示

先重述问题，并区分：

* 哪些内容属于用户真正的分析需求；
* 哪些内容属于数据库模式或实现提示；
* 输入中是否提供了明确的数据实现线索，若有，具体是什么。

注意：实现提示只能作为落地支撑，不能直接替代问题语义。

---

## Step 1. 问题分解与逻辑查询

先对用户问题进行口径整理，明确：

* 用户最终想得到什么结果；
* 结果粒度是什么，即结果中一行代表什么；
* 用户明确要求输出什么内容；

随后，围绕问题定义**基于自然语言的推理步骤列表**。这段推理应符合用户的问题语义，从最终结果出发，逐步说明：

* 结果主要围绕哪些对象、关系或连接展开；
* 为了让问题成立，需要依次引入哪些对象、关系和上下文；
* 涉及哪些计算、分析、数据操作的步骤，计算、分析、数据操作的直接对象和条件是什么；
* 哪些角色、方向、先后关系、比较基准、参考对象需要被考虑；

---

## Step 2. 选择需要显式保留的子问题，并决定是否写成 CTE

基于 Step 1 的问题分解，判断哪些子问题或中间结果值得在 conceptual SQL 中被显式保留。

对于每个候选子问题，至少分析以下内容：

1. 它解决的是问题中的哪一部分；
2. 它是否形成了一个值得后续继续引用的阶段性结果；
3. 一行代表什么是否可以清楚说明；
4. 它应该写成独立 CTE，还是直接放在其它 CTE / 主查询中表达更合适；
5. 若涉及实现提示，这些实现细节应如何包裹在该子问题内部，而不影响其概念层命名。

判断原则：

* 能单独说明“这一步在求什么”，并且后续还会继续引用的，适合写成 CTE；
* 只是一次性的局部过滤、局部匹配、局部桥接或实现路径时，通常不必单独写成 CTE；
* 若某个连接、对齐或关系本身在问题中具有明确作用，且后续还会被继续使用，可以写成单独 CTE；
* 不要为了结构完整而机械地把所有对象都写成 CTE；
* CTE 数量以**足够清楚表达问题求解过程**为准，不求多。

---

## Step 3. 梳理条件作用范围并写入查询计划

重新检查用户问题中的条件，区分它们在查询计划中的作用范围：

* 哪些条件作用于整体问题范围；
* 哪些条件只作用于局部子问题、局部子集、局部连接或局部分析口径。

要求：

* 所有对问题成立有实质作用的条件，都应在 conceptual SQL 中得到明确表达；
* 不允许依赖“默认理解”省略关键条件；
* 局部条件可以写在对应 CTE 内部；
* 全局条件可以写在主查询或相关上游 CTE 中；
* 只有在问题明确要求时，才显式写出跨单元属性对应或条件传播，避免过度扩张。

必要时可使用简洁注释辅助表达，例如：

* `-- Global Condition`
* `-- Local Condition`
* `-- implementation support`

---

## Step 4. 组织 conceptual SQL

基于前面的分析，组织整条 conceptual SQL。

要求：

* 按求解依赖顺序安排 CTE；
* 每个 CTE 都应表达一个相对清晰的子问题；
* 后续 CTE 可以引用前序 CTE，也可以引用必要的来源对象；
* 不得形成循环依赖；
* 最终主查询应直接对应用户想要的结果口径；
* 不得退化为物理实现结构的机械转写；
* 对于实现支撑相关内容，应尽量隐藏在相关 CTE 内部，而不是让实现路径主导整个查询结构。

---

## Step 5. 输出

完成上述分析后，输出 JSON：

```json
{
  "conceptual_sql": "..."
}
```

# conceptual_sql 生成要求

* 目标不是生成可直接执行的业务 SQL，但应尽量保持**语法完整、结构稳定、便于后续解析**；
* 可以使用伪代码函数或抽象列名占位，但 SQL 结构必须完整；
* 不允许出现 `...`、`WHERE ...`、`ON ...` 这类不完整表达；
* 每个 CTE 都必须写成完整的 `name AS (SELECT ... FROM ...)` 形式；
* CTE 名称优先表达语义对象或子问题本身，不需要在名称中编码“基础 / 派生 / 起始 / 后续”等阶段信息；
* 可按需要使用简洁注释，帮助说明局部条件、全局条件或实现支撑；
* 默认按 Snowflake 风格书写；
* `*_impl` / `*_source` 的使用必须严格遵守以下规则：

  * 输入中存在明确实现证据时，才允许使用 `*_impl`；
  * 语义上需要但实现未明确给出时，必须使用 `*_source`；
  * 不得凭空假设物理实现并写成 `*_impl`。
