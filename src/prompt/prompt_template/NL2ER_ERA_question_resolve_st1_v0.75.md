# 任务定义

根据全部输入中可识别的用户需求语义与数据库模式相关证据，完成该问题的**语义边界校准**与**查询子查询序列设计**。

本阶段的目标不是直接生成对问题的最终查询，也不是抽取实体、关系和属性。

本阶段只负责：

* 将问题分解为语义单元与查询子查询；
* 明确每个子查询在整体求解中的作用、语义操作、语义限定与多义性；
* 为后续从子查询中抽取基础逻辑实体、基础逻辑关系与逻辑属性提供稳定输入。

本阶段不得：

* 正式定义实体、关系和属性；
* 输出字段、连接方式、join key 或 SQL 计算表达式；
* 将数据库模式实现直接转化为逻辑模型。

---

# 基本原则

## 1. 先组织问题求解结构

首先提取问题中的语义单元，并根据查询计算的逻辑顺序构建一系列查询子查询。

数据库模式相关证据作为实现支撑，用于将语义内容落地到可能的数据来源；它可以作为问题的补充说明，但不得主导问题本身的求解结构，也不得替代用户问题的语义分解。

---

## 2. 实现证据只作支撑，不主导语义拆解

数据库模式相关证据、表名、列名、外部知识只能作为落地支撑。

它们可以帮助你：

* 判断对象与属性是否可能存在；
* 确认某些对象的实现证据是否明确；
* 补充题面未明说但由输入提示直接给出的查询语义。

它们不得：

* 替代用户问题本身的语义依赖；
* 主导子查询定义；
* 把实现字段直接当成子查询对象；
* 把某个实现表直接等同于逻辑对象。

# 分析步骤

**Think step by step**: 按照下列步骤进行分析

---

## Step 0. 问题背景与输出语言设置

判断查询问题的专业领域，并明确用户输入问题所使用的语言。后续所有子查询、约束与说明必须与用户语言一致。

---

## Step 1. 校准问题语义边界，分解问题

本步骤的目标是：按照问题本身的自然求解逻辑，将原问题拆解为一组用自然语言定义的子查询。对于查询中逻辑不确定的部分，必须明确标识其模糊性，不得直接猜测和选择一种逻辑。

### 1.0.1 确定语义边界

在设计问题求解结构之前，首先分析问题的整体查询计算逻辑和确定的语义边界。

`query_semantic_contract` 是后续子查询的语义定义和约束边界，不是自由分析过程，也不是实现方案说明。

`query_semantic_contract` 必须遵循以下优先级：

* 用户原文中的解释性短语、明确定义和限定条件优先级最高；如果外部知识或领域常规定义与用户原文冲突，应采用用户原文，并将冲突的外部解释排除。
* 用户明确给出的目标对象、范围、类别、编码、时间、方向、分组、排序、返回数量和指标要求，不得被外部知识扩展、替换或弱化。
* 外部知识只能补充题面未明说但确实属于查询语义的内容；不得覆盖用户题面，也不得把实现方式伪装成查询语义。
* 数据库模式、字段、表、标识定位、编码承载、地址层级展开、文件扩展映射、空间函数、连接方式、计算函数、物理存储方式等，只能作为实现支撑，不得进入 `resolve_process` 或 `ambiguity`。

问题语义内容是指用户问题中已经确定的查询对象、分析范围、业务概念、限定条件、结果要求以及被接受的外部语义补充。它回答“题目在问什么、对象和条件是什么”。

计算逻辑是指为了得到答案，必须对上述语义内容执行的筛选、匹配、聚合、去重、分组、比较、排序、Top-k、比例计算、派生计算和输出组织方式。它回答“答案如何由这些语义内容推导出来”。

二者的区分原则是：如果某信息描述对象、范围、条件或概念含义，则归入语义内容；如果某信息描述如何组合、计算、比较或返回结果，则归入计算逻辑。若一个题面表达同时包含二者，应拆分记录，不得混写。

不得在 `query_semantic_contract` 中单独设置计算分析域。计算结构如果已经确定，应直接体现为 `resolve_process` 中的普通子查询节点；计算结构如果存在多义性，应在 `resolve_process` 中落到对应的计算定义节点，并在该节点中用 `ambiguity` 说明不确定点；只有当不同候选解释确实导致后续查询过程分叉时，才使用 `logic_branches` 表达分支化求解结构。

#### 计算逻辑结构解析

在生成子查询之前，必须先解析问题的计算结构。计算结构解析的目标不是生成 SQL 或实现步骤，而是明确题面中的对象、范围、条件和度量如何共同构成答案。

对于包含计算、比较、排序、比例、聚合、Top-k、分组、去重、差值、变化率、存在性判断等操作的问题，必须分析以下内容：

1. calculation_type：问题涉及的主要计算类型，例如计数、聚合、比例、比较、排序、Top-k、分组聚合、集合运算、存在性判断等；
2. calculation_object：计算作用的对象单位，即最终被计数、聚合、比较、排序或筛选的对象粒度；
3. base_scope：进入计算前已经确定的基础分析范围；
4. calculation_components：该计算结构中的必要组成部分，例如候选集合、参考集合、目标集合、聚合对象、聚合粒度、度量、比较基准、排序依据、输出选择规则等；
5. condition_role_assignment：题面中每个条件在计算结构中的作用位置，例如限定基础范围、定义候选集合、定义目标集合、定义度量、定义聚合粒度、定义比较基准、定义排序依据、定义输出过滤等；
6. unresolved_calculation_points：如果某个条件可以合理地进入不同计算组成部分，并且会改变结果含义，则必须记录为计算逻辑歧义；
7. calculation_logical_structure_candidates：当计算结构不唯一时，应记录候选计算结构。只有当候选结构会导致不同的后续子查询序列时，才在后续 `resolve_process` 的对应节点中生成 `logic_branches`；否则只在该节点的 `ambiguity` 中说明不确定点，不要为了列出候选而强行分支。

#### 计算逻辑歧义进入 resolve_process

计算逻辑歧义是指自然语言问题中的计算结构存在多个合理解释，并且不同解释会改变分子/分母、候选集合/目标集合、聚合对象、分组粒度、排序基准、比较基准、时间窗口、去重对象或输出对象。

遇到计算逻辑歧义时，必须执行以下处理：

* 在 `resolve_process` 中设置一个用于定义该计算结构的子查询节点；
* 该节点的 `ambiguity` 中写入 `type: "计算逻辑"`，说明哪些条件、对象或计算组成部分的位置不确定；
* `logic_branches` 是可选的分支化建模工具，不是所有计算逻辑歧义都必须生成；
* 只有当不同解释会导致后续子查询序列明显不同，且每个分支都需要独立描述候选集合、目标集合、分母/分子、分组粒度、排序基准或输出对象时，才使用 `logic_branches`；
* 如果歧义只影响单个判断口径、边界处理、tie-break、时间锚点或局部过滤条件，应只写入当前节点的 `ambiguity`，不要生成 `logic_branches`；
* 使用 `logic_branches` 时，每个 branch 下面用 `sub_questions` 给出该候选计算结构需要执行的子问题序列；
* 后续最终计算节点如果依赖这些候选结构，应通过自然语言说明“基于选定的计算分支”进行计算，不得假装已经选定其中一种。

`resolve_process` 默认应保持线性、贴近题面自然求解顺序。只有当分支化能更清楚表达不同候选求解路径时，它才可以是一个线性主干加局部分支的结构：主干节点表示所有候选逻辑共享的求解步骤；含有 `logic_branches` 的节点表示从该处开始存在不同候选求解路径。若多个候选路径共享同一前序范围，应将该范围放在分支节点之前，避免在每个分支中重复。

查询逻辑歧义与计算逻辑歧义的处理不同：

* 查询逻辑歧义：保留在相关子查询节点的 `ambiguity` 中，说明不同语义解释会如何改变查询路径或对象范围；不强制生成 `logic_branches`，除非它确实需要不同子问题序列。
* 计算逻辑歧义：必须在相关计算定义节点写入 `ambiguity`；仅当不同解释对应不同的计算组件与子问题结构，并导致后续查询过程分叉时，才生成 `logic_branches`。
* 局部语义口径歧义：仍只放在相关子查询节点的 `ambiguity` 中，不生成计算分支。


`query_semantic_contract.semantic_definition` 只记录用户题面已经明确给出的语义内容，不输出独立计算分析。若某个约束存在多种会影响答案的合理读法，不要在这里强行落定；应保留在后续对应子查询节点的 `ambiguity` 中。若它改变计算结构，只有在不同读法导致后续查询过程分叉时，才在对应计算定义节点的 `logic_branches` 中展开。


`query_semantic_contract.excluded_assumptions` 用于记录不得采用的内容，包括：

* 题面未授权的外部扩展、领域机制、事件类型、业务流程或替代统计口径；
* 与用户显式定义冲突的外部知识或领域常规定义；
* 只属于数据实现或物理承载的信息；
* 会把题面给定范围扩展成更大集合的默认假设；

题面给定的标识、编码、地址、地理对象、token 地址等是目标范围或限定条件，不得被展开为独立的数据定位子问题；如何把这些限定条件映射到数据，不构成语义子查询。

题面未要求的领域机制、事件类型、派生规则或业务流程，即使在外部知识中出现，也不得作为默认查询逻辑。

### 1.1 按自然求解逻辑设计子查询序列

基于问题的自然分析逻辑，将原问题拆解为若干独立的子查询。

**严格遵守语义边界**：子查询定义应与问题语义边界的结论对齐，不考虑已声明的与问题不相关的内容。

子查询设计应遵循以下原则：

* 子查询是一个逻辑查询任务：必须明确查询的对象、查询计算和返回结果。
* 子查询对齐问题语义表示与题面语义解释，必须用逻辑形式和语义操作的口径表述。禁止直接使用数据提示和操作步骤作为子查询内容。
* 子查询序列必须逻辑清晰，明确覆盖问题所有语义要素，包括操作和约束条件。

对每个子查询，明确如下内容。只有当实现提示直接补充了题面语义时，才将其抽象为语义限定整合进子查询；不得把实现提示本身当作子查询内容：

1. 在问题整体求解中的作用；
2. 语义操作；
3. 语义限定；
4. 是否存在相关的外部知识与数据承载的概念；
4. 查询表示的多义性。

#### 语义操作：说明该子查询需要完成什么语义任务，需要哪些语义支持。例如：

* 确定对象或对象子集；
* 确定对象之间的联系、参与或匹配；
* 对既有对象或联系施加条件约束；
* 在对象或联系基础上进行聚合、比较、排序、Top-k、派生计算；
* 形成后续步骤所依赖的阶段性结果。

#### 语义限定：说明该子查询中的对象、联系和计算具体受到哪些语义约束；需要全面表述问题语义包含的约束，不得遗漏。

语义约束可以包括：角色限制、时间限制、方向限制、局部范围、参考对象、比较基准、分子/分母口径、去重口径、聚合前提和局部分析范围等。

#### 相关提示与数据实现：

判断给出的外部知识是否指出了某种查询计算的逻辑，或物理数据中是否给出实体-关系属性建模的提示。
注意不是所有物理数据都和提示都与问题有关，必须分析和定位确实相关的内容。
注意，相关物理数据仅是数据库中的一部分，仅用于说明数据库中存在哪些逻辑查询可以使用的概念。物理实现方式本身不构成查询语义多义性。

如果数据提示明确补充了题面语义，则应把它概括为自然的查询限定并写入对应 `question`。`question` 不要复述数据提示原文，也不要写成数据落地方式。

如果数据提示只是说明某个语义单元在数据中如何被识别、承载、展开、换算或取回，则只能作为实现支撑，不得进入 `question`，也不得进入 `ambiguity`。


#### 歧义分析：
在问题语义分析阶段，需要区分查询逻辑歧义、计算逻辑歧义、局部语义口径歧义与数据实现歧义。

查询逻辑歧义的处理：**明确逻辑分歧**
查询逻辑歧义是指某个表达存在多种合理解释，并且不同解释会改变问题的整体求解逻辑路径；这类歧义必须显式外显为多个候选查询逻辑。

计算逻辑歧义的处理：**在子查询中说明不确定点，必要时构建分支**
计算逻辑歧义是指计算组件的角色分配不唯一，例如某个条件可能定义基础范围、分母集合、分子集合、聚合对象、分组粒度、排序基准或比较基准。只要不同解释会改变最终指标含义，就必须在 `resolve_process` 的对应计算定义节点中说明不确定点；只有当这些解释会导致不同的后续查询过程时，才用 `logic_branches` 构建候选分支。

计算逻辑歧义不得只写成顶部分析说明。若没有使用 `logic_branches`，也不得在 `question` 中直接选择某一种不确定路径，而应在 `ambiguity` 中说明不确定点。使用 `logic_branches` 时，每个计算分支必须说明：

* branch_id：候选分支编号；
* interpretation：该分支对计算结构的自然语言解释；
* denominator / numerator / candidate_set / target_set / grouping / ranking_basis 等适用的计算组件；只填写当前问题需要的组件；
* sub_questions：该分支下需要执行的子问题序列，每个子问题必须仍然是自然语言查询任务，不得写成 SQL 或字段操作。

局部语义口径的处理：**抽象属性涵盖语义歧义**
局部语义口径歧义是指某个概念存在多种业务定义方式，但这种差异主要影响该局部语义单元的判断口径，不一定改变整体查询结构；这类歧义应定义为能够包含这口径的一个抽象属性，并显式记录其各种可能口径，不得随意确定一种作为默认实现。

数据实现歧义的处理：**不建模，不指出**
数据实现歧义是指问题语义与局部语义口径已经确定，但同一语义单元在数据中可能存在多种承载、识别、组织或计算落地方式；这类不影响逻辑建模，不需要且不应该指出。

判断某对象、关系或条件的证据来源不同，例如来自声明标签、检测结果、文件扩展名、预计算字段、数组元素、关联表或文本匹配，默认属于数据实现差异。除非用户题面明确要求比较这些证据来源本身，否则不得写入 `ambiguity`。


总体原则是：会改变问题求解路径和对象范围的查询歧义外显为候选查询逻辑；会改变计算组件与答案指标含义的计算歧义必须在对应节点说明不确定点，只有当后续查询过程确实分叉时才生成计算分支；只影响局部概念定义的歧义记录为候选口径。数据实现相关的不确定性不参与建模。

#### `question` 与 `ambiguity` 的分工：

`question` 字段不是把题面短语机械改写为具体实现步骤，而是描述该子查询在整体求解中的**抽象语义任务定义**。它必须用一个能够覆盖局部口径差异的抽象语义单元来表达求解逻辑。

`interpretation_and_ambiguity` 字段必须紧贴用户问题原文，只解释题面已经出现的对象、条件、指标、范围、方向、分组和输出要求。它用于说明当前子查询如何承接题面含义，以及哪些题面表达本身存在查询逻辑、计算逻辑或局部语义口径的不确定性。

`interpretation_and_ambiguity` 不得构造题面没有明确提及的对象层级、归属关系、业务状态、领域机制、统计主体或替代数据来源。若某个解释需要引入题面未出现的概念才能成立，应视为外部假设，不得写入 `ambiguity`，也不得作为 `logic_branches` 的候选分支。

如果题面已经通过 “from / by / based on / using / according to / within / among / for each / grouped by” 等表达指定了来源、依据、范围或分组，`interpretation_and_ambiguity` 应保留这些锚定含义，不得将其替换成更宽泛的领域常规定义或实现层可能口径。

`question` 必须使用自然查询语言，不要输出提示词中的分析术语。除非用户题面原文使用，否则 `question` 中不得出现“语义”“口径”“抽象业务概念”“基于XX语义”等元语言表达。

`question` 也不得直接使用数据提示中的实现术语来描述求解步骤。若数据提示补充了题面含义，应改写为自然的查询限定；若用户题面包含技术性标识，应将其作为“用户指定的目标/范围”保留其限定作用，不要把整个子查询写成获取标识或操作数据记录。

推荐表达：

* “确定用户指定的目标范围。”
* “确定目标范围内符合题面条件的对象集合。”
* “筛选出处于指定地址范围内的对象集合。”
* “统计筛选后对象的数量。”

不推荐表达：

* “确定某标识对应的对象。”
* “确定某数据表中的记录集合。”
* “将某记录与某范围关联。”
* “通过某数据组织方式展开目标范围。”

局部语义口径歧义应被包含在 `question` 的抽象语义中：`question` 保持抽象，不预先落定具体口径；`ambiguity` 只补充说明该抽象语义单元下可能存在的候选业务口径。不得因为存在局部口径歧义，就把 `question` 改写成某一种具体口径或拆成多个实现步骤。

当 `ambiguity` 讨论的是条件判断依据、时间锚点、比较基准、比例分母、关系方向、分组粒度或对象范围时，`question` 不得新造一个会暗示某种候选解释的属性名来封装该不确定性。`question` 应描述满足题面条件的对象、关系或计算任务，`ambiguity` 再说明该条件可能基于哪些候选依据判断。

`question` 中的抽象表达必须保持中性，不得暗示 `ambiguity` 候选项中的某一种实现、属性或业务口径已经被选定。

`ambiguity` 不用于记录同一语义单元如何落地到数据或执行过程中的不确定性。只有当不同解释会改变查询逻辑路径、答案口径，或是问题中某个局部语义概念的业务判断口径时，才可写入 `ambiguity`。

判断标准：

* 如果差异只是“同一抽象语义单元如何被识别、承载、实现或执行”，不写入 `ambiguity`；
* 如果差异是局部业务概念的判断标准不同，则 `question` 使用覆盖性抽象概念，`ambiguity` 记录候选口径；
* 如果差异会改变整体求解路径、参与对象范围或关系方向，则写为查询逻辑歧义；
* 如果差异会改变分子/分母、候选集合/目标集合、聚合对象、分组粒度、计量口径、排序基准、比较基准、去重对象或最终指标含义，则写为计算逻辑歧义；只有当不同解释导致后续查询过程分叉时，才在当前节点生成 `logic_branches`；
* 不得引入题面未要求、数据提示未直接补充的外部假设作为歧义。
* 如果输入提示已经为某个表达给出了适用规则，应将该规则视为当前问题的已知语义约束；不得再列出被该规则排除的替代口径。
* 不得在 `ambiguity` 中写入“该差异不影响整体查询逻辑”“仅影响具体定位/落地/执行”等说明。凡是需要这类说明的候选项，都说明它不应进入 `ambiguity`。
* 题面给出的字面目标、范围、标识或限定条件，应作为当前问题的确定约束处理；如何把这些约束解析到数据或中间表示，不构成 `ambiguity`。
* 如果无法判断某个候选项是语义口径歧义还是实现落地不确定性，默认省略，不要写入 `ambiguity`。

#### 输出前自检：

在最终输出前，必须逐条检查候选 `ambiguity`：

* 如果该候选项只是在说明如何定位、识别、承载或执行一个已经确定的语义单元，删除；
* 如果该候选项即使选择不同处理方式，也不会改变答案的语义口径或整体求解路径，删除；
* 如果该候选项来自题面未提出、数据提示也未直接补充的外部假设，删除；
* 如果该候选项只是对一个已命名、已限定、已给定标识或已由输入规则限定的目标进行解析，删除；
* 如果该候选项的描述中必须依赖数据落地方式才能成立，删除；
* 如果该候选项是在讨论一个确定语义如何映射为可执行条件，而不是讨论用户问题本身可能有哪种语义读法，删除；
* 如果该候选项混合了语义口径和实现落地内容，只保留语义口径部分；无法干净分离时，删除整项；
* 只有保留下来的候选项才写入 `ambiguity`。

#### 子查询问题构建：

推荐的子查询粒度应按抽象求解逻辑组织：

* 确定题面给出的目标范围或分析范围；
* 确定最终输出所要求的分组对象或结果对象集合；
* 在目标范围内确定符合题面条件的人、物、事件或记录集合；
* 使用前序结果执行聚合、比例、排序、Top-k、比较或派生计算；
* 返回题面要求的结果对象与度量值。

当某个计算节点存在计算逻辑歧义时，子查询结构应按“共享前序范围 + 分支计算结构”组织：

* 共享前序范围作为普通 `resolve_process` 节点；
* 计算定义作为一个含 `logic_branches` 的节点；
* 每个 `logic_branches` 项内部维护自己的 `sub_questions`，用于表达该候选解释下的分母、分子、候选集合、目标集合、聚合或输出步骤；
* 分支内的 `sub_questions` 只表达该分支特有的计算步骤，不重复共享前序范围；
* 如果题面计算结构唯一，不要生成 `logic_branches`。

推荐的 `question` 写法：

* “确定目标范围内需要参与统计的分组对象集合。”
* “确定目标范围内符合题面条件的人群/对象/事件集合。”
* “按指定分组粒度聚合计算目标度量。”
* “按目标度量排序并返回题面要求数量的结果。”

推荐的 `ambiguity` 写法：

* 某个题面条件的判断阈值可能存在不同业务口径；
* 某个抽象状态或资格的判断标准可能存在不同业务定义；
* 计数、去重、比例分子分母、时间边界、Top-k 并列处理等会影响答案口径的规则不明确。

推荐的 `logic_branches` 写法：

* “分支 A：先按对象 P 分组聚合再排序；分支 B：先按对象 Q 分组聚合再排序。”

不推荐的子查询或 `ambiguity` 写法：

* 将子查询写成“确定某对象的唯一标识”这类实现准备步骤；
* 将子查询写成数据落地或物理执行步骤；
* 将同一语义单元的数据承载、识别、转换、展开或执行方式写入 `ambiguity`；
* 题面未提出两种业务口径冲突时，主动引入外部常识中的替代统计口径。

子查询要求如下：

* 不得提前写成实体、关系、属性、字段、连接方式、join key 或计算表达式；
* 不得遗漏问题中关键但隐含的约束和限制条件。

# 输出格式

在完成上述分析后输出查询逻辑子问题序列。最终回答必须只输出一个 `json` Markdown 代码块，不要在代码块外输出任何解释文本；
ambiguity仅允许列举查询语义逻辑的模糊性；不得列举任何具体数据实现相关的内容；若查询逻辑唯一确定则不需要填写。

```json
{
  "language": "",
  "resolve_process": [
    {
      "id": "SQ1",
      "interpretation_and_ambiguity":"根据用户题面与上一步查询逻辑的状态，分析下一步骤的查询计算，并识别题面表达本身存在的计算逻辑歧义与查询语义逻辑多义性。",
      "question": "用自然查询语言描述该子查询的求解任务；在问题中用抽象描述覆盖计算逻辑、查询语义与局部口径的逻辑多义性。",
      "ambiguity_types": [
        {
          "type": "查询逻辑|计算逻辑|局部语义口径",
          "description":""
        }
      ],
      "logic_branches": [
        {
          "branch_id": "B1",
          "interpretation": "当且仅当该子查询节点存在计算逻辑歧义时，且该查询逻辑导致后续步骤存在分支时填写；说明该候选分支对计算结构的解释。",
          "calculation_components": [],
          "sub_questions": [
            {
              "id": "B1_SQ1",
              "question": "该计算分支下的自然语言子查询任务。",
              "ambiguity": []
            }
          ]
        }
      ]
    }
  ]
}
```

注意：`logic_branches` 仅在该节点存在计算逻辑歧义,且该计算逻辑歧义会导致不同的查询过程时输出；
没有计算逻辑歧义的节点，或计算逻辑歧义仅局限于单个子问题时不用输出。
