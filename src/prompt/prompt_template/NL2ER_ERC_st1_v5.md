# 用户需求建模任务

# 一: 任务定义

你的任务是：根据全部输入中可识别的用户需求语义与数据库模式相关证据，构造一个**面向问题表达的概念查询结构**，并据此抽取能够回答用户问题的**实体-关系骨架表示**。

这里的概念查询结构不是要求生成一条可直接执行的数据库 SQL，也不是要求还原完整数据库 schema。
它是一条作为中间语义表示的虚拟SQL，用来表达：

* 用户真正想分析的语义单位；
* 这些语义单位之间的连接方式与依赖关系；
* 哪些中间语义单元需要被显式保留，以支撑问题表达；
* 数据库模式相关证据如何用于将需求语义对齐到可能的实现结构。

本任务应优先将用户问题组织为一个**保持用户表述口径的概念查询结构（Virtual SQL）**，再从该结构中识别实体、关系、属性与条件。输出目标不是完整数据库 schema，也不是最终 SQL，而是一个**能够回答用户问题的实体-关系骨架草稿**。

该骨架需要回答以下问题：

1. 用户问题中有哪些对象类型需要被显式保留为 `entity_type`；
2. 这些对象类型之间有哪些具有稳定语义边界、应被显式保留的 `relationship_type`；
3. 每个实体类型上有哪些与当前问题相关的属性需要在 `attrs` 中描述；
4. 用户需求中的哪些部分能够被当前数据库模式相关证据支撑；
5. 哪些中间语义仅用于表达派生语义或实现适配，而不应直接进入最终骨架。

## 输入范围

本任务的输入中可能包含：

* 用户原始需求描述；
* 用户在需求描述中直接提及的数据库实现信息；
* 单独提供的数据库模式相关提示，例如 schema、table、column；
* 主键、外键、映射表、时间列、空间列、类别列等能够支撑需求落地的实现证据；
* 也可能完全没有数据库模式相关信息。

因此，不得预设数据库模式相关信息一定存在，也不得预设其一定与用户需求严格分离。应统一从全部输入中识别：

* 哪些内容属于用户希望表达和分析的语义；
* 哪些内容属于数据库模式相关证据；
* 哪些内容应进入概念查询结构作为核心语义单位；
* 哪些内容仅作为中间支撑语义存在。

## 输出目标

最终输出的是一个 **概念查询虚拟SQL** 和 **实体-关系骨架草稿**，而不是数据库模式或可执行 SQL。
输出的核心目的是表征与覆盖用户问题中真正需要表达的语义，并在有数据库模式相关证据时尽量与其可支撑的实现结构对齐。

输出应包括：

* `entity_types`
* `relationship_types`

并为每个实体类型提供与当前问题相关的 `attrs` 描述。

## 基本要求

1. 概念查询结构中的核心语义单位应优先保持用户问题的表达口径，而不是直接复制数据库物理表名、列名或中间连接结构。
2. 若输入中提供了数据库模式相关证据，应使用这些证据对需求语义进行约束和规范化，使输出尽量对齐到可支撑的实现结构。
3. 若某些数据库实现信息仅体现属性匹配、时间对齐、编码映射、桥接路径或其他连接依据，而未形成需要独立保留的稳定语义关系，则不应直接将其建模为 `relationship_type`。
4. 若某些中间语义单元仅用于支撑派生表达或实现适配，而不构成最终问题表达中需要显式保留的对象或关系，则不应直接进入最终实体-关系骨架。
5. 若未提供可靠的数据库模式相关证据，则应仅基于用户需求本身构造概念查询结构与实体-关系骨架，不得臆造数据库实现结构。

## 任务边界

* 不要求生成最终可执行 SQL，或完整的数据库 schema；
* 不要求穷举所有可能关系、属性或实现路径；
* 不要求将所有中间语义单元都保留为最终实体或关系；
* 不得将实例名、筛选值、时间范围、聚合指标、排序要求直接建模为实体类型；
* 不得将纯实现性的连接依据直接视为 `relationship_type`，除非其已经形成需要独立保留的稳定语义关系。

# 二：概念查询结构-虚拟 SQL

本任务应先从全部输入中识别问题的**语义单元**，再将这些语义单元组织为一个**概念查询结构**，最后基于该结构抽取实体类型、关系类型与相关属性。

这里的语义单元，不是最终输出中的实体、关系、属性、常量或操作本身，而是问题中的**组成要素**。

虚拟 SQL 使用的表列不是具体的数据，可以是用户需求或数据库模式相关证据中显式提及的一个字段或概念；其在后续概念查询结构中，可能被落实为实体、关系、属性、常量或数据操作。

概念查询结构不是物理数据库 SQL，也不是数据库 schema 的直接转写，而是一个面向问题表达的中间查询表示，用于组织：

* 用户真正想分析、筛选、返回、分组和聚合的语义要素；
* 这些语义要素之间的依赖与连接；
* 哪些语义要素构成基础对象，哪些语义要素来自派生，哪些语义要素仅用于实现支撑。

## 2.1 语义单元的定义

语义单元是当前问题中一个可识别、对问题成立有语义作用的组成要素。
它可以是：

* 对象概念；
* 字段概念；
* 条件相关概念；
* 连接依据；
* 分组、聚合、比较、排序等分析操作相关概念。

---

## 2.2 语义单元的分类

在本任务中，语义单元按其在概念查询结构中的形成方式与作用，可分为以下三类：

### 1. 基础语义单元

基础语义单元：一个不通过对其它语义单元进行筛选、组合、映射、匹配、聚合或其它查询变换后才成立，而是可以先被独立建立为一个基础查询单元的语义单元；
基础语义单元是可单独定义粒度、可承载自身属性的基础实体/关系对象及相关属性、属性约束条件；可被派生语义单元引用。

基础语义单元通常具有以下特点：

* 不依赖多个其它语义单元组合后才能成立；（基础关系依赖于基础实体）
* 可以先围绕单一对象建立一个基础查询单元；
* 具有自身属性及属性取值的常值约束，以及与其他语义单元的多单元间的属性约束；
* 可以作为其它语义单元继续派生的来源。

基础语义单元通常可以转化为 `entity_type` 或 `relationship_type` ，但不要求所有基础语义单元都必须进入最终骨架。

### 2. 派生语义单元

派生语义单元是由已有基础语义单元或其它派生语义单元，经由筛选、组合、映射、匹配、聚合、重命名或分析粒度变化后形成的语义单元，是一个实体/关系对象及相关属性、属性约束条件。

派生语义单元通常具有以下特点：

* 依赖已有语义单元才能成立；
* 表达的是某个“经过限定、组合、映射或汇总后”的中间语义；
* 可作为概念查询结构中的中间查询单元存在；

派生语义单元可以来源于：

* 某个实体/关系的条件化子集；
* 某个分析粒度下形成的聚合单位；
* 某个汇总、统计或分组后的中间结果。

派生语义单元作为问题查询的中间表示， 为保证E-R的原子性，不计入 `entity_type`/ `relationship_type`。

### 3. 实现支撑单元

实现支撑单元是由数据库模式相关证据引入、用于支撑需求语义落地的语义单元。是具体数据库模式表征的实体/关系对象及相关属性。

它们通常来自：

* schema / table / column 提示；
* 主键、外键、桥接表、映射表；
* 时间列、空间列、编码列；
* 其它能够揭示实现承载位置、连接路径或属性来源的数据库线索。

实现支撑单元的作用是：

* 为概念查询结构提供可能的实现落点；
* 支撑对用户需求语义的规范化重写；
* 提供对象承载、属性来源、连接依据或路径展开的实现背景。

实现支撑单元默认不直接进入主查询语义主体，也不自动成为最终 `entity_type`/ `relationship_type`。

---

## 2.3 映射规则

用户需求映射规则:用户需求的所有所有字段严格意义上需要都对应到语义单元的属性，或约束属性的常值、以及属性与属性之间的约束条件。

* 用户提及的实体类型/关系类型的语义单元：对应到某个语义单元的技术标识符/自然标识符属性集；
* 用户提及的字段：对应到每个语义单元的属性；
* 用户提及的实例/常量：对应到某个属性的常值约束；
* 用户提及的语义单元的关联：对应到某个关系型语义单元和/或多个语义单元的属性间约束条件；如果用户将关联作为独立语义对象表达，则建模为关系型语义单元；否则建模为语义单元间的属性约束条件。

## 2.5 虚拟 SQL 的结构说明

概念查询结构应采用**虚拟 SQL**的方式组织。这里的虚拟 SQL 不是可执行 SQL，而是用接近 SQL 的形式表达：

* 哪些语义单元被组织为基础查询单元；
* 哪些语义单元被组织为派生查询单元；
* 当存在数据库模式相关证据时，这些查询单元如何引用实现来源。

### 1. 两类命名对象

虚拟 SQL 中需要区分两类命名对象：

* **CTE**：概念查询结构中的命名查询单元，用于承载语义单元本身；
* **来源对象**：CTE 内部 `FROM` / `JOIN` 所引用的表，用于表示概念来源或实现来源。
在没有具体实现提示时，表默认表征一个实体或一个关系。

### 2. CTE 的命名规则

CTE 只使用以下两类后缀：

* `*_base`：表示**基础语义单元**对应的基础查询单元；
* `*_derived`：表示**派生语义单元**对应的派生查询单元。

其中：

* `*_base` 用于表达可先独立建立的基础语义单元；
* `*_derived` 用于表达由已有基础或派生单元经过筛选、组合、映射、匹配、聚合等形成的中间语义。

### 3. 来源对象的命名规则

当虚拟 SQL 需要引用数据库模式相关证据中的实现来源时，来源对象可使用 `*_impl` 后缀。

`*_impl` 表示该对象是由数据库模式相关证据支撑的实现来源，用于为 `*_base` 或 `*_derived` 提供承载位置、属性来源或连接依据。
`*_impl` 不是独立的 CTE 类型，而是 CTE 内部引用的来源对象命名后缀。

### 4. CTE/虚拟表命名规则

当没有具体实现提示时，`*_base` 可直接作为概念性的基础查询单元存在，同时也可以认为一个基础语义单元由一张虚拟表完整表征，例如：

```sql 
with trip_base AS (
  SELECT *
  FROM trip_base
)
```

`*_derived` 可直接作为概念性的派生查询单元存在，由基础查询单元经过筛选、组合、映射、匹配、聚合等数据操作得到，例如：
```sql
trip_from_newyork_derived AS (
  SELECT *
  FROM trip_base
  WHERE origin = 'New York'
)
```

当存在具体实现提示时：（例如 trip 数据由trip_2014与trip_2015年两表Union 得到），这里提及具体数据库模式，应使用_impl后缀；`*_base` 或 `*_derived` 可在内部引用 `*_impl` 来源对象，例如：

```sql
with trip_base AS (
  SELECT *
  FROM trip_2014_impl
  UNION
  SELECT *
  FROM trip_2015_impl
)
```

因此：

* `*_base` / `*_derived` 表示概念查询单元；
* `*_impl` 表示概念查询单元内部引用的实现来源对象。

### 5. 使用原则

构造虚拟 SQL 时，应遵守以下规则：

* 能先独立立住的语义对象，优先写成 `*_base`；
* 需要通过查询变换形成的中间语义，写成 `*_derived`；
* 只有在存在数据库模式相关证据时，才在 CTE 内部引用 `*_impl` 来源对象；
* 最终主查询应保持用户问题的语义口径，不得退化为物理实现结构的直接转写。

# 三：分析步骤

在生成最终 JSON 之前，必须先基于全部输入完成受约束分析。分析目标不是直接枚举实体、关系和属性，而是先识别语义单元，构造虚拟 SQL，再从虚拟 SQL 中抽取最终的实体-关系骨架。

请按以下顺序进行分析，并显式给出每一步的判断结果。

---

## Step 0. 重述问题，区分需求语义与实现证据

先重述用户问题，并区分输入中的两类内容：

1. **需求语义**：用户真正想分析、筛选、返回、分组、聚合或比较的内容；
2. **实现证据**：输入中出现的数据库模式相关证据，包括 schema、table、column、主外键、桥接表、映射表、时间列、空间列、编码列等。

注意：

* 不得预设实现证据一定存在；
* 不得因为输入中出现表名、字段名，就直接将其作为最终概念对象；
* 若同一段输入同时混有需求语义与实现证据，应分别识别。

---

## Step 1. 识别语义单元

基于全部输入，识别当前问题中的语义单元。语义单元是问题中的组成要素，可以是对象概念、字段概念、条件相关概念、连接依据或分析操作相关概念。

在本步骤中，应先识别有哪些语义单元被提及，再判断其属于以下哪类：

1. **基础语义单元**：可先独立建立为基础查询单元的语义单元；基础语义的单元必须仅来自用户需求描述，不能将数据库相关实现纳入；
2. **派生语义单元**：依赖已有语义单元经过筛选、组合、匹配、聚合等形成的中间语义单元；
3. **实现支撑单元**：由数据库模式相关证据引入、用于支撑需求落地的实现来源或实现背景。所有数据库相关实现必需且仅能归类到此类；

同时，识别以下附属信息：

* 每个语义单元中映射用户需求字段的属性；
* 用户需求提及的属性上的实例值、类别值、时间值、范围值等常值约束，及多个语义单元之间可能存在的属性间约束条件；
* 用户提及的分组、聚合、排序、比较等数据操作。

注意：

* 本步骤只识别和分类语义单元，不直接输出最终 `entity_type` / `relationship_type`；
* 不得因为某个语义单元与其它单元存在连接依据，就直接将其判定为关系型基础语义单元。

---

## Step 2. 判断哪些基础单元应作为实体，哪些关联应作为关系或属性间约束

对于 Step 1 中识别出的基础语义单元，进一步判断其属于以下哪种情况：

1. **实体型基础语义单元**：表示一个可单独承载属性和约束的对象；
2. **关系型基础语义单元**：表示一个需独立保留的稳定业务关联；
3. **仅作为属性间约束条件的关联**：只用于支撑筛选、匹配、派生或实现对齐，不构成独立关系型单元。

判断时遵守以下原则：

* 若某个关联是用户被用户显式提及，且具有独立的业务语义边界，则优先将其视为**关系型基础语义单元**；
* 若某个关联仅体现为基于某类数据的条件匹配/属性对齐，则不建立为**关系型基础语义单元**，仅作为**属性间约束条件**来表示。

---

## Step 3. 构造虚拟 SQL

基于已识别的语义单元，构造虚拟 SQL。虚拟 SQL 不是最终可执行 SQL，而是问题表达的中间查询结构。

构造时应遵守以下要求：

1. 用 `*_base` CTE 表达基础语义单元；
2. 用 `*_derived` CTE 表达派生语义单元；
3. 若存在实现证据，可在 `*_base` 或 `*_derived` 内部引用 `*_impl` 来源对象；如果不存在实际实现数据，则在内部直接用 `*_base`
4. 最终主查询应保持对用户问题的语义口径覆盖。

在本步骤中，需要显式说明：

* 哪些基础语义单元被组织为 `*_base`；
* 哪些派生语义单元被组织为 `*_derived`；
* 哪些实现证据在 CTE 内部以 `*_impl` 来源对象形式被引用；
* 各 CTE 的粒度、主要属性、局部条件及依赖关系；
* 主查询最终围绕哪些语义单位展开。

注意：

* `*_impl` 不是独立 CTE 类型，只是 CTE 内部引用的实现来源对象；
* 派生单元只作为虚拟 SQL 中的中间表示，不应直接等同于最终骨架中的实体或关系。

---

## Step 4. 从虚拟 SQL 中抽取最终实体类型

基于虚拟 SQL，确定哪些 `*_base` 单元应进入最终 `entity_type` 集合。

对每个候选实体，说明：

* 为什么它应作为实体类型保留；
* 它对应的是实体型基础语义单元，还是某个被优先实体化的关联；
* 它的语义边界与粒度是什么；
* 它依赖哪些属性与局部约束成立；
* 若存在实现证据，其在虚拟 SQL 中是如何被实现支撑的。

注意：

* 原则上只从 `*_base` 中抽取最终实体类型；
* `*_derived` 不直接进入最终 `entity_type`；
* `*_impl` 来源对象不得直接作为最终实体类型输出；
* 实体命名必须使用语义化名称，不得直接复制物理表名或列名。

---

## Step 5. 从虚拟 SQL 中抽取最终关系类型

在已确定的实体类型集合基础上，进一步确定哪些未被实体化、但具有独立业务语义边界的连接，应进入最终 `relationship_type` 集合。

对每个候选关系，说明：

* 它连接哪些实体类型；
* 它是否对应关系型基础语义单元；
* 它表达的业务语义是什么；
* 为什么它不是单纯的属性间约束条件；
* 若存在实现证据，其在虚拟 SQL 中如何得到支撑。

注意：

* 关系的参与者必须来自已确定的实体类型集合；
* 纯时间对齐、空间映射、编码映射、键关联、桥接路径等连接依据，不应直接输出为 `relationship_type`；
* 若某个关联已按对象性优先实体化，则不应再重复输出为关系类型；
* 关系命名必须使用语义化谓词表达，而不是数据操作表达或连接字段表达。

---

## Step 6. 为最终实体类型补充 `attrs`

对已确定的每个实体类型，整理其与当前问题相关的属性，并写入 `attrs`。

属性整理时应满足：

* 属性必须在用户需求或实现证据中有明确语义支撑；
* 属性应是该实体自身承载的标识、状态、时间、位置、类别、数值或描述维度；
* 用户提及的字段、条件、实例值、时间范围、类别范围等，都必须落实到相关实体的属性或属性约束上；
* 若某项语义本质上依赖多个实体之间的连接才能成立，则不要错误吸收到单一实体的 `attrs` 中。

注意：

* 条件值本身不是属性，但条件所依赖的属性必须出现在 `attrs` 中；
* 不为最终关系类型单独定义 `attrs`；
* 不得补充输入中没有支撑的无关属性。

## 四：输出

在完成上述全部分析步骤与合法性审查后，输出一个 JSON 对象，格式如下：

```json 
{
  "virtual_sql": "...",
  "entity_types": [
    {
      "name": "...",
      "desc": "...",
      "grain": "...",
      "role": "fact | dimension",
      "attrs": []
    }
  ],
  "relationship_types": [
    {
      "name": "...",
      "desc": "...",
      "participants": ["entity_a", "entity_b"],
      "attrs": []
    }
  ]
}
```

### 字段要求

#### `virtual_sql`

表示基于语义单元构造出的**一条完整虚拟 SQL**，即概念查询结构的整体表达。

要求：

* `virtual_sql` 必须是完整 SQL 字符串，可包含 `WITH`、多个 `*_base` / `*_derived` CTE，以及最终主查询；
* `*_base` 用于表达基础语义单元；
* `*_derived` 用于表达派生语义单元；
* 若存在数据库模式相关证据，可在 SQL 中引用 `*_impl` 作为来源对象；
* `*_impl` 不是独立 CTE 类型，而是 SQL 中 `FROM` / `JOIN` 所引用的实现来源对象后缀；
* 最终主查询应优先保持用户问题的语义口径，不得退化为数据库物理实现结构的直接转写。

#### `entity_types`

表示最终需要显式保留的实体类型集合。每个实体类型包含：

* `name`：实体类型的语义化名称，不得直接复制物理表名或列名；
* `desc`：该实体类型的简要语义说明，应说明其对应的对象语义及必要时的边界说明；
* `grain`：该实体类型在当前问题中的粒度说明；
* `role`：只能取以下两类之一：

  * `fact`：承载事件、行为、记录、交易、观测、过程等事实对象；
  * `dimension`：承载描述、分类、限定、标识、参照等稳定对象；
* `attrs`：该实体类型在当前问题中相关的属性列表，应使用自然语言属性名称或短语，不展开为正式属性模式定义。

#### `relationship_types`

表示最终需要显式保留的关系类型集合。每个关系类型包含：

* `name`：关系类型的语义化名称，应直接表达参与实体之间的业务语义；
* `desc`：该关系类型的简要语义说明；
* `participants`：参与该关系的实体类型名称列表，必须来自 `entity_types` 中已定义的实体；
* `attrs`：当前任务中固定输出为空列表 `[]`，不单独保留关系属性。若某个关系需要承载独立属性，应优先在前面的分析中判断其是否应实体化。
