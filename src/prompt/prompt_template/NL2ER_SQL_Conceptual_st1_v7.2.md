# 任务定义

你的任务是根据全部输入中可识别的用户需求语义，以及可用的数据库模式相关证据，构造一个**面向问题表达的概念查询结构（Conceptual Query Plan）**。

这里的概念查询结构不是要求生成一条可直接执行的数据库 SQL，也不是要求还原完整数据库 schema。
它是一条作为中间语义表示的**Conceptual SQL / SQL-like 查询伪代码**，用于表达：

* 用户真正想分析的对象、关系与分析主轴；
* 问题中关键子任务之间的依赖关系；
* 哪些中间语义结果值得被显式保留；
* 后续语义步骤如何依赖前序步骤逐步形成；
* 数据库模式相关证据如何作为实现支撑，对需求语义提供可能的落点。

本阶段输出的是**问题表达层 / 推理表达层**的概念查询结构，不是最终的 ER 检索规格。
本阶段不负责收敛出最小基础实体-关系-连接模型；该工作由后续解析阶段完成。

# 核心原则

## 1. 并非所有语义成分都应成为 CTE

问题中的对象、字段、条件、连接依据、实例值、分组聚合要求等，都属于需要识别的语义成分。
但只有满足以下条件的语义成分，才值得被显式组织为命名查询单元（CTE）：

1. 具有相对独立且稳定的语义边界，能够单独说明“它是什么”；
2. 能够单独定义粒度与成员范围，能够说明“一行代表什么”；
3. 在当前问题中值得作为阶段性语义结果被后续继续引用；
4. 它在当前问题中需要被显式保留，而不只是一次性局部匹配、临时桥接或实现支撑。

其余语义成分默认应回落为：

* 查询单元的属性；
* 属性上的常值约束或范围约束；
* 查询单元之间的局部连接条件或属性匹配条件；
* 实现支撑路径；
* 分组、聚合、排序、比较等分析操作。

## 2. 默认只定义核心查询单元

本任务应优先识别并定义**核心查询单元**，而不是系统性展开所有后续中间结果。
局部时间窗口、局部筛选子集、聚合结果、最终保留子集，默认不单独命名为查询单元；只有当某中间结果具有稳定独立语义，且确实值得被后续继续引用时，才例外提升为命名查询单元。

## 3. 连接不自动退化，也不自动升格

用户需求中被直接表达、且对问题成立有直接作用的对象间连接，不应因为它是连接就自动退化为局部 `JOIN ... ON ...` 条件。
但连接也不应自动拆成独立 CTE。只有当该连接本身形成值得单独保留的语义结果时，才应显式组织为查询单元。

必要时可用以下标签辅助描述连接性质：

* `relation-like`：更接近稳定关系类型；
* `connection-like`：更接近属性附着、上下文补充或分析对齐；
* `implementation-support`：仅为落地提供支撑路径，不属于概念层对象。

这些标签只是表达辅助标签，不等同于最终 ER 收敛结论。

## 4. 实现提示只作为支撑，不参与核心命名

数据库模式相关证据中的表、列、键、映射表、桥接路径、空间映射、编码映射等，只能作为需求语义的**实现支撑来源**，不得直接上升为新的概念层查询单元，也不得主导命名查询单元的语义边界。

当 Conceptual SQL 需要引用来源对象时：

* 若输入中明确提供了数据库模式相关证据，使用 `*_impl`；
* 若语义上需要该来源，但输入未提供明确实现证据，使用 `*_source`。

注意：`*_impl` 与 `*_source` 都只是 CTE 内部引用的来源对象命名，不是独立 CTE 类型。

## 5. 用户需求优先，外部知识用于辅助解释

用户需求是概念查询计划的主导来源。
外部知识仅用于帮助理解术语、方向、业务背景或隐含规则，不得替代用户需求本身。

若用户原文与外部知识存在冲突，必须：

1. 显式指出冲突；
2. 说明当前 Conceptual SQL 采用哪一侧作为解释依据；
3. 保证后续查询结构与该解释保持一致。

# 分析步骤

在生成 JSON 形式的 Conceptual SQL 之前，必须先完成以下分析。
**禁止直接生成 JSON。**

## Step 0. 区分用户需求、外部知识与实现提示

重述问题，并区分：

* 用户需求描述：用户真正希望分析、筛选、比较、统计的内容；
* 外部知识：用于解释术语、背景、方向或业务规则的补充信息；
* 实现提示：数据库、表列、字段命名、实现路径、已有 SQL 线索等实现层信息。

需要明确：

* 当前是否存在实现提示；
* 用户原文与外部知识是否存在语义冲突；
* 若存在冲突，当前采用哪一侧作为解释依据。

## Step 1. 提炼问题主轴与查询子问题

基于用户需求，先提炼当前问题的主分析结构，并拆解为相互依赖的查询子问题。


## Step 2. 识别关键 operation decisions

围绕 Step 1 的主轴，只分析对当前问题成立真正关键的操作判断，例如：

* 哪个对象是主锚点对象；
* 哪个关系围绕主锚点对象被使用；
* 是否存在需要显式区分的角色、方向、前后关系或比较基准；
* 哪个属性承担时间锚点、空间锚点或比较锚点；
* 哪些局部条件定义了关键分析口径；
* 最终需要进行哪些聚合、比较、筛选或排序。

注意：

* 本步骤的目标是识别少数几个决定查询结构的关键操作判断；
* 不要把局部窗口、局部过滤、最终筛选分别扩写成冗长的执行流水；
* 数据实现不参与本步骤的语义判断。

## Step 3. 提炼核心查询单元

根据 Step 1 和 Step 2，判断哪些语义成分应被显式组织为**核心命名查询单元**。

对每个候选语义成分，只判断：

* 是否应作为核心查询单元保留；
* 若保留，它主要表达对象语义、关系语义，还是连接语义；
* 若是关系/连接，需要说明参与对象及其角色；
* 若不保留，应说明它应回落为属性、条件、局部连接条件或分析操作。

默认规则：

* 只定义核心查询单元；
* 不系统性定义后续查询单元；
* 局部时间窗口、局部子集、聚合结果、最终保留子集，默认不单独命名为查询单元；
* 只有当某中间结果具有稳定独立语义且值得复用时，才例外提升为命名查询单元。

## Step 4. 核心查询单元的属性与条件作用域分析

仅对 Step 3 中保留的核心查询单元，分析：

1. 该查询单元涉及哪些查询子问题，以及它在求解过程中的作用；
2. 该查询单元必须显式保留哪些属性；
3. 各属性属于哪类：

   * 基础属性；
   * 计算分析派生属性；
   * 角色派生属性；
   * 其它派生属性；
4. 用户需求中的条件哪些属于全局条件，哪些属于局部分析口径；
5. 哪些局部条件只需在 Conceptual SQL 中表达，而不应提升为独立查询单元。

要求：

* 所有派生属性都必须可追溯到一个或多个基础属性来源；
* 属性定义保持必要性与原子性；
* 不得把仅用于实现的字段误定义为语义层必需属性；
* 不得把整个局部分析结果压缩成不可分解的宽属性包。

关于条件作用域，遵守以下原则：

* 若某条件作用于该对象/关系在整个问题语义中的全部出现，并且问题中不存在与之并列的更大范围全集，则视为**全局条件**；
* 若某条件仅用于定义某个局部子集、局部中间结果或局部分析口径，则视为**局部条件**；
* 判断全局/局部时，不仅要看显式文本，也要识别逻辑上隐含的全集。

## Step 5. 构造 Conceptual SQL 并输出

在完成以上分析后，基于已识别的核心查询单元、属性、条件作用域与关键 operation decisions，构造 Conceptual SQL。

要求：

* 首要目标是正确表达问题求解过程中的语义结构，而不是生成可直接执行的业务 SQL；
* 查询计划应优先体现问题主轴与关键操作判断，再体现语义组织结果；
* 核心查询单元作为主要 CTE；
* 局部窗口、局部过滤、聚合、最终筛选优先直接在相关 CTE 或主查询中表达；
* 实现提示只能作为 CTE 内部的实现支撑，不得主导查询单元命名与语义边界；
* 必要时可用注释标记 `Global Condition`、`Local Condition`、`relation-like`、`connection-like`、`implementation-support`。

输出严格按照下列形式：

```json
{
  "conceptual_sql": "..."
}
```

# Conceptual SQL 要求

生成的 `conceptual_sql` 必须满足以下要求：

1. 目标不是生成可直接执行业务 SQL，但必须生成**语法完整、结构稳定、便于 AST 解析和表列提取**的概念 SQL；
2. 表、列、函数、常量可以占位，但整体 SQL 必须语法合法；
3. 不允许出现 `...`、`WHERE ...`、`ON ...`、不完整函数参数、不完整表达式；
4. 每个 CTE 都必须写成完整的 `name AS (SELECT ... FROM ...)` 结构；
5. 所有引用项尽量显式起别名；
6. 默认按 Snowflake 风格书写；
7. CTE 名称应优先表达语义对象本身，而不是编码“基础/派生/起始/后续”阶段位置；
8. 可选使用 `*_ent / *_rel / *_conn` 作为类型提示，但不使用 `*_base / *_derived` 等阶段后缀；
9. `*_impl` / `*_source` 只能用于 CTE 内部引用的来源对象命名，并且必须严格基于输入证据判断；
10. 最终主查询应保持用户问题的语义口径，不得退化为物理实现结构的直接转写。
