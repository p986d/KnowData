## 任务定义

你的任务是根据全部输入中可识别的用户需求语义、数据库模式相关证据，以及**已给定的命名查询单元**与上阶段形成的问题理解,推理结果，为每个查询单元定义字段属性与约束条件，并构造一个**面向问题表达的概念查询结构（Conceptual Query Plan）**。

这里的概念查询结构不是要求生成一条可直接执行的数据库 SQL，或是完整的数据库 schema 结构。
它是一条作为中间语义表示的**概念 SQL / SQL-like 查询伪代码**，用于表达：

* 用户真正想分析的语义对象与分析主轴；
* 问题在逻辑上如何由已保留的语义节点逐步成立；
* 哪些中间语义结果需要被显式保留，以清楚表达问题的求解过程；
* 后续语义步骤如何依赖前序步骤逐步形成；
* 数据库模式相关证据如何用于将需求语义对齐到可能的实现结构。

本任务的目的是将用户问题组织为**符合用户表述口径的概念查询结构（conceptual SQL）**，并通过 SQL 清晰表示问题求解过程中的对象、连接、属性、条件与中间结果。

注意：

* 本阶段承接上阶段已经形成的问题理解、自然增量式推理与命名查询单元；
* 本阶段不应重新发明一套与上阶段脱节的独立问题分解；
* 本阶段的主要任务是：围绕已保留的语义节点，补充属性与条件作用域，并将其翻译为清晰稳定的 conceptual SQL；
* 输出不是最终可执行 SQL，而是结构清晰、语义稳定、便于后续解析与验证的概念 SQL。

## 核心原则：并非所有语义成分都应成为 CTE

问题中的对象、字段、条件、连接依据、分组聚合要求等，都属于需要识别的语义成分；
但**并非所有语义成分都应被显式组织为概念 SQL 中的命名查询单元**。

只有在当前问题中满足以下条件的语义成分，才值得被显式命名为查询单元（CTE）：

1. 具有相对独立且稳定的语义边界，能够单独说明“它是什么”；
2. 能够单独定义粒度与成员范围，能够说明“一行代表什么”；
3. 在当前问题的求解过程中，值得作为阶段性语义结果被后续步骤继续引用；
4. 在当前问题中需要被显式保留，而不只是一次性临时桥接、局部匹配或实现支撑步骤。

其中需要特别注意：

* 用户需求中被直接表达、且对问题成立有直接作用的对象间连接，不应因为其属于连接就自动退化为局部 `JOIN ... ON ...` 条件；
* 但并非所有连接都必须拆成独立 CTE；只有当该连接在问题表达过程中形成值得单独保留和继续引用的中间语义结果时，才应显式组织为查询单元；
* 命名查询单元优先服务于**清楚表达查询计划**，而不是提前完成最终基础实体 / 关系 / 连接模型的收敛；
* 对于数据实现提示中的空间映射、编码映射、桥接路径、键关联路径等实现相关内容，不单独组织为概念层查询单元，而应隐藏在相应查询单元内部作为实现支撑表达；
* 即使输入中显式提供了某个需求语义单元对应的数据库实现线索，这些实现对象也仍仅属于该语义单元在 CTE 内部的实现支撑来源，不得因此上升为新的概念层查询单元。

其余语义成分应作为：

* 查询单元的属性；
* 属性上的常值约束；
* 查询单元之间的局部连接条件或属性匹配条件；
* 实现支撑路径；
* 分组、聚合、排序等分析操作

附着在相关查询单元上，或在主要 Query 表达，而不应自动成为独立 CTE。

## 2.3 查询语义单元

在本任务中，输入包含已定义的命名查询单元集合：

### 1. 核心查询单元（Core Query Unit）

起始查询单元是指：**在当前概念查询计划中，不依赖此前已命名 CTE、作为其它 CTE 依赖对象的起始查询单元**。

它通常具有以下特点：

* 具有基础性与原子性；
* 具有相对稳定的语义边界；
* 可以单独定义粒度与成员范围；
* 可以直接从来源对象建立；
* 作为查询计划中的起始阶段性语义结果存在。

注意：

* 核心查询单元是一种**查询计划中的位置角色**，代表基础性、起始性；
* 其它的查询单元应建立在已有核心查询单元及已保留的前序查询单元之上展开；
* 实体型的核心查询单元不依赖任何其它查询单元；关系 / 连接型的核心查询单元不依赖参与的实体核心查询单元以外的任何其它查询单元。

### 2. 后续查询单元（Subsequent Query Unit）

后续查询单元是指：**由已有查询单元经由筛选、组合、角色化、匹配、对齐、聚合、重命名、粒度变化或其它语义变换后形成的后续查询单元**。

后续查询单元的作用是：

* 组织概念查询结构中的阶段性查询结果；
* 表达某种阶段性必要的中间语义结构；
* 承载连接语义、角色信息、跨对象属性对应、条件约束、上下文补充或分析中间结果；
* 为最终主查询提供可复用的中间查询输入。

注意：

* 这里的“后续”只表示其在当前查询计划中的依赖位置；
* 它不是最终 ER 提取阶段中“派生实体 / 派生关系 / 派生连接”的正式结论；
* 单纯的一次性桥接、局部匹配结果或局部实现路径，通常不应单独命名为后续查询单元。

### 3. 实现支撑来源（Implementation Support Source）

实现支撑来源是可选的数据实现定义，由数据库模式相关证据提示引入、用于支撑需求语义落地。

它们通常来自：

* schema / table / column 提示；
* 主键、外键、桥接表、映射表；
* 时间列、空间列、编码列；
* 其它能够揭示实现承载位置、连接路径或属性来源的数据库线索。

实现支撑的定义规则：
实现支撑需要用后缀明确分类：

* 根据问题语义推知该来源对象必然存在，但是来源对象的数据实现未明确在提示中给出，此时必须使用 `*_source`；
* 只有当输入中明确提供了某来源对象的具体数据库模式相关证据（如具体 schema、table、column 或其它可直接指向实现对象的线索）时，才可使用 `*_impl`。

注意：

* 实现支撑来源**默认不直接成为命名查询单元**；
* 它们通常作为 `FROM` / `JOIN` 中引用的来源对象出现；
* 若当前问题需要引用某类来源对象，但输入未提供其明确的数据库模式相关证据，必须使用 `*_source` 作为抽象来源占位；不得假设存在实现，并写为 `*_impl`；
* 只有输入存在明确的数据库模式相关证据，才能使用 `*_impl` 后缀；
* `*_impl` 与 `*_source` 都不是独立 CTE 类型。

## 2.4 连接语义的说明

在概念查询结构中，对于**已被判定为需要显式保留的连接语义单元**，可进一步说明其内部连接性质。

连接语义通常可表现为以下几种倾向：

### 1. 关系类型性连接（Relation-like）

指该连接更接近一个需要被独立保留的关系类型语义，通常具有以下特征之一：

* 参与对象结构明确；
* 存在稳定的参与角色；
* 连接自身可能承载属性或局部约束；
* 去掉具体实现路径后，该连接仍然是当前问题中的重要语义结构。

### 2. 属性匹配性连接（Connection-like）

指该连接主要用于在对象之间完成属性附着、上下文补充或分析所需的对齐，通常具有以下特征之一：

* 主要作用是补充上下文或附着属性；
* 更依赖时间对齐、类别对齐、同值匹配、条件匹配等方式；
* 连接本身通常不作为独立关系类型对象保留。

### 3. 实现支撑路径（Implementation Support Path）

指该连接在落地时所依赖的实现路径、桥接路径或局部实现依据，例如：

* 键关联；
* 桥接表路径；
* 空间映射；
* 编码映射；
* 其它实现层的连接步骤。

需要注意：

* 实现支撑路径不是概念层连接语义单元的同级替代类型；
* 它通常作为连接语义单元内部的实现支撑而存在；
* 不应直接上升为概念层对象。

## 2.5 用户需求到概念查询结构的映射规则

用户需求中与问题成立直接相关的对象、字段、实例值、条件、连接依据和分析要求，应尽量在概念查询结构中得到对应表达。

它们可以分别落实为：

* 查询单元的属性；
* 属性上的常值约束；
* 查询单元之间的连接语义；
* 查询单元之间的局部属性匹配和约束条件；
* 计算、分组、聚合、排序等分析操作；
* 最终分析单元的输出要求。

映射时应遵守以下原则：

* 用户提及的对象概念，优先映射为已给定查询单元的语义边界或其参与对象；
* 用户提及的字段，优先映射为相关查询单元的属性；
* 用户提及的实例值、时间值、类别值、范围值，优先映射为相关属性上的常值约束或范围约束；
* 用户需求中被直接表达、且对问题成立有直接作用的对象间连接，应优先映射为连接语义表达，而不默认退化为局部 `JOIN` 条件；
* 与连接落地相关的空间映射、编码映射、桥接路径、键关联路径等实现内容，不单独映射为概念层查询单元，而应尽量附着在相应查询单元内部表达。

## 2.6 概念 SQL 的结构说明

概念查询结构应采用**概念 SQL**的方式组织。这里的概念 SQL 不是可执行 SQL，而是用接近 SQL 的形式表达：

* 问题求解过程中的起始查询步骤；
* 后续语义步骤如何依赖前序查询结果逐步形成；
* 当存在数据库模式相关证据时，这些查询单元如何引用实现来源；
* 查询单元之间的连接、约束与依赖如何组织。

### 1. 两类命名对象

概念 SQL 中需要区分两类命名对象：

* **CTE**：概念查询结构中的命名查询单元，用于承载问题求解过程中的阶段性结果；
* **来源对象**：CTE 内部 `FROM` / `JOIN` 所引用的对象，用于表示概念来源或实现来源。

### 2. CTE 的命名规则

CTE 命名应优先表达**语义对象本身**，而不是在名称中编码其“基础 / 派生 / 起始 / 后续”的阶段位置。

推荐命名方式：

* 直接使用语义名称，在必要时保留类型后缀：
  * `*_ent`：表示查询单元主要表达实体类型语义；
  * `*_rel`：表示查询单元主要表达关系类型语义；
  * `*_conn`：表示查询单元主要表达基于属性匹配的连接语义。

注意：

* 查询计划中的“起始步骤 / 后续步骤”应由 SQL 依赖关系、CTE 顺序以及必要注释表达，而不是由名称硬编码；
* `*_ent / *_rel / *_conn` 是可选的类型提示。

### 3. 来源对象的命名规则

当概念 SQL 需要引用数据库模式相关证据中的实现来源时：

* 若输入提供了明确的数据库模式相关证据，可使用 `*_impl` 后缀；
* 若当前问题需要引用某类来源对象，但输入未提供其明确实现证据，可使用 `*_source` 作为抽象来源占位。

注意：

* `*_impl` 与 `*_source` 都不是独立 CTE 类型；
* 它们仅是 CTE 内部引用的来源对象命名后缀。

### 4. 连接语义的表达方式

在概念 SQL 中，查询单元之间的连接通过 `JOIN ... ON ...` 表达，在必要时通过简洁注释标明该连接单元更偏向何种连接性质。

当某条连接或条件的内部性质对解析十分关键时，可使用如下简洁注释辅助表达：

* `-- relation-like: ...`
* `-- connection-like: ...`
* `-- implementation-support: ...`
* `-- Global Condition: ...`
* `-- Local Condition: ...`

这些注释仅用于帮助表达该连接或条件在当前查询计划中的语义角色。

### 5. 使用原则

构造概念 SQL 时，应遵守以下规则：

* 并非所有识别出的语义成分都必须写成 CTE；只有值得单独命名的查询语义单元才应显式组织为 CTE；
* 单纯的属性约束、一次性跨单元属性匹配、实现桥接路径和临时中间结果，原则上不单独组织为 CTE；
* 不依赖此前已命名 CTE、可直接从来源对象建立的起始步骤，应通过 CTE 顺序和依赖结构自然体现；
* 依赖前序查询单元形成、且值得作为整体被后续继续引用的中间查询语义，应显式写成后续 CTE；
* 后续 CTE 可以依赖前序任意 CTE，但不得形成循环依赖；
* 连接语义是否单独写成 CTE，不取决于它是不是连接，而取决于它在当前问题中是否形成独立查询步骤；若未形成独立步骤，可仅在相关查询单元之间以显式连接结构表达；
* 参考数据、映射数据、编码数据、空间归属数据等实现相关来源，默认不直接写成概念层 CTE；它们所支撑的对象或连接语义若需要保留，应在相关 CTE 内表达；
* 只有在存在数据库模式相关证据时，才在 CTE 内部引用 `*_impl` 来源对象；若无明确实现证据但概念上需要引用来源，可使用 `*_source`；
* 最终主查询应保持用户问题的语义口径，不得退化为物理实现结构的直接转写。

# 分析步骤

在生成 JSON 形式的概念 SQL 之前，必须先基于以下步骤完成分析。**禁止直接生成 Json**；

## Step 0. 区分用户需求、上阶段推理结果与实现提示

重述问题，区分以下几类输入内容，并明确各自作用：

* 用户真正提出的问题；
* 上阶段已经形成的问题理解与 natural logical reasoning；
* 上阶段已经保留的命名查询单元；
* 外部知识；
* 数据库模式相关实现提示。

需要明确：

* 用户问题真正要求的最终结果是什么；
* 上阶段 logical reasoning 中已经确认了哪些关键语义节点；
* `query_units` 在本阶段中只是问题表达层中已保留的语义节点，不等于最终基础实体 / 关系 / 连接；
* 实现提示的作用是提供落地支撑，不得直接定义概念层基础语义单元。

---

## Step 1. 承接 logical reasoning，递增归纳基础语义单元

基于上阶段的 `problem_understanding`、`logical_reasoning` 与 `query_units`，按 logical reasoning 的自然推进顺序，递增归纳当前问题所需的**基础语义单元集合**。

这里的基础语义单元，是指应在概念层基础检索骨架中稳定保留的最小必要对象，包括：

* 基础实体（entity）
* 基础关系（relation）
* 基础连接（connection）

归纳时必须遵守以下原则：

(1) 基础语义单元的判断标准：

只有满足以下条件的对象，才可进入基础语义单元集合：

* 语义边界稳定；
* 粒度明确；
* 是问题成立所必需的原生对象或原生联系；
* 值得作为后续属性与约束定义的直接挂载对象；
* 不是仅服务于局部分析的中间结果、角色化视图、局部子集或桥接路径。

(2) 递增归纳原则：

沿 logical reasoning 的顺序，逐步判断每个 query unit 背后所依赖的基础语义单元是什么：

* 若当前 query unit 首次暴露出此前尚未纳入、但问题成立所必需的基础实体 / 关系 / 连接，则补充进入基础语义单元集合；
* 若当前 query unit 本质上只是已有基础语义单元的角色化、局部子集、上下文附着、局部匹配、局部映射、聚合结果、排序结果、Top-K 结果或窗口结果，则不得额外新建基础语义单元；
* 若当前 query unit 表面上依赖中间结果之间的连接，必须先判断其能否回落为基础实体之间的 relation / connection；
* 若该连接仅由确定性属性变换形成，则可回落到基础层；
* 若该连接依赖聚合、排序、Top-K、窗口或其它分析性选择过程，则不得直接回落为新的基础 relation / connection。

(3) 基础语义单元集合的维护要求：

* 同一基础实体 / 关系 / 连接一旦建立，应在后续 query unit 中优先复用；
* 不得因角色不同、局部条件不同或上下文不同而重复构造语义重复的基础单元；
* 基础语义单元集合最终必须足以支撑所有需要保留的 query units。

本步骤的输出目标不是立即写 SQL，而是先得到一个稳定的基础语义单元集合。

---

## Step 2. 说明每个 query unit 如何由基础语义单元构建

在 Step 1 已得到基础语义单元集合后，重新遍历所有已保留的 query units，说明每个 query unit 是如何建立在这些基础语义单元之上的。

对于每个 query unit，必须说明：

(1) 它依赖哪些基础语义单元：

* 依赖哪些基础实体；
* 依赖哪些基础关系；
* 依赖哪些基础连接；
* 是否还依赖此前已经保留的其它 query unit 作为中间结果。

(2) 它是通过什么语义变换形成的：

* 角色化；
* 条件筛选；
* 属性匹配 / 时间对齐 / 空间对齐 / 类别对齐；
* 上下文附着；
* 局部映射；
* 聚合；
* 排序；
* Top-K；
* 窗口；
* 重命名；
* 粒度变化；
* 或其它必要的语义变换。

(3) 它在概念查询计划中的地位：

* 是直接对应基础语义单元的起始性 query unit；
* 还是建立在已有基础单元上的保留型中间 query unit；
* 还是本质上只应作为局部构造过程存在，不应进一步升格为新的基础对象。

(4) 它的保留边界：

* 哪些内容是 query unit 需要显式保留的语义；
* 哪些内容只是该 query unit 内部的一次性局部操作，不应继续外溢；
* 哪些内容只应在后续 conceptual SQL 的 CTE 内部表达，而不应作为新的 query unit 或新的基础语义单元。

注意：

* 本步骤的任务是明确 query unit 与基础语义单元之间的构造关系；
* 不得把 query unit 和基础实体 / 关系 / 连接混为同一层；
* 不得因 query unit 数量较多而机械复制基础语义单元。

---

## Step 3. 对基础语义单元直接定义属性

基于 Step 1 中归纳出的基础语义单元集合，对这些基础语义单元直接定义属性。

属性应优先定义在**基础实体 / 关系 / 连接**上，而不是优先定义在 query unit 上。

### 3.1 基础实体属性定义

对每个基础实体，定义：

* 稳定基础属性；
* 必要的识别属性；
* 可作为后续连接、角色化、条件挂载和分析派生来源的属性。

要求：

* 优先保留用户问题中显式提及、直接参与分析表达的属性；
* 必要时补充约束支撑属性，但不得因为实现表里存在某列，就自动提升为概念层属性；
* 若用户未直接给出稳定自然标识，但建模上需要识别属性，则应使用 `_surrogate_id` 形式表示标识槽位；
* 不得把条件、角色、聚合结果或复合语义直接构造成单个基础属性。

### 3.2 基础关系属性定义

对每个基础关系，定义：

* 参与实体及其角色；
* 参与实体用于建立该关系的锚点属性；
* 关系自身的非标识性稳定属性。

要求：

* 单个参与实体即可唯一决定的字段，不应误写成关系属性；
* 只有真正描述这次关联本身的信息，才写入关系属性；
* 关系的标识不通过额外关系主键字段表达，而由参与实体、角色、锚点属性和 `link_condition` 共同定义。

### 3.3 基础连接属性定义

对每个基础连接，定义：

* 参与实体及其角色；
* 参与实体用于建立连接的锚点属性；
* `link_condition`。

要求：

* connection 主要表达对象如何通过属性条件连通，而不是表达独立业务关系；
* 一般不额外扩展非必要属性；
* 若某些属性只是为局部映射、局部对齐服务，应尽量保留为连接内部支撑属性，而不是提升为稳定基础属性。

### 3.4 派生属性的处理

对于由 query unit 构造过程产生的属性，必须显式区分其地位：

* 角色派生属性：由同一基础对象在不同角色下引申得到；
* 计算分析派生属性：由基础属性经过聚合、排序、Top-K、窗口、比较、映射选取等得到；
* 局部构造属性：仅在某个 query unit 的内部步骤中临时使用。

这些属性不得误写为基础语义单元的稳定基础属性，但可在后续 conceptual SQL 中显式投影或注释说明其来源。

---

## Step 4. 对基础语义单元直接定义约束，并区分全局 / 局部作用域

在完成基础属性定义后，对条件进行统一整理，并将约束直接挂载到基础语义单元上。

本步骤必须先判断条件的作用域，再决定其表达位置。

### 4.1 条件候选扫描

重新通读用户问题、logical reasoning 与 query unit 构造说明，逐句识别所有条件候选，包括：

* 时间范围；
* 空间范围；
* 类别范围；
* 状态范围；
* 对象域限定；
* 比较参照对象；
* 角色限定；
* 局部窗口；
* 局部筛选；
* 隐含限定词。

### 4.2 全局 / 局部作用域判断

对于每个条件，必须先判断：

* 它是否作用于某个基础实体 / 关系 / 连接在整个问题中的全部出现；
* 还是只用于定义某个局部 query unit、局部子集、局部窗口、局部分析结果或局部保留规则。

判断规则：

* 若某对象 / 关系与其受条件约束的子集在整个问题中同时出现，则这些额外条件通常只是局部条件；
* 只有当某条件限定了该基础对象在整个问题中的全部出现，且不存在与之并列的更大范围全集时，才可作为全局条件；
* 若某条件是沿 relation / connection 路径成立的存在 / 不存在 / 至少一个 / 全部满足等资格限制，则应整体视为量化型全局条件，而不是拆散成多个局部普通条件；
* 若某条件仅服务于一个中间构造步骤，则不得提升为基础层全局条件。

### 4.3 条件挂载规则

对每个条件，按以下顺序处理：

(1) 若条件用于建立 relation / connection 本身  
则应写入参与实体锚点属性说明或 `link_condition`，不得再作为独立全局条件重复定义。

(2) 若条件只用于构造某个局部 query unit  
则保留为局部条件，仅在 query unit 的构造说明或后续 conceptual SQL 的相关 CTE 内部表达。

(3) 若条件作用于问题整体口径  
则作为基础语义单元上的全局约束保留，并明确其目标对象与目标属性。

### 4.4 约束表达要求

* 全局条件只定义在基础实体 / 关系 / 连接上；
* 局部条件只写入 query unit 构造说明或 conceptual SQL 的局部表达；
* 不得把 relation / connection 的成立条件重复写入全局条件；
* 不得把仅用于局部中间步骤的条件误写为整体检索条件；
* 不得把聚合、排序、Top-K、窗口结果本身误写为基础约束。

---

## Step 5. 将基础语义单元与 query unit 构造过程翻译为 conceptual SQL

完成上述全部分析后，基于：

* 已归纳的基础语义单元；
* 每个 query unit 的构造说明；
* 基础语义单元上的属性与全局约束；
* query unit 内部的局部条件与局部构造步骤；

构造概念 SQL。

构造时必须遵守以下原则：

### 5.1 CTE 组织原则

* CTE 应优先对应那些在问题表达中值得继续保留的 query units；
* 起始 CTE 应自然对应起始性基础语义节点；
* 后续 CTE 应表达建立在已有基础语义单元或保留型中间节点之上的构造过程；
* 一次性局部筛选、局部映射、局部连接、临时桥接、单步推导，若不构成值得复用的中间语义结果，应尽量保留在相关 CTE 内部，而不单独拆成 CTE。

### 5.2 属性表达原则

* 基础实体 / 关系 / 连接的稳定属性应在相关 CTE 中显式投影；
* 派生属性只在其真正需要被后续引用或最终输出时才显式投影；
* 临时中间列、仅服务于局部操作的过渡列，尽量局部化，不要外溢为过多 CTE 输出列。

### 5.3 条件表达原则

* 全局条件应在能够代表整体范围的起始 CTE 或相关基础 CTE 中表达；
* 局部条件应放在相应 query unit 对应的 CTE 内部表达；
* `Global Condition` / `Local Condition` 注释可用于帮助表达作用域；
* 不得为了形式对称，把所有条件都抬到主查询或抬成独立 CTE。

### 5.4 命名与语法要求

* CTE 名称优先表达语义对象本身，而不是编码阶段位置；
* 可选使用 `*_ent / *_rel / *_conn` 作为类型提示；
* 不使用 `*_base / *_derived` 等阶段性后缀；
* `*_impl / *_source` 仅作为 CTE 内部来源对象命名；
* 概念 SQL 必须语法完整、结构稳定、便于 AST 解析和表列提取；
* 可以使用伪代码函数占位，但不得出现不完整表达式或 `...`。

### 5.5 最终主查询要求

* 最终主查询应保持用户问题的语义口径；
* 主查询表达的是用户最终想要的结果，而不是把所有中间结构机械平铺；
* 不得为了让 SQL 更像可执行实现，而退化为物理表拼接草稿。

```json
{
  "conceptual_sql": "..."
}
````

conceptual_sql 要求：

* 目标不是生成可执行业务 SQL，但是必须生成“语法完整、结构稳定、便于 AST 解析和表列提取”的概念 SQL；表、列、函数、常量可以占位表示，但必须语法合法；
* CTE 名称优先表达语义对象本身；是否是起始步骤或后续步骤，应由 SQL 依赖关系和必要注释体现，而不是由名称后缀编码；
* 可选使用 `*_ent / *_rel / *_conn` 作为类型提示，但不使用 `*_base / *_derived` 或其它表示阶段位置的后缀；
* `*_impl` / `*_source` 的后缀命名必须严格基于数据来源来定义：当语义上明确数据源的存在性，但是实现上的数据没有明确给出时，必须用 `*_source` 后缀，不得以任何形式假设物理数据的存在；仅当输入中明确的物理数据实现存在时才能用 `*_impl`。

约束如下：

1. 可以使用伪代码函数进行占位，但必须保持 SQL 语法完整。
2. 不允许出现 `...`、`WHERE ...`、`ON ...`、不完整函数参数、不完整表达式。
3. 每个 CTE 都必须写成完整的 `name AS (SELECT ... FROM ...)` 结构。
4. 所有引用项尽量显式起别名。
5. 默认按 Snowflake 风格书写。
6. 最终主查询应保持用户问题的语义口径，不得退化为物理实现结构的直接转写。
7. 不得为了让 SQL 看起来更完整，而把本应局部存在的临时分析动作强行拆成独立 CTE。
8. 不得为了让 CTE 数量与查询单元数量一一对应，而机械复制查询单元；概念 SQL 应以语义表达清晰为最高优先级。
