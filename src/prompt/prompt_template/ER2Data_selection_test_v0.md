# 任务定义

根据用户问题、候选实体-属性草图，以及数据库模式证据，构建一个能够支撑问题求解、并且可以被实际数据库模式落地支持的**实体-属性模型**。

本任务不是从候选中做简单选择，也不是直接生成 SQL。

本任务需要：

* 理解问题求解所依赖的核心语义对象；
* 参考候选实体的 `name`、`desc`、`grain` 与属性语义；
* 结合数据库表列证据，校准实体粒度、属性边界与可实现性；
* 输出最小必要的实体与属性集合，用于后续查询构造。

---

# 基本原则

## 1. 先按问题求解逻辑建模，再用数据库模式校准

首先从问题本身分析需要哪些对象、分组口径、过滤条件、计算分子/分母和聚合粒度。

然后使用候选实体-属性草图作为逻辑建模的初始参考，使用数据库模式证据确认这些实体和属性是否有可落地的数据来源。

数据库表名和列名只作为实现证据，不应直接替代逻辑实体名称或属性名称。逻辑模型应使用问题语义口径，而不是机械复制物理表列。

## 2. 候选实体是草图，不是最终答案

候选实体提供了可继承的对象概念、描述、粒度和属性集合。

你可以：

* 保留与问题求解直接相关的候选实体；
* 删除与问题无关或只属于中间实现的候选实体；
* 根据问题和数据库证据调整实体 `desc` 与 `grain`，使其更精确；
* 保留、合并或精炼候选属性，使属性能够支撑问题中的筛选、分组、聚合和计算；
* 当候选漏掉但问题求解和数据库证据都明确需要时，补充少量必要属性。

不得为了贴合某张物理表而创建题面不需要的实体；不得输出没有问题语义需求或数据库证据支撑的实体和属性。

## 3. 实体定义

实体是问题中具有稳定语义身份和粒度的对象类。

实体定义必须说明：

* `name`: 使用问题语义或候选草图中的逻辑对象名；
* `desc`: 该实体在当前问题中的语义边界；
* `grain`: 一个实体实例代表什么，必须与后续分组、计数和连接口径一致。

如果某个对象只是聚合、比例、分类结果或中间计算产物，不应作为基础实体输出。

## 4. 关系定义
关系是实体间具有明确独立事实性语义的关联。
关系定义必须说明：
* `name`: 使用问题语义或候选草图中的逻辑对象名；
*  `participant`: 参与实体名与在关系中的角色；
* `desc`: 该实体在当前问题中的语义边界；
* `grain`: 一个实体实例代表什么，必须与后续分组、计数和连接口径一致。
关系属性是作用于关系本身的属性，仅为该关系的语义存在。
如果一个关系属性可以从实体的属性派生计算得到，则其作为派生属性，不应该直接定义到关系上。

{% endif %}

## 5. 属性定义

属性必须是支持当前问题求解所需的最小原子语义属性。

属性可以来自候选草图，也可以由数据库证据提示后重新抽象得到。属性名称应表达逻辑语义，而不是直接使用物理列名。

属性定义必须说明：

* `name`: 逻辑属性名；
* `semantics`: 该属性在问题求解中的作用；
* `evidence_columns`: 支撑该属性的数据库列，可以为空但不能虚构。

不要输出最终计算结果属性，例如 percentage、rate、count result 等派生指标；这些应由后续查询计算得到。

## 6. 数据库证据的使用

`schema_snapshot.tables[*].columns` 只包含与当前问题相关的数据库列。它们用于判断：

* 某个逻辑实体是否可被数据库支持；
* 某个逻辑属性可以由哪些列实现；
* 样例值是否说明字段语义、分类口径或过滤条件。

`sample_rows` 只作为理解列值语义的辅助证据，不应把样例值当作固定输出限制。

# 分析步骤

Think step by step；请按以下步骤进行分析，最后一步输出Json。

### Step 1 理解问题相关的外部知识
如果提供了外部知识，首先理解这些知识的语义内容，并分析它们补充和说明了问题的哪些语义。

### 1.3 按自然求解逻辑设计子查询序列

基于问题的自然分析逻辑，将原问题拆解为若干独立的子查询。

子查询设计应遵循以下原则：

* 子查询是一个逻辑查询任务：必须明确查询的对象、查询计算和返回结果。
* 子查询对齐问题语义表示与题面语义解释，必须用逻辑形式和语义操作的口径表述。禁止直接使用数据提示和操作步骤作为子查询内容；
* 子查询序列必须逻辑清晰，明确覆盖问题所有语义要素，包括操作和约束条件。

对每个子查询，明确如下内容，并将实现提示对问题的解释与补充整合进子查询中。

1. 在问题整体求解中的作用；
2. 语义操作
3. 语义限定
4. 查询表示的多义性

语义操作：说明该子查询需要完成什么语义任务，需要哪些属性支持。例如：

 确定对象或对象子集；
 确定对象之间的联系、参与或匹配；
 对既有对象或联系施加条件约束；
 在对象或联系基础上进行聚合、比较、排序、Top-k、派生计算；
 形成后续步骤所依赖的阶段性结果。

语义限定：说明该子查询中的对象、联系和计算具体受到哪些语义约束；需要全面表述问题语义包含的约束，不得遗漏；
语义约束可以包括：角色限制、时间限制、方向限制、局部范围、参考对象、比较基准、分子/分母口径、去重口径、聚合前提和局部分析范围等。

查询表示的多义性：反思查询逻辑存在多义性和模糊性，对于具有模糊性/多义性的查询步骤，必须明确说明其多义表示的问题。

子查询要求如下：
* 不得提前写成实体、关系、属性、字段、连接方式、join key 或计算表达式；
* 不得遗漏问题中关键但隐含的约束和限制条件。

### Step 3 分析物理表列的数据语义：

首先列举出问题的实现支持提及的所有物理表和列，分析它们作为数据本身的语义；
数据语义是指在数据库中该模式信息的语义，而不是在这个具体问题下的语义。
  注意，物理数据的实体-关系语义建模与逻辑模型不一定一致；
  此处分析的是数据模式本身的语义；后续的问题语义理解与建模的逻辑语义需要得到数据本身的语义的支持，但两者并不相同。



## Step 5. 定义子查询求解需要的实体、关系和属性

定义求解问题所需要的实体及相关属性：
给出的实体-关系仅作为语义单元的候选参考，不是确定的建模。你需要根据问题求解逻辑和实际数据支持，选择、修改或创建实体-关系及属性。


定义满足如下要求：

* 实体-关系属性应能够被数据库实现支持。
* 是否代表题面中的基础对象；
* 粒度是否满足后续计数、分组和连接；
* 是否需要根据数据库证据调整描述或粒度；
* 属性定义是否符合问题义需求；
* 属性定义需要满足所有查询计算和条件约束要求；
* 属性定义不得建模派生的属性。


## Step 6. 写出实体-关系的查询实现，根据视图定义实体-关系语义，属性集合以及属性语义

** 根据Step 4中定义的实体与关系，写出一组SQL将查询所需要的实体-关系定义为基于该数据库模式的视图。
注意，这一组SQL独立定义且每个实体-关系及其相关属性。

SQL必须符合问题语义与数据库相关提示；视图需要表达该实体涉及问题的所有语义，包括筛选条件与数据操作。
自然语言问题必须与SQL语义一致，用于表达SQL查询的意图。

根据视图的SQL语义和问题，检查实体的语义、粒度和相关属性、属性的语义。逻辑属性为视图中用到的所有语义表达、条件约束和定义计算所用的列；正式确定问题相关的实体和属性。
