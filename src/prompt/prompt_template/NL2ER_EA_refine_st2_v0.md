# 用户需求建模与数据库模式对齐任务：实体优化阶段

在未获取完整数据库模式信息的前提下，基于用户需求描述、相关数据库模式提示，以及上一阶段已提取的实体-关系骨架草稿，对其中的实体类型与属性描述进行进一步优化，形成可直接作为后续关系优化与条件构建基础的正式实体定义。

输出目标：输出不是完整数据库 schema，而是基于给定实体-关系骨架草图后反思和调整的`entities` 与 `attrs` 集合。

用户可能提供部分数据库模式相关内容作为需求的参照实现方式提示。数据库模式提示是可选的、不保证完全覆盖具体实现。数据库模式提示具有比用户需求描述口径更高的优先级，一旦提供，凡其能够更明确支撑需求语义落地的部分，应优先使用其覆盖并规范化用户的原表述与上一阶段草稿中的高层表述。

1. 用户提到了哪些对象实体类型，包括需求想要直接分析的直接对象以及数据库模式信息提示中涉及的中间对象。
2. 每个实体的正式语义边界、粒度、角色与属性集合应如何定义。
3. 每个实体的最小可行标识符属性集是什么，其来源应归类为 `explicit`、`natural` 还是 `introduced`。
4. 每个实体的合理属性集是什么：合理属性必须是问题中显式提及或数据库相关实现显式说明存在的属性；不得编造其他属性。

对象数据库为 Snowflake，具体数据库模式信息可能包含三个字段：模式名（schema）、表名（table）、列名（column）。

本阶段以实体为主要视角，根据输入的实体-关系草图，进行 **实体定义** 与 **属性定义**的**反思与调整**；关系骨架仅作为辅助证据。本阶段不正式输出关系、条件或查询表示。

## 建模目标

你需要基于用户需求描述、相关数据库模式提示与输入的实体-关系草稿，完成以下任务：

1. 审查实体-关系草稿中的 `entity_type` 集，确定在**保持语义表达的完整性的前提下**，哪些实体应被正式保留，哪些实体是不必要的；
2. 必要时对实体进行最小必要的增删改，使其更贴近数据库实现并能稳定承载需求语义；
3. 为每个最终保留实体正式定义：

   * `name`
   * `desc`
   * `grain`
   * `role`
   * `identifier_attrs`
   * `identifier_source`
   * `attr`

4. 对上一阶段仅以 `attrs` 粗略描述的属性语义进行细化，明确属性归属；

注意：

* 本阶段不是从用户需求中重新抽取实体，而是对已有实体集进行**反思和调整**，以**保持语义表达的完整性**与**对齐到给出的数据库实现**，同时保持实体定义的清晰性、一致性与原子性；并对实体的相关属性落实定义。
* 本阶段可以参考的实体-关系草图中的关系作为实体边界的定义，但不正式定义关系角色、基数、条件与查询结构；
* 本阶段输出的是**实体-属性集**。
* 不得因为某个属性在当前问题中取值固定就认为该属性不必要 ，并改为仅通过缩窄实体 `desc` 或 `grain` 来表达该限定。

## 核心建模原则

### 0. 数据库模式相关内容是可选提供的输入证据

数据库模式相关内容不是必选输入，而是可选提供的证据来源。它可能以以下任一形式出现：

1. 作为单独的数据库模式实现提示输入；
2. 混杂在用户需求描述中，例如表名、字段名、主键、外键、映射表、坐标列、时间列等实现信息；
3. 完全未提供。

因此，本任务不得预设数据库模式相关信息一定存在，也不得预设其一定与用户需求描述严格分离。分析时应统一从全部输入中识别数据库模式相关证据。

### 1. 基于输入的实体-关系草图中的实体，进行反思、调整和最终确认

本阶段回答如下问题：

* 实体-关系草图中哪些实体是语义明确的；包括用户需求中提及的实体对象和数据库模式提示中涉及的中间对象。
* 哪些实体边界不合理，需要局部修正；修正同时必须保持对语义的完整表述；
* 最终确定的实体集是否完整覆盖用户语义表述；
* 最终确定的实体集是否存在冗余现象；
* 每个实体应承载哪些在需求表述与数据库提示中明确的属性
* 实体的主键：最小可行标识符属性集是哪些属性。

本阶段不直接回答如下问题：

* 实体之间正式存在什么关系；
* 哪些条件限制了实体实例集或关系实例集；
* 应如何执行聚合、指标计算、查询生成或多阶段分析。

### 2. Entity 的定义

本阶段基于输入的实体草稿，调整细化为正式 `entity` 定义。`entity` 表示正式保留的对象实体类型，包括：

* 相关业务 / 参照维度对象；
* 事实 / 事件对象；
* 为覆盖用户需求并贴近数据库实现而需要显式保留的中间承载对象。

每个 `entity` 包含：

* `name`
* `status`
* `desc`
* `grain`
* `role`
* `identifier_attrs`
* `identifier_source`
* `attr`

其中：

* `status` 只能取：

  * `unchanged`
  * `modified`
  * `added`
* `role` 只能取：

  * `fact`
  * `dimension`

`role` 的含义：

* `fact`：表示一次业务事件、行为、观测、交易或状态记录。判断依据是该实体是否对应“某次发生/某条记录/某个观测事实”，而不是它是否是当前问题中的主分析对象。
* `dimension`：表示相对稳定的对象、主体、地点、类别或参照实体。判断依据是该实体是否主要用于描述、分类、定位或关联事实，而不直接对应一次发生的记录。

`grain` 定义该实体在需求表示中的粒度，例如 “某地区某店铺某日与某顾客的交易事实”。

`desc` 需要定义该实体的具体语义。若上一阶段实体命名或边界存在模糊性，应在 `desc` 中将其说明清楚。

### 4. Attr 的定义

本阶段输出的 `attr` 必须仅表示该实体必须承载的性质、标识、状态、时间、位置、数值或描述维度，以满足用户需求或对应到数据库实现。

若某个语义性质依赖于实体之间的关系才能成立，则应在关系级别表达，而不是直接建模为属性。

属性语义来源验证：对所有属性必须依次分析其语义对应的合法性：

* 某属性不存在于用户需求表述，也不存在于数据库模式相关证据，缺乏明确存在性依据，必须删除；
* 某属性是基于常识的实体自然属性，但是未在需求中或数据库中提及，必须删除；
* 某属性实际属于另一个实体；
* 某属性本质上是关系语义而非实体语义，必须删除；
* 某个实例值、筛选值、聚合结果、排序要求或连接路径本身不是属性名；但若某个常量实例或筛选值明显作用于某个实体，并且语义上依赖于该实体的某个属性才能成立，则必须补出承载该值的属性槽位，而不是仅保留这个值本身；

### 5. identifier attr 的定义

`identifier_attrs` 表示能够唯一标识该实体实例的最小属性集合。

`identifier_source` 表示该标识符属性集的来源分类：

* `explicit`：用户需求或数据库模式提示中显式提及的标识符属性；
* `natural`：虽未显式声明为标识符，但可由需求语义直接支持的自然标识属性组合；
* `introduced`：仅当实体在建模上必须具备标识能力、且无法从输入中得到可用显式标识符或自然标识属性组合时，才允许引入的抽象占位标识符。

要求：

* 每个实体都必须给出 `identifier_attrs` 与 `identifier_source`；
* `identifier_attrs` 应尽量最小化；
* 不要把仅用于连接其他实体的引用字段误当作当前实体的标识符；
* 仅当确实无法从现有语义中得到可用标识时，才允许引入抽象标识符；
* 若引入抽象标识符，该属性必须表述为 `XX_sk_id` ，以明确说明其为抽象技术键。

### 6. 常量实例的对应属性存在性

如果问题中出现某个**常量实例**，且该常量实例用于限定某个实体的实例范围，则必须先识别出它所对应的**实体属性语义**，并将该属性显式保留在该实体的 `attr` 中。

这里要求保留的是**承载该常量实例的属性槽位**，而不是把常量实例本身直接当作属性名。

不得仅因为该属性在当前问题中呈现为一个固定常量实例，就将其删除、吸收到实体 `desc` 中，或隐含到 `grain` 中而不显式保留。

后续阶段可以再判断该常量实例是否对应到：

* 某个明确的数据库字段取值；
* 某个 metadata 中的枚举值；
* 某个上下文约定下的固定语义值。

但在本阶段，相关属性槽位必须先被显式建模出来。

### 7. 用户显式提及表名、字段名或数据来源时的处理原则

用户显式提及的数据库实现信息，不应被忽略，也不应按原始字面直接复制为实体或属性；而应根据其在需求到数据库模式对齐中的语义作用，选择性转化为正式实体定义中的相关语义单元。

* 若某个数据库实现揭示了应被显式建模的对象类别，则将其语义化为实体；

  该对象可以是用户直接描述的核心对象，也可以是数据库实现中用于承接中间语义、属性附着、条件约束或后续关系组织的中间对象；

  但应建模其实体级语义，而不是直接沿用数据库中的物理命名。
* 若某个数据库实现揭示需要被显式建模的属性，则必须其添加至相关实体类型。

注意：

* 当数据库实现信息能够更明确地支撑需求语义落地时，应优先使用其覆盖用户原始表述；
* 若未提供可靠的数据库模式相关证据，则禁止依据惯常实现方式臆造中间实体、属性或标识符结构；
* 即使优先贴近数据库实现，也不得直接复制表名、列名作为最终实体定义，而必须保持语义化建模。

## 输出格式

在输出 JSON 之前，先基于**全部输入中可识别的用户需求语义、数据库模式相关证据与输入的实体关系草图**，进行**实体-属性建模的反思调整分析**。分析目标不是复述需求，也不是从头创建全新的实体集合，而是严格确定：

1. 审查实体-关系草稿中的 `entity_type` 集，确定在**保持语义表达的完整性的前提下**，哪些实体应被正式保留，哪些实体是不必要的；
2. 为每个正式实体类型确定定义；
3. 实体类型需要哪些属性以唯一确定实例，优先用需求或数据库实现中显式提及的属性集；
4. 哪些语义单元应正式定义为 `entity.attr`，包括由常量实例的属性槽位；
5. 针对实体的条件约束是否能显式对应到属性，不得因其在当前问题中表现为常量实例而省略相关属性；

请按以下顺序分析，显式给出每一步的判断结果：

### Step 0. 重述用户问题与输入实体-关系草图

先重述用户需求中的核心语义，并概括上一阶段骨架中的现有实体集合、相关属性描述与关系线索。

对上一阶段实体骨架，标识：

* 明显稳定、可直接保留的实体；
* 用户需求口径表述直接提及的实体；
* 对齐到数据库实现的需要显式保留的中间实体。
* 其它实体


### Step 1. 确定最终需要保留的正式实体集

在保证实体对用户需求的表述完整性与对数据库实现的对齐性的前提下，对最终实体集合进行调整，修正冗余、非原子性、不存在语义与实现证据的实体。

定义所有的保留实体：

* 为什么它应被正式保留为实体；
* 它属于 `fact` 还是 `dimension`；
* 它在需求表示中的 `grain` 是什么；
* 它与用户需求、数据库模式提示、上一阶段骨架的对应依据是什么；
* 它相较于上一阶段是 `unchanged`、`modified` 还是 `added`。

并检查是否完整覆盖用户的需求、以及对齐到数据库实现提示。

### Step 2. 为每个实体正式分配属性，并说明属性来源与归属依据

对每个已确定实体，正式定义其 `attr`。每个属性必须满足：

* 在用户需求描述或数据库模式提示显式提及；所有不能在需求或数据找到直接对应的属性必须被删除；
* 禁止根据常识、惯例为实体编造属性；所有属性必须是需求或数据库模式提示中显式提及的；
* 描述的是该实体实例本身的性质、标识、状态、时间、位置、数值或描述维度；
* 描述的是类型级属性语义，而不是单纯的值、关系、连接路径或聚合结果。
* 不得为表达关系语义专门构建属性

对每个属性，显式说明：

* 它是用户直接提及的还是数据库模式实现提及的；
* 它是用户需求直接要求的属性，还是数据库实现中用于承接中间语义的实现属性；
* 是不是根据常识、惯例捏造的属性，没有确实的证据支持；
* 若上一阶段草稿中该属性归属不当，说明为何需要修正。

此外，对每个实体还必须检查：用户是否通过某个**常量实例**对该实体施加了限定。若存在这种情况，必须显示定义：

* 该常量实例对应的是哪个实体属性；
* 为什么该属性应保留在该实体上；
* 不能仅将该常量实例写入 `desc` 或 `grain` 而省略该属性。

### Step 3. 为每个实体确定正式标识符属性集

对每个实体，给出能够唯一标识该实体实例的最小属性集合 `identifier_attrs`，并判断其来源 `identifier_source`：

* `explicit`：用户需求或数据库模式提示中显式提及的标识符；
* `natural`：由需求语义可直接支持的自然标识属性组合；
* `introduced`：仅当所有需求与数据库实现中提及的语义单元完全无法用于唯一标识实体实例时，才允许引入抽象占位标识符; 名称必须以 `XX_sk_id` 的模式 。

注意：

* 尽可能使用在需求与数据库实现中提及的属性作为显式标识符或自然标识符，尽可能不引入抽象标识符；
* 标识符属性也必须服从本阶段的实体归属规则；
* 若上一阶段骨架中相关实体虽存在，但缺乏可行标识能力，应在此阶段明确补足。


在完成上述步骤后，才允许将输出整理为最终 JSON 对象：

```json
{
  "entities": [
    {
      "name": "...",
      "status": "unchanged | modified | added",
      "desc": "...",
      "grain": "...",
      "role": "fact | dimension",
      "identifier_attrs": [],
      "identifier_source": "explicit | natural | introduced",
      "attr": [
        {
          "name": "...",
          "status": "unchanged | modified | added",
          "desc": "..."
        }
      ]
    }
  ],
  "user_original_requirement_coverage": "..."
}
```
