# 任务定义

根据全部输入中可识别的用户需求语义与数据库模式相关证据，完成该问题的**语义边界校准**与**查询子问题序列设计**。

本阶段的目标不是直接生成对问题的最终查询，也不是抽取实体、关系和属性。

本阶段只负责：

* 将问题分解为语义单元与查询子问题；
* 明确每个子问题在整体求解中的作用、语义操作、语义限定与多义性；
* 显式记录可能影响查询逻辑的多义性，并给出默认求解路径与必要的替代路径；
* 为后续从子问题中抽取基础逻辑实体、基础逻辑关系与逻辑属性提供稳定输入。

本阶段不得：

* 正式定义实体、关系和属性；
* 输出字段、连接方式、join key 或 SQL 计算表达式；
* 将数据库模式实现直接转化为逻辑模型；
* 在存在高影响多义性时，只给出单一路径而不记录替代解释。

---

# 基本原则

## 1. 先组织问题求解结构

首先提取问题中的语义单元，并根据查询计算的逻辑顺序构建查询子问题序列。

数据库模式相关证据作为实现支撑，用于将语义内容落地到可能的数据来源；它可以作为问题的补充说明，但不得主导问题本身的求解结构，也不得替代用户问题的语义分解。

---

## 2. 实现证据只作支撑，不主导语义拆解

数据库模式相关证据、表名、列名、外部知识只能作为落地支撑。

它们可以帮助你：

* 判断对象与属性是否可能存在；
* 确认某些对象的实现证据是否明确；
* 补充题面未明说但由输入提示直接给出的查询语义。

它们不得：

* 替代用户问题本身的语义依赖；
* 主导子问题定义；
* 把实现字段直接当成子问题对象；
* 把某个实现表直接等同于逻辑对象。

---

## 3. 题面定义优先于外部知识

如果用户问题中通过括号、i.e.、means、defined as 等方式显式定义某个术语，则该定义优先于外部知识中的通用定义。

外部知识可以作为背景解释、补充说明或替代解释来源，但不得覆盖题面显式定义。

如果题面定义与外部知识存在差异，需要在语义边界中说明，并在多义性中记录可能的替代解释。

---

## 4. 多义性先在查询逻辑层表达

如果问题中存在会影响查询路径、对象粒度、关系方向、时间窗口、计数口径、筛选口径或排序口径的多义性，必须先在查询逻辑层记录。

不要只在某个子问题的说明中写“存在歧义”，而要将其结构化为 `ambiguities`，并在不同 `plans` 中选择对应解释。

默认情况下：

* 生成一个默认子问题序列；
* 对高影响多义性，生成替代 plan；
* 替代 plan 可以只写相对默认 plan 的差分，不必完整展开所有子问题。

# 分析步骤

**Think step by step**：完成 Step 0 和 Step 1 的所有分析步骤，才能得到详实准确的子问题序列。禁止跳过分析直接生成 JSON 输出。

---

## Step 0. 问题背景与输出语言设置

判断查询问题的专业领域，并明确用户输入问题所使用的语言。后续所有子问题、约束与说明必须与用户语言一致。

---

## Step 1. 校准问题语义边界，分解问题

本步骤的目标是：按照问题本身的自然求解逻辑，将原问题拆解为一组用自然语言定义的子问题。

### 1.0 分析相关外部知识

对给出的外部知识进行分析，判断其与问题相关的语义内容。

需要判断外部知识属于：

* 对题面语义的直接补充；
* 对题面术语的通用背景解释；
* 仅提供实现支撑；
* 与当前问题无关。

如果外部知识与题面显式定义存在差异，应以题面定义作为默认解释，并将外部知识解释作为可能的替代解释记录。

---

### 1.1 先从题面和相关外部知识分析语义

只看用户原始问题和相关外部知识，明确问题的查询逻辑，并用自然语言描述。

此处需要理清问题的求解逻辑，但不是确定实体、关系和属性。从题面和外部知识分析语义时，先不考虑具体数据实现。

需要明确：

* 问题要求查询或统计什么；
* 最终输出的对象粒度是什么；
* 需要哪些中间计算；
* 哪些条件是题面确定的；
* 哪些内容是题面未提及、因此不应引入的；
* 哪些语义存在多义性，并可能影响后续查询路径。

---

### 1.2 理解问题相关的数据提示，补充语义

如果输入中包含数据库模式实现说明或外部知识提示，需要找出与理解问题直接相关的内容。

实现支持只说明逻辑对象或逻辑联系的可存在性，不直接进入子问题序列。

只有当数据提示直接补充了当前问题的逻辑语义时，才可以将其抽象为问题相关的补充语义，并整合进整体查询逻辑中。

不得把数据表、字段、连接路径、函数调用、编码转换或中间实现步骤直接作为子问题内容。

---

### 1.3 注册查询逻辑多义性

在生成子问题序列之前，先识别并注册可能影响求解路径的多义性。

重点检查以下类型：

* 对象粒度多义性：例如对象到底是 application、publication、patent、event、record 等；
* 关系方向多义性：例如 A 引用 B，还是 B 引用 A；
* 时间锚点多义性：例如使用事件日期、申请日期、公开日期、授权日期等；
* 时间窗口边界多义性：例如是否包含端点、1个月是自然月还是30天；
* 计数口径多义性：例如 count rows、count distinct objects、count distinct applications；
* 筛选条件多义性：例如 AND / OR、至少一个 / 全部满足；
* 排序或输出口径多义性。

每个多义性需要给出：

* id；
* 名称；
* 类型；
* 可选解释；
* 默认解释；
* 影响程度。

默认解释选择优先级：

1. 用户问题中的显式定义；
2. 用户问题中的上下文限定；
3. 外部知识对题面语义的直接补充；
4. 数据提示支持；
5. 领域常识；
6. 最小假设原则。

---

### 1.4 按自然求解逻辑设计默认子问题序列

基于问题的自然分析逻辑，将原问题拆解为若干独立的子问题。

默认子问题序列应选择 `ambiguities` 中的默认解释。

子问题设计应遵循以下原则：

* 子问题是一个逻辑查询任务，必须明确查询对象、查询计算和返回结果；
* 子问题对齐问题语义和题面定义，禁止直接使用数据实现步骤作为子问题内容；
* 子问题序列必须覆盖问题所有语义要素，包括对象范围、条件、关系、时间窗口、聚合、筛选、排序和最终输出；
* 对涉及引用、参与、匹配、归属等语义的任务，优先先形成关系/事实集合，再在后续子问题中进行过滤和聚合；
* 聚合、计数、排序、Top-k、比例、窗口计算等应作为派生计算步骤，不应混入基础对象识别步骤；
* 每个子问题需要说明 input、output 和 output grain，以便后续 ER 生成模块使用。

每个子问题至少包含：

* id；
* task；
* op；
* input；
* output；
* constraints；
* uses_ambiguities。

其中：

* `input` 表示该子问题依赖哪些前序语义单元；
* `output.name` 表示该子问题产生的阶段性语义单元；
* `output.kind` 表示输出类型，如 object_set、relationship_set、relationship_subset、derived_measure_set、final_result_set；
* `output.grain` 表示输出粒度；
* `uses_ambiguities` 表示该子问题依赖哪些多义性选择。

---

### 1.5 生成替代子问题序列或差分

如果存在高影响多义性，需要生成替代 plan。

替代 plan 不必完整展开全部子问题，可以只输出相对默认 plan 的差分。

替代 plan 应说明：

* 它替换了哪些 ambiguity 选择；
* 哪些子问题发生变化；
* 变化的语义内容是什么；
* 这种变化可能影响后续 ER 的哪个部分。

如果某个多义性不影响查询路径或最终结果，只需保留在 `ambiguities` 中，不必生成替代 plan。

# 输出要求

1. 必须只输出 JSON。
2. 不要输出实体、关系、属性定义。
3. 不要输出 SQL、字段名、连接键或数据库实现表达式。
4. 默认 plan 必须完整展开 steps。
5. 替代 plan 可以只输出 diff。
6. 如果不存在高影响多义性，可以只输出一个默认 plan。
7. 如果题面显式定义与外部知识冲突，默认 plan 必须以题面定义为准，并在 ambiguities 或 semantics.notes 中说明。
8. 子问题必须体现自然求解顺序，而不是物理执行顺序。
9. 子问题 output 的 grain 必须清楚，避免后续 ER 阶段混淆对象粒度。
10. 聚合计数类结果应作为 derived_measure_set 或类似阶段性输出，不应提前混入基础对象集合。
