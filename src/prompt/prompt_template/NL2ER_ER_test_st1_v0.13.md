# 任务定义

根据全部输入中可识别的用户需求语义与数据库模式相关证据，构造一个**支持该问题查询的基础逻辑实体-关系草图（Object Sketch）**。

本阶段的目标不是生成 conceptual SQL，不是还原完整数据库 schema，也不是直接生成最终查询。
本阶段只负责：

* 明确最终答案围绕什么对象或对象集合展开；
* 从最终答案出发，沿**查询计算**与**语义依赖**向后逆向推理；
* 识别支撑该问题成立所必需的**基础逻辑实体**、**基础逻辑关系**与**逻辑属性**；
* 将聚合、排序、Top-k、窗口、派生计算、局部子集等**派生语义节点**排除在基础建模之外；
* 输出一份便于后续阶段继续收敛的轻量对象草图。

这里的“逆向推理”是指：
从最终答案开始，持续追问“该答案要成立，需要通过哪些查询计算得到？依赖哪些对象、关系、属性？”，
并基于查询逻辑的聚合、排序、窗口、Top-k、临时子集等派生步骤，直到逆向推理到原子性的基础对象层。

---

# 基本原则

## 1. 反推语义依赖与查询计算

本阶段但通过追溯**语义依赖**与**查询计算**反推回答问题所需要的逻辑实体、关系与属性。

你要追溯的是：

* 最终答案是如何查询计算得出的，依赖哪些对象；
* 这些对象之间有哪些联系；
* 这些对象需要哪些基础属性才能支撑问题成立；
* 哪些条件是作用在基础对象上的约束；
* 哪些只是聚合、排序、窗口、筛选所形成的派生结果。

---

## 2. 明确每个节点的数据语义，再判断其是否为派生节点

先明确：

* 最终答案的数据语义是什么，返回的是什么；
* 最终答案的粒度是什么；
* 最终答案围绕谁进行比较、排序、聚合或筛选。
* 最终答案上有哪些条件约束；

然后判断该答案节点本身是否为派生节点。

若答案依赖于以下任一语义，则默认它是**派生节点**，不得直接作为基础实体或基础关系输出：

* 聚合结果；
* 排序或 Top-k 结果；
* 窗口结果；
* 比率、均值、计数、求和、差值、变化率等派生值；
* 过滤后的局部子集；
* 基于存在 / 不存在 / 至少一个 / 全部满足等量化条件形成的临时集合。

若答案节点是派生节点，必须继续逆向推理其得出该节点的查询计算与依赖的基础对象。

---

## 3. 基础对象与派生节点必须严格区分

对逆向推理链上的每个节点，都必须判断其属于以下哪一类：

* `base_entity`：基础逻辑实体；
* `base_relation`：基础逻辑关系；
* `base_attribute`：基础实体或基础关系上的属性；
* `derived_entity/relation/attribute`：作为查询计算中间表示的实体、关系、属性。

只有 `base_entity`、`base_relation`、`base_attribute` 可以进入最终输出主体。

`constraint` 只进入约束说明，不单独建模为实体或关系。

`derived_*` 不得进入最终输出。

---

## 4. 基础逻辑实体的定义

基础逻辑实体是问题中具有稳定语义身份、明确基础粒度、可独立指称、可重复引用的对象。

判断某个对象是否应建模为基础实体时，重点检查：

* 去掉当前问题中的聚合、排序、Top-k、窗口、局部筛选后，它是否仍独立成立；
* 它是否是用户问题中被显式或隐式引用的对象；
* 它是否可以作为多个步骤共同依赖的支撑对象；
* 它是否不是某一步临时算出来的结果集合。

基础实体的属性必须是**基础属性**，能够支持问题查询的**最小化不可派生得出的属性集**，不得包含：

* 聚合指标；
* 排名、窗口值；
* 比例、变化率、统计结果；
* 仅在中间计算中出现的临时派生列。

---

## 5. 基础逻辑关系的定义

基础逻辑关系是**两个或多个基础实体**之间具有明确独立语义的关联、交互或事件。

关系必须满足：

* 参与者必须是已定义的基础实体；
* 参与者至少为两个；
* 去掉具体实现路径后，该联系仍然成立；
* 关系本身具有明确语义，而不仅仅是计算中用到的连接动作。

以下内容默认**不是**基础关系，除非确有独立业务语义：

* 单个实体上的状态、类别、标签、子类限定；
* 仅用于属性对齐的匹配动作；
* 仅用于某个中间步骤的临时过滤条件；
* 仅通过聚合、排序、窗口定义出来的联系。

特别注意：

* 单个实体的属性限定 / 标签限定 / 状态限定，默认优先落到属性或约束，不得轻易升级为关系；
* 不允许 relation 的 participant 引用另一个 relation；
* 不允许构造只有一个 participant 的 relation。

---

## 6. 基础属性的定义

基础属性是表示基础实体或基础关系本身的性质的字段。
基础属性具有基础性和原子性：如果一个属性由其它基础属性派生推导计算得出，它就不得定义为基础属性。
基础属性只需要保留一个满足问题所有查询需求的最小必要集合。

基础属性不得包括：

* count / sum / avg / ratio / percentage / rank / score；
* lag / lead / rolling / window 结果；
* 临时子集标识；
* 仅由当前问题特定分析步骤派生出的中间值；
* 由其它基础属性派生得到的属性。

若某个值明显是“根据其它值算出来的”，则它不得表示为基础属性。
若某个值的来源仅仅是“一般数据库模式里有这个属性”/“为了描述完整性需要这个属性”，但是问题没有明确定义，则不得表示为基础属性。

---

## 7. 实现证据只作支撑，不主导建模

数据库模式相关证据、表名、列名、外部知识只能作为落地支撑。

它们可以帮助你：

* 补充对象的可识别性；
* 判断某些属性是否可能存在；
* 确认某些对象的实现证据是否明确。

它们不得：

* 替代用户问题本身的语义依赖；
* 主导基础对象的定义；
* 把实现字段直接当成基础逻辑对象名；
* 把某个实现表直接等同于最终基础实体或基础关系。

# 分析步骤

在输出最终 JSON 之前，必须按如下步骤，完成整个分析流程。
**禁止跳过分析**直接生成最终对象草图。

---

## Step 0. 分析问题背景，区分用户需求与实现提示，并设置输出语言

先重述问题，分析问题背景，并区分：

* 该问题可能来源于哪些专业领域；问题中的表述和名词术语应该如何理解；
* 哪些内容属于用户真正的分析需求；
* 哪些内容属于数据库模式或语义的实现提示；
* 哪些内容属于额外的业务知识，哪些业务知识与问题相关；
* 这些实现线索能支撑哪些步骤落地，但又不应替代哪些问题语义。

专业术语的语义明确：对问题中涉及的专业术语基于自然语言定义其语义；后续所有的语义分析全部基于该术语理解进行；（本步骤明确不得预设实体-关系-属性定义，仅基于常识进行描述）

实现提示仅为辅助：实现提示只能作为落地支撑，不能直接替代用户问题本身的求解结构。

同时，明确用户输入问题用的语言；后续输出的实体/关系/属性定义需要与用户属于语言一致。

输出如下内容：
* 问题背景与领域：
* 用户需求：
* 数据实现提示：
* 术语定义：
* 输出语言：
---

## Step 1. 问题分解


问题分解不得给出任何实体/关系/属性的假设，仅仅用自然语言进行推理。
它是一组按顺序展开的**命名子问题**，用于表达：

* 最终结果是什么；
* 为了得到该结果，必须先求出哪些阶段性结果；
* 每一步的主要计算动作是什么；
* 哪些隐含约束必须在该步被显式考虑。


### Step 1.1 将问题拆解为命名子问题

围绕最终结果的形成过程，将问题拆解为若干按计算顺序展开的**命名子问题**。
每个子问题都应回答：为了得到最终结果，必须先求出的哪一个阶段性结果什么。

每个子问题定义为一个自然语言描述的查询计划：一个可以说明“这一步在求什么”的求解节点。
必须用明确具体的陈述句描述阶段性结果，包含问题里提及的所有限定细节，明确所有需要返回的数据。

### Step 1.2 明确最终结果口径

从最终结果出发，说明：

* 用户最终想得到什么结果；
* 最终结果中一行代表什么；
* 用户明确要求输出哪些内容；
* 结果围绕什么分析主轴展开；
* 是否存在明确的分组、排序、比较、聚合、时间或角色口径。

本步骤只负责明确**结果定义**，不要在这里提前把基础概念对象完整摊开。

---

## Step 2. 从答案要求，根据语义依赖反向推理

逆向推理基于子问题，从答案开始，根据子问题序列反推基础查询语义单元。

## 逆向推理分析

逆向推理时必须同时分析两部分内容：

(1) 首先进行当前子问题的实体关系抽取
首先，从当前子问题提取具独立的实体类型和关系类型，作为当前子问题语义依赖的语义单元; 为了保证查询计算的正确性，必须先明确语义单元的构成。

实体与关系可以理解为该子问题对应查询的逻辑表：该子问题的查询逻辑需要基于这些逻辑表进行；

语义优先分解为多个实体类型、关系类型的单元，而不是简单的用属性挂载：
若某个概念本身可以被稳定标识、并且在语义上应作为独立对象存在，则应优先将其建模为实体单元，并通过关系连接到其它实体，而不是将其压缩为某个实体的附属属性。

命名实体检测：对于问题中出现的命名实体实例或实体集合的字段：例如名称和标识符，必须将该字段表征的实体明确建立为实体类型，不得将其仅视作属性或约束条件处理；




(2) 其次判断当前子问题的查询逻辑  

其次，按照SQL支持的数据操作与函数语义来定义查询逻辑；但这里的目的不是生成 SQL，而是用标准 SQL 语义准确表达当前子问题是如何由下层子问题推导得到的。必须明确指出当前子问题的查询在语义上依赖了哪些下层实体、关系、属性和条件，以及这些依赖在查询计算中分别承担什么作用。

查询逻辑的多义性：一个逻辑查询可能以多种不同的形式生成，包括不同的实体关系结构，实体和关系可定义不同的逻辑属性以及使用不同的计算方式；对于查询逻辑，需要明确考虑可能的多种标识，在此基础上根据如下规则：
实体-关系层面：优先考虑合理地将语义概念元素表示为独立的实体-关系集合，而不是将其作为属性表示；
属性层面：对于具有多种表示可能性的属性，优先考虑符合用户问题的描述和定义口径，设计最直接的属性定义，且满足属性原子性、最小化原则；不允许构造额外在原问题表述中没有明确的属性定义。

实体 - 关系抽取原则：优先构建完整的**独立性**的**原子化**的实体和关系集合。在问题拆解过程中，如果一个概念表示为独立、可标识的实体:例如使用名称或标识符指代，则应该优先构建为实体单元和到其它实体的关系，而不是作为其它实体的属性子问题附属存在。

查询逻辑定义原则：按照标准SQL数据操作与函数定义查询逻辑；

对每一个逆向推理到的子问题，都必须显式判断其求解内容类别：

* `base_entity`
* `base_relation`
* `base_attribute`
* `derived_entity`
* `derived_relation`
* `derived_attribute`

如果某节点仍然是 `derived_node`，则继续逆向推理，直到追到基础层。

---

## Step 3. 确定基础逻辑实体

在完成逆向推理后，保留真正的基础逻辑实体。
实体是问题中具有稳定语义身份、明确基础粒度、可通过属性明确标识和重复引用的对象。

* 基础逻辑实体类型: 明确该实体类型的详细语义，每个实体实例指代什么，是否可标识，在问题中的作用；

对每个基础实体，都要明确：

* `name`
* `desc`
* `grain`
* `key_attributes`
* `attributes`

要求：

* `name` 必须符合问题语义，优先采用问题里的措辞口径；
* `grain` 必须准确描述一个实例代表什么；
* `key_attributes` 必须是标识该实体的基础属性；
* `attributes` 只能保留基础属性；
* 若某属性只是计算中间值，不得写入。

基础逻辑属性的定义：

对每个实体的基础逻辑属性，必须显式分析其语义，必须有从输入的明确来源，满足：

* 完整性：支持所有后续步骤与表示的属性派生计算需求；满足所有语义表示，连接，条件约束的字段需求。
* 最小化：当某个属性可以通过与其他属性的连接、计算得到时，不应直接在逻辑表中定义为独立属性。
* 语义准确性：明确语义的合理归属对象；
* 多义性分析：如果某种逻辑属性定义存在多种表示可能性，必须明确说明其它的属性表示可能性，在sql实现选择以最符合标准数据库设计与业务常识的形式表示；
* 逻辑属性的定义必须完全来源于问题：每个属性必须用于表示语义，支持计算或条件约束，禁止基于常识：“从常识上来看”，或为“可读性”，“定义完整性”擅自添加任何额外属性。

标识符属性key_attributes：若用户没有直接给出天然标识属性或可作为标识符属性的自然键，则允许构建补充标识符；补充标识符必须带上 `_surrogate_id` 作为后缀，以明确这是为了定义的可行性构建的标识符槽位。


---

## Step 4. 确定基础逻辑关系

在完成逆向推理后，只保留真正的基础逻辑关系。
关系是**两个或多个实体类型**之间具有明确独立语义的关联、交互或事件，用于表达实体之间实际存在的联系。参与关系的实体具有角色：一个基础实体可以以不同角色在关系中出现多次。

* 基础逻辑关系类型：明确该关系类型的详细语义，每个关系实例指代什么，是否可标识。参与该关系的必须为两个以上的角色化逻辑实体类型，在问题中的作用；

对每个基础关系，都要明确：

* `name`
* `desc`
* `grain`
* `participants`
* `attributes`

其中：

* `participants` 中每个参与者必须包含：
  * `entity`
  * `role`

要求：

* `participants` 中引用的实体必须来自 `entities`；
* 每个关系至少包含两个参与者；
* 不允许 participant 引用 relation；
* `attributes` 只能保留该关系本身的基础属性；
* 不得把单个实体上的状态/标签/类别限定错误建模为关系。

对每个关系的基础逻辑属性，必须显式分析其语义，明确满足：完整性，最小化，语义准确性，多义性分析。


---

# Step 5. 输出

完成上述所有分析步骤后，才能输出最终的基础逻辑实体-关系草图，格式如下：

```json
{
  "answer_target": {
    "name": "",
    "grain": "",
    "is_derived": true,
    "reason": ""
  },
  "entities": [
    {
      "name": "",
      "desc": "",
      "grain": "",
      "key_attributes": {
        "attr": "attr_semantics"
      },
      "attributes": []
    }
  ],
  "relations": [
    {
      "name": "",
      "desc": "",
      "grain": "",
      "participants": [
        {
          "entity": "",
          "role": ""
        }
      ],
      "attributes": []
    }
  ]
}
```

# 输出要求

* 输出必须是单个合法 JSON 对象；
* 不得输出 conceptual SQL；
* 不得输出 CTE；
* 不得输出执行步骤；
* `entities` 与 `relations` 只保留基础层对象；
* 所有说明使用与用户输入一致的语言；
* 字段值必须具体、清晰，不得使用 `...`、`same as above`、`TBD` 等占位表达。
