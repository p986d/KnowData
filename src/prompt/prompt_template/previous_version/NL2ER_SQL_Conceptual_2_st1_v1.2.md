
## 任务定义

你的任务是根据全部输入中可识别的用户需求语义与数据库模式相关证据，识别并组织当前问题中的**命名查询单元（Named Query Units）**，构造一个**面向问题表达的概念查询骨架（Conceptual Query Skeleton）**。

这里的概念查询骨架不是要求生成一条可直接执行的数据库 SQL，或是完整的数据库 schema 结构。
它用于表达：

* 用户真正想分析的语义对象与分析主轴；
* 问题在逻辑上应如何被逐步想通；
* 哪些中间语义结果需要被显式保留，以清楚表达问题的求解过程；
* 后续语义步骤如何依赖前序步骤逐步形成；
* 数据库模式相关证据如何用于将需求语义对齐到可能的实现结构。

本任务的目的是将用户问题组织为**符合用户表述口径的概念查询骨架**，明确哪些语义成分应被显式保留为命名查询单元，以及这些查询单元之间的依赖结构。

注意：本阶段的输出首先是**问题表达层 / 推理表达层**，不是最终的 ER 检索规格。
本阶段不负责定义查询单元的字段属性集合，也不负责生成最终的概念 SQL。

---

## 核心原则：并非所有语义成分都应成为命名查询单元

问题中的对象、字段、条件、连接依据、分组聚合要求等，都属于需要识别的语义成分；
但**并非所有语义成分都应被显式组织为命名查询单元**。

只有在当前问题中满足以下条件的语义成分，才值得被显式命名为查询单元：

1. 具有相对独立且稳定的语义边界，能够单独说明“它是什么”；
2. 能够单独定义粒度与成员范围，能够说明“一行代表什么”；
3. 在当前问题的求解过程中，值得作为阶段性语义结果被后续步骤继续引用；
4. 在当前问题中需要被显式保留，而不只是一次性临时桥接、局部匹配或实现支撑步骤。

其中需要特别注意：

* 用户需求中被直接表达、且对问题成立有直接作用的对象间连接，不应因为其属于连接就自动退化为局部 `JOIN ... ON ...` 条件；
* 但并非所有连接都必须拆成独立查询单元；只有当该连接在问题表达过程中形成值得单独保留和继续引用的中间语义结果时，才应显式组织为查询单元；
* 命名查询单元优先服务于**清楚表达查询计划**，而不是提前完成最终基础实体 / 关系 / 连接模型的收敛；
* 对于数据实现提示中的空间映射、编码映射、桥接路径、键关联路径等实现相关内容，不单独组织为概念层查询单元，而应隐藏在相应查询单元内部作为实现支撑表达；
* 即使输入中显式提供了某个需求语义单元对应的数据库实现线索，这些实现对象也仍仅属于该语义单元内部的实现支撑来源，不得因此上升为新的概念层查询单元。

其余语义成分应作为：

* 查询单元的属性；
* 属性上的常值约束；
* 查询单元之间的局部连接条件或属性匹配条件；
* 实现支撑路径；
* 分组、聚合、排序等分析操作

附着在相关查询单元上，而不应自动成为独立查询单元。

## 2.2 值得单独命名的查询语义单元

**值得单独命名的查询语义单元**，指的是在当前问题中具有相对独立且稳定的语义边界、能够单独定义粒度与成员范围，并且值得作为整体被后续查询步骤继续引用的查询语义对象。

只有这类语义单元才应被显式组织为命名查询单元。

需要注意：

* 对象语义单元、关系类型语义单元，以及在当前问题中需要被独立保留的连接语义单元，都可能成为命名查询单元；
* 连接语义单元是否需要显式组织，不以前置地区分其属于“稳定关系类型”还是“属性匹配”为条件；只要该连接在问题表达中需要被独立保留，就可以先被视为查询单元候选；
* 数据库实现提示中的实现相关来源：表、列、值等，需要作为需求语义的实现，被包含在相关语义单元内部，不得独立建模或影响命名查询单元。

下列内容默认**不应**单独命名为查询单元，除非它们在当前问题中确实形成独立查询步骤或独立中间结果：

* 关系的参与实体的不同角色：角色语义应包含在关系中，而不是独立作为查询单元；
* 单纯的属性常值约束；
* 单纯的时间范围、类别范围、状态范围；
* 单纯的一次性跨单元属性匹配或时间对齐；
* 单纯的空间映射、编码映射、键关联、桥接路径；
* 只为一次局部连接服务的临时中间结果；
* 仅作为实现支撑而存在的局部步骤。

## 2.3 查询语义单元

在本任务中，只有被判定为值得单独命名的语义单元，才进一步组织为以下几类命名查询单元与来源对象。

### 1. 核心查询单元（Core Query Unit）

起始查询单元是指：**在当前概念查询计划中，不依赖此前已命名查询单元、作为其它查询单元依赖对象的起始查询单元**。

它通常具有以下特点：

* 具有基础性与原子性；
* 具有相对稳定的语义边界；
* 可以单独定义粒度与成员范围；
* 可以直接从来源对象建立；
* 作为查询计划中的起始阶段性语义结果存在。

注意：

* 核心查询单元是一种**查询计划中的位置角色**，代表基础性、起始性；其它的查询单元应建立在已有核心查询单元及已保留的前序查询单元之上展开；
* 实体型的核心查询单元不依赖任何其它查询单元；关系 / 连接型的核心查询单元不依赖参与的实体核心查询单元以外的任何其它查询单元。

### 2. 后续查询单元（Subsequent Query Unit）

后续查询单元是指：**由已有查询单元经由筛选、组合、角色化、匹配、对齐、聚合、重命名、粒度变化或其它语义变换后形成的后续查询单元**。

后续查询单元的作用是：

* 组织概念查询结构中的阶段性查询结果；
* 表达某种阶段性必要的中间语义结构；
* 承载连接语义、角色信息、跨对象属性对应、条件约束、上下文补充或分析中间结果；
* 为后续表达提供可复用的中间查询输入。

注意：

* 这里的“后续”只表示其在**当前查询计划中的依赖位置**；
* 它不是最终 ER 提取阶段中“派生实体 / 派生关系 / 派生连接”的正式结论；
* 单纯的一次性桥接、局部匹配结果或局部实现路径，通常不应单独命名为后续查询单元。

### 3. 实现支撑来源（Implementation Support Source）

实现支撑来源是由数据库模式相关证据引入、用于支撑需求语义落地的实现来源或实现背景。

它们通常来自：

* schema / table / column 提示；
* 主键、外键、桥接表、映射表；
* 时间列、空间列、编码列；
* 其它能够揭示实现承载位置、连接路径或属性来源的数据库线索。

实现支撑来源的作用是：

* 为概念查询结构提供可能的实现落点；
* 支撑对用户需求语义的规范化重写；
* 提供属性来源、连接依据或路径展开的实现背景。

实现支撑的定义规则：
实现支撑需要用后缀明确分类：
根据问题语义推知该来源对象必然存在，但是来源对象的数据实现未明确在提示中给出，此时必须使用 `*_source`。
只有当输入中明确提供了某来源对象的具体数据库模式相关证据（如具体 schema、table、column 或其它可直接指向实现对象的线索）时，才可使用 `*_impl`。

注意：

* 实现支撑来源默认不直接成为命名查询单元；
* 若当前问题需要引用某类来源对象，但输入未提供其明确的数据库模式相关证据，必须使用 `*_source` 作为抽象来源占位；不得假设存在实现，并写为 `*_impl`；
* 只有输入存在明确的数据库模式相关证据，才能使用 `*_impl` 后缀；
* `*_impl` 与 `*_source` 都不是独立查询单元类型。

### 4. 关系类型 / 连接查询单元建模

对于关系类型 / 连接一类的语义要素，可以将其显式组织为关系型或连接型查询单元，其首要职责是表达参与对象之间的关系类型定义或属性连接约束；不得默认写成“表达连接完成后形成的复合实体类型结果”。

这类查询单元应优先回答：

* 连接的是哪些对象；
* 各对象在连接中的参与角色是什么；
* 连接基于哪些属性、条件或约束成立；
* 连接本身是否承载局部约束或连接属性；
* 一行代表一个什么关系类型实例或连接约束实例。

若确有需要构造复合实体类型结果，也应建立在已显式保留的关系类型 / 连接查询单元之上，而不应直接用复合实体类型结果替代本应保留的连接语义表达。

注意：在本阶段中，是否把某条关系 / 连接显式写成独立查询单元，首先取决于它是否有助于清楚表达查询计划。

## 2.4 连接语义的说明

在概念查询结构中，对于**已被判定为需要显式保留的连接语义单元**，可进一步说明其内部连接性质。

连接语义通常可表现为以下几种倾向：

### 1. 关系类型性连接（Relation-like）

指该连接更接近一个需要被独立保留的关系类型语义，通常具有以下特征之一：

* 参与对象结构明确；
* 存在稳定的参与角色；
* 连接自身可能承载属性或局部约束；
* 去掉具体实现路径后，该连接仍然是当前问题中的重要语义结构。

### 2. 属性匹配性连接（Connection-like）

指该连接主要用于在对象之间完成属性附着、上下文补充或分析所需的对齐，通常具有以下特征之一：

* 主要作用是补充上下文或附着属性；
* 更依赖时间对齐、类别对齐、同值匹配、条件匹配等方式；
* 连接本身通常不作为独立关系类型对象保留。

### 3. 实现支撑路径（Implementation Support Path）

指该连接在落地时所依赖的实现路径、桥接路径或局部实现依据，例如：

* 键关联；
* 桥接表路径；
* 空间映射；
* 编码映射；
* 其它实现层的连接步骤。

需要注意：

* 实现支撑路径不是概念层连接语义单元的同级替代类型；
* 它通常作为连接语义单元内部的实现支撑而存在；
* 不应直接上升为概念层对象。

注意：上述 `relation-like` / `connection-like` / `implementation-support` 更偏向**概念查询计划中的表达辅助标签**。

# 分析步骤

在输出命名查询单元结果之前，必须先基于以下步骤完成分析。**禁止直接输出结果**；

## Step 0. 区分用户需求与实现提示

重述问题，区分用户需求的描述、外部知识和实现提示这三类内容，明确：

* 用户真正提出的问题是什么；
* 外部知识是否参与了问题解释；
* 是否存在实现提示；
* 若存在实现提示，其作用是提供实现支撑，而不是直接定义概念层语义对象。

## Step 1. 问题口径整理与自然增量式推理

先对用户问题进行口径整理，明确：

* 用户最终想得到什么结果；
* 结果粒度是什么，即结果中一行代表什么；
* 用户明确要求输出什么内容；
* 用户显式给出的筛选条件、时间范围、空间范围、类别范围、排序或排名要求是什么；
* 问题中是否存在外部知识冲突、表述歧义、方向歧义、角色歧义、范围歧义或其它待验证点。

随后，围绕问题主轴写出一段**自然推进的增量式推理**。这段推理应从最终结果出发，逐步说明：

* 结果主要围绕哪些对象、关系或连接展开；
* 为了让问题成立，还需要依次引入哪些对象、关系、连接或上下文；
* 每个新增语义成分为什么必要，它解决的是问题中的哪一部分；
* 哪些角色、方向、先后关系、比较基准、时间锚点、空间锚点或参考对象是关键；
* 哪些条件定义整个问题的整体范围；
* 哪些条件只定义局部分析口径、局部子集、局部窗口或局部中间结果；
* 哪些中间结果值得被后续继续引用并显式保留；
* 哪些步骤只是一次性局部分析动作，不应升格为命名查询单元。

这段推理必须采用**自然段落**表达，不使用过度结构化的字段化步骤列表；
推理保持依赖关系清晰、前后推进明确。

注意：

* 本步骤的重点是把问题逻辑上如何成立讲清楚，而不是立即枚举查询单元；
* 推理中可以提到对象、关系、连接、角色、条件和分析动作；
* 数据实现不参与问题主轴与语义对象的定义；实现提示只能作为落地支撑背景，不得主导概念推理。

## Step 2. 从自然增量式推理中回收命名查询单元

基于 Step 1 中已经形成的自然增量式推理，识别其中哪些语义节点应被显式组织为命名查询单元。

注意：**命名查询单元必须从上一步已经完成的推理中回收，不得脱离该推理重新平铺枚举语义成分。**

对于推理中出现的关键语义节点，必须进行如下判断：

(1) 问题相关内容列举：
完整列举问题中提及该成分的内容，以及在 Step 1 推理中该成分承担的作用，作为该查询单元表达的基准来源；

(2) 是否构建为命名查询单元：

* 适合作为基础对象直接建立的核心查询单元；
* 适合作为中间表示，依赖已有查询单元形成的后续查询单元；
* 还是不应该独立作为查询单元，而应回落为其它单元的属性、角色、条件、局部连接表达、实现支撑或一次性分析操作。

(3) 查询单元类型：
该查询单元主要表达的是实体类型语义、关系类型语义，还是连接语义；
若是关系 / 连接，需要说明参与对象及其角色；
必要时可标注其更偏 `relation-like` 或 `connection-like`；

(4) 依赖关系判断：
若某语义节点适合作为后续查询单元，需要明确它依赖哪些已保留的前序查询单元；
这里的依赖关系是概念查询计划中的语义依赖，不要求提前写成 SQL 结构；
同类对象在关系 / 连接中的不同角色，应在关系 / 连接查询单元中表达，不应仅因角色不同而重复构造多个实体查询单元；

(5) 核心查询单元补充：
核心查询单元集合必须足以支撑所有后续查询单元；
若某个后续查询单元缺少必要的前序基础对象，必须补充相应核心查询单元，不得以简单的虚构实现来源 `*_source` / `*_impl` 代替概念层对象；

(6) 禁止将数据实现 / 数据源建模为查询单元：
在给出数据库实现提示时，若数据库实现中的要素在用户需求中未显式提及，则将其视为实现支撑，不应被显式组织为命名查询单元，也不得影响查询单元的命名；实现细节应被包裹在查询单元内部，或留待后续阶段处理。

判断时遵守以下原则：

* 能单独定义“这一步在求什么”，且能单独说明“一行代表什么”的，可作为命名查询单元候选；
* 若某语义单元需要建立在已有查询单元之上，通过组合、角色化、属性匹配、上下文附着、条件组合或其它语义变换后才成立，则更适合作为后续查询单元候选；
* 若某语义单元表达的是对象间的关系类型定义，或多个对象之间基于属性成立的连接约束，并且该语义在当前查询计划中需要被后续继续引用，则可以显式组织为关系型或连接型查询单元；
* 不得用“带连接上下文的实体类型”“聚合前宽表”“附着多个外部属性后的复合实体类型单元”替代本应独立保留的关系类型 / 连接查询表达；
* 保持角色区分：对于同类对象在关系 / 连接中的不同角色，必须在关系 / 连接查询单元中显式区分，不得忽略角色概念；同时，不应将角色区别表现为不同的查询单元定义；
* 单纯的属性约束、一次性局部匹配、实现桥接路径、一次性临时中间结果，默认不单独命名为查询单元；
* 查询单元定义必须严格按照用户需求描述口径；实施细节必须包裹在查询单元内部，不得影响单元本身的概念定义。

组织命名查询单元时，可以进行以下操作：

1. 将一个语义节点定义为一个命名查询单元；
2. 将多个语义节点提取 / 合并为一个命名查询单元；
3. 从一个较大的语义节点中分解出多个命名查询单元。

## Step 3. 命名查询单元整合优化

在初步得到命名查询单元后，对整体结果进行一次全局检查与整合优化。

重点检查：

* 是否所有被保留的查询单元都确实对应 Step 1 推理中值得持续保留的语义节点；
* 是否存在本应回落为属性、条件、局部连接或分析操作，却被误升格为查询单元的内容；
* 是否遗漏了对问题成立至关重要、且在推理中被反复引用的对象、关系或连接；
* 核心查询单元集合是否足够支撑后续查询单元；
* 后续查询单元的依赖关系是否清晰；
* 是否存在命名粒度不一致、边界重叠、语义重复或角色表达不清的问题；
* 是否有实现支撑内容误进入概念层查询单元；
* 查询单元整体是否足以清楚表达问题求解过程，而不至于过重、过碎或过度对象化。

必要时可以对查询单元进行删减、合并、拆分、重命名或依赖关系调整。

---

## 输出格式

基于上述分析，输出最终的查询单元定义：

```json
{
  "problem_understanding": {
    "restated_question": "",
    "result_grain": "",
    "required_outputs": [],
    "explicit_constraints": [],
    "ordering_or_ranking": [],
    "external_knowledge_conflicts": [],
    "open_ambiguities": []
  },
  "logical_reasoning": "",
  "query_units": [
    {
      "unit_name": "",
      "unit_role": "core | subsequent",
      "semantic_type": "entity | relation | connection",
      "participants": [
        {
          "role": "",
          "object": ""
        }
      ],
      "dependency_units": [],
      "row_semantics": ""
    }
  ]
}
```

输出要求：

* `problem_understanding` 用于稳定表达问题本身；
* `logical_reasoning` 必须是自然段落形式的增量式推理正文，而不是字段化 step list；
* `query_units` 必须从 `logical_reasoning` 中回收，不得与其脱节；
* `unit_name` 仅对被保留为命名查询单元的对象填写；
* `unit_role` 用于标记其是核心查询单元还是后续查询单元；
* `semantic_type` 表示该查询单元主要表达实体、关系或连接语义；
* `participants` 仅对关系 / 连接型查询单元填写；
* `dependency_units` 仅对后续查询单元填写；
* `row_semantics` 明确说明“一行代表什么”。

禁止事项：

* 不得跳过 Step 1 的自然增量式推理直接输出查询单元；
* 不得在 Step 1 中直接给出最终 ER 层属性、条件或实现字段；
* 不得把数据库实现提示直接改写成概念层查询单元；
* 不得把局部条件、局部桥接结果、临时分析步骤机械升格为查询单元；
* 不得让 `logical_reasoning` 退化为 SQL 草稿、CTE 草稿或机械分点枚举。
