
# 用户需求建模任务

# 一：任务定义

你的任务是：根据全部输入中可识别的用户需求语义与数据库模式相关证据，构造一个**面向问题表达的概念查询结构（Conceptual Query Plan）**

这里的概念查询结构不是要求生成一条可直接执行的数据库 SQL，或是完整的数据库schema结构。
它是一条作为中间语义表示的**概念 SQL / SQL-like 查询伪代码**，用于表达：

* 用户真正想分析的语义对象与分析主轴；
* 语义对象之间的关系、连接与条件约束；
* 哪些语义对象需要构建为基础实体/关系；后续的中间表示和最终查询完全基于这些基础实体/关系进行；
* 哪些语义对象需要显式作为中间表示，以明确阶段性产物并提供给最终查询；
* 数据库模式相关证据如何用于将需求语义对齐到可能的实现结构。

本任务的目的是将用户问题组织为**符合用户表述口径的概念查询结构（conceptual SQL）**，并通过SQL清晰表示基础的实体、关系、属性与条件。

---

## 核心原则：并非所有语义成分都应成为 CTE

问题中的对象、字段、条件、连接依据、分组聚合要求等，都属于需要识别的语义成分；
但**并非所有语义成分都应被显式组织为概念 SQL 中的命名查询单元**。

只有在当前问题中同时满足以下条件的语义成分，才值得被显式命名为查询单元（CTE）：

1. 具有相对独立且稳定的语义边界，能够单独说明“它是什么”；
2. 能够单独定义粒度与成员范围，能够说明“一行代表什么”；
3. 值得作为基础实体/关系，或者阶段性中间表示实体/关系，被后续查询步骤继续引用，而不只是一次性临时桥接或局部匹配。

其余语义成分应作为：

* 查询单元的属性；
* 属性上的常值约束；
* 查询单元之间的连接条件或属性匹配条件；
* 实现支撑路径；
* 分组、聚合、排序等分析操作

附着在相关查询单元上表达，而不应自动成为独立 CTE。

---

## 输入范围

本任务的输入中可能包含：

* 用户原始需求描述；
* 用户在需求描述中直接提及的数据库实现相关信息，单独提供的数据库模式相关提示，例如 schema、table、column；
* 也可能完全没有数据库模式相关信息。

因此，不得预设数据库模式相关信息一定存在，也不得预设其一定与用户需求严格分离。应统一从全部输入中识别：

* 哪些内容属于用户希望表达和分析的语义；
* 哪些内容属于数据库模式相关证据；
* 哪些内容应进入概念查询结构作为命名查询单元；
* 哪些内容仅作为属性、约束、连接依据或实现支撑存在。

---

## 输出目标

最终输出的是：

* SQL 形式的 **概念查询计划**

而不是根据具体数据库模式的可执行 SQL。

输出的核心目的是：覆盖用户问题中真正需要表达的语义，并在有数据库模式相关证据时尽量与其可支撑的实现结构对齐。

# 二：概念查询结构（conceptual SQL）

本任务应先从全部输入中识别问题的语义成分，再判断哪些语义成分值得被显式组织为命名查询单元，最后基于这些命名查询单元构造一个概念查询结构，以表达问题涉及的实体、关系、属性与条件约束。

这里的概念 SQL 不是针对具体物理数据库 SQL，而是一个基于问题表达的概念查询计划。

---

## 2.1 语义成分的定义

语义成分是当前问题中一个可识别、对问题成立有语义作用的组成要素。
它可以是：

* 对象概念；
* 字段概念；
* 条件相关概念；
* 连接依据；
* 分组、聚合、比较、排序等分析操作相关概念；
* 数据库模式相关实现线索。

注意：

* 语义成分是问题中的组成要素；
* 但并非所有语义成分都应被显式组织为概念 SQL 中的命名查询单元。

---

## 2.2 值得单独命名的查询语义单元

**值得单独命名的查询语义单元**，指的是在当前问题中具有相对独立且稳定的语义边界、能够单独定义粒度与成员范围、能够承载自身属性或局部约束，并且值得作为整体被后续查询步骤引用的查询语义对象。

只有这类语义单元才应被显式组织为概念 SQL 中的 CTE。

下列内容默认**不应**单独命名为 CTE，除非它们在当前问题中确实形成独立查询单元：

* 单纯的属性常值约束；
* 单纯的时间范围、类别范围、状态范围；
* 单纯的跨单元属性匹配或时间对齐；
* 单纯的空间映射、编码映射、键关联、桥接路径；
* 只为一次局部连接服务的临时中间结果；
* 仅作为实现支撑而存在的局部步骤。

---

## 2.3 查询语义单元的分类

在本任务中，只有被判定为值得单独命名的语义单元，才进一步组织为以下两类命名查询单元：

### 1. 基础查询单元（Base Query Unit）

基础查询单元是指：在当前问题中可以先被独立识别和建立为一个基础查询单元的语义对象。

它通常具有以下特点：

* 具有相对稳定的语义边界；
* 可以单独定义粒度与成员范围；
* 可以承载自身属性及局部约束；
* 可以作为后续派生查询单元的来源。

基础查询单元通常对应一个 `*_base` CTE。

注意：

* 基础查询单元可能对应最终 ER 中的实体类型、关系类型，或仅作为概念查询结构中的基础承载单元；
* 并非所有基础查询单元都必须进入最终骨架。

### 2. 派生查询单元（Derived Query Unit）

派生查询单元是指：由已有基础查询单元或其它派生查询单元，经由筛选、组合、映射、匹配、聚合、重命名、粒度变化或其它查询变换后形成的中间查询语义单元。

派生查询单元的作用是：

* 组织概念查询结构中的阶段性查询结果；
* 表达“经过限定、补充上下文、映射、汇总或重组后”的中间查询语义；
* 为最终主查询提供可复用的中间查询输入。

派生查询单元通常对应一个 `*_derived` CTE。

注意：

* 派生查询单元是概念查询结构中的中间查询承载单元，不默认被视为独立实体或独立关系；
* 只有当某个派生结果形成相对稳定的中间语义、具有可说明的粒度，并且值得作为整体被后续步骤继续引用时，才应被显式组织为 `*_derived`；
* 单纯的一次性桥接、局部匹配结果或局部实现路径，通常不应单独命名为派生查询单元。

### 3. 实现支撑来源（Implementation Support Source）

实现支撑来源是由数据库模式相关证据引入、用于支撑需求语义落地的实现来源或实现背景。

它们通常来自：

* schema / table / column 提示；
* 主键、外键、桥接表、映射表；
* 时间列、空间列、编码列；
* 其它能够揭示实现承载位置、连接路径或属性来源的数据库线索。

实现支撑来源的作用是：

* 为概念查询结构提供可能的实现落点；
* 支撑对用户需求语义的规范化重写；
* 提供属性来源、连接依据或路径展开的实现背景。

注意：

* 实现支撑来源默认不直接成为命名查询单元；
* 它们通常作为 `FROM` / `JOIN` 中引用的来源对象出现；
* 实现支撑来源不自动成为最终 `entity_type` / `relationship_type`。

---

## 2.4 连接语义的分类

在概念查询结构中，查询单元之间的连接应区分为以下三类：

### 1. 稳定语义关系（Stable Semantic Relation）

指的是：去掉具体实现路径以后，两个对象之间仍然成立、且在当前问题中需要被独立保留的稳定业务语义连接。

这类连接是最终 `relationship_type` 的候选。

### 2. 语义对齐 / 属性匹配（Semantic Alignment / Attribute Matching）

指的是：为了补充上下文、附着属性、完成分析所需的跨对象对齐，但未必需要作为最终独立关系保留的连接。

例如时间对齐、类别对齐、同值匹配、条件匹配等。

这类连接通常不直接成为最终 `relationship_type`，除非在当前问题中形成需要独立保留的稳定关系。

### 3. 实现支撑连接（Implementation Support Link）

指的是：只用于当前数据库实现落地的连接路径、桥接路径或局部实现依据。

例如键关联、桥接表路径、空间映射、编码映射等。

这类连接不应直接成为最终 `relationship_type`。

---

## 2.5 用户需求到概念查询结构的映射规则

用户需求中与问题成立直接相关的对象、字段、实例值、条件、连接依据和分析要求，应尽量在概念查询结构中得到对应表达。

它们可以分别落实为：

* 查询单元的属性；
* 属性上的常值约束；
* 查询单元之间的属性匹配条件；
* 查询单元之间的稳定语义关系；
* 局部或跨单元约束；
* 分组、聚合、排序等分析操作；
* 最终分析单元的输出要求。

映射时应遵守以下原则：

* 用户提及的对象概念，优先映射为查询单元候选；
* 用户提及的字段，优先映射为相关查询单元的属性；
* 用户提及的实例值、时间值、类别值、范围值，优先映射为相关属性上的常值约束或范围约束；
* 用户提及的对象关联，应判断其属于稳定语义关系、语义对齐/属性匹配，还是实现支撑连接；
* 不要求所有需求片段都被对象化或单独组织为查询单元；只有当某一语义成分形成独立查询语义时，才考虑将其提升为命名查询单元。

---

## 2.6 概念 SQL 的结构说明

概念查询结构应采用**概念 SQL**的方式组织。这里的概念 SQL 不是可执行 SQL，而是用接近 SQL 的形式表达：

* 哪些查询语义单元被组织为基础查询单元；
* 哪些查询语义单元被组织为派生查询单元；
* 当存在数据库模式相关证据时，这些查询单元如何引用实现来源；
* 查询单元之间的连接、约束与依赖如何组织。

### 1. 两类命名对象

概念 SQL 中需要区分两类命名对象：

* **CTE**：概念查询结构中的命名查询单元，用于承载基础查询单元或派生查询单元；
* **来源对象**：CTE 内部 `FROM` / `JOIN` 所引用的对象，用于表示概念来源或实现来源。

### 2. CTE 的命名规则

CTE 只使用以下两类后缀：

* `*_base`：表示基础查询单元；
* `*_derived`：表示派生查询单元。

其中：

* `*_base` 用于表达可先独立建立的基础查询单元；
* `*_derived` 用于表达由已有基础或派生单元经过筛选、组合、映射、匹配、聚合等形成的中间查询语义。

### 3. 来源对象的命名规则

当概念 SQL 需要引用数据库模式相关证据中的实现来源时，来源对象可使用 `*_impl` 后缀。

`*_impl` 表示该对象是由数据库模式相关证据支撑的实现来源，用于为 `*_base` 或 `*_derived` 提供承载位置、属性来源或连接依据。

注意：

* `*_impl` 不是独立 CTE 类型；
* 它仅是 CTE 内部引用的来源对象命名后缀。

### 4. 连接语义的表达方式

在概念 SQL 中，查询单元之间的连接既可以通过 `JOIN ... ON ...` 表达，也可以在必要时通过简洁注释标明该连接在当前问题中的语义性质。

当某条连接的语义性质对后续 ER 抽取十分关键时，可使用如下简洁注释辅助表达：

* `-- relation: ...`
* `-- alignment: ...`
* `-- implementation: ...`

这些注释仅用于帮助表达该连接属于：

* 稳定语义关系
* 语义对齐 / 属性匹配
* 实现支撑连接

注释是可选的，但当连接语义容易混淆时，建议显式标明。

### 5. 使用原则

构造概念 SQL 时，应遵守以下规则：

* 并非所有识别出的语义成分都必须写成 CTE；只有值得单独命名的查询语义单元才应显式组织为 `*_base` 或 `*_derived`；
* 单纯的属性约束、跨单元属性匹配、实现桥接路径和一次性临时中间结果，原则上不单独组织为 CTE；
* 能先独立立住的查询语义对象，优先写成 `*_base`；
* 需要通过查询变换形成、且值得作为整体被后续继续引用的中间查询语义，写成 `*_derived`；
* 语义关系是否单独写成 CTE，不取决于它是不是关系，而取决于它在当前问题中是否形成独立查询单元；若未形成独立查询单元，可仅在查询单元之间以连接语义显式表达；
* 只有在存在数据库模式相关证据时，才在 CTE 内部引用 `*_impl` 来源对象；
* 最终主查询应保持用户问题的语义口径，不得退化为物理实现结构的直接转写。

# 四：分析步骤

在生成 JSON 形式的 概念 SQL之前，必须先基于以下步骤完成分析。**禁止直接生成Json**；

分析目标不是直接枚举实体、关系和属性，而是：

1. 先识别问题中的语义成分；
2. 判断哪些语义成分值得单独命名为查询单元；
3. 基于这些查询单元构造概念 SQL；

---

## Step 0. 重述问题，区分需求语义与实现证据

先重述用户问题，并区分输入中的两类内容：

1. **需求语义**：用户真正想分析、筛选、返回、分组、聚合或比较的内容；
2. **实现证据**：输入中出现的数据库模式相关证据，包括 schema、table、column、主外键、桥接表、映射表、时间列、空间列、编码列等。

注意：

* 不得预设实现证据一定存在；
* 不得因为输入中出现表名、字段名，就直接将其作为最终概念对象；
* 若同一段输入同时混有需求语义与实现证据，应分别识别。

---

## Step 1. 识别语义成分

基于全部输入，识别当前问题中的语义成分。

语义成分可以包括：

* 对象概念；
* 字段概念；
* 条件相关概念；
* 连接依据；
* 分组、聚合、排序、比较等分析操作；
* 数据库模式相关实现线索。

同时识别以下附属信息：

* 每个对象概念涉及的属性；
* 属性上的实例值、时间值、类别值、范围值等常值约束；
* 多个对象之间可能存在的连接、属性匹配或实现路径；
* 用户提及的分组、聚合、排序、比较等数据操作。

注意：

* 本步骤的目标是识别问题中的语义成分，而不是立即决定哪些成分应被组织为命名查询单元；
* 不得因为某个语义成分与其它成分存在连接依据，就直接将其判定为关系型基础单元。

---

## Step 2. 判断哪些语义成分应被显式组织为命名查询单元

对于 Step 1 中识别出的语义成分，判断哪些成分在当前问题中：

* 具有相对独立且稳定的语义边界；
* 能够单独定义粒度与成员范围；
* 能够承载自身属性或局部约束；
* 值得作为整体被后续查询步骤引用。

只有这类成分才应被显式组织为概念 SQL 中的命名查询单元。

判断时遵守以下原则：

* 能单独定义“这是什么”，且能单独说明“一行代表什么”的，才可作为查询单元候选；
* 能承载自身属性或局部约束，且后续需要作为整体继续被引用的，才值得单独命名；
* 单纯的属性约束、跨单元属性匹配、实现桥接路径、一次性临时中间结果，默认不单独命名为查询单元；
* 语义关系只有在其自身形成独立查询对象时，才单独组织为查询单元；否则应仅作为查询单元之间的连接语义保留。

---

## Step 3. 判断查询单元之间的连接方式与约束方式

基于已确定的命名查询单元，判断它们之间的连接在当前问题中属于以下哪类：

1. **需要独立保留的稳定语义关系**；
2. **仅用于属性匹配或分析对齐的跨单元连接**；
3. **仅用于实现支撑的连接路径或桥接依据**。

注意：

* 本步骤的目标是为构造概念 SQL 和后续 ER 抽取提供依据；
* 不要因为某个连接在实现上依赖时间对齐、空间映射、编码映射或桥接路径，就自动否定其在问题表达中的稳定关系地位；
* 也不要因为某个连接能用 `JOIN` 表达，就自动将其视为最终 `relationship_type`。

---

## Step 4. 构造概念 SQL

基于已识别的语义成分、已确定的命名查询单元以及连接方式，构造概念 SQL。

构造时应遵守以下要求：

1. 用 `*_base` CTE 表达被判定为值得单独命名的基础查询单元；
2. 用 `*_derived` CTE 表达被判定为值得单独命名的派生查询单元；
3. 若存在实现证据，可在 `*_base` 或 `*_derived` 内部引用 `*_impl` 来源对象；
4. 单纯的属性约束、局部匹配、临时桥接路径不应被强行单独写成 CTE，而应通过 `WHERE`、`JOIN`、局部表达或必要的简洁注释附着在已有查询单元中；
5. 最终主查询应保持对用户问题语义口径的覆盖。

注意：

* `*_impl` 不是独立 CTE 类型，只是 CTE 内部引用的实现来源对象；
* 派生查询单元只作为概念 SQL 中的中间查询表示，不应直接等同于最终骨架中的实体或关系。

---

# 五：输出

仅当完成上述全部分析步骤Step 1 - Step 4 之后，才能输出最终的json对象，格式如下：

```json
{
  "query_units": [],
  "conceptual_sql": "..."
}
````

---

## 字段要求

### `conceptual_sql`

表示基于查询语义单元构造出的**一条完整概念 SQL**，即概念查询结构的整体表达。

要求：

* `conceptual_sql` 必须是完整 SQL 字符串，可包含 `WITH`、多个 `*_base` / `*_derived` CTE，以及最终主查询；
* `*_base` 用于表达基础查询单元；
* `*_derived` 用于表达派生查询单元；
* 若存在数据库模式相关证据，可在 SQL 中引用 `*_impl` 作为来源对象；
* `*_impl` 不是独立 CTE 类型，而是 SQL 中 `FROM` / `JOIN` 所引用的实现来源对象后缀；
* 并非所有识别出的语义成分都需要出现在 `conceptual_sql` 的命名 CTE 中；只有值得单独命名的查询语义单元才应被显式组织为 CTE；
* 最终主查询应优先保持用户问题的语义口径，不得退化为数据库物理实现结构的直接转写。
