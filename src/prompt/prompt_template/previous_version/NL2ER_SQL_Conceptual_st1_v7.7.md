# 任务定义

根据全部输入中可识别的用户需求语义与数据库模式相关证据，构造一个**面向问题表达的概念查询结构（Conceptual Query Plan）**。

这里的概念查询结构不是要求生成一条可直接执行的数据库 SQL，也不是要求还原完整数据库 schema，更不是要求在本阶段完成基础实体、关系、属性集合的完整抽取与收敛。
它是一条作为中间语义表示的 **conceptual SQL / SQL-like 查询伪代码**，用于表达：

* 用户最终想得到什么结果；
* 为了得到该结果，问题应如何被拆解为若干按依赖顺序展开的命名子问题；
* 每一步需要完成的主要计算动作与关键约束；
* 哪些阶段性结果值得被显式保留；
* 最终结果如何由这些阶段性结果逐步构成；
* 数据库模式相关证据如何作为实现支撑，帮助这些子问题落地到可能的数据来源。

该 conceptual SQL 的核心作用，是将用户问题组织为一组按依赖顺序展开的**命名子问题**，并在需要时用 CTE 显式承载其中值得保留的阶段性结果。

本阶段关注的是：**问题如何成立、需要先求哪些子问题、哪些中间结果值得保留、支持该问题需要哪些基础实体关系**。

---

# 基本原则

## 1. 先组织问题求解结构，再考虑实现支撑

conceptual SQL 首先服务于**表达用户问题如何成立、如何逐步求解**，而不是直接转写物理实现。
构造查询计划时，应优先从最终结果出发，识别为得到该结果必须依次成立的阶段性求解步骤，并说明这些步骤之间的依赖关系。

数据库模式相关证据只作为实现支撑背景，用于帮助这些步骤落地到可能的数据来源；
它可以影响某一步如何表达，但不得主导问题本身的求解结构，也不得替代用户问题的语义拆解。

---

## 2. logical query plan 的基本单位是“命名子问题”

conceptual SQL 的核心，是将用户问题组织为若干按依赖顺序展开的**命名子问题**。
每个命名子问题都应对应问题求解过程中的一个相对清晰的阶段性结果，即能够说明：

* 这一步在求什么；
* 这一步产出的结果是什么；
* 这一步依赖什么前提；
* 这一步如何为后续步骤提供输入。

这些命名子问题的设立标准首先是**求解作用、语义清晰度与后续复用价值**，而不是概念对象是否齐全。
不要为了对象罗列、结构对称或概念完整，而机械地把所有基础对象都上升为独立步骤。


---

## 3. 命名子问题应尽量先保持 schema-agnostic

构造子问题时不应考虑具体数据库表、列、join key 与物理实现细节，优先表达问题本身所要求的**抽象求解步骤**。
 
不要过早把表名、列名、连接键或实现路径写死。

数据库模式相关证据主要用于后续将逻辑步骤映射为 conceptual SQL 结构，并在必要时为某些步骤提供来源支撑；
它不应主导 Logical Query Plan 本身的构造。

---

## 4. 基础逻辑实体与基础逻辑关系定义

基于子问题的查询与分析需求，定义问题求解所需要的基础逻辑实体与基础逻辑关系。基础实体与关系作为数据源，支持整个查询步骤所有的派生语义单元与计算分析步骤；

逻辑实体：实体是问题中具有稳定语义身份、明确基础粒度、可独立指称和重复引用的对象。

逻辑关系：关系是**两个或多个实体**之间具有明确独立语义的关联、交互或事件，用于表达实体之间实际存在的联系。参与关系的实体具有角色：一个基础实体可以以不同角色在关系中出现多次。

逻辑关系的定义约束：参与关系的至少需要两个以上的实体角色；实体的属性限定/子类限定通过逻辑属性上的取值约束实现，不得独立建立为关系。
---
### 5 逻辑属性与条件定义

* 基于子问题的语义表达、 查询分析与条件限定需求，定义逻辑实体与逻辑关系的逻辑属性集。逻辑属性作为数据源的具体化，必须支持整个查询步骤所有的派生语义单元与计算分析步骤与条件限定；
必须完整承载逻辑查询计划所需要的语义表示性属性、连接属性、条件属性。

---
## 6. conceptual SQL的定义原则：

当 conceptual SQL 中需要引用数据逻辑表时，必须遵守以下规则。

### 6.1 定义作为基础语义单元表示的逻辑表

所有作为数据来源引用的逻辑表必须以`*_source` / `*_impl`后缀结尾。
所有数据源表应被理解为某个**基础语义单元的逻辑表来源**，而不是任意中间步骤的命名占位。

* 若某逻辑表对应的是基础实体单元，则应将其理解为该实体单元的**实体逻辑表**；
* 若某逻辑表对应的是基础关系单元，则应将其理解为该关系单元的**关系逻辑表**。

`*_source` / `*_impl` 的作用，是为某个基础语义单元提供来源承载；
它们不是独立的概念查询单元，也不是独立的 CTE 类型。

因此，不得将下列内容伪装为来源表对象：

* 中间结果；
* 局部桥接步骤；
* 映射路径；
* 临时匹配过程；
* 派生分析步骤；
* 过滤后的局部子集；
* 仅为某一步服务的实现动作。

`*_source` 的命名应对应其所承载的基础语义单元本身，而不是某个过滤动作、连接动作或实现动作。

---

### 6.2 `*_impl` 只能在存在明确数据库实现证据时使用

只有当输入中**明确提供了数据库实现证据**时，才允许使用 `*_impl`。

这里的实现证据必须是可直接指向数据库实现对象的线索，例如：

* 明确给出的 schema；
* 明确给出的 table / view；
* 明确给出的 column；
* 其它足以识别具体数据库对象的实现信息。

若输入中没有明确实现证据，即使语义上很可能存在某类逻辑表，也**不得**写成 `*_impl`；
此时必须使用 `*_source` 作为抽象来源占位。

不得将推测性的、常识性的、或仅由问题语义暗示出来的逻辑表写成 `*_impl`。

---

### 6.3 `*_source` 与 `*_impl` 的使用定位

* `*_source` 表示：该基础语义单元在概念层需要一个来源承载，但实现未被明确提供；
* `*_impl` 表示：该基础语义单元已有明确数据库实现证据，可引用相应实现来源；
* 它们都只是**某个结构节点内部引用的逻辑表命名方式**；
* 它们本身不构成新的命名子问题，除非用户问题本身就在分析该逻辑表。

# 分析步骤

在输出最终 JSON 之前，必须先完成以下分析。
**禁止跳过分析直接生成 conceptual SQL。**

---

## Step 0. 分析问题背景，区分用户需求与实现提示，设置分析与输出的语言

先重述问题，分析问题背景，并区分：

* 该问题可能来源于哪些专业领域；问题中的表述和名词术语应该如何理解；
* 哪些内容属于用户真正的分析需求；
* 哪些内容属于数据库模式或实现提示；
* 输入中是否提供了明确的数据实现线索；若有，具体是什么；
* 这些实现线索能支撑哪些步骤落地，但又不应替代哪些问题语义。

注意：实现提示只能作为落地支撑，不能直接替代用户问题本身的求解结构。

同时，明确用户输入问题用的语言；后续输出的实体/关系/属性定义需要与用户属于语言一致。
---

## Step 1. 构造 Logical Query Plan

先暂时撇开具体数据库表、列、join key 与物理实现细节，围绕用户问题本身，构造一份 **Logical Query Plan**。

这里的 Logical Query Plan 不不得给出任何实体/关系/属性的假设，仅仅用自然语言进行推理。
它是一组按依赖顺序展开的**命名子问题**，用于表达：

* 最终结果是什么；
* 为了得到该结果，必须先求出哪些阶段性结果；
* 每一步的主要计算动作是什么；
* 每一步依赖哪些前提；
* 哪些隐含约束必须在该步被显式考虑。


### Step 1.1 将问题拆解为命名子问题
根据Step 0 用户真正的分析需求的分析，围绕最终结果的形成过程，将问题拆解为若干按依赖顺序展开的**命名子问题**。
每个子问题都应回答：为了得到最终结果，必须先求出的哪一个阶段性结果什么。
子问题描述对原问题的忠实性：子问题必须基于原问题的口径展开。

每个子问题定义为一个自然语言描述的查询计划：一个可以说明“这一步在求什么”的求解节点。
必须用明确具体的陈述句描述阶段性结果，包含问题里提及的所有限定细节，明确所有需要返回的数据。

输出为一个**子问题**与一个**阶段性结果**。

---

## Step 2. 将 Logical Query Plan 映射为 Conceptual SQL 骨架

基于上一步已经得到的 **Logical Query Plan**，进一步判断：

* 哪些命名子问题形成了值得显式保留的阶段性结果；
* 哪些内容只应作为其他步骤内部的局部逻辑；
* 这些阶段性结果之间应如何按依赖顺序组织；
* 最终应如何映射为一条结构稳定的 conceptual SQL 骨架。

这里的目标不是重新理解问题，也不是开始做完整的实体-关系-属性抽取。
本步骤只负责：**把 Logical Query Plan 中真正值得保留的阶段性结果，收束为 conceptual SQL 中的结构节点。**


### Step 2.1 从子问题序列提取基础逻辑实体与基础逻辑关系

（1）遍历子问题，定义整个问题其所需要的基础语义单元：基础**逻辑实体**单元和基础**逻辑关系**单元；

基础语义单元，是指在整个问题中应被保留为数据检索起点的必要实体/关系对象。

语义单元的命名：语义单元的命名必须符合问题中的详细语义，每个实例的语义必须清楚合理，可标识。语义单元定义的口径和范围必须完全符合问题的描述，不懂泛化和特化描述实体与关系。

首先定义问题所需要的所有基础实体类型：实体是问题中具有稳定语义身份、明确基础粒度、可独立指称和重复引用的对象。
* 基础逻辑实体类型: 明确该实体类型的详细语义，每个实体实例指代什么，是否可标识，在问题中的作用；

其次基于基础实体集，定义问题所需要的所有基础关系类型：关系是**两个或多个实体类型**之间具有明确独立语义的关联、交互或事件，用于表达实体之间实际存在的联系。
参与关系的实体具有角色：一个基础实体可以以不同角色在关系中出现多次。

* 基础逻辑关系类型：明确该关系类型的详细语义，每个关系实例指代什么，是否可标识。参与该关系的必须为两个以上的角色化逻辑实体类型，在问题中的作用；

关系约束：参与关系的至少需要**两个以上的已定义的角色化逻辑实体类型**；
不得用关系表示子类/条件限定：单个逻辑实体类型的属性限定/子类限定通过逻辑属性上的取值约束实现，不得独立建立为关系。

注意区分关系与单纯的连接：连接表示多个基础逻辑实体类型之间，为完成问题要求的属性匹配、属性对齐、上下文附着而需要保留的基础连接语义。连接不表示独立业务关联，不应与关系类型混淆。



**基础语义单元的独立性**：每个实体和每个关系必须作为语义独立的个体，单独区分和建模。语义单元必须保持在实体/关系级别，禁止用一个语义单元的属性表示其它语义单元的实体/关系。每个实体和关系必须被明确表示为一个独立的语义单元，而不能隐含在其它实体或关系的属性中；

**所有关系和实体必须独立表示**：部分实体/关系可能只有少量属性/一个标识符属性，但是这些关系和实体也必须作为独立的语义单元存在。

**派生语义单元不单独建模**：派生的语义单元视为从基础的逻辑实体/关系计算得出，不独立建模，不在此处提及。

注意：

* 本阶段禁止定义数据源和逻辑表；本阶段禁止定义确定的具体属性。

（2）定义自检：在定义完成后，明确检查：
* 是否独立构建所有基础逻辑语义单元；
* 所有关系是否都有两个以上的已定义角色化逻辑实体类型；
* 关系的定义是否区分了单纯的连接；
* 派生单元不独立建模；



### Step 2.2 遍历子问题，检查实体-关系完整性，反推属性规格


遍历每个子问题：
(1) 判断其语义表示与主要操作类型。常用操作类型如下：

* 选择对象，根据条件筛选子集；
* 建立连接、匹配或对齐；
* 角色化拆分；
* 时间顺序或窗口限制；
* 分组聚合；
* 比较、排序或 Top-k；
* 派生计算；
* 最终结果整合。

若某一步同时包含多种操作，应指出主操作与次操作，不要只做笼统描述。

(2) 检查所有语义约束条件。常见语义约束条件如下：

* 角色约束；
* 方向约束；
* 属性取值约束：
* 时间先后约束；
* 局部子集范围；
* 比较基准；
* 参考对象；
* 分子 / 分母口径；
* 去重口径；
* 聚合前提；
* 局部分析范围。
从问题的自然语言出发，检查是否自然语言问题里的**每一个字段**都在子问题集里有表示出来；尤其注意检查限定条件字段，每一个字段都应该落实到属性上，不能假设隐含。
所有问题中提及的约束都需要纳入考虑，不得默认省略这些条件。
每个基础语义单元都应有相应的属性来和承载计算与约束条件。

(3) 反推逻辑表属性规格：重述 Step 1里针对每个子问题的对象表达、数据操作与隐含约束；分析该语义表达、操作/约束的对逻辑表提出的属性字段要求；
每个步骤的中间表示和最终查询的所有属性皆派生于逻辑表；逻辑表作为源头，必须有最够的规格支持所有派生属性和约束条件。
多义性注明：如果一个语义要素可能用不同的实体/关系的不同表示，必须显式说明；不在这一阶段决定属性定义。

### Step 2.3 根据实体-关系结构定义逻辑表

（1）对每个中间表示和最终查询，明确其**实体**和**关系**的数据来源：是来自前步骤的CTE，还是来自某个基础的实体/关系逻辑表；

逻辑表作为概念查询的唯一**基础数据源**存在。在某个结构节点的实体/关系没有确切的落实时，考虑其内部如何引用 `*_source` / `*_impl`。对于前步骤的CTE引用，应视为中间表示，而不是基础数据源。
命名要求：每个实体/关系的语义单元必须用`_ent`,`_rel`后缀命名。

要求：
**逻辑表的原子性与单纯性**：逻辑表在概念定义上保持原子性与单纯性：每个表仅允许表示一个实体，或一个关系。禁止将多个实体或关系合并到一个表中。
* 逻辑表只能作为**某个基础语义单元的来源**出现；

* 命名需要明确逻辑表承载的实体/关系：使用 `*_ent`,``*_rel`后缀。表名主体必须明确表示实体/关系的语义。
* 命名需要明确逻辑表的实现情况：仅当输入中存在明确数据库实现证据时，才允许使用 `*_table_name_impl`，对相关实现也必须将实体/关系作为主体前缀，不得直接用原表名；否则必须使用 `*_source`。

一个逻辑表命名可能为如下形式：`customer_ent_source`.
逻辑表的作用是支撑概念查询的数据源，不是重新组织查询计划。

### Step 2.4 根据子问题确定逻辑表属性集

（1）正式定义逻辑表属性集： 对每个逻辑表，基于满足完整性、语义准确性与最小化原则，进行必要的逻辑属性集的设计；对于可能有多种表示的属性，需要明确其多义性，并在conceptual SQL中标明alternative：

* 完整性：支持所有后续步骤与表示的属性派生计算需求；满足所有语义表示，连接，条件约束的字段需求。
* 最小化：当某个属性可以通过与其他属性的连接、计算得到时，不应直接在逻辑表中定义为独立属性。
* 语义准确性：明确语义的合理归属对象；
* 多义性分析：如果某种逻辑属性定义存在多种表示可能性，必须明确说明其它的属性表示可能性，在sql实现选择以最符合标准数据库设计与业务常识的形式表示；



---

## Step 3. 组织 conceptual SQL

基于前面的分析，将 Step 2 得到的结构节点组织为一条完整的 conceptual SQL，并以json形式输出。

要求：

* 按求解依赖顺序安排 CTE；
* 每个独立 CTE 都应表达一个相对清晰的阶段性结果或命名子问题；
* 后续 CTE 可以引用前序 CTE，也可以在内部引用必要的 `*_source` / `*_impl`；
* 不得形成循环依赖；
* 主查询必须直接对应用户最终想要的结果口径；
* conceptual SQL 应表现为一条**问题求解骨架**，而不是物理实现结构的机械展开；
* 实现支撑相关内容应尽量隐藏在相关节点内部，而不是让实现路径主导整体结构。
* 对具有多义性的属性表示，需要在Conceptual SQL里明确以SQL注释的形式进行标注 ；


必要时可使用简洁注释辅助表达，例如：

* `-- Global Condition`
* `-- Local Condition`
* `-- implementation support`
* `-- alternative attribute: ...`
（注释必须标注在SQL语句内部；不能以附加文本形式）

```json
{
  "conceptual_sql": "..."
}
```

# conceptual_sql 生成要求

* conceptual_Sql 的数据对象是逻辑性的，但是其语法结构需要满足**语法完整、结构稳定、便于后续解析**；
* 可以使用伪代码函数、抽象列名或抽象条件表达，但 SQL 结构必须完整；
* 不允许出现 `...`、`WHERE ...`、`ON ...` 这类不完整表达；
* 每个 CTE 都必须写成完整的 `name AS (SELECT ... FROM ...)` 形式；
* CTE 名称优先表达该步骤所代表的**子问题或阶段性结果**，而不是表达其是否属于基础对象、派生对象或实现来源；
* 若某个基础逻辑表仅用于支撑某个结构节点，但本身并不构成一个值得保留的阶段性结果，则应仅作为该节点内部的来源引用出现，而不应单独提升为 CTE；
* 可按需要使用简洁注释，帮助说明局部条件、全局条件或实现支撑；
* 默认按 Snowflake 风格书写；
* `*_source` / `*_impl` 的使用必须严格遵守以下规则：

  * 所有逻辑表都应按基础语义单元的逻辑表来源来定义；
  * 基础实体单元对应实体逻辑表，基础关系单元对应关系逻辑表；
  * 输入中存在明确数据库实现证据时，才允许使用 `*_impl`；
  * 语义上需要但实现未明确给出时，必须使用 `*_source`；
  * 不得凭空假设物理实现并写成 `*_impl`；
  * 不得将中间结果、局部桥接步骤、映射路径、临时匹配过程或推测性的物理来源伪装成 `*_source` 或 `*_impl`。
