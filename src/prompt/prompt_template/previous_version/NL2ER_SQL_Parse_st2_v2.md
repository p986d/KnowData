## 一：任务定义

你的任务是：根据用户输入的查询问题与一个SQL形式的概念查询方案 **conceptual SQL**，提取并优化一份面向数据检索的结构化规格。

这份规格不是最终 SQL，也不是数据库实现方案，而是一份 **ER Retrieval Spec**，用于显式定义：

* 需要检索的基础实体，关系、属性连接；
* 实体/关系的属性；
* 单个属性的约束条件、属性间的约束条件；
* 对 conceptual SQL 中不太符合用户需求、表述有问题的属性、条件与连接表达进行适当优化。

---

## 二：核心思路

提取基于 Conceptual SQL的 CTE 定义； 每个CTE指代一个实体、关系或实体间的连接；每个CTE可能指代一个基础的实体/关系/连接，或作为问题的中间表示。

* 局部属性的常量约束；

### 1. 基础查询单元 CTE `*_base`

`*_base` 查询单元用于提取最为基础的实体、关系或连接。

对于 `*_ent_base`，应提取其对应的基础实体，包括：

* 实体名称；
* 粒度（即一行代表什么）；
* CTE 投影中保留的概念属性；
* 局部属性的常量约束；
* 必要时补充其主键或识别属性。

对于 `*_rel_base`，应提取其对应的基础关系，包括：

* 关系名称；
* 粒度（即一行代表一个什么关系实例）；
* 参与实体及其角色；
* CTE 投影中保留的概念属性；
* 局部属性的常量约束。

对于 `*_conn_base`，应识别其连接的基础实体、连接所依赖的属性以及该连接在这些属性之间引入的约束；
* 连接名称；
* 粒度（即一行代表一个什么连接实例）；
* 参与实体及其角色；
* 连接属性之间的约束。

### 2. 派生查询单元 CTE `*_derived`

`*_derived` 表示基于 `*_base` 查询单元构建的中间表示实体、关系或连接;

对于 `*_ent_derived` / `*_rel_derived` / `*_conn_derived`，需要：

* 确定其依赖哪些基础实体/关系/连接衍生得出；
* 识别它对这些基础单元属性施加了哪些额外约束；
* 识别它是否表达了某种连接语义，并将该连接语义落实为单元之间的属性约束条件；

* 若其仅表达聚合、排序、Top-K、窗口计算等分析性组织，则原则上不将其转写为新的实体/关系属性约束，仅作为 conceptual SQL 中的分析要求看待。


### 3. 实现来源

输入中的 `*_impl` / `*_source` 仅作为实现提示保留在查询单元对象内部，而不是作为查询单元：

* 不得提升为实体；
* 不得提升为关系；
* 不得因为实现来源在 conceptual SQL 中出现，就影响概念层对象命名。

### 4. 提取边界说明

本任务提取的是基于问题面向数据检索的**基础实体-关系-连接-属性-约束规格**。

因此：

* `*_base` 是基础实体/关系/连接的主要提取来源；
* `*_derived` 默认不新增新的基础实体或关系，主要补充已有基础实体/关系上的约束条件、连接条件；
* `*_impl` / `*_source` 仅为实现支撑来源，不得直接提升为实体、关系或概念属性；
* 提取结果应保持用户问题的语义口径，不得退化为对实现表字段、桥接路径或物理筛选条件的直接转写。

## 四：提取内容

提取包括实体，关系，连接、属性以及属性约束条件五个部分。

* 关系 relation 指在当前问题中具有明确业务语义、应被独立保留的对象间关联；即使脱离具体实现路径，该关联本身仍成立并具有稳定含义。relation 可以具有明确的参与角色，并可承载关系属性。

* 连接 connection 指不构成独立业务关联、仅用于在对象之间完成属性匹配对齐、上下文补充等的语义连接；其语义重点不在“关联本身是什么”，而在“对象如何通过某些属性条件连通”。

connection 通常不作为独立关系，不应与 relation 混淆。

属性约束条件记录 **关系/连接的属性匹配** 以外的属性约束：conditions 用于记录实体、关系、连接上的属性约束，但不重复记录 relation / connection 自身成立所依赖的锚点属性匹配，包括：

* 单个实体/关系/连接属性的常值、集合或范围约束
* 多个实体/关系/连接之间，不以建立 relation / connection 为目的的属性比较、对应或限制条件

## 五：提取规则

### 1. 对 `*_ent_base`/ `*_rel_base`/ `*_conn_base`

提取为 `entities`，`relations` 中的实体/关系类型或 `connection` 中的属性连接。

应优先识别：

* 一行代表什么；
* 连接的是哪些对象，这些对象的参与角色；
* 连接的性质是什么：是一个具有语义的关系类型，还是仅通过属性条件的连接；
* 具有哪些概念属性。属性应以用户需求中显式提及、直接参与分析表达的核心语义属性为主；若某属性虽非用户显式输出字段，但在 conceptual SQL 中已被显式用于连接、匹配、角色、空间/时间约束等语义表达，且没有该属性相关语义无法成立，则也可作为约束支撑属性保留。
* 如果 `rel_base` 与 `conn_base` 提及未显式建模为 `ent_base`的实体类型，这些实体必须被显式建模并添加至 `entity`。
* 对于关系/连接，需要明确参与对象用于连接的属性（anchor attributes）与 连接条件(link condition); 以简短的自然语言定义参与实体的属性匹配关系，禁止引用conceptual sql中的任何具体实现；conceptual sql 是伪代码，引用具体实现会出错。

### 3. 对 `*_ent_derived`/ `*_rel_derived`/ `*_conn_derived`

派生查询单元应建立于基础单元之上，默认不添加新的基础实体/关系，仅补充查询单元间的属性约束条件/连接条件。

* 作用于哪些基础查询单元的哪些属性；
* 构造了哪些通过属性条件的连接；
* 非连接性的属性取值条件约束；
* 分析性条件。

ER建模完整性：对于如下的场景，可以考虑补充实体-关系-属性：

* 对于实体 `*_ent_derived`，如果其引用了不存在的关系/连接，必须将该关系作为补充的"relation"/"connection"建模；
* 对于关系 `*_rel_derived`，如果其参与实体本来是未关联的，必须将该关系作为补充的"relation"建模；
* 对于属性匹配连接 `*_conn_derived`，如果参与实体没有用于连接的属性，必须将该属性作为补充的"connection"建模；
* 区分基础属性与派生属性：若某 `*_derived` 仅表达聚合、排序、Top-K 或其它分析，或作为某种中间表示，不得将这些表示的列作为属性回挂为基础实体/关系属性；基础属性保持原子性，派生属性不得与基础属性混合。
* 对于关系/连接，需要明确参与对象用于连接的属性（anchor attributes）与 连接条件 (link condition); 以简短的自然语言定义参与实体的属性匹配关系，禁止引用conceptual sql中的任何具体实现；conceptual sql 是伪代码，引用具体实现会出错。

### 3. 属性提取与优化规则

查询单元的属性应优先提取以下两类：

1. **核心语义属性**：用户在需求中显式提及、直接参与分析表达的属性；
2. **约束支撑属性**：虽然不是用户显式输出字段，但在 conceptual SQL 中已被显式用于实体标识、连接、匹配、角色、空间/时间约束等语义，且为这些约束成立所必需的属性。

属性定义检查：

正确性：属性必须完全贴合用户问题的表述口径，不得创建或臆造未提及、不一致的属性；
必要性：属性只在其对当前问题的对象定义、约束表达或分析目标确有直接作用时才保留；
原子性：每个属性只表达一个单一稳定语义，条件、角色、派生结果或复合含义不得构建为属性。

属性提取时应遵守以下限制：

* 不得将仅存在于 `*_impl` / `*_source` 内部、且未在概念查询单元投影中作为概念属性显式保留的实现字段，直接提升为实体/关系属性；
* 不得因为某字段在实现来源中出现，就自动把它当作概念层属性；
* 属性定义优化: 若某属性虽然在 conceptual SQL 中作为CTE投影列出现，但结合用户问题判断后更像分析结果列、临时中间列或依赖后续约束成立后才稳定的属性，则不得保留为基础实体/关系属性；必要时可以对 conceptual SQL 中出现的属性进行收缩、删减、重述或降级处理，但不得脱离用户问题语义任意发明新属性。

### 4. 约束条件抽取与优化规则

约束条件是对一个或多个实体/关系的特定属性施加的取值约束或属性间约束，包括：

* 单个实体/关系属性基于常量值/集合/范围的取值范围约束；
* 多个实体/关系属性之间的匹配、比较或对应约束；
* 非连接条件：表示连接的属性间约束条件不在此处重复建模；

约束条件进入 `conditions`，并明确作用的对象属性集：
注意：关系/连接也会定义用于匹配的属性集；对于表示连接的属性间约束条件,在 `relation`/ `connection` 上完成定义，重复添加至condition。

* 约束条件名称：简洁的描述性名称；
* 约束条件类型：
- `single_attribute`：表示只作用于单个实体属性或关系属性的条件，其语义是该属性被固定常量、常量集合或固定范围限制，而不涉及与其他属性的对应关系。
- `inter_attribute`：表示非连接语义的多查询单元属性约束；约束同时作用于两个或多个实体/关系属性，表示这些属性之间的对应关系，例如：属性值相等、不相等、在某个范围内等。

* 作用对象属性集：列出该约束条件作用的所有实体属性和关系属性，格式为 `entity_name.attr` 或 `relation_name.attr`；约束条件作用对象必须是查询单元的稳定属性；

* 约束条件描述：以简短的自然语言定义单个属性的基于常量的约束或多个属性间的对应比较关系，禁止引用conceptual sql中的任何具体实现；conceptual sql 是伪代码，引用具体实现会出错。


约束条件抽取与优化时应遵守以下规则：

* `conditions` 仅承载非连接语义的属性约束，不承载单纯的分组、聚合、排序、Top-K、窗口计算等分析操作的语义； 连接语义的属性约束条件，在 `relation`/ `connection` 上完成定义；
* 若 conceptual SQL 中某条件写法过于贴近物理实现、分析操作或中间列组织，应在保持问题语义不变的前提下，将其重述为更稳定的概念性属性约束表达。
* 约束必须用自然语言简明扼要的描述，禁止提及任何Conceptual SQL中的具体实现的写法；

### 8. 禁止事项

你必须遵守以下限制：

* 不得把 `*_impl` / `*_source` 提升为实体或关系；
* 不得把实现表、映射表、桥接表、空间表直接改写为概念层对象；
* 不得把 `*_derived` 默认理解为新的复合宽表实体；
* 不得为了让结果更像可执行 SQL 而发明输入中未明确给出的物理字段名；
* 若某条件本质上是跨对象属性约束，应保留为概念性约束表达，而不是伪造实现列名。
* 不得将仅存在于 `*_impl` / `*_source` 内部的实现字段，提升为实体/关系属性或 `conditions.targets`；
* 不得将 `SUM`、`COUNT`、`AVG`、`ORDER BY`、`LIMIT`、Top-K 等分析操作直接改写为 `conditions`；

## 六：执行步骤

在生成 JSON 形式的 实体-关系-条件模型之前，必须先基于以下步骤完成分析，**禁止直接生成Json**；

### CTE Iteration 遍历所有CTE

你需要遍历conceptual_sql中的所有CTE;**对每个CTE**,连续完成如下步骤：

For each CTE:

### Step 0: 列举问题相关片段

对于每个CTE，你需要显式列举问题中提及这个语义单元的文本片段，并明确该片段的语义。

### Step 1: 语义成分识别

根据上述提取规则，分析该CTE的语义成分，判断其是基础查询单元还是派生查询单元；判断其是实体、关系还是连接；
注意这个步骤只是识别这些语义成分，而不是最终提取
遵守提取规则，仅建模基础实体/关系/连接：保持实体-关系的原子性；如果一个派生实体基于基础实体，或派生关系基于基础关系，则不得独立建模为 `entity`/`relationship`；基于属性的连接需要建模为`connection`；
对于关系/连接，必须明确参与实体的角色，显式建模相同实体类型的不同角色；
输入中的 `*_impl` / `*_source` 仅作为实现提示保留在查询单元对象内部,禁止提升至实体/关系。
这个仅确定实体/关系/连接，以及是否是基础/派生，不得对属性与约束进行判断。

### Step 2: 属性与约束定义

首先需要回顾用户问题，显式列举出提及该语义成分对应的所有文本段落，包括需求描述与实现提示；

属性集定义：基于Conceptual SQL CTE中的属性，定义正式的属性集，必须完整承载用户需求，符合用户表述，同时在结构上支持实体/关系/连接与分析计算的定义；
属性名称定义：任何属性，只要用户表述有提到属性名的字段，必须按照用户表述命名。
conceptual SQL 中的属性、条件和连接表达是草稿，必须对照用户需求与实现描述，检验属性和约束定义是否准确；如果不符合用户表述必须优化后再落实为正式定义。

实体标识性属性定义：对于实体的标识符属性，必须检查该属性是否为用户是否直接提及能作为主键的属性集（ id型属性或能唯一标识实体的属性集）；必须用用户口径定义的属性集作为主键，不得自行构造；

标识符属性命名约束：当用户没有**直接**提及标识性属性、且不存在可用的自然键时，主键属性命名必须表示为"_surrogate_id"后缀，以表示并非用户直接定义，而是为实体定义的语义完整额外构建的属性；
**"隐含"标识符存在或"上下文暗示"的标识符存在**也必须带上"_surrogate_id"后缀；只要不是用户显式提出存在的属性作为标识符，标识符必须带上"_surrogate_id"后缀。


关系/连接标识性属性与条件定义： 对于关系/连接，需要明确参与对象用于连接的属性（anchor attributes）与 连接条件 (link condition); 注意关系/连接的属性必须存在于实体的稳定属性集；

条件约束定义：定义表示某种语义限定的属性取值约束，以完整准确的表示用户需求。条件约束的属性必须存在于属性集。
**条件约束**可能会以较为隐晦的形式存在，需要综合分析识别用户表述中的常量/常值字段，与跨实体/关系的字段相关性约束条件字段，全面表示条件约束；同时，条件约束可能会具有传递性，例如一个实体的属性约束通过关系/连接传递给另一个实体。另外，条件约束主要建模取值范围的约束，除非问题明确提出，一般不建模属性非空性/存在性。

* 当前拟提取的属性是否完全符合用户表述口径和实体/关系/连接的定义需求，不得曲解属性语义或构建额外属性的字段；
* 当前拟提取的条件，是否属于属性间的约束条件，而不是分析操作；对于表示连接的语义单元间的条件约束，只需要确定用于连接的属性即可，不用添加额外的属性；
* 约束必须用自然语言简单描述，禁止使用conceptual SQL的具体实现；
