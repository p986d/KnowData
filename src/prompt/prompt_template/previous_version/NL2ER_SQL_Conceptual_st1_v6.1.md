## 任务定义

你的任务是根据全部输入中可识别的用户需求语义与数据库模式相关证据，构造一个**面向问题表达的概念查询结构（Conceptual Query Plan）**。

这里的概念查询结构不是要求生成一条可直接执行的数据库 SQL，或是完整的数据库 schema 结构。
它是一条作为中间语义表示的**概念 SQL / SQL-like 查询伪代码**，用于表达：

* 用户真正想分析的语义对象与分析主轴；
* 构建整个问题的分析语义对象序列；
* 哪些语义单元属于独立的基础语义单元，需要哪些基础语义单元以支持问题分析流程；
* 哪些语义单元属于依赖已有语义单元进一步构成的派生中间表示；
* 数据库模式相关证据如何用于将需求语义对齐到可能的实现结构。

本任务的目的是将用户问题组织为**符合用户表述口径的概念查询结构（conceptual SQL）**，并通过 SQL 清晰表示基础的实体类型、关系类型、实体间的连接、属性与条件，以及后续由这些基础语义单元构成的中间表示。

---

## 核心原则：并非所有语义成分都应成为 CTE

问题中的对象、字段、条件、连接依据、分组聚合要求等，都属于需要识别的语义成分；
但**并非所有语义成分都应被显式组织为概念 SQL 中的命名查询单元**。

只有在当前问题中满足以下条件的语义成分，才值得被显式命名为查询单元（CTE）：

1. 具有相对独立且稳定的语义边界，能够单独说明“它是什么”；
2. 能够单独定义粒度与成员范围，能够说明“一行代表什么”；
3. 属于可以先被独立建立的基础语义单元，或属于依赖已有语义单元进一步构成、且值得作为整体被后续继续引用的派生语义单元；
4. 在当前问题中需要被显式保留，而不只是一次性临时桥接、局部匹配或实现支撑步骤。


其中需要特别注意：

* 用户需求中被直接表达、且对问题成立有直接作用的对象间连接，不应因为其属于连接就自动退化为局部 `JOIN ... ON ...` 条件；
* 但并非所有连接都必须拆成独立 CTE；只有当该连接在当前问题中形成值得单独保留和继续引用的语义单元时，才应显式组织为查询单元；
* 命名查询单元优先建模实体类型和关系类型、实体类型间基于属性的连接，而不是建模 “带上下文的实体类型记录”“聚合前宽表”等中间表示；
* 对于数据实现提示中的空间映射、编码映射、桥接路径、键关联路径等实现相关内容，不单独组织为概念层查询单元，而应隐藏在相应查询单元内部作为实现支撑表达；
* 即使输入中显式提供了某个需求语义单元对应的数据库实现线索，这些实现对象也仍仅属于该语义单元在 CTE 内部的实现支撑来源，不得因此上升为新的概念层查询单元。


其余语义成分应作为：

* 查询单元的属性；
* 属性上的常值约束；
* 查询单元之间的局部连接条件或属性匹配条件；
* 实现支撑路径；
* 分组、聚合、排序等分析操作

附着在相关查询单元上，或在主要 Query 表达，而不应自动成为独立 CTE。

## 2.2 值得单独命名的查询语义单元

**值得单独命名的查询语义单元**，指的是在当前问题中具有相对独立且稳定的语义边界、能够单独定义粒度与成员范围，并且值得作为整体被后续查询步骤继续引用的查询语义对象。

只有这类语义单元才应被显式组织为概念 SQL 中的 CTE。

需要注意：

* 对象语义单元、关系类型语义单元，以及在当前问题中需要被独立保留的连接语义单元，都可能成为命名查询单元；
* 连接语义单元是否需要显式组织，不以前置地区分其属于“稳定关系类型”还是“属性匹配”为条件；只要该连接在问题表达中需要被独立保留，就可以先被视为查询单元候选；
* 数据库实现提示中的实现相关来源：表、列、值等，需要作为需求语义的实现，被包含在相关语义单元的CTE内，不得独立建模或影响命名查询单元CTE；


下列内容默认**不应**单独命名为 CTE，除非它们在当前问题中确实形成独立查询单元：

* 单纯的属性常值约束；
* 单纯的时间范围、类别范围、状态范围；
* 单纯的一次性跨单元属性匹配或时间对齐；
* 单纯的空间映射、编码映射、键关联、桥接路径；
* 只为一次局部连接服务的临时中间结果；
* 仅作为实现支撑而存在的局部步骤。

## 2.3 查询语义单元

在本任务中，只有被判定为值得单独命名的语义单元，才进一步组织为以下几类命名查询单元与来源对象。

### 1. 基础查询单元（Base Query Unit）

基础查询单元是指：**在当前问题中可以先被独立建立的基础语义单元**。

这里的“基础”指其不是通过已有查询单元之间的组合、角色化、匹配、对齐、聚合或其它语义变换后才成立的中间结果。

它通常具有以下特点：

* 具有相对稳定的语义边界；
* 可以单独定义粒度与成员范围；
* 可以承载自身属性及局部约束；
* 作为原生基础语义单元存在，而不是后验构造出的中间表示。

基础查询单元可以为实体，关系，连接三种类型，对应一个 `*_base` CTE。

注意：

* `*_base` 可以用于表达基础实体类型语义单元，也可以用于表达基础关系类型语义单元；
* 关系类型和连接语义单元是否为 `*_base`，取决于它本身是否是当前问题中的原生基础语义单元；
* 只有当某关系类型需要在已有查询单元之上通过角色展开、属性匹配、上下文附着、条件组合或其它语义变换后才成立时，才不应作为 `*_base`。

### 2. 派生查询单元（Derived Query Unit）

派生查询单元是指：**由已有基础查询单元或其它派生查询单元，经由筛选、组合、角色化、匹配、对齐、聚合、重命名、粒度变化或其它语义变换后形成的派生语义单元**。

派生查询单元的作用是：

* 组织概念查询结构中的阶段性查询结果；
* 表达某种阶段性必要的中间语义结构；
* 承载连接语义、角色信息、跨对象属性对应、条件约束、上下文补充或分析中间结果；
* 为最终主查询提供可复用的中间查询输入。

派生查询单元通常对应一个 `*_derived` CTE。

关系类型/连接的基础/派生定义：由于关系类型/连接必须参照已有实体类型查询单元，现定义基础连接如下：当关系类型/属性匹配连接作用于两个未关联的实体类型时，称这个关系类型/连接是基础的 `*_base `; 反之，基于已存在基础关联的实体类型进一步定义的关系类型/连接是派生的 `*_derived`。

注意：

* `*_derived` 的“派生”是指其语义成立方式；
* 单纯的一次性桥接、局部匹配结果或局部实现路径，通常不应单独命名为派生查询单元。

### 3. 实现支撑来源（Implementation Support Source）

实现支撑来源是由数据库模式相关证据引入、用于支撑需求语义落地的实现来源或实现背景。

它们通常来自：

* schema / table / column 提示；
* 主键、外键、桥接表、映射表；
* 时间列、空间列、编码列；
* 其它能够揭示实现承载位置、连接路径或属性来源的数据库线索。

实现支撑来源的作用是：

* 为概念查询结构提供可能的实现落点；
* 支撑对用户需求语义的规范化重写；
* 提供属性来源、连接依据或路径展开的实现背景。

注意：

* 实现支撑来源默认不直接成为命名查询单元；
* 它们通常作为 `FROM` / `JOIN` 中引用的来源对象出现；
* 若输入中存在明确的数据库模式相关证据，来源对象可使用 `*_impl` 后缀；
* 若当前问题需要引用某类来源对象，但输入未提供其明确的数据库模式相关证据，可使用 `*_source` 作为抽象来源占位；
* `*_impl` 与 `*_source` 都不是独立 CTE 类型。

注意：只有当输入中明确提供了某来源对象的数据库模式相关证据（如具体 schema、table、column 或其它可直接指向实现对象的线索）时，才可使用 *_impl；仅凭问题语义推知该来源对象必然存在，不足以将其标注为 *_impl，此时必须使用 *_source。


### 4. 关系类型 / 连接查询单元建模

对于关系类型/连接一类的语义要素，需要将其显式建模以表达其连接性质为 `*_rel_*` 或 `*_conn_*` 等查询单元，其首要职责是表达参与对象之间的关系类型定义或属性连接约束；不得建模为表达连接完成后形成的复合实体类型。

这类查询单元应优先回答：

* 连接的是哪些对象；
* 各对象在连接中的参与角色是什么；
* 连接基于哪些属性、条件或约束成立；
* 连接本身是否承载局部约束或连接属性；
* 一行代表一个什么关系类型实例或连接约束实例。

不应将 `*_rel_*` / `*_conn_*` 查询单元直接写成“已附着多个上下文属性的复合实体类型结果”；若后续确有需要构造复合实体类型结果，也必须建立在已显式保留的关系类型/连接查询单元之上，而不能反过来用复合实体类型结果替代本应保留的关系类型/连接查询单元。

## 2.4 连接语义的说明

在概念查询结构中，对于**已被判定为需要显式保留的连接语义单元**，可进一步说明其内部连接性质。

连接语义通常可表现为以下几种倾向：

### 1. 关系类型性连接（Relation）

指该连接更接近一个需要被独立保留的关系类型语义，通常具有以下特征之一：

* 参与对象结构明确；
* 存在稳定的参与角色；
* 连接自身可能承载属性或局部约束；
* 去掉具体实现路径后，该连接仍然是当前问题中的核心语义结构。

### 2. 属性匹配性连接（Connection）

指该连接主要用于在对象之间完成属性附着、上下文补充或分析所需的对齐，通常具有以下特征之一：

* 主要作用是补充上下文或附着属性；
* 更依赖时间对齐、类别对齐、同值匹配、条件匹配等方式；
* 连接本身通常不作为独立关系类型对象保留。

### 3. 实现支撑路径（Implementation Support Path）

指该连接在落地时所依赖的实现路径、桥接路径或局部实现依据，例如：

* 键关联；
* 桥接表路径；
* 空间映射；
* 编码映射；
* 其它实现层的连接步骤。

需要注意：

* 实现支撑路径不是概念层连接语义单元的同级替代类型；
* 它通常作为连接语义单元内部的实现支撑而存在；
* 不应直接上升为最终 `relationship_type`。

## 2.5 用户需求到概念查询结构的映射规则

用户需求中与问题成立直接相关的对象、字段、实例值、条件、连接依据和分析要求，应尽量在概念查询结构中得到对应表达。

它们可以分别落实为：

* 查询单元的属性；
* 属性上的常值约束；
* 查询单元之间的连接语义；
* 查询单元之间的局部属性匹配和约束条件；
* 计算、分组、聚合、排序等分析操作；
* 最终分析单元的输出要求。

映射时应遵守以下原则：

* 用户提及的对象概念，优先映射为查询单元候选；
* 用户提及的字段，优先映射为相关查询单元的属性；
* 用户提及的实例值、时间值、类别值、范围值，优先映射为相关属性上的常值约束或范围约束；
* 用户需求中被直接表达、且对问题成立有直接作用的对象间连接，应优先映射为连接语义单元候选，而不默认退化为局部 `JOIN` 条件；
* 该连接最终是否组织为独立 CTE，取决于它是否在当前问题中形成值得独立保留并被后续继续引用的查询语义单元；
* 与该连接落地相关的空间映射、编码映射、桥接路径、键关联路径等实现内容，不单独映射为概念层查询单元，而应尽量附着在相应查询单元内部表达；
* 不要求所有需求片段都被对象化或单独组织为查询单元；只有当某一语义成分形成独立查询语义时，才考虑将其提升为命名查询单元。

## 2.6 概念 SQL 的结构说明

概念查询结构应采用**概念 SQL**的方式组织。这里的概念 SQL 不是可执行 SQL，而是用接近 SQL 的形式表达：

* 哪些查询语义单元被组织为基础查询单元；
* 哪些查询语义单元被组织为派生查询单元；
* 当存在数据库模式相关证据时，这些查询单元如何引用实现来源；
* 查询单元之间的连接、约束与依赖如何组织。

### 1. 两类命名对象

概念 SQL 中需要区分两类命名对象：

* **CTE**：概念查询结构中的命名查询单元，用于承载基础查询单元或派生查询单元；
* **来源对象**：CTE 内部 `FROM` / `JOIN` 所引用的对象，用于表示概念来源或实现来源。

### 2. CTE 的命名规则

CTE 使用以下两段式后缀表示其语义成立方式：

* `*_base`：表示基础查询单元；
* `*_derived`：表示派生查询单元。

* `*_ent`：表示查询单元是实体类型；
* `*_rel`：表示查询单元是关系类型；
* `*_conn`：表示查询单元是基于属性匹配的连接；

禁止使用其他的语义后缀

其中：

* `*_base` 用于表达可以先被独立建立的基础语义单元；
* `*_derived` 用于表达由已有基础或派生单元经过筛选、组合、角色化、匹配、对齐、聚合等语义变换后形成的中间查询语义。

为增强语义清晰度，CTE 名称宜尽量体现其语义类型：

* `<name>_ent_base`
* `<name>_rel_base`
* `<name>_ent_derived`
* `<name>_rel_derived`


### 3. 来源对象的命名规则

当概念 SQL 需要引用数据库模式相关证据中的实现来源时：

* 若输入提供了明确的数据库模式相关证据，可使用 `*_impl` 后缀；
* 若当前问题需要引用某类来源对象，但输入未提供其明确实现证据，可使用 `*_source` 作为抽象来源占位。

注意：

* `*_impl` 与 `*_source` 都不是独立 CTE 类型；
* 它们仅是 CTE 内部引用的来源对象命名后缀。

### 4. 连接语义的表达方式

在概念 SQL 中，查询单元之间的连接既可以通过 `JOIN ... ON ...` 表达，也可以在必要时通过简洁注释标明该连接单元更偏向何种连接性质。

当某条连接的内部性质对后续 ER 抽取十分关键时，可使用如下简洁注释辅助表达：

* `-- relation-like: ...`
* `-- connection-like: ...`
* `-- implementation-support: ...`

这些注释仅用于帮助表达该连接单元内部更偏：

* 关系类型性连接
* 属性匹配性连接
* 实现支撑路径

注释是可选的，但当连接语义容易混淆时，建议显式标明。

### 5. 使用原则

构造概念 SQL 时，应遵守以下规则：

* 并非所有识别出的语义成分都必须写成 CTE；只有值得单独命名的查询语义单元才应显式组织为 `*_base` 或 `*_derived`；
* 单纯的属性约束、一次性跨单元属性匹配、实现桥接路径和临时中间结果，原则上不单独组织为 CTE；
* 能先独立立住的基础语义单元，优先写成 `*_base`；
* 需要通过组合、角色化、匹配、对齐、聚合等语义变换形成，且值得作为整体被后续继续引用的中间查询语义，写成 `*_derived`；
* 连接语义是否单独写成 CTE，不取决于它是不是连接，而取决于它在当前问题中是否形成独立查询单元；若未形成独立查询单元，可仅在相关查询单元之间以显式连接结构表达；
* 参考数据、映射数据、编码数据、空间归属数据等实现相关来源，默认不直接写成概念层 CTE；它们所支撑的对象或连接语义若需要保留，应在相应 `*_base` 或 `*_derived` 中表达；
* 只有在存在数据库模式相关证据时，才在 CTE 内部引用 `*_impl` 来源对象；若无明确实现证据但概念上需要引用来源，可使用 `*_source`；
* 最终主查询应保持用户问题的语义口径，不得退化为物理实现结构的直接转写。

# 分析步骤

在生成 JSON 形式的 概念 SQL之前，必须先基于以下步骤完成分析。**禁止直接生成Json**；

## Step 0. 区分用户需求与实现提示
重述问题，区分用户需求的描述与实现提示字段，明确数据实现提示的存在性与具体内容；

## Step 1. 分解问题并识别语义成分

基于用户的需求描述内容，首先将当前问题拆解为为多个相互依赖的查询子问题；输出明确的子问题列表。
其次，从每个查询子问题中识别语义成分；

**数据实现不参与语义成分定义**：在识别语义成分时，禁止从数据实现识别相关内容：数据实现是对语义成分的实现支持，不得直接作为语义成分。

(1) 列举语义成分，以对象、连接、分析的自然语言形式描述：
* 对象概念；
* 对象之间的连接概念以及连接中的角色概念；
* 分组、聚合、排序、比较等分析操作；

禁止直接包括数据库模式与实体关系模型的内容：
* 数据库模式相关实现线索。
* 实体/关系/属性/条件的定义。

注意：
* 本步骤的目标是识别问题中的语义成分，而不是立即决定哪些成分应被组织为命名查询单元；
* 本阶段仅能定义对象、连接和分析操作作为草稿；禁止按实体类型/关系类型/属性的结构进行识别；
* 具体实体类型、关系类型与属性需要在后续步骤确定定义；

## Step 2. 判断哪些语义成分应被显式组织为命名查询单元


对于 Step 1 中识别出的语义成分，判断哪些成分在当前问题中应被显式组织为命名查询单元。

迭代所有语义成分：
For Each 语义成分，必须进行如下分析：

(1) 问题相关内容列举：完整列举问题中提及该成分的内容部分，作为命名查询单元定义的基准来源；
(2) 是否构建为语义单元及基础性/派生性：是语义独立的基础单元，还是基于基础单元通过组合、角色化、聚合等语义变换后的派生单元，还是不应该独立作为语义单元，而是作为其它单元的属性/角色/条件等；
(3) 语义单元类型：该语义单元的类型是：实体类型/关系类型/连接类型，区分关系性连接还是属性匹配性连接：当连接具有明确语义或连接本身具有属性时应建模为关系类型 relation，当连接仅为根据某些条件匹配的属性时，应建模为属性匹配连接 connection；对于关系/连接，必须明确参与实体的角色，并显式建模相同实体类型的不同角色；
(4) 用户需求的属性字段化：将用户需求中提及的语义信息准确、全面地落实为实体类型的属性字段；同时，实体类型、关系类型应该有确定的标识符属性，优先使用用户定义提及的属性作为标识符；
(5) 禁止将数据实现/数据源建模为查询单元：明确查询单元是否有数据库实现细节：在给出数据库实现提示时，若数据库实现中的要素在用户需求中未显式提及，则将其视为实现支撑，不应被显式组织为命名查询单元，也不得以任何形式影响查询单元的命名：查询单元的本身定义需要严格按照用户需求描述的口径，必须忽略实现细节；实现细节需要被包裹在单元CTE内部；

判断时遵守以下原则：

* 能单独定义“这是什么”，且能单独说明“一行代表什么”的，可作为基础查询单元候选；
* 若某语义单元需要建立在已有查询单元之上，通过组合、角色化、属性匹配、上下文附着、条件组合或其它语义变换后才成立，则更适合作为派生查询单元候选；
* 若某语义单元表达的是实体类型之间的关系类型定义，或多个实体类型之间基于属性成立的连接约束，并且该关系类型/约束本身需要被后续查询继续引用，则必须显式组织为 `*_rel_*` 或 `*_conn_*` 查询单元；禁止用连接结果的中间表示实体类型直接覆盖关系类型/基于属性约束的连接；关系类型/连接需要建模为表示对象连接的单独CTE。对于参与角色，应在CTE内对参与实体类型赋于别名以表达参与角色；
* 保持实体类型单元和关系类型/连接型单元的独立性与区分：不得用“主要实体类型连接参照实体类型”的形式替代本应独立保留的实体类型查询单元；不得用“带连接上下文的实体类型”“聚合前宽表”“附着多个外部属性后的复合实体类型单元”替代本应独立保留的关系类型/连接查询单元；
* 保持实体类型的角色区分：对于关系类型中的不同角色的同类实体类型，必须要在关系类型中显式表示出来，不得忽略角色概念；
* 单纯的属性约束、一次性局部匹配、实现桥接路径、一次性临时中间结果，默认不单独命名为查询单元。
* 查询单元定义严格按照用户需求描述口径，实现细节必须包裹在查询单元内部，不得影响单元本身的定义。

组织命名查询单元时，可以进行操作：
1. 将一个语义成分定义为为一个基础/派生命名查询单元；
2. 将多个语义成分提取/合并为基础/派生命名查询单元；
3. 从一个语义成分分解为多个基础/派生命名查询单元；

## Step 3. 全局性属性约束构建：

对上一步确定的命名查询单元，全面列举出用户需求中提出的全局性属性约束；

约束条件作用对象需要区分**作用域**：
若某个实体/关系与其被特定条件约束的子集在同一问题中同时出现，则这些额外条件通常只用于定义该子集的成员范围，属于局部属性条件，不得直接建模为该基础实体/关系的全局属性约束。
只有当某个条件作用于该实体/关系在整个问题中的全部出现，并且问题中不存在与之并列出现的更大范围全集时，才应将其视为全局属性条件。
注意：判断全局/局部时，不仅要看问题文本中是否显式出现更大范围全集，也要识别逻辑上隐含的全集。若某条件嵌套在 “X 与任意/某些/不使用满足条件的 Y” 这类量化结构中，则未受限的 Y 全集应视为隐含存在；此时该条件通常只是在定义 Y 的局部子集，而不是 Y_base 的全局条件。

(0) 重新通读用户问题原文，逐句扫描所有可能缩小分析对象范围、限定属性取值来源、限定角色/位置/时间/空间/总体适用范围的修饰语，并形成“条件候选”。这里的条件候选不仅包括显式过滤条件，也包括容易被忽略的隐含限定词，例如：时间、空间范围，对象域限定等。
约束条件的定义必须**基于全局考虑**，而不是单纯看一个字段；对于这个问题写概念查询时，某个单元如何参与总体的概念查询：一次还是多次参与，是作用在实体还是关系上，是否涉及不同的筛选条件/角色/计算口径等，基于查询需求对基础或派生语义单元作哪些属性取值约束，不得仅看问题局部的单个字段就下定义。
条件的显式建模：所有条件必须完整明确地表达，不允许假设任何隐含表示，必须全部明确表示。同时，条件约束可能会具有传递性，例如一个实体的属性约束可以通过关系/连接传递给另一个实体相连接的属性；分析连接语义，判断是否存在传递约束。

(1) 判断局部性条件：根据条件涉及的实体/关系在**整个问题**中的出现情况（不是单个命名查询单元），明确其作用域：若某个实体/关系与其被特定条件约束的子集在整个问题中同时出现，则这些额外条件通常只用于定义该子集的成员范围，属于局部属性条件，不得直接建模为该基础实体/关系的全局属性约束。
只有当某个条件作用于该实体/关系在整个问题中的全部出现，并且问题中不存在与之并列出现的更大范围全集时，才应将其视为全局性条件。

* 派生查询单元的规则：派生查询单元的所有非连接性条件本质上应该全部是局部性的，这些语义是对基础单元的进一步筛选/聚合/计算，不需要检索。

(2) 用户需求的受约束条件表示：将全局性约束条件作为该语义成分的属性常值约束或多个单元的属性之间的约束/匹配。
* 对于涉及条件表达的Conceptual SQL CTE，明确注释:Global Condition/ Local Condition

## Step 4. 构建基础实体/关系/连接查询单元集
 （1）构建基础连通查询单元集：遍历上述的查询单元整合为一个基础的查询单元集合，该基础查询单元集合应完全连通，且支持派生出所有的派生查询单元，作为查询的最小必要元素集。

 连通性的定义：实体之间必须存在直接或间接的关系或连接，使整个模型图里所有的实体保证连通。

 *  对于基础查询单元，直接添加至基础单元集合即可；

* 对于派生查询单元，必须明确其派生路径所使用的基础实体/关系/连接，并保证这些单元的存在性，如果缺失则添加至基础单元集合；派生单元本身不需要添加。

* 关系和连接应被视为独立且需要明确用**单独语义单元**表达的语义，而不是从基础实体里派生得到的，也不是由基础实体的属性隐含表示的。如果派生查询单元ent_derived/ conn_derived 里提到了基础实体之间的连接，而基础连通查询单元集里没有建模该连接，则必须将该连接也构建为一个基础查询单元。

错误案例：`_conn_derived` 依赖于 `A_ent_base` 和 `B_ent_base`，所以不构造为基础连接。这样的表述不正确：基础实体间的连接也必须构建为一个基础查询单元，而不是派生查询单元。
错误案例：`A_ent_base` 和 `B_ent_base` 存在相关的属性 （例如A_ent 有外键指向 B_ent），所以不构造`_conn`。基础单元的连接表示为明确独立的语义单元，不能用其他形式隐含表达。



## Step 5. 构造概念 SQL 并输出

完成上述全部分析步骤Step 1 - Step 4，基于已识别的语义成分、已确定的命名查询单元以及连接说明，构造概念 SQL。
概念 SQL 的首要目标是正确表达语义结构，而不是完全符合具体数据库结构的可执行 SQL。


```json
{
  "conceptual_sql": "..."
}
```

conceptual_sql 要求：
* 注意:目标不是生成可执行业务 SQL，但是必须生成“语法完整、结构稳定、便于 AST 解析和表列提取”的概念 SQL; 表、列、函数、常量可以占位表示，但必须是语法合法。
* 所有的 _derived 查询单元直接从 _base 查询单元引申得出；其数据源必须是_base的CTE，不得引用其它数据源。

约束如下：
1. 可以使用伪代码函数进行占位，但必须保持 SQL 语法完整。
2. 不允许出现 `...`、`WHERE ...`、`ON ...`、不完整函数参数、不完整表达式。
4. 每个 CTE 都必须写成完整的 `name AS (SELECT ... FROM ...)` 结构。
5. 所有引用项尽量显式起别名。
6. 默认按 Snowflake 风格书写。
