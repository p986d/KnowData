# 用户需求建模与数据库模式对齐任务

在未获取完整数据库模式信息的前提下，根据用户的自然语言需求和相关的数据库模式提示，提取涉及的对象实体类型与关系线索，用于将用户需求与数据库模式对齐。

输出目标：输出不是完整数据库 schema，而是能够回答用户问题的数据库的实体关系模型中应该有哪些实体类型和关系类型，并对齐到用户给出的具体数据库模式提示。

1. 用户提到了哪些对象实体类型，包括需求想要直接分析的直接对象以及数据库模式信息提示中涉及的中间对象。
2. 实体类型之间存在哪些语义联系关系类型，包括需求直接分析的对象间的语义关系以及到数据建库模式信息提示中的中间对象的关系。

对象数据库为 Snowflake，具体数据库模式信息可能包含三个字段：模式名（schema）、表名（table）、列名（column）。

本阶段以实体类型为主要视角，进行 **实体类型骨架的提取** ，同时定义**实体类型间的关系类型**；对每个实体类型，对其必要属性集进行描述。

## 建模目标

你需要从用户需求描述和相关的数据库模式提示中提取：

1. 对象实体类型，形成 `entity`
2. 实体类型之间的关系类型，形成 `relationship`
3. 每个实体类型的属性集描述，形成 `attr_desc`

注意：

* 本阶段需要显式指出实体类型之间存在何种语义关联，但**不要求**完整分析和枚举正式关系；
* 不要将实体实例建模为实体类型；
* 对于用户需求提及的数据库模式具体表列，为了将用户需求对齐到数据库，需要将其建模为语义清晰的实体类型、关系类型及相关属性；
* 本阶段输出的是**实体-关系骨架草稿**，不是最终定稿的实体类型-关系类型-属性定义。

## 核心建模原则

### 1. 根据用户需求和数据库模式提示的建模

实体类型、关系类型建模应符合用户需求与数据库实现 hint 的表述口径，在此之上不允许构建用户未在需求表述和数据库实现中显式提及、且无法由需求直接支持的其它语义单元。

本阶段的实体-关系建模为概念级建模：所有实体类型、关系类型与属性为类型级概念，而不是实例或字面值。

实例级/取值级提及应被规范化为某个类型级概念上的具体绑定、筛选值或约束值。

* 实体类型（entity type）是用户需求中被当作一类对象来谈论的概念，能够容纳多个可能实例，并作为后续关系、约束或统计的语义承载对象。
* 关系类型（relationship type）表示两个实体类型之间存在的具有语义的关联，本阶段根据实体类型定义关系存在性与其语义。
* 属性（attribute ）是实体类型或关系类型可能承载的性质、标识、状态、时间、位置、度量或描述维度的字段。 本阶段仅要求对实体-关系进行相关属性描述，不正式定义属性集。

### 2. 本阶段构建“实体-关系骨架”，而不是完整 ER 定义

本阶段只回答如下问题：

* 用户提及哪些对象：包括需求的直接分析对象和数据库模式提示中涉及的中间表示对象；
* 对象之间的关系线索：为了需求表示与数据库模式实现的完整性与可用性，哪些对象之间存在表示特定语义的关系。

本阶段定义关系的规范化名称与简要语义说明，但不展开关系角色、基数、可选性、关系属性及实现方式。

本阶段不直接回答如下问题：

* 不正式定义实体类型的属性集；
* 应如何执行聚合、指标计算和多阶段分析等任务

实体类型与关系的建模应保持语义独立性：每个实体类型应承载对应用户需求或数据库模式实现的特定语义部分，不同实体类型-关系类型间不得重复；由所有实体类型-关系类型集合构成对用户需求的完整表示覆盖。关系类型语义应独立于实体类型，在实体类型的属性描述中不应重复由关系表达的语义。

关系类型的基础性：若用户显式声明或数据库模式声明某个关系类型需要通过多个中间对象实体类型、映射关系类型或桥接路径链接得到，则本阶段优先建模这些基础关系类型，而不将其传递闭包的关系链条直接作为一个 `relationship` 输出。  

### 4. Entity 的定义

`entity` 表示对应需求中的业务含义或数据库实现模式结构的语义实体类型，包括：

* 相关业务 / 参照维度对象
* 事实 / 事件对象

本阶段的`entity`应优先定义为**可直接对齐到数据库模式的实体类型集**，包括：
  * 用户需求显式提及的业务实体类型
  * 数据库模式信息中涉及的构成关系中间表示的中间实体类型、桥梁对象
  * 用于分析需求的维度实体类型

每个 `entity` 包含：

* `name`
* `desc`
* `grain`
* `role`
* `attr_desc`

其中：

* `role` 只能取：
  * `fact`
  * `dimension`

`role` 的含义：

* `fact`：承载事件、行为、记录等事实记录；
* `dimension`：用于描述、分类、限定、标识的稳定实体记录。

`grain` 定义该实体类型在需求表示中的粒度，例如“一次交易事件记录”，“一件商品”，“一家店在一个时间段的销售事实”
`desc` 需要定义该实体类型的具体语义。特别的，如果存在某些具有二义性、模糊性的实体类型表述时，可以在描述中加以说明。

`attr_desc` 表示对当前实体类型的在用户需求与数据库模式里提及的相关属性集的描述。以自然语言形式进行，本阶段不详细展开为正式定义。属性描述应满足：

* 能对应到用户需求描述或数据库模式 hint 中的显式提及；
* 描述的是该实体类型自身可能承载的性质、标识、状态、时间、位置、数值或描述维度；
* 是类型级属性语义，而不是具体值。

### 5 Relationship 的定义

基于定义的实体类型，`relationship` 表示对应需求中的业务含义或数据库实现模式结构的语义关系谓词。关系类型的定义需要覆盖用户需求说明和数据库模式提示，将作为孤立单位的实体类型进一步的组织起来；

本阶段的 `relationship` 应优先定义为**可直接对齐到数据库模式的非传递基础关系类型**，即：
* 能由用户需求或数据库模式 hint 直接支持；
* 对应单步语义连接，而不是由多跳关系链传递推出的关系类型；
* 能为后续数据库模式对齐、连接路径展开和约束挂载提供基础支撑。

若某个语义关系类型通过多个基础关系类型组合得到，则不将其直接输出为 `relationship`；而应优先输出组成它的基础关系类型，并在相关关系类型的 `desc` 中说明其支撑的更高层语义。

每个 `relationship` 包含：

* `name`
* `desc`
* `participants`

其中：

* `name`：该关系类型的规范化语义名称，应直接表达关系类型成立的业务语义：

优先使用这类表达：

* `customer_places_order`
* `employee_works_for_department`
* `enrollment_enrolled_by_student`
* `enrollment_enroll_in_course`

禁止使用明显偏数据操作口径的关系类型命名关系，例如：

* `join`
* `lookup`
* `match`
* `map`
* `desc`：对该关系类型业务含义的简要说明，需要以实体类型的角色+业务语义谓词的形式定义；
* `participants`：参与该关系的实体类型列表；本阶段不需要详细定义实体类型在关系中的具体角色。

### 6. 用户显式提及表名、字段名或数据来源时的处理原则

用户显式提及的数据库实现信息，不应被忽略，也不应按原始字面直接建模为实体类型或关系类型；而应根据其在需求到数据库模式对齐中的语义作用，选择性转化为相关语义单元：

* 若某个数据库实现揭示了需要被显式建模的对象类别，则将其语义化为实体类型。
  该对象可以是用户直接描述的核心实体类型，也可以是用于承接中间语义、属性附着、条件约束或后续关系组织的数据库模式实现的实体类型；
  但应建模其实体类型级语义，而不是直接沿用数据库中的物理命名。
* 若某个数据库实现提及揭示了需要被显式建模的关联，则将其语义化为关系类型。
  该关联可以是用户直接描述的业务关系类型，也可以是用于承接中间语义、条件约束或后续关系组织的辅助关系类型；
  但应建模其关系类型级语义，而不是直接沿用数据库中的物理命名。
* 若某个数据库实现提及揭示了需要被显式建模的属性类别，则将其添加至相关的实体类型或关系类型的属性描述字段。

## 输出格式

在输出 JSON 之前，先基于用户需求描述与数据库模式 hint 进行**面向实体骨架建模的受约束分析**。分析目标不是复述需求，也不是提前完成完整关系、约束或聚合逻辑，而是严格确定：

* 哪些语义单元应建模为 `entity`
* 哪些语义单元应建模为 `relationship`
* 哪些语义单元应在 `entity` 或 `relationship` 的 `attr_desc` 字段进行描述；
* 哪些内容仅属于实例值、筛选条件、连接路径、聚合语义。
  请按以下顺序分析，并显式给出每一步的判断结果：

### Step 1. 识别候选语义单元

从用户需求描述和数据库模式 hint 中抽取所有与建模相关的语义单元，并区分为以下五类：

1. **候选实体类型**：表示一类可重复出现、可承载属性的对象类型；
2. **候选关系类型**：表示对象类型间存在的具有特定业务语义或数据库实现语义的连接关系；
3. **候选属性语义**：实体类型或关系类型承载的属性语义；
4. **实例/值**：实例名、字面值、筛选常量、范围值、时间值等；这些内容必须对应到特定的实体类型、关系类型的某个属性，说明其是该实体类型、关系类型的某个属性的取值、筛选值或约束值；
5. **操作**：分组键、聚合指标、排序要求、连接路径、映射规则等。这些内容必须确定相关实体类型、关系类型的作用属性，以明确作用对象

注意Step 1 仅提取语义单元并进行候选分类，不对候选实体-关系进行具体定义；不得定义实体类型的`role`；不得定义关系类型是`基础关系`还是`推导关系`。

### Step 2. 基于需求语义与 schema hint，确定需要建模的实体类型集

对 Step 1 中识别出的候选实体类型进行筛选，保留以下两类实体类型：

1. 用户需求直接分析的对象类型；
2. 虽未被用户直接作为分析对象提出，但在 schema hint 中出现，且为承接需求语义、属性附着、关系组织或后续约束所必需的中间对象类型。

对每个实体类型，说明：

* 为什么它应被建模为实体类型，属于 `fact` 还是 `dimension`；
* 与用户需求或数据库模式 hint 的对应依据，语义及粒度；
* 实体需要根据语义完成定义，而不是实际表列模式；

### Step 3. 基于需求语义与 schema hint，确定需要建模的关系类型集

首先，枚举Step 2 定义的实体类型集作为合法实体类型集；对 Step 1 中识别出的候选关系类型进行筛选 ,保留满足以下条件的关系类型：

1. 该关系的参与实体全部属于合法实体类型集，不包含任何其他实体类型；
2. 不涉及任何中间实体类型，不包含任何其它基础关系的关系类型；


对每个关系说明：

* 它连接哪些实体类型；
* 它对应的业务语义或数据库实现语义是什么；
* 如果该基础关系类型构成某个推导关系类型的传递闭包，说明其高层语义背景；


### Step 4. 为实体类型定义 `attr_desc`

对已确定实体类型编写 `attr_desc`，用自然语言概括该实体类型在用户需求与数据库模式 hint 中相关的属性集。对于提供的数据库具体模式信息，仅将与需求直接相关或与数据库查询实现相关的表列总结为属性，显然无关的表列可忽略。

要求：

* 只描述该实体类型自身可能承载的属性语义； 不展开为正式字段列表；
* 描述的是该实体类型本身的性质、标识、状态、时间、位置、数值或描述维度；
* 实例名、条件值、时间范围、聚合指标、排序要求等，应在分析过程中落实到相关实体类型、关系类型及其对应属性上，以明确其作用对象；对应属性必须在attr_desc中提及；
* 若某语义本质上依赖于当前实体类型与其他实体类型之间的关联才能成立，则不要吸收到当前实体类型的 `attr_desc` 中，而应在 `relationship` 表达。

### Step 5. 合法性审查

在生成 JSON 前，逐项检查以下问题：

1. 现有实体-关系骨架草稿是否覆盖了用户需求的表示；
2. 是否引入了用户需求与数据库模式 hint 中未明确支持的额外实体类型、关系类型或语义单元；
3. 是否将实例名、条件值、时间范围、聚合指标、排序要求落实到实体类型、关系类型的相关属性并在attr_desc里提及该属性，而不是忽略该值的语义；
4. 数据库模式相关信息是否基于语义进行建模，而不是直接复制表列名。
5. 输出的 `relationship` 是否均为可直接对齐到数据库模式的非传递基础关系类型，而不是由多跳关系链推导得到的传递闭包关系类型

只有在完成上述检查后，才输出最终 JSON 对象：

```json
{
  "entities": [
    {
      "name": "...",
      "desc": "...",
      "grain": "...",
      "role": "fact | dimension",
      "attr_desc": "..."
    }
  ],
  "relationships": [
    {
      "name": "...",
      "desc": "...",
      "participants": ["entity_a", "entity_b"]
    }
  ]
}
```
