# 用户需求建模与数据库模式对齐任务：关系优化与条件定义阶段

在未获取完整数据库模式信息的前提下，基于用户需求描述、相关数据库模式提示、已经正式确定的 `entities` 集合，对输入的关系类型进行检查优化，并定义单个实体实例集或单个关系实例集上的属性限定约束条件，形成后续查询构建可直接依赖的正式 `relationships` 与 `conditions` 集合。

输出目标：输出不是完整数据库 schema，也不是查询语句，而是经过审查、修正与细化后的 `relationships` 与 `conditions` 集合。该结果应能够更稳定地组织已经确定的实体集合，并尽可能贴近数据库实现所揭示的连接结构、关系成立边界与单个实体/条件的约束。本阶段不正式建模不同实体或关系之间的**属性**对应、对齐、映射、桥接的约束条件；

跨实体/关系属性约束可能为关系的表示，也可能是为了落实查询或数据实现而需要满足的属性匹配条件，而不是具有具体语义的关系。此类约束可在分析中作为连接依据说明，但不进入最终 relationships 或 conditions。

用户可能提供部分数据库模式相关内容作为需求的参照实现方式提示。数据库模式提示是可选的、不保证完全覆盖具体实现。数据库模式提示具有比用户需求描述口径更高的优先级，一旦提供，凡其能够更明确支撑需求语义落地的部分，应优先使用其覆盖并规范化用户的原表述与上一阶段草稿中的高层关系表述。

1. 上一阶段关系骨架中的哪些关系类型应被保留、删除、拆解、细化或补充。
2. 每个保留关系的正式语义边界、参与实体角色与 `cardinality` 应如何定义。
3. 哪些限定语义应建模为 `condition`，它们应作用于实体实例集还是关系实例集，其最小 `basis` 是什么。

对象数据库为 Snowflake，具体数据库模式信息可能包含三个字段：模式名（schema）、表名（table）、列名（column）。

本阶段以关系为主要视角，进行 **关系定义优化** 与 **条件定义**；实体优化阶段输出的 `entities` 集合是本阶段唯一合法的实体集合。本阶段不正式输出实体定义修正，也不输出查询表示。

## 建模目标

你需要基于用户需求描述、相关数据库模式提示、上一阶段 ER 骨架草稿与实体优化阶段的正式实体集合，完成以下任务：

1. 审查上一阶段 `relationship_type` 骨架，确定哪些关系应被正式保留；
2. 必要时对关系进行最小必要的增删改，使其更贴近数据库实现并能稳定组织实体语义；
3. 为每个最终保留关系正式定义：

   * `name`
   * `status`
   * `desc`
   * `participants`
   * `attr`

4. 为每个关系中的 `participants` 正式定义语义角色与 `cardinality`；
5. 识别并定义应附着在实体实例集或关系实例集上的 `conditions`；
6. 形成后续查询构建阶段可直接依赖的正式 `relationships` 与 `conditions` 集合。

注意：

* 本阶段不是从用户需求中重新抽取关系，而是**基于上一阶段骨架做受约束优化**；
* 本阶段必须以实体优化阶段输出的 `entities` 作为唯一合法实体集合，不得新增、删除或改写实体；
* 对于用户需求提及的数据库模式具体表列，应将其视为需求落地到数据库的实现证据，在必要时优先用于覆盖上一阶段骨架中的高层关系划分与条件口径；
* 本阶段输出的是**正式关系定义与条件定义**，供后续查询构建使用。

## 核心建模原则

### 0. 输入的 `entities` 是本阶段的唯一合法实体集合

本阶段所有关系的 `participants`、所有条件的 `target` 与 `basis` 中引用的实体属性，都必须来自实体优化阶段已经正式确定的 `entities` 集合。

本阶段不得因关系建模便利而新增实体、删除实体、修改实体属性归属或回写实体标识符定义；若发现当前实体集合存在不足，只能在分析中指出其影响，不得在本阶段擅自修正实体。

### 1. 基于输入的关系草稿

输入中的的 `relationship_type` 骨架是本阶段正式关系定义的基础，优先使用其中已经成立的关系线索，仅在存在明确依据时做局部修正。

本阶段不得因表达偏好、命名风格或形式整齐而任意重写上一阶段关系集合；一切修正必须有用户需求语义、数据库模式相关证据或实体优化结果支撑。

### 2. 数据库模式相关证据优先于用户高层关系表述

用户需求是建模起点，但不是最终输出口径。若用户提供了数据库模式相关内容，应优先将其作为需求落地到数据库的实现证据。
只有当这些证据揭示的是具有确定语义的稳定语义连接时，才允许其覆盖上一阶段草稿中的高层关系表述。
对于数据库模式相关内容中的实现路径、桥接方式、中间依赖、属性对应或连接步骤等内容，如果未表明为某种稳定关系语义，若其仅体现为实现层的连接依据，而未形成应独立保留的稳定关系语义，则不得仅因数据库中可连接而将其直接改写为最终 relationship。此时应保留语义上成立的关系，并仅在分析中说明其实现依据。

### 3. 本阶段进行关系优化与条件定义，而不是重新抽取全部关系

本阶段只回答如下问题：

* 上一阶段哪些关系类型已经稳定，可以直接保留；
* 上一阶段的哪些关系类型未直接对应到确定的实体，需要修正；
* 哪些关系过于高层、过于传递或边界不合理，需要局部修正；
* 哪些基础关系需要被显式保留，以贴近数据库实现并支撑后续查询构建；
* 哪些语义本质上属于实体/关系间的属性对应，而不是具有确定语义的关系,不应建模为 `relationship`;

本阶段不直接回答如下问题：

* 实体本身应承载哪些属性；
* 应如何执行聚合、指标计算、查询生成或多阶段分析；
* 查询语句中的 join 顺序、投影字段或执行细节。

### 4. 本阶段输出正式关系与条件定义，而不是新的实体-关系骨架

上一阶段的 `relationship_type` 与 `desc` 仍属于骨架级草稿描述；本阶段要将其细化为正式 `relationship` 定义，使每个关系都具备：

* 明确且稳定的语义边界；
* 合法的 `participants`；
* 合法的语义角色 `role`；
* 合法的 `cardinality`；
* 合法的关系属性 `attr`（仅在确有需要时）。

同时，本阶段需要补充上一阶段未正式展开的 `conditions`，将属性限定语义定义到正确的对象的属性上。

### 5. Relationship 的定义

`relationship` 表示多个实体具有稳定语义含义的正式关系类型，用于组织已确定的实体集合。
* 区分关系与数据连接：关系应具有稳定的语义边界，能够表达实体之间具有某种语义连接；而数据连接可能只是为了落实查询或数据实现而需要满足的属性匹配条件，并不具有具体语义。

每个 `relationship` 包含：

* `name`
* `status`
* `desc`
* `participants`
* `attr`

其中：

* `status` 只能取：

  * `unchanged`
  * `modified`
  * `added`

* `participants` 表示参与该关系的实体及其在关系中的语义角色；
* `attr` 表示关系实例本身的属性语义，仅当某属性属于参与实体之间形成的关联本身，而不属于任何一个参与实体时，才允许放入 `relationship.attr`。
* `relationship.desc` 只用于定义关系本身的稳定语义边界，不用于展开 join、lookup、match、derive、映射路径或桥接步骤。
* 若数据库模式提示提供了支持该关系成立的实现证据，应在分析部分说明其依据；不得展开操作过程。

### 6. 基础关系优先于高层关系

本阶段的关系优化应优先保留**基础关系类型**，即：

* 在当前输入中具有明确语义支撑的关系；
* 优先对应单步语义连接，而不是由多跳关系链传递推出的高层关系；
* 能为后续数据库模式对齐、连接路径展开和条件挂载提供基础支撑；
* 当存在数据库模式相关证据时，优先采用数据库实现能够明确支撑的关系口径来覆盖用户原始高层关系表述。

若某个用户高层关系可通过多个基础关系组合得到，则通常不将其直接保留为最终 `relationship`；而应优先输出组成它的基础关系，并在相关关系的 `desc` 中说明其支撑或覆盖的更高层语义。

### 7. participants 与 `cardinality` 的定义

每个 participant 包含：

* `entity`
* `role`
* `cardinality`

其中：

* `entity`：必须填写实体优化阶段已经确定的实体名；
* `role`：该实体在当前关系中的语义角色；
* `cardinality`：在固定其他所有 participant 实例的前提下，语义上该角色最多可对应多少个该实体实例。

`cardinality` 只能取：

* `one`
* `many`
* `unknown`

要求：

* 若用户需求或数据库模式相关证据足以支持判断，则给出保守但明确的 `cardinality`；
* 若无法稳定判断，则使用 `unknown`；
* 不得仅依据惯常数据库实现模式、常见主外键设计习惯或表名猜测来细化 cardinality；只有在当前输入确有稳定支撑时才给出明确判断。
* `cardinality` 的判断必须与实体的 `grain` 与标识符语义保持一致。

### 8. Relationship Attribute 的定义

`relationship.attr` 是一个可选域，表示关系实例本身的属性语义。仅当某个属性描述的是参与实体之间形成的关联，而不是任何一个参与实体自身的属性时，才应将其建模为 `relationship.attr`。

例如：

* 学生-选课-课程关系上的成绩；
* 教师-任职-部门关系上的开始时间 / 结束时间。

不要把明显属于某个实体本身的属性错误挂到关系上；若某语义可以归属于某个实体自身，则优先保留在实体优化阶段定义的属性集合中。

### 9. Condition 的定义

`condition` 表示作用于一个或多个实体类型或关系类型的属性限定语义，其作用是缩小这些对象各自实例集合的范围。
`condition` 仅用于表达该对象自身属性的常量相关的限定取值。
`condition` 不用于表达不同实体或关系之间的属性匹配、时间对齐、编码映射、空间落位、桥接路径或其他跨对象对应关系。

每个 `condition` 包含：

* `name`
* `target`
* `basis`
* `condition_desc`

其中：

* `target`：该条件所作用的实体类型或关系类型；当多个实体/关系有同类属性时，一个条件可以作用于多个实体/关系；这表示多个对象各自满足同一约束，不表示这些对象之间的属性对应关系被正式建模；
* `basis`：该条件定义所依赖的属性；
* `condition_desc`：基于 `basis` 的语义单位对条件的描述。

### 10. Condition 与关系、实现路径的区分

一条语义说明可判为 `condition`，当且仅当：

1. 它表达的是实体类型或关系类型自身属性上的限定；
2. 加上该条件后，被缩小的是该对象自身的保留范围，而不是不同对象之间的连接方式。
3. 它必须基于常量型取值、范围、集合或阈值，而不是多个不同语义单元属性（变量）之间的关系。

以下内容不应写入 condition：

* 不同实体或关系之间的属性对应关系；
* 对齐规则；
* 映射路径；
* 桥接过程；
* 派生步骤；
* 输出字段来源说明；
* 分组、排序、排名；
* 数据操作层面的 join、lookup、match、derive 过程。

若某条语义说明表达的是不同对象之间如何通过属性对应、时间对齐、空间映射或桥接过程建立连接，则它不属于 condition。
但若同一常量型限定语义同时作用于多个对象的同类属性，可以合并为一个 `condition`；
此时该 `condition` 只是把多个对象上的并列限定合并表达，不表示这些属性之间存在被正式建模的对应、相等或映射关系。
 这类内容仅可作为分析中的连接依据说明，不进入最终 conditions 集合。

### 11. `basis` 的定义

`basis` 表示约束条件直接作用的实体/关系的属性：

* 实体属性：`entity_name.attr_name`
* 关系属性：`relationship_name.attr_name`

要求：
basis 只保留判断当前条件成立所必需的已建模语义单位。
若同一常量型限定语义同时作用于多个对象的同类属性，则 `basis` 可以包含多个实体的同类属性；
此时仅表示这些属性分别受到同一限定，不表示这些属性之间的对应、相等或映射关系被建模。
不得为了追溯实现路径而把额外的桥接关系、中间对象或跨对象属性对应机械写入 basis。

### 12. relationship、condition 与跨对象属性对应的边界
`relationship`: 用于表达多个实体之间具有稳定语义边界的正式连接。
`condition`: 用于表达一个或多个实体实例集或关系实例集各自属性上的常量型限定；若同时作用于多个对象，表示共享约束的合并表达，而不是对象之间的属性对应关系。
`cross-object attribute correspondence`: 不同实体或关系之间的属性匹配、时间对齐、编码映射、空间落位、区间命中或其他跨对象对应关系，通常用于数据连接、筛选、聚合等任务，不属于本阶段的正式 relationship 或 condition；除非其本身已形成应独立保留的稳定关系语义，否则仅在分析中作为连接依据说明。

### 13. 用户显式提及表名、字段名或数据来源时的处理原则

用户显式提及的数据库实现信息，不应被忽略，也不应按原始字面直接复制为关系或条件；而应根据其在需求到数据库模式对齐中的语义作用，选择性转化为正式关系定义与条件定义中的相关语义单元。

若某个数据库实现揭示了某个单独实体实例集或单独关系实例集自身的属性限定条件，则将其语义化为 condition；
若某个数据库实现揭示的是不同对象之间的属性对应、连接依据、桥接方式或映射路径，则不要将其建模为 condition。

## 输出格式

在输出 JSON 之前，先基于**全部输入中可识别的用户需求语义、数据库模式相关证据、正式实体集合与关系草图**，进行**面向关系优化与条件定义的受约束分析**。分析目标不是复述需求，也不是从头创建全新的关系集合，而是严格确定：

* 哪些语义单元应正式定义为 `relationship`；
* 哪些限定语义应正式定义为 `condition`；
* 哪些关系应被数据库实现口径覆盖、细化、拆解、合并或删除；
* 哪些关系本身不具有稳定关系语义，而仅是数据连接；
* 哪些内容仅属于实现路径、连接步骤、映射规则、筛选值、聚合语义或查询组织要求而不进入本阶段输出。

请按以下顺序分析，显式给出每一步的判断结果：

### Step 0. 概括与关系优化和条件定义直接相关的需求语义、当前实体集合与关系草图

仅概括与关系优化和条件定义直接相关的需求语义，不复述聚合指标、排序规则、输出组织要求或查询步骤。

对上一阶段关系骨架，区分为：

* 明显稳定、可直接保留的关系；
* 实体边界或命名存在模糊性的关系；
* 用户需求口径表述、未确定数据库实现的关系；
* 可能需要因数据库实现证据而显式保留、但仍需判断其是否具有稳定语义边界的中间关系，还是仅是用于数据连接、匹配等的语义单元的属性对应约束。
**注意不要混淆关系与条件**：条件是对单个实体实例集或单个关系实例集自身属性的筛选/限定语义，而不是不同对象之间的匹配、对齐、映射、桥接或命中关系。
**注意不要混淆关系与数据连接**


### Step 1. 确定最终需要保留的正式关系集
对最终关系集合做受约束筛选与优化。

对每个最终保留关系，说明：

* 为什么它应被正式保留为关系；是否表达出了实体之间具有某种语义的连接；
* 它是否是原子性的基础关系，而不能是由多个基础关系传递性构成的。

在确定正式关系集时，意味着整个需求的语义框架已确定。此时需要以现有的实体-关系为语义单元的约束范围，仅用当前实体与候选关系描述需求中的连接框架，以检查现有实体-关系集是否连通、是否覆盖需求中的连接语义

### Step 2. 为每个关系正式定义 participants、语义角色与 `cardinality`

对每个已确定关系，正式定义其 `participants`。每个 participant 必须满足：

* `entity` 来自当前正式实体集合；
* `role` 能表达该实体在关系中的稳定语义角色；
* `cardinality` 在当前输入支持下给出保守但明确的判断，若无法稳定判断则使用 `unknown`。

对每个 participant，显式说明：

* 为什么该实体应作为该关系的参与者；
* 为什么该语义角色成立；
* 为什么其 `cardinality` 是 `one`、`many` 或 `unknown`。

### Step 3. 判断是否存在合法的 `relationship.attr`

对每个已确定关系，判断是否存在应附着于关系实例本身的属性。

要求：

* 若某语义明显属于某个参与实体自身，则不得放入 `relationship.attr`；
* 仅当该语义属于实体之间形成的关联本身时，才允许建模为 `relationship.attr`；
* 若不存在合法的关系属性，则显式说明该关系的 `attr` 为空。


### Step 4. 识别候选条件

基于用户需求、数据库模式提示、上一阶段骨架与当前正式实体关系集合，识别所有可能需要建模为条件的语义说明。

将候选条件区分为：

* 作用于单个实体/关系类型的属性的条件；
* 作用于多个实体/关系类型的同类属性的共享条件；
* 属于跨对象属性约束、实现路径、桥接步骤、映射规则或查询组织要求而不应建模为条件的内容。

注意：条件是问题的语义限定，而不是数据库实现；数据库实现所提到的需求语义到实现语义映射不是条件。

### Step 5. 为每个条件确定 `target`、 `basis` 与 `condition_desc`

对每个最终保留条件，正式定义：

* `name`
* `target`
* `basis`
* `condition_desc`

对每个条件，显式说明：

* 作用域是一个或多个实体/关系各自的属性限定，而不是跨对象属性对应；
* 为什么它应建模为条件，而不是关系或属性；
* 为什么它应作用于当前 `target`；
* `basis` 可以包含多个语义单元的属性，但仅限于同一常量型限定语义并列作用于同类属性；这不表示这些属性之间的对应、相等或映射关系被正式建模。
* 若上一阶段或用户原表述中该语义更像实现路径，应说明为何不直接照搬为条件。

### Step 6. 做最终合法性审查

在生成 JSON 前，逐项检查以下问题：

1. 是否仍以“关系优化 + 条件定义”为目标，而不是重新从头创建了一套新关系集合；
2. 是否严格以实体优化阶段输出的 `entities` 作为唯一合法实体集合；
3. 是否引入了用户需求、数据库模式提示、上一阶段骨架与当前实体集合中均无依据的额外关系或条件；
4. 是否优先使用数据库模式相关证据覆盖并规范化了上一阶段草稿中的高层、不稳定关系口径；
5. 是否避免将实现路径、映射过程、join 步骤、聚合与排序要求误建模为关系或条件；
6. 是否每个关系都给出了合法的 `participants`、语义角色与 `cardinality`；
7. 是否每个条件都给出了合法的 `target` 与 `basis`；
8. 最终关系集与条件集是否足以支撑后续查询构建。
9. 是否将不同实体或关系之间的属性对应、时间对齐、空间映射、桥接或命中关系误写成了 `condition`；
10. 是否将数据库实现中的中间桥接结构仅因可连接而误提升为最终 `relationship`。

只有在完成上述检查后，才允许将输出整理为最终 JSON 对象：

```json
{
  "relationships": [
    {
      "name": "...",
      "status": "unchanged | modified | added",
      "desc": "...",
      "participants": [
        {
          "entity": "...",
          "role": "...",
          "cardinality": "one | many | unknown"
        }
      ],
      "attr": [
        {
          "name": "...",
          "desc": "..."
        }
      ]
    }
  ],
  "conditions": [
    {
      "name": "...",
      "target": [],
      "basis": [],
      "condition_desc": "..."
    }
  ]
}
```
