# 用户需求建模与数据库模式对齐任务

在未获取完整数据库模式信息的前提下，根据用户的自然语言需求和相关的数据库模式提示，提取涉及的实体对象与像相关的属性字段，表示一组 `entity` 及其相关 `attr`，用于将用户需求与数据库模式对齐，以支持后续数据分析工作。

输出目标：输出不是具体数据库 schema，而是能够回答用户问题的数据库的实体关系模型中应该有哪些实体和属性集，并对齐到用户给出的具体数据库模式提示。

* 用户提到了哪些对象实体类型，包括需求想要直接分析的直接对象以及数据库模式信息提示中涉及的中间对象。
* 每个对象实体类型有哪些语义属性

对象数据库为Snowflake, 具体数据库模式信息可能包含三个字段：模式名（schema）、表名（table）、列名（column）。

本阶段进行 **实体与属性抽取** ，为关系建模与数据库支持等后续步骤提供基础。

## 建模目标

你需要从用户需求描述和相关的数据库模式提示中提取：

1. 对象实体类型，形成 `entity`
2. 实体类型相关的属性语义，形成 `entity.attr`

注意:

* 本阶段可以考虑关系，但不需要具体分析和枚举实体间的关系；
* 不要将实例建模为实体；
* 对于用户需求提起的数据库模式的具体表列，为了将用户需求对齐到数据库，需要将其建模为语义表述清晰的实体-属性。

## 核心建模原则

### 1. 根据用户需求和数据库模式提示的建模

实体与属性的建模应符合用户需求与数据库实现hint的表述口径，在此之上不允许构建用户未在需求表述和数据库实现中显式提及的其它实体-属性。
实例级/取值级提及应被规范化为某个类型级概念上的具体绑定、筛选值或约束值。

本阶段建模的实体与属性，均应是类型级概念，而不是实例或字面值。

* 实体类型（entity type）是用户需求中被当作一类对象来谈论的概念，能够容纳多个可能实例，并作为后续关系、约束或统计的语义承载对象。
* 属性类型（attribute type）是某个实体类型的对象普遍具有的性质、标识、状态、时间、位置、度量或描述维度，应能作为该实体类型实例上的一般性取值槽位。
* 实例级/取值级提及（instance/value-level mention）是某个实体实例、属性取值、过滤常量、范围值或命名对象，只是在当前查询中用于限定范围、指定上下文或给出具体条件；这些条件需要对应到具体的实体-属性，作为属性取值存在。

应建模“对象实体类型 / 属性类型”，而不是“此处出现的具体值”；但具体值应能回挂到某个对应的实体-属性类型概念上。

### 2. 本阶段只建模实体 - 属性语义

本阶段只回答如下问题：

* 用户提及哪些对象：包括需求的直接分析对象和数据库模式提示中涉及的中间表示对象
* 每个对象本身有哪些属性语义

本阶段不直接回答如下问题：

* 对象之间是什么关系，哪些条件限制了对象的实例范围
* 应如何执行聚合、指标计算和多阶段分析等任务

如果某个语义单元仅基于实体的关系而不是单个实体，则本阶段不要提前结构化为实体的属性 - 在后续阶段组织为关系的属性。

实体与属性的建模应保持语义独立性：每个实体应承载其自身对象语义的属性集合，不同实体不应大面积重复承载同一字段语义。
当某字段语义已经归属于一个最合适的实体时，其他实体与该字段的相关性不在本阶段通过重复属性表达，而应在后续关系建模阶段体现。
但避免属性重复，并不意味着将原本具有独立对象语义的内容并入其他实体；若一组语义描述的是另一类稳定对象或事实类型，仍应保持其独立实体建模。

### 3. Entity 的定义

`entity` 表示对象实体类型，包括：

* 普通业务对象
* 事实 / 事件对象

每个 `entity` 包含：

* `name`
* `desc`
* `role`
* `identifier_attrs`
* `identifier_source`
* `attr`

其中：

* `role` 只能取：
  * `fact`
  * `dimension`

`role` 的含义：

* `fact`：承载事件、行为、记录等事实记录： 表示在特定时间、地点、参与主体的事件实例的一次记录；
* `dimension`：用于描述、分类、限定、标识的稳定实体的实例的记录：

标识符属性集：`identifier_attrs` 的含义：

* 用于唯一标识该实体的最小属性集合，优先选择用户需求或数据库实现 hint 中显式提及的标识符属性；
* 若未显式提及，但可由需求语义直接支持自然标识属性组合，则使用自然标识属性组合；
* 每个实体都应给出标识符属性集；当需求中不存在可直接支持的显式标识符或自然标识组合时，才允许引入抽象占位标识符，并将 `identifier_source` 置为 `introduced`。

`identifier_source` 表示 `identifier_attrs` 的来源分类：

* `explicit`：用户需求或数据库模式提示中显式提及的标识符
* `natural`：由需求语义可直接支持的自然标识属性组合
* `introduced`：为满足建模所需而补充的抽象占位标识符；仅当该实体不存在可直接支持的显式标识符或自然标识组合时允许。

属性集 `attr`：实体相关的属性字段集合

### 4. Attribute 的定义

`attr` 表示某个实体类型的属性语义字段。

要求：

* 每个属性必须是用户需求与数据库模式描述显式提及字段的对应。
* 属性必须描述该实体实例本身的性质、状态、类别、标识信息、时间信息、数值信息或其他直接相关特征
* 不要把聚合结果、排序结果等中间表示当作属性；不要把对象之间的连接条件、映射路径、对齐规则当作属性
* 不要把实例级/取值级内容作为属性

### 4.1 实体标识符属性

  用于唯一标识该实体的最小属性集合，每个实体必须定义标识符属性集；优先使用显式提及的标识符属性，其次使用需求与数据库模式描述显式提及字段对应的自然标识属性组合；
  标识符与自然标识属性必须对应于在用户需求或数据库模式描述中显式提及的字段。

  唯一例外：仅当该实体在建模上必须具备标识能力、且无法使用需求与模式描述的相关属性唯一标识该实体实例时，才允许补充抽象标识符属性，并将 `identifier_source` 置为 `introduced`；不要仅为形式完整而无依据地补造技术键。补充抽象标识符命名后缀必须为"_sk_id"，说明这是抽象技术键(surrogate key)。

### 4.2 字段语义独立性原则

当用户需求或数据库 schema hint 提及某个字段时，原则上应该仅对应一个最合适的实体上定义，不应因为其他实体与该字段存在映射、归属、关联或可间接获得的关系，就在多个实体上重复定义为属性。
若其他实体与该字段语义相关，这种相关性应在后续步骤中通过实体之间的关系建模来表达，而不是通过重复添加相同或相近属性来表达。

### 4.3 关系/引用语义与属性语义区分

两独立建模实体之间的关联、归属、指向或连接不应在此处建模为当前实体的属性。每个实体的属性只记录本身的属性，不建模对其它实体的引用。该类关联语义在后续关系建模阶段表达。

### 5. 用户显式提及表名、字段名或数据来源时的处理原则

用户显式提及的数据库实现信息，不应被忽略，也不应按原始字面直接建模为实体或属性；而应根据其在需求到数据库模式对齐中的语义作用，选择性转化为 ER 模型中的相关语义单元。

* 若某个数据库实现提及揭示了需要被显式建模的对象类别，则将其语义化为实体类型。
  该对象可以是用户直接描述的核心对象，也可以是用于承接中间语义、属性附着、条件约束或后续关系组织的辅助对象；
  但应建模其实体类型级语义，而不是直接沿用数据库中的物理命名。
* 若某个数据库实现提及表达的是某类对象上稳定存在的一般性质、标识、时间、位置、度量或描述维度，则将其语义化为属性类型，并挂接到相应实体类型上。
* 表达具体实例、取值等条件的，必须将其落实到某个实体、属性类型的约束条件；本阶段不输出约束条件，仅定义其约束的实体-属性。

## 输出格式

在输出 JSON 之前，先基于用户需求描述与数据库模式 hint 进行**面向实体-属性建模结果的约束化分析**。分析目标不是复述需求，也不是提前建模关系、约束或聚合逻辑，而是严格确定：**哪些语义单元应建模为 entity，哪些语义单元应建模为 entity.attr，哪些内容仅属于实例值、筛选条件、连接路径或聚合语义而不进入本阶段输出。**

请按以下顺序分析，并显式给出每一步的判断结果：

### Step 1. 识别候选语义单元，并区分类型级概念与作用级内容

从用户需求描述和数据库模式 hint 中抽取所有与建模相关的语义提及，并区分为以下四类：

1. **候选实体**：表示一类可重复出现、可承载属性的对象类型，包括稳定对象、事实记录、事件记录、观测记录、中间承载对象；
2. **候选属性**：表示某类对象实例自身的标识、状态、类别、时间、位置、度量或描述维度；
3. **值**：实例名、字面值、筛选常量、范围值、时间值等；这些内容必须确定相关 entity.attr，说明其是该属性的取值、筛选值或约束值；
4. **操作**：分组键、聚合指标、排序要求、连接路径、映射规则等；这些内容必须确定相关 entity.attr，说明其作用对象。

### Step 2. 基于需求语义与 schema hint，确定最终需要建模的实体

对 Step 1 中识别出的候选实体进行筛选，只保留以下两类实体：

1. **用户需求直接分析的对象类型**；
2. **虽未被用户直接作为分析对象提出，但在 schema hint 中出现，且为承接需求语义、属性附着、后续约束或关系组织所必需的中间对象类型**。

不要将数据库模式提示中出现的表名、列名，直接映射为实体。数据库模式提及的表列可以分为两类：一类为用户需求的直接承载的实体-属性，另一类为数据库实现中的中间表示实体 - 属性。
你需要理解每个数据库模式的表列的实际语义，并根据上述两类实体类型分类，再基于语义定义实体。对中间表示实体，你需要将其表述为独立的实体，而不能将其定义为某种关系的中间表示。

对每个保留实体，说明：

* 为什么它应被建模为实体；
* 它属于 `fact` 还是 `dimension`；
* 它与用户需求或数据库模式 hint 的对应依据。

### Step 3. 为每个实体分配属性，并标明来源

对每个已确定实体，定义并将其写成 `entity.attr`。每个属性必须满足：

* 能对应到用户需求描述或数据库模式 hint 中的显式提及；
* 描述的是该实体实例本身的性质、标识、状态、时间、位置、数值或描述维度；
* 描述的是实例名、条件值、时间范围、聚合指标、排序要求对应的属性类型，而不是单纯的值。

对每个属性，显式说明：

* 它来自 **用户直接提及** 还是 **数据库模式提示**；注意**用户提及的数据库模式**的部分属性
* 它是用户需求直接声明需要的属性，还是数据库模式实现中用于中间表示、计算等步骤的实现属性；
* 它为什么归属于当前实体，而不应重复挂到其他实体。

若某可用于连接、映射或定位到其他实体，不要把它建模为当前实体对其他实体的引用属性；关联语义留到后续关系建模阶段处理。

### Step 4. 为每个实体确定标识符属性集

对每个实体，给出能够唯一标识该实体实例的最小属性集合 `identifier_attrs`，并判断其来源 `identifier_source`：

* `explicit`：用户需求或数据库模式 hint 中显式提及的标识符；
* `natural`：由需求语义可直接支持的自然标识属性组合；
* `introduced`：仅当无法从已提及语义中得到可用标识时，才允许引入抽象占位标识符，且名称必须以 `_sk_id` 结尾。

注意：

* 尽可能不引入抽象标识符；
* 不要把仅用于连接其他实体的引用字段误当作当前实体的标识符；
* 标识符属性也必须服从本阶段的实体归属规则。

### Step 5. 做最终合法性审查

在生成 JSON 前，逐项检查以下问题：

1. 是否引入了用户需求与数据库模式 hint 中未明确支持的额外实体或属性；
2. 是否将实例名、条件值、时间范围、聚合指标、排序要求对应到相应的属性类型，而不是将单纯的值建模为属性，或忽略该值的语义。
3. 是否避免同一字段语义重复挂载到多个实体上；
4. 是否把实体之间的关联、归属、映射或连接语义误建模为属性；
5. 是否每个实体都给出了合法的 `identifier_attrs` 和 `identifier_source`；
6. 数据库模式相关信息是否被基于语义建模为实体-属性，而不是直接复制表列名。

只有在完成上述检查后，才输出最终 JSON对象：

```json
{
  "entities": [
    {
      "name": "...",
      "desc": "...",
      "role": "fact | dimension ",
      "identifier_attrs": [],
      "identifier_source": "explicit | natural | introduced",
      "attr": [
        {
          "name": "...",
          "desc": "..."
        }
      ]
    },
    ...
  ]
}
```
