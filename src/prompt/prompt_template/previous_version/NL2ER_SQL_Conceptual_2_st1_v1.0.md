## 任务定义

你的任务是根据全部输入中可识别的用户需求语义与数据库模式相关证据，识别并组织当前问题中的**命名查询单元（Named Query Units）**，构造一个**面向问题表达的概念查询骨架（Conceptual Query Skeleton）**。

这里的概念查询骨架不是要求生成一条可直接执行的数据库 SQL，或是完整的数据库 schema 结构。
它用于表达：

* 用户真正想分析的语义对象与分析主轴；
* 构建整个问题的分析语义对象序列与子问题依赖关系；
* 哪些中间语义结果需要被显式保留，以清楚表达问题的求解过程；
* 后续语义步骤如何依赖前序步骤逐步形成；
* 数据库模式相关证据如何用于将需求语义对齐到可能的实现结构。

本任务的目的是将用户问题组织为**符合用户表述口径的概念查询骨架**，明确哪些语义成分应被显式保留为命名查询单元，以及这些查询单元之间的依赖结构。

注意：本阶段的输出首先是**问题表达层 / 推理表达层**，不是最终的 ER 检索规格。
本阶段不负责定义查询单元的字段属性集合，也不负责生成最终的概念 SQL。

---

## 核心原则：并非所有语义成分都应成为命名查询单元

问题中的对象、字段、条件、连接依据、分组聚合要求等，都属于需要识别的语义成分；
但**并非所有语义成分都应被显式组织为命名查询单元**。

只有在当前问题中满足以下条件的语义成分，才值得被显式命名为查询单元：

1. 具有相对独立且稳定的语义边界，能够单独说明“它是什么”；
2. 能够单独定义粒度与成员范围，能够说明“一行代表什么”；
3. 在当前问题的求解过程中，值得作为阶段性语义结果被后续步骤继续引用；
4. 在当前问题中需要被显式保留，而不只是一次性临时桥接、局部匹配或实现支撑步骤。

其中需要特别注意：

* 用户需求中被直接表达、且对问题成立有直接作用的对象间连接，不应因为其属于连接就自动退化为局部 `JOIN ... ON ...` 条件；
* 但并非所有连接都必须拆成独立查询单元；只有当该连接在问题表达过程中形成值得单独保留和继续引用的中间语义结果时，才应显式组织为查询单元；
* 命名查询单元优先服务于**清楚表达查询计划**，而不是提前完成最终基础实体/关系/连接模型的收敛；
* 对于数据实现提示中的空间映射、编码映射、桥接路径、键关联路径等实现相关内容，不单独组织为概念层查询单元，而应隐藏在相应查询单元内部作为实现支撑表达；
* 即使输入中显式提供了某个需求语义单元对应的数据库实现线索，这些实现对象也仍仅属于该语义单元内部的实现支撑来源，不得因此上升为新的概念层查询单元。

其余语义成分应作为：

* 查询单元的属性；
* 属性上的常值约束；
* 查询单元之间的局部连接条件或属性匹配条件；
* 实现支撑路径；
* 分组、聚合、排序等分析操作

附着在相关查询单元上，而不应自动成为独立查询单元。

---

## 2.2 值得单独命名的查询语义单元

**值得单独命名的查询语义单元**，指的是在当前问题中具有相对独立且稳定的语义边界、能够单独定义粒度与成员范围，并且值得作为整体被后续查询步骤继续引用的查询语义对象。

只有这类语义单元才应被显式组织为命名查询单元。

需要注意：

* 对象语义单元、关系类型语义单元，以及在当前问题中需要被独立保留的连接语义单元，都可能成为命名查询单元；
* 连接语义单元是否需要显式组织，不以前置地区分其属于“稳定关系类型”还是“属性匹配”为条件；只要该连接在问题表达中需要被独立保留，就可以先被视为查询单元候选；
* 数据库实现提示中的实现相关来源：表、列、值等，需要作为需求语义的实现，被包含在相关语义单元内部，不得独立建模或影响命名查询单元。

下列内容默认**不应**单独命名为查询单元，除非它们在当前问题中确实形成独立查询步骤或独立中间结果：

* 关系的参与实体的不同角色：角色语义应包含在关系中，而不是独立作为查询单元；
* 单纯的属性常值约束；
* 单纯的时间范围、类别范围、状态范围；
* 单纯的一次性跨单元属性匹配或时间对齐；
* 单纯的空间映射、编码映射、键关联、桥接路径；
* 只为一次局部连接服务的临时中间结果；
* 仅作为实现支撑而存在的局部步骤。

---

## 2.3 查询语义单元

在本任务中，只有被判定为值得单独命名的语义单元，才进一步组织为以下几类命名查询单元与来源对象。

### 1. 核心查询单元（Core Query Unit）

起始查询单元是指：**在当前概念查询计划中，不依赖此前已命名查询单元、作为其它查询单元依赖对象的起始查询单元**。

它通常具有以下特点：

* 具有基础性与原子性；
* 具有相对稳定的语义边界；
* 可以单独定义粒度与成员范围；
* 可以直接从来源对象建立；
* 作为查询计划中的起始阶段性语义结果存在。

注意：

* 核心查询单元是一种**查询计划中的位置角色**，代表基础性、起始性，其它的查询单元必须完全依赖核心查询单元展开；
* 实体型的核心查询单元不依赖任何其它查询单元；关系/连接型的核心查询单元不依赖参与的实体核心查询单元以外的任何其它查询单元。

### 2. 后续查询单元（Subsequent Query Unit）

后续查询单元是指：**由已有查询单元经由筛选、组合、角色化、匹配、对齐、聚合、重命名、粒度变化或其它语义变换后形成的后续查询单元**。

后续查询单元的作用是：

* 组织概念查询结构中的阶段性查询结果；
* 表达某种阶段性必要的中间语义结构；
* 承载连接语义、角色信息、跨对象属性对应、条件约束、上下文补充或分析中间结果；
* 为后续表达提供可复用的中间查询输入。

注意：

* 这里的“后续”只表示其在**当前查询计划中的依赖位置**；
* 它不是最终 ER 提取阶段中“派生实体 / 派生关系 / 派生连接”的正式结论；
* 单纯的一次性桥接、局部匹配结果或局部实现路径，通常不应单独命名为后续查询单元。

### 3. 实现支撑来源（Implementation Support Source）

实现支撑来源是由数据库模式相关证据引入、用于支撑需求语义落地的实现来源或实现背景。

它们通常来自：

* schema / table / column 提示；
* 主键、外键、桥接表、映射表；
* 时间列、空间列、编码列；
* 其它能够揭示实现承载位置、连接路径或属性来源的数据库线索。

实现支撑来源的作用是：

* 为概念查询结构提供可能的实现落点；
* 支撑对用户需求语义的规范化重写；
* 提供属性来源、连接依据或路径展开的实现背景。

实现支撑的定义规则：
实现支撑需要用后缀明确分类：
根据问题语义推知该来源对象必然存在，但是来源对象的数据实现未明确在提示中给出，此时必须使用 `*_source`。
只有当输入中明确提供了某来源对象的具体数据库模式相关证据（如具体 schema、table、column 或其它可直接指向实现对象的线索）时，才可使用 `*_impl`。

注意：

* 实现支撑来源默认不直接成为命名查询单元；
* 若当前问题需要引用某类来源对象，但输入未提供其明确的数据库模式相关证据，必须使用 `*_source`` 作为抽象来源占位；不得假设存在实现，并写为 `*_impl`。只有输入存在明确的数据库模式相关证据，才能使用 `*_impl` 后缀；
* `*_impl` 与 `*_source` 都不是独立查询单元类型。

### 4. 关系类型 / 连接查询单元建模

对于关系类型/连接一类的语义要素，可以将其显式组织为关系型或连接型查询单元，其首要职责是表达参与对象之间的关系类型定义或属性连接约束；不得默认写成“表达连接完成后形成的复合实体类型结果”。

这类查询单元应优先回答：

* 连接的是哪些对象；
* 各对象在连接中的参与角色是什么；
* 连接基于哪些属性、条件或约束成立；
* 连接本身是否承载局部约束或连接属性；
* 一行代表一个什么关系类型实例或连接约束实例。

若确有需要构造复合实体类型结果，也应建立在已显式保留的关系类型/连接查询单元之上，而不应直接用复合实体类型结果替代本应保留的连接语义表达。

注意：在本阶段中，是否把某条关系/连接显式写成独立查询单元，首先取决于它是否有助于清楚表达查询计划。

---

## 2.4 连接语义的说明

在概念查询结构中，对于**已被判定为需要显式保留的连接语义单元**，可进一步说明其内部连接性质。

连接语义通常可表现为以下几种倾向：

### 1. 关系类型性连接（Relation-like）

指该连接更接近一个需要被独立保留的关系类型语义，通常具有以下特征之一：

* 参与对象结构明确；
* 存在稳定的参与角色；
* 连接自身可能承载属性或局部约束；
* 去掉具体实现路径后，该连接仍然是当前问题中的重要语义结构。

### 2. 属性匹配性连接（Connection-like）

指该连接主要用于在对象之间完成属性附着、上下文补充或分析所需的对齐，通常具有以下特征之一：

* 主要作用是补充上下文或附着属性；
* 更依赖时间对齐、类别对齐、同值匹配、条件匹配等方式；
* 连接本身通常不作为独立关系类型对象保留。

### 3. 实现支撑路径（Implementation Support Path）

指该连接在落地时所依赖的实现路径、桥接路径或局部实现依据，例如：

* 键关联；
* 桥接表路径；
* 空间映射；
* 编码映射；
* 其它实现层的连接步骤。

需要注意：

* 实现支撑路径不是概念层连接语义单元的同级替代类型；
* 它通常作为连接语义单元内部的实现支撑而存在；
* 不应直接上升为概念层对象。

注意：上述 `relation-like` / `connection-like` / `implementation-support` 更偏向**概念查询计划中的表达辅助标签**。

---

## 2.5 用户需求到概念查询结构的映射规则

用户需求中与问题成立直接相关的对象、字段、实例值、条件、连接依据和分析要求，应尽量在概念查询结构中得到对应表达。

它们可以分别落实为：

* 查询单元候选；
* 查询单元之间的连接语义；
* 连接中的参与角色；
* 实现支撑来源；
* 分组、聚合、排序等分析要求。

映射时应遵守以下原则：

* 用户提及的对象概念，优先映射为查询单元候选；
* 用户提及的字段，优先作为后续属性分析的候选来源，但本阶段不展开正式属性定义；
* 用户提及的实例值、时间值、类别值、范围值，优先作为后续条件分析的候选来源；
* 用户需求中被直接表达、且对问题成立有直接作用的对象间连接，应优先映射为连接语义单元候选，而不默认退化为局部 `JOIN` 条件；
* 该连接最终是否组织为独立查询单元，取决于它是否在当前问题中形成值得独立保留并被后续继续引用的查询语义单元；
* 与该连接落地相关的空间映射、编码映射、桥接路径、键关联路径等实现内容，不单独映射为概念层查询单元，而应尽量附着在相应查询单元内部表达；
* 不要求所有需求片段都被对象化或单独组织为查询单元；只有当某一语义成分形成独立查询语义时，才考虑将其提升为命名查询单元。

# 分析步骤

在输出命名查询单元结果之前，必须先基于以下步骤完成分析。**禁止直接输出结果**；

## Step 0. 区分用户需求与实现提示

重述问题，区分用户需求的描述与外部知识和实现提示这三种字段，明确**实现提示**的存在性与具体内容；

## Step 1. 分解问题并识别语义成分

基于用户的需求描述内容，首先将当前问题拆解为多个相互依赖的查询子问题；输出明确的子问题列表。
其次，从每个查询子问题中识别语义成分；

**数据实现不参与语义成分定义**：在识别语义成分时，禁止从数据实现识别相关内容；数据实现是对语义成分的实现支持，不得直接作为语义成分。

(1) 列举语义成分，以对象、连接、分析的自然语言形式描述：

* 对象概念；
* 对象之间的连接概念以及连接中的角色概念；
* 分组、聚合、排序、比较等分析操作；

禁止直接包括数据库模式与实体关系模型的内容：

* 数据库模式相关实现线索；
* 实体 / 关系 / 属性 / 条件的最终正式定义。

注意：

* 本步骤的目标是识别问题中的语义成分，而不是立即决定哪些成分应被组织为命名查询单元；
* 本阶段仅能定义对象、连接和分析操作作为草稿；禁止在此处直接给出最终 ER 层的实体类型 / 关系类型 / 属性正式定义。

---

## Step 2. 判断哪些语义成分应被显式组织为命名查询单元

对于 Step 1 中识别出的语义成分，判断哪些成分在当前问题中应被显式组织为命名查询单元。

迭代所有语义成分：
For Each 语义成分，必须进行如下分析：

(1) 问题相关内容列举：完整列举问题中提及该成分的内容部分，作为该查询单元表达的基准来源；

(2) 是否构建为命名查询单元：

* 适合作为可直接从基础对象建立的核心查询单元；
* 适合作为依赖已有查询单元形成的后续查询单元；
* 还是不应该独立作为查询单元，而是作为其它单元的属性 / 角色 / 条件 / 局部连接表达；
 核心查询单元与后续查询单元应分别在Conceptual SQL 中用注释标注。

(3) 查询单元类型：该查询单元主要表达的是实体类型语义、关系类型语义，还是连接语义；若是关系 / 连接，需要说明参与对象及其角色；必要时可标注其更偏 `relation-like` 或 `connection-like`；

(4) 后续查询单元的依赖关系：后续查询单元必须显式建立在一组核心查询单元之上；**其CTE中使用的数据源必须是核心查询单元**，不得虚构或引用其它表列。对于关系/连接存在角色语义的情况，用CTE的 aliase 为核心查询单元赋予角色定义，不必要基于角色重复构建核心查询单元的派生。

(5) 核心查询单元的补充：核心查询单元集合必须足够支撑所有后续查询单元；如果有一个后续查询单元缺少必要的核心查询单元，必须显式定义补充该核心查询单元，不得用简单的虚构表`*_source`/`*_impl`代替。

(6) 禁止将数据实现 / 数据源建模为查询单元：在给出数据库实现提示时，若数据库实现中的要素在用户需求中未显式提及，则将其视为实现支撑，不应被显式组织为命名查询单元，也不得以任何形式影响查询单元的命名；实现细节需要被包裹在单元 CTE 内部。


**注意：本步骤只定义查询单元本身，不定义该单元的属性字段集合。**

判断时遵守以下原则：

* 能单独定义“这一步在求什么”，且能单独说明“一行代表什么”的，可作为命名查询单元候选；
* 若某语义单元需要建立在已有查询单元之上，通过组合、角色化、属性匹配、上下文附着、条件组合或其它语义变换后才成立，则更适合作为后续查询单元候选；
* 若某语义单元表达的是实体类型之间的关系类型定义，或多个对象之间基于属性成立的连接约束，并且该语义在当前查询计划中需要被后续继续引用，则可以显式组织为关系型或连接型查询单元；
* 不得用“带连接上下文的实体类型”“聚合前宽表”“附着多个外部属性后的复合实体类型单元”替代本应独立保留的关系类型 / 连接查询表达；
* 保持角色区分：对于同类对象在关系/连接中的不同角色，必须在关系/连接查询单元中显式区分，不得忽略角色概念；同时，不应将角色区别表现为不同的查询单元定义；
* 单纯的属性约束、一次性局部匹配、实现桥接路径、一次性临时中间结果，默认不单独命名为查询单元；
* 查询单元定义严格按照用户需求描述口径，实施细节必须包裹在查询单元内部，不得影响单元本身的概念定义；


组织命名查询单元时，可以进行操作：

1. 将一个语义成分定义为一个命名查询单元；
2. 将多个语义成分提取 / 合并为一个命名查询单元；
3. 从一个语义成分分解为多个命名查询单元。
