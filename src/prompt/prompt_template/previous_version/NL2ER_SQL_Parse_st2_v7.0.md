## 一：任务定义

你的任务是：根据用户输入的查询问题与一个 SQL 形式的概念查询方案 **conceptual SQL**，提取并优化一份面向数据检索的结构化规格。

这份规格不是最终 SQL，也不是数据库实现方案，而是一份 **ER Retrieval Spec**，用于显式定义：

* 需要检索的基础实体、关系、属性连接；
* 实体 / 关系的属性；
* 单个属性的约束条件、属性间的约束条件；
* 对 conceptual SQL 中不太符合用户需求、表述有问题的属性、条件与连接表达进行适当优化。

注意：本任务是一个**独立的结构化解析与收敛任务**。  
输入中的 conceptual SQL 只是待分析的概念查询计划，不是最终 ER 规格本身。  
你需要基于整个 conceptual SQL 的全局结构，提取并收敛出最小、连通、适合数据检索的基础语义模型。

---

## 二：核心思路

本任务的核心思路不是照抄 conceptual SQL 中的 CTE 命名结果，而是：

1. 先从整体上理解 conceptual SQL 如何组织问题求解过程；
2. 再从中识别哪些对象、关系、连接和约束属于基础检索层应保留的内容；
3. 去除仅服务于局部分析、筛选、聚合、排序、Top-K、窗口计算等的中间表示；
4. 对派生步骤中暴露出的基础连接语义进行必要的回落与补充；
5. 收敛为一份最小、连通、原子化的 ER Retrieval Spec。

因此：

* conceptual SQL 中的每个 CTE 可能表达实体、关系、连接，也可能只是中间分析步骤；
* CTE 的名称、顺序、是否显式独立命名，都只是线索，不是最终 ER 分类结论；
* 是否应建模为基础实体 / 关系 / 连接，应由其在整个问题中的语义地位决定，而不是由名称后缀直接决定。

### 1. 基础语义单元

本任务中的基础语义单元，是指在整个问题中应被保留为数据检索起点的最小必要对象，包括：

* 基础实体；
* 基础关系；
* 基础连接。

它们应满足：

* 语义边界稳定；
* 粒度明确；
* 能作为问题表达中的原生对象或原生对象间联系被保留；
* 能支持 conceptual SQL 中后续中间步骤的成立。

### 2. 中间语义单元

conceptual SQL 中还可能包含大量中间语义单元，它们常由如下操作形成：

* 筛选；
* 组合；
* 角色化；
* 匹配 / 对齐；
* 聚合；
* 排序；
* Top-K；
* 窗口计算；
* 重命名；
* 粒度变化。

这些中间语义单元默认**不直接进入**最终 ER Retrieval Spec；
只有当它们暴露出某些原本未显式建模、但在基础层必须保留的实体 / 关系 / 连接时，才据此补建基础语义单元。

### 3. 实现来源

输入中的 `*_impl` / `*_source` 仅作为实现提示保留在查询单元内部，而不是作为查询单元：

* 不得提升为实体；
* 不得提升为关系；
* 不得提升为连接；
* 不得因为实现来源在 conceptual SQL 中出现，就影响概念层对象命名。

### 4. 提取边界说明

本任务提取的是基于问题、面向数据检索的**基础实体 - 关系 - 连接 - 属性 - 约束规格**。

因此：

* 是否保留某对象，取决于它是否属于基础检索骨架；
* 是否保留某连接，取决于它是否在基础层构成原生关系 / 原生连接，或可由派生步骤稳定回落得到；
* conceptual SQL 中仅服务于局部分析组织的中间步骤，不应直接转写为新的基础实体 / 关系 / 连接；
* 提取结果应保持用户问题的语义口径，不得退化为对实现表字段、桥接路径或物理筛选条件的直接转写。

## 四：提取内容

提取包括实体、关系、连接、属性以及属性约束条件五个部分。

* 关系 `relation` 指在当前问题中具有明确业务语义、应被独立保留的对象间关联；即使脱离具体实现路径，该关联本身仍成立并具有稳定含义。`relation` 可以具有明确的参与角色，并可承载关系属性。

* 连接 `connection` 指不构成独立业务关联、仅用于在对象之间完成属性匹配、对齐、上下文补充等的语义连接；其语义重点不在“关联本身是什么”，而在“对象如何通过某些属性条件连通”。

`connection` 通常不作为独立业务关系，不应与 `relation` 混淆。

属性约束条件记录 **关系 / 连接的属性匹配** 以外的属性约束：`conditions` 用于记录实体、关系、连接上的属性约束，但不重复记录 relation / connection 自身成立所依赖的锚点属性匹配，包括：

* 单个实体 / 关系 / 连接属性的常值、集合或范围约束；
* 多个实体 / 关系 / 连接之间，不以建立 relation / connection 为目的的属性比较、对应或限制条件。

## 五：提取规则

### 1. 基础实体 / 关系 / 连接的识别来源

基础实体、关系、连接的识别来源包括：

* conceptual SQL 中直接表达原生对象、原生关系、原生连接的 CTE；
* conceptual SQL 中虽未显式独立命名，但在多个步骤中稳定出现的对象与联系；
* 某些中间步骤中首次暴露出的、应回落到基础层的连接语义。

注意：

* 不得仅因某个 CTE 看起来像“起始步骤”就自动将其全部视为基础单元；
* 也不得仅因某个对象 / 连接出现在后续步骤中，就自动视其为派生单元而不进入基础模型；
* 是否属于基础层，应由其在**整个问题与整个 conceptual SQL** 中的语义地位决定。

### 2. 对实体的提取

当某对象满足以下条件时，应提取为 `entities` 中的实体类型：

* 能单独说明“它是什么”；
* 能单独定义粒度与成员范围；
* 是问题中应保留的原生对象，而不是仅服务于局部分析的复合结果；
* 其属性和标识在问题语义中稳定成立。

对于实体，应提取：

* 实体名称；
* 粒度（即一行代表什么）；
* 稳定属性；
* 必要时补充主键或识别属性。

### 3. 对关系的提取

当对象间联系满足以下条件时，应提取为 `relations` 中的关系类型：

* 该联系本身具有明确、稳定的语义；
* 去掉具体实现路径后，该联系仍然成立；
* 联系中存在明确参与对象与参与角色；
* 联系本身可能承载属性或局部约束。

对于关系，应提取：

* 关系名称；
* 粒度（即一行代表一个什么关系实例）；
* 参与实体及其角色；
* 参与实体用于建立该关系的锚点属性；
* `link_condition`；
* 关系属性。

### 4. 对连接的提取

当对象间联系主要用于属性匹配、时间 / 空间 / 类别 / 标识对齐、上下文补充，而不构成独立业务关系时，应提取为 `connections` 中的连接类型。

对于连接，应提取：

* 连接名称；
* 粒度（即一行代表一个什么连接实例）；
* 参与实体及其角色；
* 参与实体用于建立该连接的锚点属性；
* `link_condition`。

### 5. 派生步骤的处理原则

conceptual SQL 中的中间步骤默认不直接新增新的基础实体 / 关系 / 连接。  
对于中间步骤，应重点识别：

* 它依赖哪些已有对象；
* 它只是做了局部筛选 / 聚合 / 排序 / Top-K / 窗口 / 计算，还是暴露了新的基础层连接语义；
* 它是否构建了原本不连通对象之间的关系 / 连接；
* 它是否只是“带上下文的复合结果”，而非新的基础对象。

处理原则如下：

* 若某中间步骤仅表达聚合、排序、Top-K、窗口计算等分析性组织，则原则上不将其转写为新的实体 / 关系 / 连接；
* 若某中间步骤只是已有基础实体 / 关系 / 连接的局部子集或局部结果，则不得额外构建新的基础对象；
* 若某中间步骤暴露了原本未显式建模、但在基础层必须保留的关系 / 连接，则应将该关系 / 连接补建到基础模型中；
* 若某中间步骤提及未独立存在、但语义上必须保留的实体类型，则这些实体必须被显式建模并加入 `entities`。

### 6. 派生连接的回落规则

当 conceptual SQL 中出现“两个中间结果直接连接”或“连接首次出现在后续步骤中”的情况，不得机械地把中间结果本身当作新的基础实体参与连接；必须先判断该连接是否可以回落到基础层。

#### （1）可回落的情况

若该连接的依据，本质上是基础实体属性经过**确定性变换**后形成的匹配键，则该连接可以回落为基础实体之间的基础连接。

例如：

* 时间取日期部分后对齐；
* 位置映射为区域编码后对齐；
* 标准化后的类别值对齐。

此时应保留：

* 基础实体；
* 基础连接；
* 该连接的自然语言 `link_condition`；

而不应把中间结果本身建模为新的基础实体。

#### （2）不可直接回落的情况

若该连接的成立依赖：

* 聚合；
* 排序；
* Top-K；
* 窗口；
* 最近一次 / 最大值 / 最小值选择；
* 占比阈值；
* 其它分析性选择过程；

则该连接通常不应直接回落为基础实体之间的基础连接。

此时应保留其所依赖的基础实体 / 基础关系 / 基础连接，而不把该分析性连接本身压回基础层。

#### （3）子集 / 角色化情况

若某中间对象本质上只是基础实体的局部子集或角色化定义，则应尽量把连接还原到基础实体与基础关系 / 基础连接上，并把该中间对象视为局部语义，而不是新的基础实体。

### 7. 属性提取与优化规则

查询单元的属性应优先提取以下两类：

1. **核心语义属性**：用户在需求中显式提及、直接参与分析表达的属性；
2. **约束支撑属性**：虽然不是用户显式输出字段，但在 conceptual SQL 中已被显式用于实体标识、连接、匹配、角色、空间 / 时间约束等语义，且为这些约束成立所必需的属性。

属性定义检查：

* **正确性**：属性必须完全贴合用户问题的表述口径，不得创建或臆造未提及、不一致的属性；
* **必要性**：属性只在其对当前问题的对象定义、约束表达或分析目标确有直接作用时才保留；
* **原子性**：每个属性只表达一个单一稳定语义，条件、角色、派生结果或复合含义不得构建为属性。


**实体标识性属性定义**：实体的标识符属性，优先使用用户在问题中**直接提及**、且能够稳定唯一标识该实体的属性或属性组。若用户未直接提及可作为标识符的属性/属性组，则不得因为实现层通常存在主键、上下文似乎隐含存在唯一标识、或某个属性在数据库中看起来像 id，就直接将其固化为确定的概念属性名。当实体为保证建模完整性需要补充识别属性、但该标识符不是用户显式提出的属性时，必须统一命名为带 `"_surrogate_id"` 后缀的属性，例如 `customer_surrogate_id` 表示这是一个用于后续检索与对齐的**标识槽位**，不是已被用户明确确认的确定属性；只要不是用户显式提出存在的属性作为标识符，都必须使用 `"_surrogate_id"` 后缀，而不得直接写成确定属性名。

**关系属性定义**：关系的标识不通过 `relations.attributes` 重复表达，而是由 `participants`、`participants.anchor_attribute` 与 `link_condition` 共同定义。`relations.attributes` 只用于承载**关系本身的非标识性语义**，即描述“该关系实例本身还具有什么信息”的属性，例如关系发生时间、关系状态、关系数量、关系金额等；不得将参与实体的主键 / 外键、已作为 `anchor_attribute` 使用的连接锚点属性、仅用于建立关系成立的匹配字段，重复加入关系属性。若某关系在当前问题中没有独立的非标识性语义属性，则 `relations.attributes` 可以为空数组 `[]`。


属性提取时应遵守以下限制：

* 不得将仅存在于 `*_impl` / `*_source` 内部、且未在概念查询单元投影中作为概念属性显式保留的实现字段，直接提升为实体 / 关系属性；
* 不得因为某字段在实现来源中出现，就自动把它当作概念层属性；
* 若某属性虽然在 conceptual SQL 中作为投影列出现，但结合用户问题判断后更像分析结果列、临时中间列或依赖后续计算后才稳定的属性，则不得保留为基础实体 / 关系属性；
* 必要时可以对 conceptual SQL 中出现的属性进行收缩、删减、重述或降级处理，但不得脱离用户问题语义任意发明新属性。

### 8. 约束条件抽取与优化规则

约束条件是问题对基础实体 / 关系施加的、会影响最终检索范围的全局性语义约束；并非 conceptual SQL 中出现的所有过滤条件都属于 `conditions`。:contentReference[oaicite:0]{index=0}

对任一条件，必须先按以下顺序判断其语义地位：

1. **若条件用于建立 `relation` / `connection` 本身**，则应写入 `participants.anchor_attribute` 或 `link_condition`，不得进入 `conditions`。
2. **若条件仅用于定义某个对象 / 关系的局部子集**，则属于局部条件，不得进入 `conditions`。
3. **只有当条件限定了某个基础实体 / 关系在整个问题中的全部出现时**，才可作为全局条件进入 `conditions`。

判断局部 / 全局时，核心标准不是条件写在某个 CTE 的哪里，也不是它是否看起来像普通属性过滤，而是：

* 问题中是否同时存在该对象 / 关系的更大范围全集；
* 该条件是在限定对象本身的整体检索范围，还是只在定义其中一个子集。

若某个对象 / 关系与其受条件约束的子集在整个问题中同时出现，则这些额外条件通常只是在定义子集成员范围，属于局部条件。  
只有当某个条件作用于该对象 / 关系在整个问题中的全部出现，并且不存在与之并列的更大范围全集时，才应将其视为全局条件。

进入 `conditions` 的全局条件分为三类：

* `single_attribute`：作用于单个基础实体 / 关系属性的全局取值约束；
* `inter_attribute`：作用于多个基础实体 / 关系属性之间的全局对应 / 比较约束；
* `link_quantified`：作用于某个基础实体 / 关系的全局资格约束；其成立需要沿已建模的 `relation` / `connection` 路径，对相关对象集合施加存在 / 不存在 / 全部满足 / 至少一个满足等量化判断。

注意：

* `link_quantified` 不是 `relation` / `connection` 的 `link_condition`；
* 它是在 `relation` / `connection` 已成立的基础上，对相关对象集合施加额外的全局资格限制；
* 对于量化约束，默认只提升**外层资格限制**进入 `conditions`；内层用于刻画相关对象子集的谓词，默认仍视为局部子集定义条件，除非用户单独把该相关对象子集本身作为研究对象；
* 若某条件本质上是沿 `relation` / `connection` 路径成立的存在 / 不存在型资格限制，则应优先整体建模为一个 `link_quantified`，不得拆写为一个内层 `single_attribute` / `inter_attribute` 条件，再加一个外层跨对象条件；
* 若某条件仅用于定义某个中间子集，即使其写法是简单的属性过滤，也不得进入 `conditions`。

约束条件进入 `conditions` 时，需要明确：

* `condition_name`
* `condition_type`
* `targets`
* `description`

其中：

* 对于 `single_attribute` 与 `inter_attribute`，`targets` 列出被直接约束的稳定属性；
* 对于 `link_quantified`，`targets` 只列被施加资格限制的主体对象属性；路径中被量化引用到的相关对象及其谓词，只在 `description` 中说明，不得并列写入 `targets`；
* 约束必须用自然语言简明扼要地描述，禁止提及任何 conceptual SQL 中的具体实现写法。
* 进入 `conditions.targets` 的属性必须是稳定属性；不得将仅用于定义局部中间子集的临时列、派生列、聚合结果列或实现绑定字段写入 `targets`。

### 9. 全局 / 局部条件的判断规则

约束条件的定义必须基于整个问题的全局语义，而不是单纯看某个字段、某个 CTE 或某条 `WHERE` 子句。
判断时必须遵守以下顺序：

#### （1）先判断该条件是在限定“谁”

先明确该条件是在：

* 限定某个基础实体 / 关系在整个问题中的检索范围；
* 还是只在定义某个局部中间子集、局部分支、局部分析口径。

只有前者才可能进入最终 `conditions`。

#### （2）再判断该条件是否存在“更大范围全集”

若某个对象 / 关系与其被特定条件约束的子集在整个问题中同时出现，则这些额外条件通常只是在定义该子集的成员范围，属于局部条件，不得直接建模为该对象 / 关系的全局约束。

这里的“全部出现”是相对于该基础对象 / 关系在**整个问题语义中的全集**而言，而不是相对于某个局部分析支路、某个分母集合、某个分子集合或某个当前 CTE 内部的工作范围而言。

不仅要看问题文本中是否显式出现更大范围全集，也要识别逻辑上隐含的全集。

#### （3）基于查询逻辑的判断

注意：判断全局 / 局部时，不仅要看问题文本中是否显式出现更大范围全集，也要识别逻辑上隐含的全集。若某条件嵌套在 “X 与任意/某些/不使用满足条件的 Y” 这类量化结构中，则未受限的 Y 全集应视为隐含存在；此时该条件通常只是在定义 Y 的局部子集，而不是 Y 的全局条件。

#### （4）禁止误判

* 不得把局部子集定义条件误写成基础实体 / 关系的全局约束；
* 不得把“分子 / 分母支路中的当前筛选范围”误当作该对象在整个问题中的全集；
* 不得把沿关系路径成立的“存在 / 不存在 / 全称 / 至少一个”约束误写成普通 `single_attribute` 或拆散写成多个普通条件；
* 不得把 `relation` / `connection` 的锚点匹配条件重复转写进 `conditions`。

### 10. ER 建模完整性与原子性

提取结果应同时满足：

#### 完整性

* 整个基础模型中的实体应通过关系 / 连接保持连通；
* 若 conceptual SQL 中某个语义步骤构建了原本不连通对象之间的基础层关系 / 连接，则必须显式建模；
* 若关系 / 连接提及的参与实体尚未被建模，则这些实体必须补建。

#### 原子性

* 不得把“带上下文的实体类型”“聚合前宽表”“附着多个外部属性后的复合结果”误建模为新的基础实体；
* 若参与实体之间已经存在稳定的基础关系 / 基础连接，则不得重复构造仅由派生语义驱动的冗余 relation / connection；
* 若某连接只是使用了已有关系 / 连接的结果，则该连接不得再作为新的独立基础 relation / connection 建模。

### 11. 禁止事项

你必须遵守以下限制：

* 不得把 `*_impl` / `*_source` 提升为实体、关系或连接；
* 不得把实现表、映射表、桥接表、空间表直接改写为概念层对象；
* 不得把中间步骤默认理解为新的复合宽表实体；
* 不得为了让结果更像可执行 SQL 而发明输入中未明确给出的物理字段名；
* 若某条件本质上是跨对象属性约束，应保留为概念性约束表达，而不是伪造实现列名；
* 不得将仅存在于 `*_impl` / `*_source` 内部的实现字段，提升为实体 / 关系属性或 `conditions.targets`；
* 不得将 `SUM`、`COUNT`、`AVG`、`ORDER BY`、`LIMIT`、Top-K 等计算分析条件纳入 `conditions`。

---

## 六：分析步骤

在生成 JSON 形式的实体 - 关系 - 条件模型之前，必须先基于以下步骤完成分析，**禁止直接生成 Json**；

## 问题分解与语义内容连接
基于用户的需求描述内容和Conceptual SQL的查询逻辑，首先将当前问题拆解为为多个相互依赖的查询子问题，每个查询子问题对应Conceptual SQL的部分内容；

## CTE Iteration：遍历所有 CTE 和最终 SQL 的分析

在完成全局理解后，再遍历 conceptual_sql 中的所有 CTE 和最终 SQL。  
**对每个 CTE 和最终 SQL**，必须按顺序连续完成如下 Step 1 - Step 4 分析步骤；但局部分析必须服从前面的全局判断结论，严禁仅凭单个 CTE 的局部形式直接下最终定义。

For each CTE / Final SQL:

### Step 1: 语义成分识别

(1) 判断该 CTE / Final SQL 主要表达的是哪些要素：

* 基础实体；
* 基础实体间关系/连接；
* 还是局部中间表示。

(2) 若其是中间表示，判断其更偏向：

* 局部筛选结果；
* 局部匹配 / 对齐结果；
* 局部聚合 / 排序 / Top-K / 窗口结果；
* 还是暴露了应回落为基础层 relation / connection 的语义。

(3) 遵守提取规则，仅建模基础实体 / 关系 / 连接，保持实体 / 关系 / 连接的**原子性**：

* 若某中间对象只是基础对象的局部结果，则不得独立建模为 `entity` / `relation` / `connection`；
* 若某联系本质上只是已有基础 relation / connection 的重复表达，则不得重复建模；
* 对于同类实体在同一关系 / 连接中的不同角色，必须显式区分。

注意，一个CTE可能涉及多个基础语义单元，例如同时包含实体和关系。
本步骤仅确定实体 / 关系 / 连接及其中间 / 基础地位，不得在此步骤对属性和约束作最终判断。

### Step 2: 实体定义
对当前语义单元，检查其中是否包含**基础实体**，并落实为 `entity` 建模。
（1）基础实体的存在性与约束判定：对于实体语义单元，必须满足下列约束条件，才能建模为`entity`。
* 基础性约束：该实体必须为构建分析的基础单元，而不是一个关系中的带有角色语义的单元，或者作为中间表示的单元。对于带角色语义的实体，必须去除角色本身的语义进行建模。
* 原子性约束：若带有角色语义的单元，或者作为中间表示的单元的源基础实体已存在，则不重复构建 entity。

### Step 3: 关系 / 连接定义

对当前语义单元，检查其中是否包含**基础实体之间**应保留的 relation / connection；对于存在 relation / connection 语义的，必须满足下列约束，才能建模为 `relation` / `connection`。

(1) 关系/连接的存在性与约束判定：对于存在关系/连接语义的单元，必须满足下列约束条件，才能建模为`relation`/ `connection`。
* 参与者约束：关系 / 连接的参与者必须是明确定义在`entity`里的基础实体，不能以另一个关系 / 连接作为关系 / 连接的参与者；不能以未构建为实体。
* 原子性约束： 若参与者之间已经存在稳定的基础 relation / connection，则不重复建模同义 relation / connection。
* 基础性约束：若当前语义单元表面上连接的是中间对象，必须先判断其能否回落到这些中间对象所依赖的基础实体；只有回落后的基础实体之间的联系，才可进入最终 relation / connection。
* 完整性约束： 若当前语义单元首次暴露了原本不连通基础实体之间应保留的 relation / connection，则必须将该 relation / connection 显式建模，以保证模型完整性与连通性。

（2）关系 / 连接标识性属性与条件定义

对于 relation / connection，需要明确：

* 参与实体；
* 参与角色；
* 参与实体用于连接的锚点属性（anchor attributes）；
* `link_condition`。

注意：

* 锚点属性必须是参与实体的稳定属性；
* `link_condition` 必须用简短自然语言定义参与实体间的属性匹配 / 对齐 / 联系方式；
* 禁止引用 conceptual SQL 中的具体实现写法。

### Step 4: 属性定义

(1) 基于当前语义单元与全局语义结构，定义正式属性集。属性必须完整承载用户需求，并在结构上支持实体 / 关系 / 连接与约束表达。

(2) 属性命名规则：

* 任何属性，只要用户表述有直接提及，应按用户表述命名；
* conceptual SQL 中的属性、条件和连接表达是草稿，需要对照用户需求检验是否准确；
* 若不符合用户表述，必须优化后再落实为正式属性定义。

(3) 实体标识性属性定义：

* 对于实体主键 / 识别属性，优先使用用户直接提及且能唯一标识实体的属性集；
* 不得凭空发明未被问题语义支持的自然键；
* 当用户没有**直接**提及标识性属性、且不存在可用自然键时，主键属性命名必须表示为 `"_surrogate_id"` 后缀，以表示并非用户直接定义，而是为语义完整性额外补充的识别属性；
* 只要不是用户显式提出存在的属性作为标识符，标识符必须带上 `"_surrogate_id"` 后缀。

(4) relation / connection 的锚点属性必须来自参与实体的稳定属性集；relation 自身可承载关系本身的描述性属性，可写入 `relations.attributes`（不得重复写入表示关系连接的实体锚点属性；关系本身用锚点属性标识，不需要额外构建关系标识）；connection 单纯表示连接语义，一般不额外扩展非必要属性。

### Step 5: 条件约束定义

将整个问题视为全局，CTE单元视为一个局部部分，根据条件涉及的实体/关系在**整个问题**中的出现情况（不是单个CTE的局部部分），明确其作用域：若某个实体/关系与其被特定条件约束的子集在整个问题中同时出现，则这些额外条件通常只用于定义该子集的成员范围，属于局部属性条件，不得直接建模为该基础实体/关系的全局属性约束。
只有当某个条件作用于该实体/关系在整个问题中的全部出现，并且问题中不存在与之并列出现的更大范围全集时，才应将其视为全局性条件。

对每个条件，按以下顺序判断：

(1) **该条件是否在建立 `relation` / `connection` 本身**  
   若是，则应写入 `participants.anchor_attribute` 或 `link_condition`，不得进入 `conditions`。

(2) **该条件是否只是在定义某个局部子集**  
   若当前对象 / 关系在整个问题中还存在更大范围的全集，而该条件只作用于其中一个子集，则该条件属于局部条件，不得进入 `conditions`。
   局部性条件处理：对于任何派生语义单元,作用域为CTE局部的条件及在CTE中标注为 **Local Condition**的，必须视为局部性的语义，不是用于检索的内容，必须明确说明**这是局部条件，不参与建模，不在后续步骤以任何形式出现**，不添加至`conditions`。这些局部条件语义禁止在后续步骤中以任何形式来体现补充；错误添加会导致检索范围偏差。

(3) 抽取作用域为问题整体的条件：`conditions`仅允许建模**全局性的基础实体/关系上的属性约束条件**以表示对实体/关系/连接本身的属性限定；这些属性限定直接作用于检索，表示为基础的`entity`/`relationship`上的属性条件约束。明确作用对象与属性，不要将关系的约束错误表达在实体上，或者将实体约束错误表达在关系上。任何作用域为局部的条件不得被认为是全局性的，不得参与建模，避免污染检索。

* 条件约束必须用自然语言简单描述，禁止使用conceptual SQL的具体实现；

抽取进入 `conditions` 的条件时：

* 若是单个稳定属性的取值限制，建模为 `single_attribute`；
* 若是多个稳定属性之间的全局对应 / 比较，建模为 `inter_attribute`；
* 若是沿已建模的 `relation` / `connection` 路径，对相关对象集合施加存在 / 不存在 / 全部满足 / 至少一个满足等资格限制，必须整体建模为 `link_quantified`。

注意：

* 不得把局部子集定义条件误写成基础实体 / 关系的全局约束；
* 不得把 `relation` / `connection` 的成立条件重复转写进 `conditions`；
* 不得把一个本质上属于 `link_quantified` 的量化约束拆散写成一个内层普通属性条件，再加一个外层跨对象条件；
* 所有进入 `conditions` 的约束都必须用自然语言简洁描述，不得引用 conceptual SQL 的具体实现写法；
* 进入 `conditions.targets` 的属性必须是稳定属性；不得把仅用于定义局部中间子集的临时列、派生列或实现绑定字段写入 `targets`。
