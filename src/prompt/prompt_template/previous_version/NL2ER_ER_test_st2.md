# 任务定义

基于用户问题、数据库模式相关证据、外部知识，以及 **已产出的基础逻辑实体-关系草图（Object Sketch）**，完成一轮 **ER 复核 + 约束补全 + 逻辑查询草图构建**。

本阶段的目标：

* 复核基础实体、基础关系和稳定基础属性是否足以准确表达问题；
* 在必要时对 Stage1 的对象草图做最小必要修正；
* 补充 Stage1 中尚未建模的约束条件；
* 用 **逻辑查询草图（Logical Query Sketch）** 复查当前 ER 建模是否足以支撑问题语义；
* 显式指出哪些问题语义已经被当前 ER 与约束支撑，哪些仍然没有被准确承载。

这里的“逻辑查询草图”不是 SQL，也不是 CTE 序列，更不是物理执行计划。
它是一个面向语义验证的轻量查询表达，用于说明：

* 最终答案的粒度是什么；
* 查询从哪些基础实体/关系出发；
* 需要哪些连接语义；
* 需要施加哪些过滤与存在性条件；
* 需要构造哪些派生指标；
* 需要哪些分组、排序、Top-k 或最终投影；
* 这些步骤是否都能被当前的基础 ER 与约束支撑。

本阶段的核心作用，是把 Stage1 的“基础对象层”与问题中的“查询语义层”对齐，并借此复查建模表达是否准确。

---

# 基本原则

## 1. 先复核基础 ER，再补查询语义，不直接写 SQL

本阶段允许使用查询逻辑来验证建模，但禁止直接退化为 conceptual SQL 或 SQL-like 伪代码生成。

你要复核的是：

* Stage1 的实体是否真的是基础对象；
* Stage1 的关系是否真的是稳定关系；
* Stage1 的属性是否真的是稳定基础属性；
* 问题中的约束、过滤、存在性条件、时间/空间限定是否被遗漏；
* 当前 ER 是否足以支撑最终问题所需的聚合、排序、Top-k、比例、窗口或统计结果。

你不要输出：

* conceptual SQL；
* CTE；
* SELECT / FROM / JOIN / WHERE / GROUP BY / ORDER BY 等 SQL 片段；
* 物理表、列、join key 的显式执行过程；
* 任意可执行语句。

---

## 2. Stage1 Object Sketch 不是最终真相，但默认优先保留

Stage1 输出提供了一个基础对象草图，但它可能存在以下问题：

* 漏掉必要基础实体；
* 漏掉必要基础关系；
* 把本应是约束的内容漏掉；
* 把本应是基础属性的内容建模得不够准确；
* 关系粒度、命名、角色定义不够清晰；
* 用过于抽象或过于实现化的对象名表达基础对象。

本阶段必须优先做 **最小必要修正**：

* 若 Stage1 已经正确表达了基础对象，应尽量保留；
* 只有在问题语义无法被当前草图支撑时，才允许新增、删除、重命名或重分类；
* 不得为了让逻辑查询草图“更顺手”而随意重写 Stage1；
* 每个修正都必须在 `review_report.repairs` 中说明原因。

---

## 3. 约束必须单独建模，不得继续混入实体或关系

本阶段要显式补充约束条件。
约束是作用于基础实体、基础关系或稳定属性上的限制，不是新的基础对象。

常见约束包括：

* 属性取值过滤；
* 时间范围限定；
* 空间范围限定；
* 状态限定；
* 类型限定；
* 角色方向限定；
* 存在 / 不存在某类关联；
* 至少一个 / 恰好一个 / exactly one / top-k 前的候选集限定；
* 去重口径；
* distinct counting 口径。

这些内容应输出为 `constraints`，而不是重新建模为实体或关系。

---

## 4. 逻辑查询草图用于验证，而不是替代基础 ER

逻辑查询草图的作用，是检查：

* 答案能否从当前基础对象推导出来；
* 推导链条是否闭合；
* 聚合与排序依赖的对象是否齐全；
* 缺失的其实是基础对象，还是仅仅是约束条件；
* 当前实体、关系、属性是否被正确归类。

逻辑查询草图可以包含：

* `answer_grain`
* `base_scope`
* `join_semantics`
* `filters`
* `group_by`
* `derived_metrics`
* `ranking`
* `final_projection`

逻辑查询草图不得包含：

* SQL 语法；
* 物理表路径；
* 中间 CTE 名；
* 执行顺序优化细节；
* 任何可执行表达。

---

## 5. 派生内容不得回流成基础属性或基础对象

问题里很多内容是派生的，不属于基础 ER。

不得把以下内容重新写回基础实体、基础关系或稳定基础属性：

* count / sum / avg / ratio / percentage / rank / score；
* lag / lead / rolling / window 结果；
* top-k 结果集；
* grouped summary；
* “最高/最低/前 N / 后 N”结果；
* 由多个基础属性计算出的中间指标；
* 仅在当前问题分析中出现的临时集合。

这些内容只能放在 `logical_query_sketch.derived_metrics`、`ranking`、`final_projection` 等派生层中。

---

## 6. 实现证据只作支撑，不主导建模

数据库模式、表名、列名、外部知识只能作为支撑证据。
它们可以帮助你：

* 识别对象是否可落地；
* 判断某个属性是否合理；
* 判断某个关系是否确有实现支撑；
* 判断某个约束是否可能是时间、空间或存在性条件。

但它们不得：

* 直接替代用户问题的语义；
* 主导基础 ER 的抽象定义；
* 把物理字段名直接当作基础对象名；
* 把实现过程直接变成逻辑查询草图。

# 分析步骤

在输出最终 JSON 之前，必须按如下步骤，完成整个分析流程。
**禁止跳过分析**直接生成任何内容。

---

## Step 0. 分析问题背景，区分用户需求与实现提示，并设置输出语言

先重述问题，分析问题背景，并区分：

* 该问题可能涉及哪些专业领域；
* 哪些内容属于用户真正的分析需求；
* 哪些内容属于数据库模式或实现提示；
* 输入中是否提供了明确的数据实现线索；若有，具体是什么；
* 这些实现线索只能支撑哪些内容落地，但不能替代哪些语义依赖。

同时，明确用户输入问题使用的语言；后续实体、关系、属性和约束说明必须与用户语言一致。


---

## Step 1. 复核 Stage1 基础对象草图

逐项检查 Stage1 的：

* `entities`
* `relations`
* `attributes`

并判断：

* 这些实体是否都是真正的基础实体；
* 这些关系是否都是真正的基础关系；
* 是否存在粒度不对、命名不准、语义过泛或过窄的情况；
* 是否缺少为支撑问题所必需的基础对象；
* 是否把本应是约束的内容遗漏掉了；
* 是否把本应是派生内容的东西误当成了基础对象或基础属性。

本步骤的结果不是立即生成最终输出，而是形成一个 **refined_object_sketch**：

* 保留正确的内容；
* 最小必要修正错误内容；
* 仅在问题语义无法被当前草图支撑时，才补充新的基础实体或基础关系。

---

## Step 2. 构造逻辑查询草图

基于基础对象，对构造一份逻辑查询草图 conceptual SQL，用于表达：

* 最终答案粒度是什么；
* 查询从哪些基础对象出发；
* 需要哪些连接语义；
* 需要施加哪些过滤与候选集限定；
* 需要构造哪些派生指标；
* 需要哪些分组；
* 需要哪些排序或 Top-k；
* 最终返回哪些结果。

 conceptual_Sql 的数据对象是逻辑性的，基于逻辑实体关系和逻辑属性，但是其语法结构需要满足**语法完整、结构稳定、便于后续解析**；

---

## Step 3. 用逻辑查询草图反查建模是否足够

构造完逻辑查询草图后，反向检查：

* 逻辑查询草图中的基础对象是否足够覆盖查询需求；
* 每个约束是否都能落到明确的逻辑属性；
* 每个派生指标是否都能回溯到基础实体、基础关系、稳定基础属性和约束；
* 是否仍有问题语义无法被当前模型 支撑；

* 如果不能支撑，原因是：
  * Stage1 漏了基础对象；
  * Stage1 命名/粒度有误；
  * 仅仅缺少约束，还是缺少约束可作用的属性；
  * 问题本身语义存在歧义；

若发现问题，允许进行必要修正。

## Step 4. 补充约束条件

根据条件涉及的实体/关系在**整个问题**中的出现情况，明确其作用域：若某个实体/关系与其被特定条件约束的子集在整个问题中同时出现，则这些额外条件通常只用于定义该子集的成员范围，属于局部属性条件，不得直接建模为该基础实体/关系的全局属性约束。
只有当某个条件作用于该实体/关系在整个问题中的全部出现，并且问题中不存在与之并列出现的更大范围全集时，才应将其视为全局性条件。

对每个条件，按以下顺序判断：

(1) **该条件是否在建立关系本身**  
   关系的连接条件不得进入 `constraints`。

(2) **条件全局性判断**  
   若条件约束了当前实体 / 关系类型在整个问题中出现的所有可能元素集合；整个问题不会以任何形式用到这个集合以外的其它元素，则该条件约束定义了一个问题中出现的整体全集。
   若当前对象 / 关系在整个问题中还存在更大范围的全集，而该条件只作用于其中一个子集，用于数据分析、计算、条件筛选；同时问题中会涉及到其它不属于该集合的元素，则该条件属于局部条件，不得进入 `constraints`。
   局部性条件处理：不可用局部性条件来限定基础实体/关系，这会导致检索范围过小的错误，必须明确说明**这是局部条件，不参与建模，不在后续步骤以任何形式出现**，不添加至`constraints`。这些局部条件语义禁止在后续步骤中以任何形式来体现补充；错误添加会导致检索范围偏差。

(3) 抽取作用域为问题整体的条件：`constraints`仅允许建模**全局性的基础实体/关系上的属性约束条件**以表示对实体/关系/连接本身的属性限定；这些属性限定直接作用于检索，表示为基础的`entity`/`relationship`上的属性条件约束。明确作用对象与属性，不要将关系的约束错误表达在实体上，或者将实体约束错误表达在关系上。任何作用域为局部的条件不得被认为是全局性的，不得参与建模，避免污染检索。

(4) 条件可以定义在实体、关系和角色上；问题可能对某个关系的参与角色定义条件约束，而不是对该实体本身进行约束，注意区分对实体本身的限定条件与对实体在某个关系中的角色的限定条件，特别是当某个实体以多个角色参与关系时。

* 条件约束必须用自然语言简单描述，禁止使用conceptual SQL的具体实现；

抽取进入 `constraints` 的条件时：

* 若是单个稳定属性的取值限制，建模为 `single_attribute`；
* 若是多个稳定属性之间的全局对应 / 比较，建模为 `inter_attribute`；
* 涉及两个实体以上的复杂约束条件（例如两个实体+关系），由查询逻辑表示，不在此处建模。

注意：

* 不得把局部子集定义条件误写成基础实体 / 关系的全局约束；

* 所有进入 `constraints` 的约束都必须用自然语言简洁描述，不得引用 conceptual SQL 的具体实现写法；
* 进入 `constraints.based_on` 的属性必须是稳定属性；不得把仅用于定义局部中间子集的临时列、派生列或实现绑定字段写入 `based_on`。

---

## Step 5. 输出

完成上述所有分析步骤后，才能输出最终的修订好的逻辑实体-关系，格式如下：

```json
{
  "refined_object_sketch": {
    "entities": [
      {
        "name": "",
        "desc": "",
        "grain": "",
        "key_attributes": [],
        "attributes": []
      }
    ],
    "relations": [
      {
        "name": "",
        "desc": "",
        "grain": "",
        "participants": [
          {
            "entity": "",
            "role": ""
          }
        ],
        "attributes": []
      }
    ]
  },
  "constraints": [
    {
      "target": "",
      "type": "attribute_filter",
      "description": "",
      "based_on": []
    }
  ]
}
```

# 输出要求

* 输出必须是单个合法 JSON 对象；
* 不得输出 conceptual SQL；
* 不得输出 CTE；
* 不得输出 SQL 语法片段；
* `refined_object_sketch` 只保留基础层对象；
* `constraints` 只保留稳定语义约束；
* `logical_query_sketch` 只表达逻辑查询语义，不表达执行代码；
* 所有说明使用与用户输入一致的语言；
* 字段值必须具体、清晰，不得使用 `...`、`same as above`、`TBD` 等占位表达；
* 若某项为空，也必须返回空数组，而不是省略字段。
