## 一：任务定义

你的任务是：根据用户输入的查询问题与一个SQL形式的概念查询方案 **conceptual SQL**，抽取一份面向数据检索的结构化规格。

这份规格不是最终 SQL，也不是数据库实现方案，而是一份 **ER Retrieval Spec**，用于显式定义：

* 需要检索的基础实体，关系；
* 实体/关系的属性；
* 属性的常值约束条件、属性间的约束条件；

---

## 二：核心思路

抽取基于 Conceptual SQL的 CTE 定义； 每个CTE指代一个实体、关系或实体间的连接；每个CTE可能指代一个基础的实体/关系/连接，或作为问题的中间表示。

### 1. `*_base`

`*_base` 查询单元用于抽取最为基础的实体或关系。

对于 `*_ent_base`，应抽取其对应的基础实体，包括：

* 实体名称；
* CTE投影Select属性集；
* 局部属性的常量约束；

对于 `*_rel_base`，应抽取其对应关系，包括：

* 关系名称；
* 参与实体及其角色；
* CTE投影Select属性集；
* 局部属性的常量约束；

### 2. `*_derived`

`*_derived` 表示基于_base 查询单元构建的中间表示实体/关系/连接；

对于 `*_ent_derived`/ `*_rel_derived`/ `*_conn_derived`，需要确定其从哪些基础实体关系衍生得出，是否对基础实体/关系的属性提出了额外的约束条件；应抽取这些约束条件作用于的基础单元的属性，描述该约束条件：

* 确定其依赖哪些基础实体关系衍生得出；
* 提取属性约束条件；

### 3. 实现来源

输入中的 `*_impl` / `*_source` 仅作为实现提示保留在查询单元对象内部，而不是作为查询单元：

* 不得提升为实体；
* 不得提升为关系；
* 不得因为实现来源在 conceptual SQL 中出现，就影响概念层对象命名。

## 四：抽取目标

抽取包括实体，关系，属性以及属性约束条件四个部分。

---

## 五：抽取规则


### 1. 对 `*_ent_base`/ `*_rel_base`/ `*_conn_base`

抽取为 `entities`，`relations` 中的实体/关系类型或 `conditions` 中的属性约束条件。

应优先识别：

* 一行代表什么；
* 连接的是哪些对象，这些对象的参与角色；
* 具有哪些属性，注意这里的属性必须是用户需求中显式提及的字段；
如果 `rel_base` 与 `conn_base` 提及未显式建模为 `ent_base`的实体类型，这些实体必须被显式建模并添加至`entity`。

### 3. 对 `*_ent_derived`/ `*_rel_derived`/ `*_conn_derived`

派生查询单元应建立于基础单元之上，默认不添加新的基础实体/关系，仅补充查询单元间的属性约束条件/连接条件。

* 作用于哪些查询单元的哪些属性；
* 局部属性约束条件；
* 跨查询单元的约束条件；
* 分析性条件。

ER建模完整性：对于如下的场景，可以考虑补充实体-关系-属性：
对于实体`*_ent_derived`，如果其引用了不存在的关系/连接，必须将该关系作为补充的"relation"/"condition"建模；
对于关系`*_rel_derived`，如果其参与实体本来是未关联的，必须将该关系作为补充的"relation"建模；
对于属性匹配连接`*_conn_derived`，如果其参与实体没有该属性，必须将该属性作为补充的"condition"建模；

### 4. 约束条件抽取规则

约束条件的定义：约束条件是对一个或多个实体/关系的特定属性的取值约束条件，包括对单个实体/关系的属性基于常量的取值约束条件和对多个实体/关系的属性之间的取值条件约束；

约束条件进入 `conditions`，并明确作用的对象属性集：

* 约束条件名称：可以是一个简洁的描述性名称，或直接使用约束条件表达式的文本摘要；
* 作用对象属性集：列出该约束条件作用的所有实体属性和关系属性，格式为 `entity_name.attr` 或 `relation_name.attr`；
* 约束条件描述：以自然语言形式描述该约束条件的语义，包括其作用于的属性之间的约束条件或常量约束值等。

### 8. 禁止事项

你必须遵守以下限制：

* 不得把 `*_impl` / `*_source` 提升为实体或关系；
* 不得把实现表、映射表、桥接表、空间表直接改写为概念层对象；
* 不得把 `*_derived` 默认理解为新的复合宽表实体；
* 不得为了让结果更像可执行 SQL 而发明输入中未明确给出的物理字段名；
* 若某条件本质上是跨对象属性约束，应保留为概念性约束表达，而不是伪造实现列名。

## 六：执行步骤

在生成 JSON 形式的 实体-关系-条件模型之前，必须先基于以下步骤完成分析，**禁止直接生成Json**；

### CTE Iteration 遍历所有CTE
你需要遍历conceptual_sql中的所有CTE;**对每个CTE**,连续完成如下步骤：

For each CTE:
### Step 1: 语义成分识别
根据上述抽取规则，分析该CTE的语义成分，判断其是基础查询单元还是派生查询单元；判断其是实体、关系还是连接；
注意这个步骤只是识别这些语义成分，而不是最终抽取
注意严格服从抽取规则，仅建模基础实体/关系：保持实体-关系的原子性；如果一个派生实体基于基础实体，或派生关系基于基础关系，则不得独立建模为`entity`/`relationship`；同时不要把基于属性的连接独立建模为关系；


### Step 2: 验证与抽取定稿
回顾用户问题，明确每个CTE里的属性和约束定义是否准确，是否符合用户的问题定义并准确落实语义。在此步骤才可落实为最终抽取结果。
