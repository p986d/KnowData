# 任务定义

根据全部输入中可识别的用户需求语义与数据库模式相关证据，构造一个支持该问题查询的**基础逻辑实体-关系草图**。

本阶段的目标不是直接生成最终查询。
本阶段只负责：

* 将问题分解为语义单元与查询子查询；
* 根据查询子查询，识别支撑该问题成立所必需的**基础逻辑实体**、**基础逻辑关系**与**逻辑属性**；

---

# 基本原则

## 1. 先组织问题求解结构，再考虑查询子查询的语义需求

首先，对问题提取语义单元，并根据查询计算的逻辑顺序构建一系列有顺序的查询子查询。
其次，对每个查询子查询，依次判断该问题依赖哪些实体-关系的概念；这些实体-关系可能是整个问题查询所需要的基础逻辑实体-关系，也可能是之前的子查询输出的中间表示语义结果。
中间表示是问题求解的阶段性结果，默认不进入基础 ER 草图。只有支撑这些阶段性结果成立的基础对象、基础联系与相关属性，才允许进入基础建模。
数据库模式相关证据作为实现支撑，用于将语义内容落地到可能的数据来源；它可以作为问题的补充说明，但不得主导问题本身的求解结构，也不得替代用户问题的语义分解。

---

## 2. 基础逻辑实体的定义

基础逻辑实体是问题中具有确定语义身份、明确基础粒度、可独立指称的对象类。实体应理解为类型概念，是一个包含多个实例的集合。

**实体语义来源**：

它不仅包括问题直接查询、筛选或统计的核心对象，也包括那些在计算逻辑上表现为筛选条件、分类口径、参照范围或分析限定，但在当前问题中实际上具有独立语义地位的对象。
判断一个语义是否应建模为基础逻辑实体，它是否在问题中引入了可被单独识别的对象、独立的语义范围，而不在于它在表述上是否像“条件”或“属性”。
如果某一语义只是已有实体的单纯内在性质，不涉及其它独立对象身份，则应建模为属性。

**实体定义严格遵循问题表达口径**:

基础逻辑实体必须与题面实际指称的对象范围、语义边界和分析粒度保持一致。不得为了形式整齐、复用方便或迎合实现结构，将题面中明确指向的对象上推为更抽象的父类、上位类或更宽泛的集合；也不得将题面中的一个完整对象无依据地下拆为更细粒度的多个子实体。
实体定义需要明确表达问题分析对象的性质和边界。当问题指向的是某一特定对象类、特定子集、特定角色对象或特定范围对象时，应严格按该问题中的概念描述口径建模，而不是泛化或细化为其它概念。

**实体定义避免使用泛化父类**：

当题面中明确出现多个语义不同、粒度不同、在问题中承担不同作用或角色的对象类时，应优先分别建模为独立的基础逻辑实体，不得仅因为它们共享某个更抽象的上位概念、层级结构或类别体系，就将其合并为一个统一的父类实体。

**基础实体与派生实体的区分**：

基础逻辑实体是支撑问题查询的基本实体，不是经过问题相关查询计算之后得到的结果派生实体。
如果某个实体只有在数据操作和计算之后其语义才成立，则它不是基础实体。此时应继续向下追溯：该派生实体依赖哪些基础实体，派生计算基于什么基础属性。

---

## 3. 基础逻辑关系的定义

基础逻辑关系是**两个或多个基础实体的角色**之间具有明确独立语义的关联。它用于表达实体之间的关联关系。

**关系的语义来源**：

基础逻辑关系不仅包括题面中直接出现的动词性、事件性或关联性表达，也包括那些在计算逻辑上表现为筛选条件、分类口径、参照范围或分析限定，但实际表达了多个实体之间基础联系的语义。
判断一个语义是否应建模为基础逻辑关系，不在于它表面上是否写成“关系词”或“连接词”，而在于它是否引入了多个实体角色之间的基础关联。如果某一语义必须依赖两个或多个实体角色才能完整表达，例如一个实体与另一个实体的关联或者多个实体共同构成关联，则应优先考虑建模为基础关系，而不是简单压缩为某个实体的属性。
如果某一语义只描述单个实体自身的性质，脱离该实体后不能独立成立，则应建模为该实体的属性，而不是关系。

**关系参与对象**

关系应表示多个参与对象之间的语义关联，单个参与者不能构成关系。参与对象在关系中必须具有角色；同一实体类型可以在同一关系中以不同角色多次出现，通过关系中不同的角色进行区分。关系中的角色不得重复定义实体。

**关系定义严格遵循问题表达口径**

基础逻辑关系必须与题面实际表达的实体间联系、语义边界、角色结构和关系粒度保持一致。不得为了形式整齐、复用方便或迎合实现结构，将题面中明确表达的具体关系上推为更抽象的泛化关系；也不得无依据地把一个完整关系拆成多个更细粒度关系。

**关系定义避免使用泛化父类**：
当题面中出现多个语义不同、粒度不同、角色结构不同或业务含义不同的关系时，应优先分别建模为独立的基础关系，不得仅因为它们都能归入某个抽象关系类型，就合并为一个统一关系，再依赖“关系类型”“关系类别”等属性区分。

**基础关系与派生关系的区分**：

基础逻辑关系必须是支撑问题查询的基础关系，而不是经过问题相关查询计算之后得到的结果派生关系。
如果某个候选关系只有在数据操作和计算之后其语义才成立，则它不是基础关系。此时应继续向下追溯：该派生关系依赖哪些基础实体，这些实体之间原本存在什么基础联系。派生计算基于什么基础属性，该属性应挂载在哪个更基础的关系上。

**基础关系的原子性**
基础关系应表示一个原子性的语义关联；如果某个联系的语义可以由其它更基础的语义关系链和派生计算推理到，则它不是基础关系。

---

## 4. 逻辑属性的定义

基础实体和关系的属性必须是能够支持问题查询的**原子逻辑抽象属性集**；

实体和关系都可以拥有属性：

- 实体属性描述单个实体实例自身的稳定性质；
- 关系属性描述多个实体之间的关联性质。

**原子非派生**：如果某一属性可以由更基础的属性通过计算、判断、聚合或映射得到，则不应作为独立基础属性。查询计算结果视为派生，不作为基础属性。
**非冗余**：对于同一语义要素，不应同时保留多个等价或可相互推导的属性表达。
**逻辑抽象**：属性可以保持为抽象性质槽位，在语义内容不充分时，不必过早固定为具体数据库字段；但必须能明确支撑问题中的计算。
**属性挂载位置**：判断属性在语义上描述的是“对象自身”还是“对象之间的关联”；若属性描述对象自身，挂载到实体；若属性描述实体之间的关联本身，挂载到关系。脱离关系语境后，不能独立成立的属性就是关系属性；

---

## 5. 实现证据只作支撑，不主导建模

数据库模式相关证据、表名、列名、外部知识只能作为落地支撑。

它们可以帮助你：

* 判断对象与属性是否可能存在；
* 确认某些对象的实现证据是否明确。

它们不得：

* 替代用户问题本身的语义依赖；
* 主导基础对象的定义；
* 把实现字段直接当成基础逻辑对象名；
* 把某个实现表直接等同于最终基础实体或基础关系。

# 分析步骤

**Think step by step**: 你必须完成Step 0, 1, 2的所有分析步骤，才能得到详实准确的建模。**禁止跳过分析**直接生成逻辑实体-关系草图Json输出。

---

## Step 0. 问题背景与输出语言设置

判断查询问题的专业领域，并明确用户输入问题所使用的语言。后续所有实体、关系、属性与说明必须与用户语言一致。

---

## Step 1.  校准问题语义边界，分解问题

本步骤的目标是：按照问题本身的自然求解逻辑，将原问题拆解为一组用自然语言定义的子查询。
**不得预先假设概念建模形式**：本步骤只关注语义，不得将语义提前固化为逻辑间模结构。**不得**定义实体、关系、属性等概念建模的形式，也不得提前写成任何数据库实现形式。

### 1.1  分析题面确定语义

通读问题，识别其中涉及的关键语义内容，包括但不限于：

* 问题提及的对象概念；
* 对象概念之间可能存在的关联；
* 查询和计算所用的相关字段；
* 查询和计算逻辑。

明确语义：对于问题中的关键语义内容，给出符合专业领域和题面上下文的语义解释。关键语义内容的定义必须使用题面原文文本的口径，不得额外泛化、细化或补充题面未声明的限制。

如果题面没有明确给出某类限定语义或分析语义，例如筛选条件、统计口径、状态、类型、时间窗口、有效性、归属方式或范围限制，则禁止考虑这些未声明的限制或分析。

未提及即无关：需要明确所有未提及的对象都是与问题不相关的语义内容：不是未确定的内容，而是不需要确定这些内容，后续步骤的任何分析与建模均不以任何形式考虑它们。

### 1.2 理解问题相关的数据提示与外部知识

如果输入中包含数据库模式、实现说明或外部知识提示，这些内容可能与问题相关，也可能无关。
需要理解问题的相关提示，并明确哪些提示与问题相关且补充解释了问题的逻辑语义。

### 1.2.1 数据理解：

分析数据实现提示:

1. 列举提示中的物理表列与计算逻辑，分析其语义；
  
  提示可能直接说明某个题面语义单元如何在数据中表示，也可能需要从模式信息，例如表、列、值、函数说明和数据采样中推断其落地方式。
  对数据提示判断相关、无关性：只有直接为题面补充说明逻辑语义的提示是相关的需要考虑的提示。

2. 识别与题面语义相关的提示，分析哪些提示为题面补充了哪些逻辑语义。

  注意，不得将“数据库中存在某张表、某个字段、某条连接路径或某个函数调用”直接等同于“问题建模中需要存在对应的概念实体、关系或属性”。实现提示中的对象、字段和连接路径，只有在能够直接解释题面中明确语义内容的识别、映射、归属、对齐、约束或计算方式时，才可作为语义补充依据。
  如果实现提示直接补充了当前问题求解的语义逻辑，则可以将其抽象为问题相关的补充语义单元。该语义单元必须按照题面语义重新命名和定义，将补充的逻辑语义单元整合到问题整体的查询逻辑中，而不是保留物理数据中的物理表、字段、函数或连接路径命名，不得机械得将物理模式直接转化为逻辑实体或关系。

3. 无关提示不得影响后续分析
  如果某个数据实现提示不能用于直接说明和解释题面明确语义信息，则将其视为无关信息，不得带入后续分析和建模。
  实现层面的存储结构、字段来源、函数调用、编码转换和中间连接步骤，只有在被重新抽象为题面语义的补充口径后，才可以影响后续建模。

### 1.2.2 题面语义解释：

给出题面解释：说明相关数据为题面补充解释了哪些逻辑语义，而不是说明数据实现具体是如何支持题面落地。
相关数据提示应作为题面语义的补充说明进行重新抽象，而不是保留具体表名、字段名或实现路径结构。实现提示可以解释和补充题面语义，但不得改变题面语义本身的对象、关系、属性、条件和分析口径边界。

* 后续使用：

对于已经确认相关的提示，后续子查询分解和语义建模必须继承其对题面语义的解释和限定；但不得把实现表、实现字段、连接路径、函数调用、编码转换或中间实现步骤直接作为基础 ER 单元。后续建模应基于提示对问题语义的补充解释进行抽象，形成面向问题语义的逻辑实体、关系和属性，而不是基于数据库实现结构逐表、逐字段、逐连接地生成概念模型

### 1.3 语义多义性

对于问题中存在多义表示、抽象性或多种合理理解方式的语义，需要说明其可能的语义解释，优先选择一种**最符合问题上下文的**的理解方式作为本步骤的分析基础。
如果问题对该语义没有任何其它可以支持判断、有效的上下文，则选择一种最自然、符合常规数据库模式设计范式的方式。

**语义严格遵守语义边界**：语义不确定性应与题面确定语义与问题相关提示对齐，不考虑任何**未提及即不考虑**的内容，不考虑已声明的与问题不相关的内容。
表示为字典形式：对每个问题的特定文本段给出多义性分析。

处理原则如下：

* 若某一语义表现为对象性内容，但其具体边界未定，仅保留其对象性，不提前落为逻辑实体；
* 若某一语义表现为关联性内容，但其具体承载方式未定，仅保留其关联性，不提前落为逻辑关系或连接；
* 若某一语义表现为条件约束，仅保留其约束作用，不提前落为逻辑属性或字段条件；
* 若某一语义表现为分析或计算要求，仅保留其分析目标，不提前写成具体计算表达式。

### 1.4 按自然求解逻辑设计子查询序列

基于问题的自然分析逻辑，将原问题拆解为若干独立的子查询。

**严格遵守语义边界**：子查询定义应与Step 0 问题语义边界的结论对齐，不考虑已声明的与问题不相关的内容。

子查询设计应遵循以下原则：

* 子查询是一个查询任务：必须明确查询的对象、查询计算和返回结果。
* 子查询可以围绕对象范围的确定、对象之间联系的识别、约束的施加、分析口径的形成、聚合比较排序的执行、以及结果整合等自然步骤来组织；
* 多个语义内容若共同服务于同一个求解目标，可以在同一个子查询中统一处理；
* 只有当某个语义内容在求解过程中需要被单独建立、单独保留或被后续重复依赖时，才适合形成独立子查询。

对每个子查询，明确如下内容，并将实现提示对问题的解释与补充整合进子查询中。：

1. 在问题整体求解中的作用；
2. 语义操作
3. 语义约束条件

语义操作：说明该子查询需要完成什么语义任务，例如：

* 确定对象或对象子集；
* 确定对象之间的联系、参与或匹配；
* 建立必要的上下文附着、空间/时间/编码对齐；
* 对既有对象或联系施加范围限制；
* 在对象或联系基础上进行聚合、比较、排序、Top-k、派生计算；
* 形成后续步骤所依赖的阶段性结果。

约束语义：说明该子查询受到哪些限制，例如：

* 角色限制；
* 时间或顺序限制；
* 方向限制；
* 局部范围或子集范围；
* 参考对象或比较基准；
* 分子 / 分母口径；
* 去重口径；
* 聚合前提；
* 局部分析范围。


对齐到相关问题解释语义：对于提示中已明确的问题补充和解释的逻辑语义，需要在子查询中表达出来。

要求如下：
* 不得提前写成实体、关系、属性、字段、连接方式、join key 或计算表达式；
* 不得遗漏问题中关键但隐含的约束和限制条件。

---

### 2.1 提取子查询依赖的候选语义单元

从问题的子查询序列提取基础实体与基础关系；
基础实体与关系视为一组最小化的逻辑表，所有子查询基于该逻辑表和其它前序子查询输出的中间表示进行查询和计算；
基础实体和关系是整个问题必要且充分的语义输入。
子查询序列需要被视为一个整体的各个步骤，从整体判断其依赖哪些逻辑表，不必逐个分析；

对语义单元判断其建模表示类型时，必须遵循以下规则：

1. 若该语义内容具有独立语义身份，在查询中需要作为独立的语义来源，则作为候选实体。实体建模需明确满足下文的规则：

   * 非派生：可由其它基础实体、关系、条件或计算得到的语义，不作为基础实体。
   * 建模口径准确：实体定义使用题面的概念表达；
   * 禁止定义泛化实体：对于问题中具有独立语义身份、独立筛选范围或独立分析作用的实体，必须分别建模为独立实体。**禁止将多个问题中明确区分的实体合并为泛化实体，再通过分类属性加以区分**。
   * 禁止将关系语义带入实体定义：实体本身不带关系语义，同一实体类型在关系中的多个不同角色的语义仅在关系中表达
  
  对每个实体，定义其语义和粒度。定义必须保持语义单一，不涉及其它实体和关系的语义。

2. 若该语义表达问题候选实体之间具有独立业务含义的关联，则作为候选关系。关系建模需明确满足下文的规则：

   * 多参与者：每个关系表示多个参与者之间的关联语义，参与者必须是基于已确定的实体类型的角色；
   * 非派生：可由其它基础关系的语义组合、或需要计算推导得到的关系，不作为基础关系；
   * 禁止定义泛化角色：对于每个关系，需要明确其所有参与角色。若同一实体类型在关系中承担多个不同角色，或不同实体在关系中的参与含义不同，应分别定义独立角色；
     不得将这些角色合并为泛化角色，也不得用抽象父类替代具体参与角色。
  
  对每个关系，定义其参与者，参与者的角色，语义和粒度。定义必须保持语义单一，不涉及关系参与者以外的其它实体。

3. 若该语义仅用于描述实体或关系自身的性质，或表达计算、限定和约束，则作为属性和计算逻辑。
4. 若该语义内容是由已有实体、关系或属性经过计算操作派生得到的，则作为派生语义单元，不作为基础实体或基础关系。对于派生语义单元，需要明确其依赖的基础实体与关系。
5. 若该语义来自数据库表、列或实现说明，但只用于说明问题语义如何落地，则作为实现绑定或实现中介；只有当它本身也是问题语义中独立需要识别、筛选、分组或分析的对象时，才允许提升为基础实体。

语义对齐：提取的基础实体与关系必须严格对齐 Step 1 中识别的问题相关的逻辑语义解释。
不考虑物理实现：实现提示仅用于补充逻辑解释，其具体的物理模式与数据存储方式不需要考虑。

注意：候选语义单元建模遵循最小必要原则：只建模当前问题查询必须依赖的基础实体、基础关系及其参与角色。凡是题面未明确要求、查询计算不依赖，或仅依据常识、业务背景、实现想象补充出的实体与关系，均不得作为建模的一部分。

注意：语义单元建模不得重复：语义要素的实体-关系建模不得重复，一个语义要素只能建模为单个实体、关系或属性，不得用多个建模单元重复表达同一个语义要素。

# Step 3. 输出

完成上述所有分析步骤后，才能输出最终的基础逻辑实体-关系草图，注意所有实体、关系、属性的名称与说明必须与用户输入语言一致。

#### 定义基础实体

基础实体表示问题中具有稳定身份、明确基础粒度、可独立指称的对象类型。不得将具体实例、条件集合、筛选结果、统计口径、角色身份或派生集合建模为基础实体。

实体**命名**和**定义**需要同时满足上述实体建模规则：实体名不能只使用宽泛父类、角色名、条件集合名或实现字段名来概括实际语义；实体名应直接反映该实体在当前问题中的对象类型、语义边界和基础粒度。若实体定义已经明确收敛到某一具体类型或粒度，则实体名也必须同步收敛，避免出现“命名为父类、定义为子类”的不一致。

- 独立定义：实体的名称、描述、粒度和属性只描述该对象自身，不依赖其它实体或关系，不包含外键式引用。
- 约束分离：条件、实例值、子类型和统计口径不写入实体名或定义，应由条件、关系或后续计算表达。
- 命名一致：实体名与描述必须对齐当前问题中的基础实体语义，不进行额外的定义、泛化或细化。

每个实体输出 `name`、`desc`、`grain`。

* `name` 必须符合问题的表达口径和上述定义规则，不将条件约束、实例值与角色作为实体定义的语义部分，按照问题定义口径，不随意泛化或细化定义。
* `desc` 必须保持实体语义的独立性，进行语义的简短说明。实体描述应表示为一个独立的类型概念，禁止提及与问题中其它实体和关系的关联，禁止提及问题中的特定实例。
* `grain`准确描述一个实例代表什么；

#### 定义基础关系

基础关系表示两个或多个基础实体角色之间具有独立语义的基础关联。关系必须承载明确的实体间联系，不能只是派生计算结果或实体上的引用属性。

关系定义和命名需要满足上述关系建模规则。

每个关系输出 `name`、`desc`、`grain`、`participants`。

`participants` 中每个参与者包含 `entity` 和 `role`；`entity` 必须来自 `entities`。

#### 本阶段不必定义详细属性，仅定义基础实体和基础关系。

输出格式如下：

```json
{
  "entities": [
    {
      "name": "",
      "desc": "",
      "grain": ""
    }
  ],
  "relations": [
    {
      "name": "",
      "desc": "",
      "grain": "",
      "participants": [
        {
          "entity": "",
          "role": ""
        }
      ]
    }
  ]
}
```
